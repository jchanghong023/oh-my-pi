# 从需求到交付：OpenSpec × Superpowers × OMP 的四阶段协作

需求还没确认就开始实现、方案只剩一句总结、计划写完便自动开工——这些问题不能只靠给模型增加一段“请严格遵守流程”解决。OMP 的 `/dev` 在**无代理、需求、方案、计划、执行**五种状态间切换原生会话，其中四个阶段 Agent 负责调查、设计与工程实施；程序管理工作区归属、正式材料及用户明确决定。

![OMP 四阶段工作流：文件检查、完整交接、明确用户决策和验收后归档](assets/spec-driven-orchestration/omp-workflow.svg)

图中验收与归档是生命周期边界，不是第五、第六个 Agent。本文解释设计，正式行为以[需求规格](../openspec/specs/spec-driven-orchestration/spec.md)为准，不建立第二套需求权威，也不表示这些行为已在所有平台通过验证。

## 一、为什么只让程序管它能确定的事

程序很适合判断文件是否存在、JSON 能否解析、字段是否齐全、批准后的文件是否改变，以及用户有没有明确作出决定。但它不能仅凭报告里写着“测试通过”，就知道软件正确；也不能靠一套自然语言关键词判定哪个方案更好。

因此，这里的责任划分是：

| 程序的文件合同 | Agent 的工程责任 |
| --- | --- |
| 确定产物路径并读取真实文件 | 调查项目事实、澄清需求与取舍 |
| 检查格式和最低字段 | 写出可执行计划并覆盖需求 |
| 核对字节版本与用户明确决定 | 实施、测试、调试及必要审查 |
| 完整文件和原始确认回复交接 | 如实说明实际验证和剩余问题 |
| 控制阶段、归属及停止结清 | 遵守项目规则及用户授权 |

这意味着 `/dev` 不维护另一套逐任务执行状态、固定 reviewer 席位、修复次数、RED／GREEN 证据账本或本地 commit 门槛。TDD、代码审查、子代理仍可作为工程方法使用，但不是四阶段控制器附加的强制流水线。方案可选 Team；执行默认正常工作，用户可手动使用当前执行会话的原生 Goal，不增加阶段或审批。

减少程序条件不等于降低工程责任。计划需要说明如何验证，执行需要真正验证，报告不能把未运行的检查写成已通过；这些工作由承担完整目标的 Agent 按项目规则完成，最终由用户判断是否接受。

## 二、几套能力各自做什么

**OpenSpec 保存“要做什么”。** 提案说明动机与范围，规格描述可观察行为和验收场景；长期主规格与本次变更分开管理。独立内置 CLI、默认 `spec-driven` schema、模板工厂和底层能力采用固定上游 OpenSpec 1.15.0，终端通过 `omp openspec` 使用；Dev 另用需求专用 `omp-spec` schema，阶段和授权边界不因此扩大。上游技能的 OMP 发现范围与原生 CLI 能力是不同的边界。需求文档已同步或变更已归档，不等于软件交付。

**Superpowers 提供工程方法。** Dev 按职责自动注入原版技能，无需用户手动调用：需求为 `brainstorming`＋`jch-grill-me`（Grill-me 最后），计划为 `writing-plans` 的执行交接章节之前正文，执行为完整的 `subagent-driven-development`。方案不注入需求访谈技能，直接根据已确认需求调查并产出候选；方案、计划、执行均不要求访谈提问或技能附加确认轮次，真实缺口如实报告，阶段批准仍由用户 `/dev next` 完成。非需求阶段的固定职责约束放在技能正文之后，避免技能中的提问或交接步骤覆盖当前阶段职责。普通会话仍按既有规则发现或手动调用。

**Brainstorming 与 Grill-me 自动用于 Dev 需求澄清。** 需求 Agent 必须自动注入包内原版 `brainstorming` 和 `jch-grill-me` 全文：Brainstorming 在前，Grill-me 放在系统提示最后；无需用户再手动调用，新建及恢复需求会话均适用。提问方式冲突时以最后的 Grill-me 为准；技能只用于当前阶段需求澄清，不提前编写方案、计划或额外设计文件，不替用户批准阶段。需求产物仍使用原 OpenSpec instructions 编写 proposal／specs，计划 Agent 使用原 `writing-plans`。普通会话可发现 Brainstorming，Grill-me 仍仅手动调用；Dev 的准确资源授权仅限对应会话。澄清回答不替代正式文件确认。

**OMP 连接文件与决定。** 功能所需的上游原始资源直接保存在仓库 `packages/coding-agent/src/spec-driven/vendor/resources/` 下，按 `openspec/`、`superpowers/`、`jch/` 等相对路径查找。只纳入 OpenSpec 运行包及技能、Superpowers 技能、上游插件／扩展及其运行资源，以及 JCH／OMP 所需资源与必要元数据，不复制无关上游仓库文件；构建时打包，运行时离线解压复制到按版本划分的缓存并生成 MD5，后续 MD5 不变时复用缓存，变化时删除该资源的缓存目录并重新复制。内网无需临时克隆或额外安装上游项目，也不提交 Base64 巨型生成源。Superpowers 以固定上游原始文件为基线，不为 OMP 改写工具、子代理或脚本指令；Dev 阶段权限与受控资源授权仍独立适用。固定版本和系统规则提供的是可追溯输入，不是模型一定遵循或质量已经提高的保证。

## 三、四个 Agent，四次明确决定

### 1. 需求：先把目标写进真实文件

需求 Agent 阅读项目、通过只读 `wiki` 查询已入库的企业资料、澄清目标、范围、不做什么、约束与验收行为，不提前编写方案、计划或业务代码。Wiki 使用当前 profile 的既有索引，不自动建库，不扩大需求文件写入白名单。

原生 OpenSpec 项目的本次材料为：

```text
openspec/changes/<change-id>/proposal.md
openspec/changes/<change-id>/specs/<capability>/spec.md
```

已有明确 Markdown 需求权威的项目仍生成上述原格式 proposal／delta specs，描述本次变更并引用已有权威；原权威继续原位维护，不替代这两个正式产物，也不复制成第二套主规格。用户阅读材料后以 `/dev next` 触发原生结构校验，通过才确认需求并进入方案。正常澄清不因文件尚未生成报错。验收后使用真实原生归档，已有 Markdown 权威用 `--skip-specs` 避免产生影子主规格。

前三阶段的 write／edit 由程序执行前校验，不仅依赖提示词：需求仅允许本次 proposal／增量 spec 及已登记的原需求权威，方案仅允许指定方案 JSON，计划仅允许指定计划 Markdown。授权路径的目标或工作区根以下父目录存在符号链接／Windows junction（包括工作区内部或悬空链接），以及已有目标是硬链接或非普通文件时，均拒绝写入，防止借文档路径改写业务文件；正常目录下创建、编辑授权文档不受影响。执行阶段仍可按获批计划修改业务代码，不套用前三阶段文档白名单。

### 2. 方案：比较真实方向，不硬凑三案

方案 Agent 直接收到已确认需求原文件和用户原始确认回复，不自动注入 Brainstorming／Grill-me，也不重新开展强制需求访谈。它可直接调用只读 `wiki` 核实企业规范及技术约束，无需开启 Team 才能检索；直接依据确认需求调查、比较可行方向，将完整候选写到：

```text
docs/superpowers/plans/YYYY-MM-DD-<change>-solutions.json
```

文件格式固定且简单，`content` 是完整方案 Markdown，应说明范围、实现方法、取舍风险和验证思路：

```json
{
  "candidates": [
    {
      "id": "existing-request-deadline",
      "title": "沿用现有请求链的截止时间",
      "content": "## 范围\n沿用登录请求链。\n\n## 实现方法\n复用现有截止时间传播。\n\n## 取舍风险\n需核对取消语义和现有错误反馈。\n\n## 验证思路\n覆盖超时、成功及权限检查保留场景。"
    }
  ]
}
```

至少一个候选，每项 `id`、`title`、`content` 非空，ID 唯一且不含空白，可用于 `/dev next <方案ID>`；单候选可省略 ID。只有一个合理方向时就说明原因，不为了填满 A／B／C 编造方案。程序检查 JSON 合同，不靠模型投票或关键词给方案自动盖章。

用户**选择并确认候选**后，只授权编写计划，还没有授权实施。

### 3. 计划：收到完整方案和用户原始回复

这是最重要的交接边界：用户确认方案后，程序将**完整方案文件、已确认需求、所选候选 ID、用户完整原始确认回复**直接交给计划 Agent。不是只发一句“用户选了 A”，不是只留下选中候选，不生成交接文档，也不额外调用模型总结。

计划 Agent 将需求和方案转成执行范围、任务、接口、依赖、修改位置与验证安排。唯一计划放在：

```text
docs/superpowers/plans/YYYY-MM-DD-<change>.md
```

OpenSpec 原 proposal／specs 模板、Superpowers 原 `writing-plans` 格式和工程方法保持不变。用户阅读完整计划后以 `/dev next` 批准，程序检查计划确实是可读、非空的 Markdown 文件，不附加自制计划 JSON；计划是否周全、命令是否适用、任务能否落地，仍是 Agent 的工程责任。批准后进入执行，不隐含提交、推送、发布、创建 PR 或扩大范围的权限。

### 4. 执行：真正实施，然后写完成报告

执行 Agent 直接收到完整原文件、用户原始确认回复与获批材料，并自动注入包内原版 `subagent-driven-development` 全文，用原生工具按计划组织实施和审查，不以 `executing-plans` 替代。新建及恢复执行会话均加载，准确资源授权仅限当前会话；普通会话也可发现该技能。如何拆分、并行、测试和审查，服从获批计划、用户授权和目标项目规则；不因技能中的工作流步骤创建 worktree、逐任务状态文件、强制提交或自动验收，外层程序不另建工程执行引擎。

结束工作时，执行 Agent 必须写出真实报告：

```text
docs/superpowers/plans/YYYY-MM-DD-<change>-completion.md
```

报告采用固定标题和三个非空栏目：

```markdown
# 完成报告

## 完成情况
说明实际完成的内容。

## 验证结果
说明真实验证命令、状态、结果和限制，区分已运行、未运行与失败。

## 未完成项
说明未完成事项；确实没有时明确写“无”。
```

报告就绪后等待用户验收；用户可检查实际结果、继续提问或明确要求范围内修复。完成报告的结构只在用户最终 `/dev next` 时核验，**不会把报告存在当作测试通过或软件正确**。

## 四、每次转换都交文件，不让模型再总结一次

阶段进入时直接传完整原文件和用户原始确认回复，方案到计划还传全部候选及选中 ID，并带上相关 Team 配置；不生成交接或确认文档，不调用原生 `/handoff` 或其他模型总结。用户原话逐字保留、不裁剪。普通追问、补充及范围内修复直接续聊，支持原生附件，不反复注入未变化的全套材料，也不重新派发 Team。

单能力只有五个正式文件：OpenSpec 原 proposal／spec，以及同放 `docs/superpowers/plans/` 的一个完整方案 JSON、一个原格式计划、一个完成报告。另只持久化恢复业务所需的阶段、Team 配置、变更身份、会话关联、批准原文与版本及必要收尾进度，不保存正文副本、忙碌标记、消息队列或 Goal 状态。

继续依赖批准、推进或恢复前，程序核对本流程正式需求、方案、计划及报告所需版本。失配只返回文件和原因、阻止依赖旧批准的新工作，不自动改阶段、回退或回滚。用户需按提示返回相应阶段重新确认；这不扫描业务代码或整个工作区，也不证明代码未被外部修改。

产物存在、结构及最低字段检查集中在用户的 `/dev next`。缺文件、JSON 错误、候选字段不足或报告栏目为空，保留当前阶段、对话、输入、附件和文件，指出具体缺口；用户继续与当前 Agent 完善材料。不要求聊天输出 JSON，不靠 `yield` 或自动修复轮数掩盖阻塞。

## 五、用户如何操作

先在输入框发送 `/dev` 进入模式，再配置或新建流程。Dev 仅有以下六个入口：

| 入口 | 用途 |
| --- | --- |
| `/dev` | 进入或退出 Dev，保留普通聊天历史 |
| `/dev config` | 手动查看、保存当前工作区的方案 Team 开关 |
| `/dev new <需求内容>` | 自动分配合法唯一变更 ID、固定产物路径并启动需求 Agent |
| `/dev next [方案ID]` | 检查材料并明确确认当前阶段；执行阶段为最终验收 |
| `/dev back` | 空闲时返回相邻上一阶段，不自动启动工作 |
| `/dev drop` | 结清自有工作，清除流程及 Dev 配置，不回滚材料或代码 |

例如：

```text
/dev
/dev new 明确登录超时行为，保留现有权限检查，并通过实际入口验收
```

普通模式的 Dev 子命令不会隐式进入。无代理时普通输入不调用模型，并保留输入及附件，需先 `new`。有阶段 Agent 后，普通文字和受支持附件直接进入其原生会话；“可以”“继续”“同意”不是阶段批准。四次 `next` 分别确认需求、选择方案、批准计划、最终验收；多候选时必须指定方案 ID，其他阶段不接受此参数。

### 只保存工作区 Team 配置

Team 默认关闭，`/dev config` 保存后生效，取消不改变值。只有无代理、需求阶段且运行条件允许时可改，方案及后续阶段不可改；返回需求后可改。新流程继承保存值，正常完成保留，`drop` 或确实无效旧状态清除后恢复关闭。

Team 复用 `/team configure` 的成员及原生只读讨论，仅在进入方案时启动；方案主聊天不切到成员，普通追问不重跑。讨论失败不静默回退单代理；如需重新讨论，先结清工作，再 `back` 返回需求、`next` 重新进入方案。Dev 没有 Goal 配置：执行默认正常工作，用户可手动开启当前执行会话的原生 Goal；Dev 不按聊天轮次创建、删除或重建 Goal，恢复时也不自动启动。

方案 Team 讨论期间，普通 `Esc` 或 ZCode 的停止操作也会取消并结清当前方案会话拥有的讨论，不要求先退出或 `drop`。停止保留阶段、批准、Team 配置和原生历史，不自动启动方案 Agent 或重跑讨论；需要重新讨论时仍通过 `back`、`next` 明确重入。

### 原生主聊天与三行固定区

主聊天直接显示当前阶段原生会话的消息、流式回复、工具事件和附件，保留原生队列、草稿、历史、压缩及停止，不复制回复到父会话或由另一 Agent 转述。唯一新增常驻显示是输入框上方三行：第一行显示 Dev、当前角色及实际运行情况和保存的 Team 值；第二行显示主要操作及后果；第三行显示错误、进度或简短提示。

配置与详情手动使用原生交互，不设 Dev 决策或材料面板，不自动弹窗、不刷聊天摘要、不抢焦点或发送草稿。忙碌输入沿用原生队列，绑定提交时的阶段，不转交后继；未结清时阶段切换直接拒绝，不延迟排队。

### 工作区唯一控制者与恢复

Dev 使用当前已有工作区，不创建或要求创建 Git worktree。Git 项目同一工作树的子目录、路径别名及分支共享一个未结束流程和一个控制者；不同已有工作树隔离，非 Git 项目按进入时工作目录归属。其他实例不能接管被占用工作区。

进入前普通会话工作须结清，并先退出冲突的外层 Plan／Loop／Goal／Vibe 等模式。`/dev` 退出会停止并结清当前 Agent、工具、Team、Goal 及其他自有任务，保存必要状态、释放控制权后才恢复普通聊天；失败保留真实原因，不能把“请求停止”当作已安全退出。`drop` 也须结清，但清除流程和配置，不回滚已有写入。

再次显式进入时可依据最小持久状态核对并恢复同一流程及可取得的原生历史，不重放输入或工具、不自动启动 Team／Goal；聊天缺失不使有效业务状态自动丢弃。确实不可恢复时才清除旧 Dev 状态及 Team 配置，旧任务未结清前不能新建。仅查看冷历史不会取得控制权或恢复执行。

## 六、验收之后才收尾

待验收时，角色仍是执行，一般询问仅解释或只读调查。用户明确要求获批范围内修复或继续实施，才恢复执行并撤销旧报告的本轮验收资格；更新报告后仍等待用户最终 `/dev next`。范围变化应相邻 `back` 到对应阶段重新确认，保留文件与代码，不自动删除或重置工作区。

执行阶段的 `/dev next` 仅由用户触发，作为唯一最终验收。程序直接调用原生 OpenSpec 同步、校验及归档，不调用模型、不委派执行 Agent 或另建收尾 Agent。原生项目同步增量到主规格；已有 Markdown 权威原位维护，归档用 `--skip-specs` 避免影子权威。仅归档需求变更，方案、计划和报告原地保留。

失败或部分成功时保留执行原生会话、历史及实际收尾进度，不标为完成。用户可直接提问，Agent 按需读取失败诊断；一般问题只读，明确修复也只能处理不改变已验收材料、范围和交付内容的直接收尾故障，不恢复业务任务或 Goal，不自行同步归档。修复后由用户再次 `next`，程序只继续剩余步骤，不重新验收或重复已完成步骤；已归档材料按实际位置读取，不重建原目录。

若原生归档已搬移变更、但旧规格 retirement backup 清理失败，搬移不等于收尾完成。保留真实待清理路径；用户明确修复清理故障后，再次 `next` 只核实剩余清理并完成收尾，不重复同步或归档。

实际同步或归档已有结果后不能普通 `back` 或继续业务修改。正式材料版本失配时不能沿用旧验收；可恢复原材料后重试，或 `drop` 后新建变更。`drop` 不撤销既有同步归档结果，也不表示交付完成。全部收尾成功后回到无代理，保留 Team 配置、原生聊天和正式产物。

ZCode 开放入口投影同一工作区控制者、原生阶段及动作事实，不另建执行器或消息系统，不把 `/dev` 冒充动态工作流；冷历史只读。TUI 和桌面 UI 的实际验收须分别报告，后端结果不能代替界面证据。

## 七、不需要每次都使用 `/dev`

小修复可以继续用普通对话和原生工具。内置完整的十二项上游 `openspec-*` 技能，通过 `/skill:<name>` 调用，例如 `/skill:openspec-explore`、`/skill:openspec-propose`、`/skill:openspec-sync-specs`、`/skill:openspec-archive-change` 和 `/skill:openspec-verify-change`；终端入口为 `omp openspec ...`。当前工作目录直接包含 `openspec/` 时，OMP 将上游名称和描述放入默认索引，正文按需读取，其他目录保留手动调用。

这些技能原文中的 `openspec` 和 `/opsx:` 引用不等于 OMP 内置同名 slash 命令；OMP 的发现包装不改写上游技能。原生 CLI 的初始化、更新及外部工具配置遵循固定上游；Dev 仍遵守自身阶段权限和用户批准。同步或归档时应遵循项目需求权威及用户授权。

普通会话发现全部包内 Superpowers 技能，并保留手动入口；原版 Pi 扩展定义了启动和压缩后的 `using-superpowers` 引导。例如独立更新需求后可用 `writing-plans` 编写计划、用 `executing-plans` 实施。实际操作仍受用户授权和项目规则约束。

这套设计希望减少阶段越权和交接信息损失，不承诺减少 token、费用或等待，也不承诺提高任意真实模型的能力。文件合同、模拟模型测试、真实模型质量和实际软件交付是不同层面的证据，不能互相替代。收益仍需用真实任务中的遗漏、返工、人工纠偏、交付缺陷与实际成本衡量。

公开终端验证使用 `test/spec-driven/tui.e2e.test.ts`，共用 `tui-harness.ts` 启动真实源码 CLI；`tui-capabilities.e2e.test.ts` 覆盖独立需求维护、阶段技能与已有 Wiki 索引，`tui-lifecycle.e2e.test.ts` 覆盖范围回退、原生 Goal／重试及外层模式互斥，`tui-closing.e2e.test.ts` 覆盖实际归档后的保存失败恢复与 Markdown 权威。以上路径均相对 `packages/coding-agent/`，模型使用隔离的本地 HTTP/SSE 服务。`native-surface.test.ts` 验证 native 协议文档与输入，不冒充 Tern 像素布局；ZCode 的公开 stdio 验证也不替代终端界面验证。
