## OpenSpec 文件约定

一个 IR 对应一个 OpenSpec Change；一个 SR 对应一个能力的 `spec.md`，文件内可包含多条 Requirement 和 Scenario，整份 IR 共用一份 `design.md`。

```text
/tmpdata/DFT_LAB/omp/{project_name}/{原提交人工号}/{提案id}/
└── openspec/
    └── changes/
        └── {change-id}/
            ├── proposal.md                    # IR：业务需求与范围
            ├── specs/
            │   ├── {capability-a}/spec.md      # SR A：能力增量规格
            │   └── {capability-b}/spec.md      # SR B：能力增量规格
            └── design.md                      # 共享技术方案、SR 顺序及依赖
```

先在固定临时目录生成，不直接写项目工作区；由已确认版本准备提案分支。`design.md` 说明技术设计、架构、模块、文件、函数、SR 实施顺序及依赖。IR、SR、Change 与 capability 使用稳定映射；标题、列表筛选和显示顺序不是业务身份。

提案合入表示需求和方案正式入库，不代表实现完成。未实现的 Change 增量规格不能在提案 PR 中提前同步为 `openspec/specs/` 的已实现规格。

## 并行与冻结

- 同一仓库一次只有一个进入开发的 IR；按仓库身份统一判断，跨项目登记、工号、clone、worktree、Release 或目录别名不能绕过。
- 当前 IR 内满足依赖的独立 SR 可以并行，默认最多 2 个；不限制同一工号只能开发一个 SR。不同仓库和提案讨论可并行。
- 方案阶段明确依赖及实施顺序。前置 SR 的 PR 真实合入、默认分支核验后，依赖它的 SR 才可开始；不只依据 Agent 声称完成或分支已推送。
- 每个 SR 从开发人的 Git 开发仓库，以启动时最新默认分支创建独立分支和 worktree，记录确切基点提交。后续对齐默认分支保留更新记录，不隐式改写启动基点。
- SR 的开发人、目录、分支、worktree、会话固定；一个 SR 不能重复接手。切换浏览对象或修改个人设置不重绑已经开始的工作。
正式需求入库后可在自己的 Git 项目自由修改和提交；保留历史版本，旧报告不自动适用于新提交。
- 准备中、开发中、等待评审或合并均占 SR 名额；真实合并且工作结清后释放该 SR 名额。仓库 IR 占用一直保留到最终验收／归档 PR 合并并核验。
- 准入与占用通过共享状态原子检查。暂停、断线、关闭页面、重启或删除列表显示不释放占用，不自动删除 worktree 或分支。

## 业务流程

### 1. 需求讨论与业务评审

业务需求 Agent 整理 IR、拆分 SR，写 `proposal.md` 与增量规格。业务需求评审 Agent 独立检查业务完整性、一致性、边界和可验证性，给出具体问题及对应材料版本；不通过返回业务需求 Agent 补充。

业务范围争议或多轮无法解决的问题交人工决定，不无限循环，不用静态“通过”或格式检查冒充真实评审。提交给开发人员接手不要求已有技术方案，但业务评审须通过。

### 2. 技术方案

开发人员明确接手后，方案 Agent 生成共享 `design.md`，解决技术问题并确定 SR 顺序与依赖。需要业务补充时附原因打回业务需求 Agent；保留历史，旧方案和受影响确认失效，重新评审并生成本轮方案。

提案状态与当前讨论阶段分开：草稿可以处于业务需求或正在生成方案；确认方案完成后才可准备提案 PR，提交后仍为 PR 待合并。没有独立“待评审”状态。提案内点击 IR 的“需求讨论”或任一 SR，进入同一当前阶段的整份提案会话；业务需求和方案各保留自己的历史。

### 3. 提案入库

人工确认需求及方案 → AI 在授权范围内提交、推送提案分支并提供 PR 标题、正文 → 人工创建、评审、合并 PR → 告知平台。

平台核对默认分支已包含确认版本的 `proposal.md`、全部 SR 增量规格与 `design.md`，才转为正式提案，进入现有“正式需求”导航。提案文件仍位于 `openspec/changes/{change-id}/`，此时不归档、不提前更新已实现规格。通知、PR 链接或勾选不能替代 Git 事实；核验应兼容 squash／rebase。

### 4. 按依赖开发 SR

明确开始 SR → 校验自己的 Web 与 Git 路径、本 Web 内的并发及依赖 → 本 Web 内预留名额 → 获取最新默认分支 → 创建独立分支与 worktree → 开发计划 → 开发与验证 → 交付 PR。

Superpowers 提供计划、开发、测试和代码审查方法，OMP 唯一负责原生会话、工具、子任务及状态。计划与执行使用相应职责，测试／代码审查使用 OMP 原生子代理，不另建重复顶层 Agent 或第二执行器。阶段推进需要明确批准，并绑定当前阶段、轮次和完整材料版本；未执行、失败或环境受限的验证如实记录。

**代码、测试以及将该 SR 增量落实到 `openspec/specs/{capability}/spec.md` 的更新放在同一个 PR**，保留源 Change／SR／版本映射。提交前不改写当轮记录的 Change 需求。合并前对齐最新默认分支并重跑受影响验证；需求冲突、Git 合并冲突暂停交人工，普通实现问题由 Agent 修复。

AI 提交／推送并给出 PR 标题和正文；人工创建、评审、合并并告知。平台核验默认分支的代码、测试和规格后完成该 SR、释放其名额，允许依赖就绪的下一 SR 开始；IR 继续占用仓库。

### 5. IR 验收与归档

全部 SR 已合入后，IR 验收 Agent 基于最新默认分支验证完整 IR 的跨 SR 行为、兼容性及需求覆盖。可修复实现问题；正式需求或方案可在自己的 Git 项目修改提交，新版本需重新核对验证结果。修复后重跑受影响验证和 IR 整体验收，保留失败、限制与实际证据。

最终候选提交包含全部修复，验收绑定该候选及默认分支基点；合并前默认分支变化时重新核对影响并补充必要验证。归档前检查各 SR 代码、测试和已实现规格均已合入且完整一致。

**修复与归档放进最后一个 PR**；没有修复则提交归档 PR。归档仅将 Change 目录移入原生归档位置，使用不再同步规格的归档方式（`--skip-specs`），不重复执行规格同步。最终 PR 不因归档遗漏修复带来的必要测试或已实现规格一致性更新。

人工创建、评审、合并最终 PR 并告知，平台核验最终默认分支的成果与归档结果后，IR 才完成并释放仓库占用。不自动删除开发目录、worktree、分支或历史。

## 界面及运行边界

Dev 面向桌面浏览器，不要求手机适配；保留 Chromium 与 Firefox 128 的后续验证目标。原 WebGUI 自有的手机要求与实现本次不改。

现有原型预览与 OMP 正式启动共用同一套 Dev UI，由不同入口注入样例或真实宿主数据；预览启动命令保持不变，正式资源不加载样例，真实错误不回退演示。此次只实施数据源分离与现有原生接口挂载，不新增原型功能，不补做下述完整业务，也不恢复旧 Dev 流程。


左侧继续为当前项目的“自由会话”“正式需求”“需求提案”。自由会话功能与 WebGUI 原“单项目”一致，只显示当前开发项目，默认右侧审查，仅查询最近 5 条历史，进入后才加载消息；不绑定 Release 或走提案流程。新建只打开未发送草稿，重复点击保留正文、附件和模型选择，首次发送成功后才显示历史记录。访问他人的 OMP Web 时仍显示自由会话行及按钮，不显示历史，点击操作提醒进入自己启动的 OMP Web、以自己的工号登录并配置开发项目路径。正式需求和提案使用同一 IR／SR 控件，IR 展开 SR；三栏尺寸与 WebGUI 相同；刷新后右侧默认展开，自由会话显示审查，需求会话显示只读材料。左侧自由会话及需求栏目展开到 IR 层，IR 下 SR 默认收起，不因恢复会话自动展开；手动折叠偏好在本页按当前浏览上下文保留。

自由会话是正式 Dev 必需能力，必须接入 OMP 原生会话的新建、历史读取、发送与流式回复、停止、重命名、置顶、归档及文件／审查，并按原生规则持久化。数据源分离不得成为取消或隐藏入口的理由；真实失败保留目标与草稿，不回退样例或以空列表冒充成功，不自动重放操作。当前独立原型保留入口和样例，正式适配层仍关闭自由会话且尚未接入；本次仅更新原型边界及文档要求，不修改正式代码、不运行测试，也不宣称真实功能已恢复。

项目与依赖它的 Release 在左下角工作区菜单相邻展示，切换项目重选其 Release，不改变运行中的任务。正在开发入口须容纳本 IR 的多个开发 SR，分别显示阶段与开发人；浏览他人的开发只读。选中、搜索、筛选、查看历史或重试读取均不启动 Agent、推进阶段或重新绑定目录。

模型及追加系统提示词涵盖业务需求、业务需求评审、方案、计划、执行、IR 验收、Skill 设计七个职责，沿用每个开发者自己的 OMP 配置目录／profile，个性化、模型、Agent 和个人技能互不共用，不落共享业务数据库；只作用于新建角色会话，历史保留创建时快照。不增加追加提示词预览。现有技能页保留，独立 Skill 设计页复用原生聊天能力：表单将全部实际填写值按“字段名称：内容”组合，连同临时技能目录及主文件路径填入右侧聊天输入框；无需填写技能标识，由模型推荐并用于预览及保存路径，保留原有草稿，由用户直接发送或继续补充后发送；不根据表单直接生成技能。所有人看见同样的 Skill 设计页面；业务人员点击填入时弹出不支持提示，不改变输入框；开发者填入时保留原草稿，成功写入后才提示。实际发送后由大模型澄清并在临时目录生成技能，用户可预览文件清单、路径和内容，继续讨论修改，最后明确选择并保存整份技能目录到自己的当前开发项目 `.omp/skills/<skill-name>/` 或个人 OMP profile `skills/<skill-name>/`。缺少项目绑定只阻止项目目标，不影响有效个人目标；不写共享只读目录或他人目录，不覆盖所选目标中的同名技能。Skill 设计会话与临时文件也仅属于当前开发者后端。当前会话仅修改文档与前端原型，不改真实实现、不跑测试；原型使用明确标注的固定产物样例，不代表模型生成或真实文件写入。

材料缺失、读取失败、目录失效、仓库不符或发送失败须明确原因，保留原目标和未发送输入；重试不自动重放命令、创建对象或回落固定样例。退出前结清自有主任务及递归子工作；浏览器关闭不退出服务。跨机器接管须先结清原宿主，不凭超时、PID 或文件可见性自动夺取占用。

团队长期 Web 与开发者各自的本地 Dev 同时存在，各自运行 OMP 原生能力，业务元数据跨后端共享，开发者配置独立；原先仅本机的 Dev 访问假设不再定义本部署。原 WebGUI 的访问边界、普通 OMP、独立 OpenSpec／Superpowers 和 TUI 独占准入保持原约定；本次不实现新的服务或网络接入。
