# 从需求到交付：OpenSpec × Superpowers × OMP 的规格驱动多 Agent 编排

把需求写清楚、把方案选明白、把计划变成代码，最后拿出能够验收的结果——这些事情不适合全部塞进同一次长对话。OMP 的 `/dev` 协同开发模式，把它们拆成四类职责，再用明确的用户决策、独立审查和真实验证连接起来。

## 一、为什么还需要一层编排

编码 Agent 很容易把几个不同的问题混在一起：用户还在讨论目标，它已经开始选框架；刚写完计划，它就认为获得了实施授权；代码能跑，它便把“实现完成”说成“需求满足”。任务越大，这些偏差越容易沿着后续工作放大。

企业内网还会遇到模型选择有限、上下文较小的问题。把更多规则、技能和历史记录塞给模型，不一定能解决这些问题，反而可能挤掉真正重要的业务信息。

我的处理方式不是要求模型记住更长的流程，而是把两类责任分开：

- **模型负责理解和创造。** 调查业务、发现问题、比较方案、编写代码、提出审查意见。
- **程序负责状态和边界。** 当前处于哪个阶段，允许做什么，哪些材料已经批准，证据是否有效，能否继续向前。

这仍然是单个开发者使用的工具。需求确认、方案选择、计划批准和最终验收都由同一个人完成；多个 Agent 提供分工和独立视角，不是增加一层多人审批。

它适合跨模块改造、重要功能和需要认真比较方案的任务。小修复没有必要一律进入这套流程，普通对话、原生工具和子代理仍然可以独立使用。

## 二、几套能力分别解决什么问题

### OpenSpec：保存“要做什么、怎样算完成”

规格驱动开发（SDD）先明确目标、边界和可观察行为，再讨论技术实现。需求不只是开工前的一段提示词，而是方案、计划、实现和验收共同引用的依据。

OpenSpec 把长期有效的主规格与本次变更分开管理。主规格描述系统行为；变更中的提案解释动机和范围，规格增量记录新增、修改、删除或重命名的需求。这样修改存量系统时，不必每次重写整本需求文档。

在 OMP 中，OpenSpec 负责需求维护和独立实现核对，不承担代码实施。需求确认、规格同步和变更归档可以先于代码实现，不能据此宣布软件已经交付。

### Superpowers：提供从计划到交付的工程方法

Superpowers 提供计划编写、测试驱动开发、调试、子代理协作、代码审查和完成验证等方法。

其中，TDD 强调先得到针对目标行为的失败证据，再实现并验证通过。它不只是规定“先写测试”，更重要的是让测试证明自己能够发现尚未实现或已经出错的行为。

这些方法可以单独使用。在 `/dev` 中，它们被放进明确的阶段：计划方法不负责自行启动实施，执行方法也不能替用户批准需求。

### Grill-me：让需求澄清更容易回答

Grill-me 的价值是把模糊需求组织成有依赖关系的决策树，而不是不断追问开放式问题。

OMP 的需求节点结合 Brainstorming 的需求探索与 `jch-grill-me` 的分轮访谈：先调查能从项目中查明的事实，再询问真正需要用户决定的事项。每轮集中提出当前可以回答的独立问题，给出编号、推荐答案及取舍；依赖这些答案的问题留到下一轮。

用户可以逐项回答，也可以接受本轮全部推荐。这样减少的是回答负担，不是把推荐意见直接当成用户决定。

### OMP：连接方法，而不是再运行一套平行流程

OMP 已将这些技能及必要资源随包交付，内网运行不要求临时克隆来源仓库或在线下载技能。内置也不意味着每轮都加载全部正文：普通会话只暴露相应的技能索引，阶段会话按职责加载所需方法和材料。

OMP 额外承担的是跨阶段协调：复用 Team 比较方案，用原生 handoff 交接上下文，用原生子代理执行任务，并把批准、权限、任务状态和验证证据关联起来。

关键不是多启动几个 Agent，而是让每一份结果有明确的用途和边界。

## 三、四类职责，四次用户决策

### 需求阶段：先形成可以共同确认的目标

需求 Agent 可以阅读代码、查询 Wiki／Repo、检索资料并向用户澄清，但不能提前修改业务代码、编写执行计划或运行任意实验。

以“增加登录超时”为例，真正需要确认的可能包括：超时针对连接还是整个登录过程，超时后如何反馈，已有重试和权限检查是否保持不变，以及怎样观察到正确结果。直接开始写一个定时器，可能很快，却未必解决了用户的问题。

访谈收敛后，目标、范围、不做什么、约束和验收场景写入 proposal／specs。独立审查检查遗漏、冲突和无法验收的表述；涉及业务意图的问题仍由用户决定，不交给模型投票。

用户确认当前版本的需求材料后，才进入方案阶段。接受澄清推荐与确认正式需求是两件事。

### 方案阶段：展示真实取舍，不硬凑候选

方案节点复用 OMP Team：参与者独立调查，再对齐差异、交叉审查和修订。用户看到的不应只是一个结论，还应包括可采用的方向、关键代价、采用条件和未解决问题。

只有一个合理方向时，就说明为什么。存在真实取舍时，再展示多个候选。没有可采用方案时，流程停住，而不是为了凑齐选项再编一个答案。

例如，同一个超时需求，可能既可以在现有请求链增加统一截止时间，也可以在登录流程中分别控制几个步骤。比较的重点是语义、侵入范围、错误反馈和验证成本，而不是哪份方案文字更多。

用户选择后，保留候选原文和条件，不让后续 Agent 根据印象重新发挥。**选定方案只授权编写计划，还没有授权修改代码。**

### 计划阶段：把方向变成可以执行和验证的任务

计划 Agent 将已确认需求和选定方案转换为任务，明确修改范围、接口、依赖、执行位置及验证方法。计划保存在一份文档中，不同时维护几份相互竞争的任务清单。

好的计划不只是列出“修改接口、补充测试、更新文档”。它还要说明哪些需求由哪些任务落实，哪些工作可以并行，哪些必须等待前置条件，以及每项结果如何证明。

计划随后经过独立审查。方案合理，不代表任务拆分一定正确；接口遗漏、依赖倒置、不可执行的验证命令，都可能在这一阶段暴露。

批准前，用户可以查看完整计划、任务路径、验证命令、工作区安排及 TDD 例外。批准计划同时授权获批范围内的实施、本地提交和既定任务工作区集成，但不包含推送、发布、创建 PR 或把整个执行分支合入其他分支。

### 执行阶段：让主代理真正负责推进

执行 Agent 是一个持有完整目标的主代理，不是每次只能接收一个任务的被动 worker。它可以自己实现，也可以委派原生子代理；独立工作可以并行，存在接口或共享状态冲突的工作则按依赖推进。

并行不能只看文件名是否不同。两个任务即使修改不同文件，也可能争用同一个接口、Git index 或审查区间。任务隔离、来源记录和最终集成同样属于执行工作。

计划批准后，不再为每个子任务、常规测试或范围内修复询问“是否继续”。主代理自主组织实现、验证、独立审查和修复；遇到无法在现有约定内解决的问题，再明确停住。

默认使用普通执行。用户也可以选择执行 Agent 自己的原生 Goal，持续推进获批目标；普通执行同样可以主动编排和并行，Goal 不是获得这些能力的前提，也不会扩大权限。

当实施任务、必需验证和整体审查都具备当前有效证据时，流程进入待用户验收。用户确认交付后，才执行已授权的规格同步和归档。

## 四、交接上下文，不继承旧权限

分成四个 Agent，如果每个都从一句任务描述重新开始，前面的澄清就白做了；如果把全部聊天原封不动复制过去，又失去了职责隔离和控制上下文的意义。

OMP 在需求到方案、方案到计划、计划到执行之间，调用上一阶段真实会话的原生 handoff。后继同时获得交接说明、已确认的正式材料和必要原文引用。

交接说明负责延续目标、决定、依据和进展，不取代需求原文。正式材料与摘要发生冲突时，不能让摘要悄悄覆盖已确认约定。

权限则重新授予。需求阶段的资源授权不会因为写进交接文档，就自动变成执行阶段的写入权；材料里出现某个命令，也不等于获准执行它。交接失败、保存失败或批准版本变化时，下一阶段不会先启动再补手续。

执行阶段也采用相同思路：主代理持有整体目标，子代理只接收本任务需要的需求、接口、约束和证据，不默认继承整段历史、废弃方案或全部技能。

这种拆分追求的是业务理解连续、上下文负担可控，而不是机械地把每个任务切得越小越好。强耦合工作仍然需要放在一起处理。

## 五、审查和验证为什么不能只靠一句“通过”

### 独立视角有用，但不是多数票

方案讨论与审查复用 `team.members`，不再配置另一套模型名单。需求、计划、任务和整体审查各使用一个独立只读席位；初审与复核保留同一席位和问题记录。

优先使用不同于作者的模型。内网只有一个可用模型时，也可以使用新的独立上下文，但应明确这是同模型独立分析，而不是多模型交叉验证。

审查者不能代替测试，也不能代替用户决定业务目标。多个模型可能共享同一个错误前提，一个有证据的反例仍然比几份笼统的肯定更重要。

### 实现、验证和完成是不同状态

实现者返回代码，只能说明实现工作已经产出。测试通过之后，还需要独立审查；单个任务通过之后，还要检查集成后的整体结果。

例如，两个任务各自在隔离工作区通过，并不能证明合并后的接口仍然一致。最终验证针对的是交付给用户的目标内容，不只是各自的来源工作区。

程序根据实际工具记录和审查结果更新状态，而不是根据 Agent 写出的 `complete`、计划中的勾选或已有 commit 判断完成。缺工具、必需检查未运行、仍有阻断问题时，结果就是未完成。

### 证据必须对应当前内容

TDD 的红灯说明测试曾经发现目标问题；绿灯说明某一版内容通过了验证。相关代码、测试、配置或运行条件改变后，旧绿灯不能继续证明新内容正确。

OMP 保留原始检查输出，并生成可回查的验证材料，关联实际命令、退出码、任务、审查问题和被验证内容。无关变化不必使所有结果失效，仍有效的工作可以复用；相关变化则需要补齐受影响的验证和审查。

验证命令也是计划的一部分。执行 Agent 不能因为某条命令失败或不方便，就自行换成一个更容易通过的“等价命令”；需要改变命令、参数或范围时，先修订计划。

保存一份报告不等于保存了可恢复的执行现场，更不等于证明模型判断绝对正确。程序能够检查证据是否齐备、是否对应当前对象，证据本身的质量仍要靠合适的测试、审查和真实入口验证。

## 六、使用时，用户实际面对什么

### 从操作面板开始，而不是记住全部命令

在 OMP 输入框发送 `/dev`，切换普通聊天与协同开发输入模式；发送 `/dev help`，打开当前阶段的决策面板。切换模式和查看帮助本身都不启动 Agent。

没有流程时，可以在面板先填写需求，再确认自动生成、可编辑的变更名。也可以直接启动：

```text
/dev start login-timeout 明确登录超时行为，保留现有权限检查，并通过实际入口验收
```

启动后，输入区持续显示当前模式和消息去向。协同开发模式下的普通文字直接交给当前阶段 Agent，不要求额外添加回答命令，也不先经过外层聊天模型判断意图。

面板围绕当前决策组织内容：需求阶段查看问题和材料，方案阶段比较候选，计划阶段阅读任务与授权，验收阶段检查交付和证据。完整材料可以阅读，命令和版本参数由程序提供，不要求用户手抄内部 ID。

### 对话不等于批准

等待决策时仍然可以提问、要求解释或修订尚未批准的材料。只有明确的批准命令或等价界面操作才会转换阶段，普通文字中的“继续”“可以”“同意”不自动授权后续工作。

Agent 忙碌时，消息绑定当前运行、阶段和实际接收 Agent 排队。“已排队”不等于“已经处理”，旧阶段的消息也不会自动交给后继。

指定消息可以取消，但消息取消与取消整个流程不同。已经发生的文件写入不会因取消消息自动回滚；正在处理的消息也要真正停止并隔离迟到结果，才能解除转换阻塞。

### 待验收时，先讨论，再决定是否修复

进入待验收后，执行 Agent 可以解释结果、分析反馈和只读调查，但不能因为一句意见就继续修改目标工作区。

确实需要修复时，选择“返回执行并修复”，填写说明。程序使旧验收版本失效，恢复获批范围内的执行；修复、验证和审查齐备后，再产生新的验收版本。

这样区分，是为了避免用户还在核对结果，Agent 就悄悄改变了正在被验收的内容。

### 暂停、切换和退出不是同一件事

切回普通聊天或关闭面板，不会取消后台开发流程。协同开发输入模式与外层 Plan、Goal、Vibe 模式互斥；这不妨碍执行 Agent 在获批计划内使用自己的 Goal。

`/dev pause` 暂停当前运行，暂停期间输入保留为草稿；`/dev resume` 恢复仍存活的运行，但不会自动发送草稿。`/dev cancel` 停止当前工作并保留已有文件，不重置工作区。

这些能力限于当前进程内仍存活的会话。退出进程、切换或释放会话后，保留的文档、提交和聊天记录可以供查阅，但不能恢复旧批准和原来的调度状态。

## 七、计划改变或审查卡住时怎么办

流程不只是一路向前，还要能够准确回到发生变化的位置。

- **目标或验收标准改变**：回到需求阶段，重新确认受影响的约定。
- **需求没变，核心方案改变**：重新比较方案，更新受影响的计划和交接。
- **需求和方案没变，只需要调整任务、验证或工作区安排**：使用 `/dev revise-plan` 修订当前计划，保留已批准上游和仍有效的工作，经审查后重新批准。
- **只是实现细节或内部调度变化**：在获批约定内由执行 Agent 自主处理，不重新走完整流程。

回退撤销的是受影响的批准和证据资格，不是删除代码，也不是重置整个工作区。

自动修复同样需要边界。需求、计划、任务和整体审查默认各有两轮修复额度；暂停、继续或重新委派不会清零。额度耗尽后，用户可以通过 `/dev extend-review` 明确追加一轮，但追加不等于问题消失，更不豁免测试、审查或最终验收。

这种停止机制的目的，是让没有收敛的问题重新回到人的判断中，而不是用无限循环掩盖模型无法解决的阻塞。

## 八、不需要每次都进入 `/dev`

只维护需求时，可以独立使用 OpenSpec：`opsx-explore` 探索问题，`opsx-propose` 新建提案和规格，`opsx-update` 修订或补齐已有需求，`opsx-sync` 同步正式规格，`opsx-archive` 归档，`opsx-verify` 核对实现及证据。

在 OMP 中，这些技能使用 `/skill:opsx-*` 调用；当前工作目录直接包含 `openspec/` 时，名称和描述也会进入模型索引，正文按需读取。终端入口是 `omp openspec ...`，无需另外安装一份 OpenSpec。

普通会话也保留全部包内 Superpowers 的手动入口。例如，独立维护需求后，可以显式调用 `writing-plans` 编写计划，再用 `executing-plans` 实施。默认发现只包含调试、完成验证和技能编写三项 Superpowers 技能，不会因为装进了 OMP 就自动启动整套方法。

已有项目如果有明确的 Markdown 需求权威，就继续维护原文，不再制造另一套可编辑主规格。小范围需求维护也不强制创建变更；只有需要独立追踪时，再引入提案、规格增量和归档。

不过，一旦主动启动 `/dev`，就按它的阶段和批准机制推进，不能在中途借独立技能绕过门禁。预期行为没有改变的普通 bug 修复，也不必为了留痕而强行改需求。

## 九、这套流程的收益与代价

这套组合希望减少的是需求误解、未经批准的推进、无证据放行，以及开发者不断把 Agent 拉回正轨的负担。它不承诺把弱模型变成强模型，也不承诺降低 token、费用或等待时间。

多一次独立调查、多一轮审查、保存并阅读正式材料，都会产生额外成本。按需加载降低的是单个上下文的负担，不代表整条流程的总消耗更少。

评价效果时，更值得看的是同类真实任务中的交付缺陷、遗漏、返工和额外人工纠偏，同时记录请求、token、实际费用与等待。刻意设置的需求确认和最终验收，是开发者保留的决策权，不应算作流程失败。

本地模拟模型可以验证输入路由、版本检查和流程状态，不能证明真实模型的任务质量。源码、发行包、不同平台、后端协议与桌面界面的验证结果，也不能互相替代。

最终要保留的分工很简单：**人决定目标和关键取舍，Agent 承担调查与实现，程序守住权限和状态，真实证据支持交付判断。**
