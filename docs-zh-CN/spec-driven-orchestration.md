# Dev 需求澄清、管理与开发进度跟踪

Dev 是 AI 驱动的需求澄清、需求管理和开发进度跟踪平台。人提供业务信息、检查材料并作决定；AI 整理需求、评审、分析方案与代码证据。**Dev 不参与实际编码，不安排编码执行 Agent，不执行开发计划、测试、代码交付或 IR 验收归档流程。** 实际开发与代码 PR 在平台之外完成。

本文说明当前目标规则及独立原型边界，不是后端实现或运行验证报告。可复现的原型启动与演示路径见 [前端 README](../packages/dev-frontend/README.md)。

## 1. 从自然语言到 IR／SR

用户通过对话描述目标、范围和异常场景，业务需求 Agent 澄清信息，生成 IR（业务需求）及其 SR（系统需求），包括可检查的验收条件。正常入口是与 AI 对话，不要求人手工编辑或复制修补规格文件。

- 新建提案先打开未发送草稿，按 Web、账号、项目及 Release 隔离；重复点击复用草稿。首次消息接纳后才加入列表，失败保留输入，不重复创建提案。
- 首发失败仍为未接纳草稿，材料区显示尚未生成，不提前展示占位材料；允许移除的草稿沿用确认／取消入口，正式需求及历史不随之开放删除。
- 提案以 IR 为讨论、修改及推进单位；左侧只显示 IR，保留提出人、当前阶段、搜索、筛选与排序。SR 在右侧材料选择器中阅读，没有独立讨论或推进流程。
- 提案主线为“业务需求 → 需求评审 → 技术方案 → 需求入库”。查看历史、切换材料或选择项目不启动 Agent、不推进阶段。
- 新建输入及空材料区引导描述业务目标、使用场景与完成标准，再由 AI 追问；四阶段名称在三栏中完整可见，查看历史不改变当前阶段。
- 业务需求 Agent 只维护 IR／SR 需求材料，方案 Agent 维护技术方案；均不修改实现代码、开发计划、测试报告或交付产物。

## 2. 四 Agent 评审，人工决定

需求文件完整后，由人发起当前版本评审：

1. 评审 A／B／C 使用三个不同模型，并行独立只读检查同版 IR 及全部 SR，不先参考彼此结论。
2. 第四个综合评审 Agent 等待三份报告完成，归并重复意见，保留来源、依据、原文和分歧。
3. 人默认阅读综合意见，按需切换原始报告和会话，决定“通过，进入技术方案”或“返回业务补充”。模型的票数、评分、问题标签或分歧不能代替人的判断。

“只读”指评审工具不修改文件，不是关闭聊天；人可以追问依据。当前需求材料及四份同版报告完整可读，是人工判断的材料条件，不是模型自动批准。需求修改后，旧报告和人工决定保留历史但失效，须重新评审。原始报告改变时综合意见也须更新。

“返回业务补充”实际退回业务阶段，列表和重新进入保持一致，取消不改变阶段。评审或方案退回后，须先在业务讨论中处理意见并更新 IR／SR，才能重新发起评审；不能用重跑评审跳过待处理意见，不增加逐项裁决表单。

界面复用 ZCode 原生工作流时间线、Agent 头像和会话；“评审流程”展示三路并行汇入综合评审，再进入人工判断，不将人工判断画成第五个 Agent。头像顺序为综合意见、A、B、C，支持键盘切换及名称／模型提示。

连续方向键及 Home／End 切换后，焦点留在对应评审头像；用户主动进入输入框时不强制抢回。异常推送情境预览只限制当前弹窗提交，关闭后可以重新打开并恢复正常交接。

## 3. 方案、依赖与人员排期

方案 Agent 与人讨论整体设计、各 SR 的实现思路、边界和取舍，在同一 OpenSpec Change 下同轮生成／更新共享 `design.md` 及同目录的 `sr-dependencies.json`。`design.md` 保留实现思路和技术取舍并引用 JSON，不重复依赖清单；SR `spec.md` 不再维护依赖。不编制编码任务执行计划。

`sr-dependencies.json` 是依赖及原因的唯一权威，结构为 `{ "srs": [ { "srId": "...", "prerequisites": [ { "srId": "...", "reason": "..." } ] } ] }`。每个稳定 SR ID 唯一覆盖 IR 全部 SR，无依赖用空数组，前置项记录稳定 SR ID 与原因；不允许自依赖、未知 ID 或循环。界面读取 JSON 展示依赖及原因，可并行关系由依赖图推导，不在 JSON 重复存储。

两个方案产物共用现有需求版本／方案轮次绑定，同轮生成、更新、失效并纳入查看和人工逐文件确认。需求或任一产物变化使旧方案确认失效。JSON 缺失、无效或过期时明确显示原因，不回退旧文档或旧依赖，不沿用旧确认，不允许提交或自动转正。

方案阶段保持三栏：中间讨论，右侧阅读材料及逐 SR 的实现思路、依赖、待确认事项；独立开发安排卡片展示建议开始／结束时间、人员可用性、计划起点和日历假设。信息不足须明确标注，不把计划跨度当作实际用时，也不单列工时。

材料区顶部可直接切换“技术方案／SR 依赖／人员与排期”，无需读到长文末尾再安排人员。业务名称优先，文件路径收进可展开的技术信息；实际文件、版本及逐文件确认不变。

- 管理员按工号为 IR 分配唯一负责人；管理员或该 IR 负责人可调整 SR 开发人员及起止时间，其他用户只读。
- 负责人分配可按工号、姓名／部门检索并保留工号手输；原型仅提供明确标注的虚构人员目录，不核验身份、不拒绝目录外合法工号。
- 保留 AI 原建议、假设、人工调整标记和记录；后续分析不覆盖人工安排。起止须同时填写或清空，结束晚于开始。
- 开发人员工号旁显示格式说明：一个小写英文字母后接 8 位数字，例如 `j00808874`；可留空。格式错误显示具体原因，修正后清除。
- 前置依赖时间冲突或同一人排期重叠持续提醒，不自动移动其他 SR，不据此推算代码进度。
- IR 时间汇总各 SR 最早开始和最晚结束，存在未排期 SR 时标明。
- 人员及时间是共享业务数据库元数据；需求、验收条件和方案以仓库材料为权威，依赖只以 `sr-dependencies.json` 为权威，数据库可读取投影但不另行维护。调整人员或时间不生成 PR、不改变文档版本或已有推送；修改依赖仍须经方案讨论同轮更新两个方案产物并评审。
- 方案未完成或已失效时，不把旧分析作为当前建议。人员未分配、排期提醒不增加入库门槛。

方案无法解决的业务问题，由人填写退回意见，返回业务 Agent 补充，再评审并重新分析方案。取消退回不改变阶段；保留历轮意见和会话，旧方案及确认不能用于新版本。长意见可滚动及全屏阅读，不自动拆题、分派或逐项裁决。

方案参与人工号只是来源记录，不形成独占锁；团队 Web 的其他业务参与人可继续讨论、生成或退回方案，并按当前文档确认入库。其他 Web 仍只读，不借此获得真实项目编码或 Git 工具权限。

## 4. 确认、推送与后台自动转正

业务澄清和方案设计期间不创建 Git 分支。方案完成后，人逐文件确认当前 IR、全部 SR、`design.md` 和有效 `sr-dependencies.json`，平台才按需拉取配置仓库，从最新默认分支创建提案分支（如 `ir/<IR-ID>`），将上述完整材料一同 Git 提交并推送，提供 PR 标题和正文。无需配置本地或个人开发目录。

人到企业 Git 网页创建、评审及合并包含 JSON 的 PR；平台不自动创建 PR，不依赖 PR API。PR 地址是选填参考，不是入库门槛，也没有“人工确认合入”操作。

后台自动转正只有两个条件：

1. 提案分支已合入配置的默认分支；
2. 默认分支上的 IR、全部 SR、`design.md` 及有效 `sr-dependencies.json` 完整。

满足后自动成为正式需求，保持项目／IR／SR 身份、负责人、开发人员、人工排期和仓库依赖；不按转正时间重置。随后从包含提案的最新默认分支创建并推送各 SR 分支，记录映射和基点。重复检查不重复入库或创建分支。新 SR 进度为 0%，转正只表示需求获准开发，不表示实现完成。

未合入、文档不完整（包括 JSON 缺失、无效或过期）或获取失败时保留提案，展示原因、最近与下次检查时间并继续检查；JSON 有效性属于第二个条件，不新增入库审批。无法确定合入事实时不转正；核验需兼容 merge、squash 和 rebase。真实后台须独立于浏览器运行。

管理员可在提案列表按检查失败、文档不完整、等待合入等状态巡查和组合筛选，不必逐份打开；数量来自已有检查记录，筛选不执行 Git 或触发转正。

## 5. 正式需求：代码证据、进度与遗留问题

正式需求使用当前项目／Release 的 IR／SR 大表格，IR 可展开 SR，支持名称／编号搜索、状态筛选和“我负责的”（IR 负责人或所属 SR 开发人员），可一键清除筛选。表格包含九列：需求、状态与进度、负责人／开发人员、开发分支、依赖关系、计划开始、计划结束、问题、最近分析。固定表头及名称列，单层横向滚动，不使用聊天 Markdown 表格工具栏。

正式表格另支持指定 IR 负责人工号精确筛选和未分配 IR 筛选；指定负责人与 SR 开发人员区分，“我负责的”语义不变，工号检索在弹层中完成。

筛选可自动展开匹配的 SR，但用户仍可手动收起／展开；不会强制维持展开或改写无筛选时的偏好。

正式需求默认收起左侧提案导航，顶部可展开导航及切换项目／版本。选中行后表格仍保留，右侧同页显示可拖拽的“进度报告／需求材料”面板，默认约 380px，可在 320～480px 调整。切换行或收起面板保留浏览状态，不跳入开发详情页，不显示编码聊天或开发阶段操作。

开发者展开 IR，即可在各 SR 行“开发分支”列查看并点击复制完整分支名，无需进入设置。复用需求进度分析已有的分支复制、提示组件；长名可省略，悬停或聚焦查看完整名称，成功／失败明确反馈。所有访问者均可复制，不触发行选择或 Git 操作；IR 行提示查看各 SR。分支优先读取平台 SR 分支映射，其次为当前分析关联分支，不使用执行历史或猜测名称；无关联显示“尚未关联分支”，不提供空值复制。

需求进度分析 Agent 根据需求、验收条件和代码证据，报告实现情况、遗漏、遗留问题、不确定项、代码活动、合入依据、分析时间和代码版本；不编码或修复问题。

- **SR 未合入默认分支时，AI 与人工均最高 99%，不能完成。**
- **合入后，AI 确认全部实现或人工根据证据确认，才能达到 100%／已完成。** 合入是必要条件，不是完成结论；AI 不确定时仍显示当前百分比与问题。
- 管理员或该 IR 负责人可调整 SR 进度、确认完成并填写依据。人员和排期调整不改变代码进度。
- IR 进度为所属全部 SR 百分比的算术平均；没有 SR 时为 0%，只有全部 SR 完成才完成。显示精度不能把未完成值四舍五入成 100%。

人工进度在百分比旁标明“人工调整”或“人工确认”，首屏显示工号、时间及依据，旧 AI 问题与代码证据标为此前报告。新转正 SR 首次分析前保持 0%／尚未分析，不预填历史分析时间、代码版本或实现结论；提案合入基点不等于 SR 代码分析版本。

Dev 不控制开发启动、并发名额、worktree、编码会话或交付 PR，也不要求 IR 完成后再执行验收／归档 PR。代码开发、测试、评审及规格归档由外部开发流程负责，不能作为旧执行流程重新出现在 Dev 中。

### 需求进度分析设置与调度

平台配置新增独立“需求进度分析”，两部分共用一套权限：全员可查看、筛选和阅读报告，仅共享 Web 启动者能修改或触发分析。

1. **项目分析范围**：可按项目名称搜索的紧凑表格，按项目直接启停，显示待分析 SR 数、最近分析及状态。新项目默认关闭，不要求逐 SR 创建任务。
2. **统一调度与执行历史**：全局自动分析开关、统一间隔（默认 60 分钟、正整数分钟）及运行摘要，下方为“SR 任务／执行历史”两个标签，只展示当前标签的分页列表。沿用定时任务风格，不复制通用任务新建／模板／工作流或开发模式。

一个调度器管理全部项目，每个正式 SR 自动有一条唯一任务记录；稳定 ID 不因重命名、配置修改或重复检查而变化。不创建每 SR 定时器或独立 cron。全局开关只暂停自动接纳，仍可对开启项目立即分析；项目关闭同时排除自动与手动接纳。已接纳项继续，同 SR 不重复并发、失败彼此隔离。已完成 SR 停止自动分析，重开后复用原记录；需求与代码证据均未变化则跳过模型分析。

项目 → IR 联动筛选和 SR 名称／编号搜索直接过滤任务及历史，历史另可筛状态和时间。两个列表分别分页，默认 25 条、可选 50 条，有匹配总数、首尾及前后翻页，固定表头和限定滚动区域。筛选变化重置相应页码，翻页／切标签保留筛选与各自页码，数据减少时夹至合法页。历史摘要按 SR 记录批次、触发方式、开始／结束、耗时、结果和进度变化；任务失败行直接查看原因或仅重试当前 SR，报告按需读取，在当前视口弹窗展示版本、合入依据或错误，关闭返回原控件；切筛选／分页／标签关闭旧详情。分析成功不等于需求完成。

任务与历史均展示每个 SR 的分支名，历史保留当次执行分支。点击分支文字复制完整名称，长名可截断但可查看完整值；所有人可复制，成功／失败明确反馈，不属于管理写操作、不执行 Git。

“分析当前筛选范围的 N 个 SR”按全部匹配项计数与执行，不是当前页，不受历史状态或时间过滤影响；不改变自动范围，不纳入停用项目、已完成或正在分析的 SR。查询只返回当前页摘要，状态刷新不携带所有报告；真实后端必须分页查询。独立原型 `?demo=analysis-scale` 初始提供恰好 300 个任务与 1000 条历史，共用相同查询／调度逻辑，供实际浏览器验证，不能当作真实代码分析或生产性能证明。

模型、思考强度和追加提示词沿用既有需求进度分析 Agent 配置，不重复设置。原型只在内存模拟任务及历史，通过显式“模拟一次调度检查（原型）”推进虚拟时间，不自动运行真实定时器、模型、Git 或数据库，不覆盖正式需求报告；刷新恢复样例。首个项目可预置开启供演示，新增项目仍关闭。

失败样例区分仓库读取、模型调用与文档读取，说明阶段、原因、下一步和重试条件，不冒充真实后端诊断。重试仅启动者可操作，项目关闭、已完成或正在运行时禁用；单 SR 重试不派发其他 SR，不重复并发。


## 6. 文档与数据归属

一个 IR 对应一个 OpenSpec Change，一个 SR 对应一个能力规格，IR 共用一份技术方案：

```text
openspec/changes/{change-id}/
├── proposal.md                 # IR：目标、范围与验收条件
├── specs/{capability}/spec.md   # SR：稳定 ID、需求及验收条件，不维护依赖
├── design.md                   # 整体设计、各 SR 思路与技术取舍，引用依赖 JSON
└── sr-dependencies.json        # 全部 SR 的前置依赖及原因，唯一依赖权威
```

提案材料先位于 `/tmpdata/DFT_LAB/omp/{project_name}/{原提交人工号}/{提案id}/` 下的同一文档结构，经确认后提交仓库。原提交人和业务身份不随查看者、标题或排序改变。正式材料来自仓库，提案材料来自临时工作区。提案合入不提前把未实现的增量同步为 `openspec/specs/` 中的已实现规格，也不自动归档 Change。

只读材料按业务类型选择，再显示完整换行路径及内容；IR 可阅读原始需求、全部 SR、`design.md` 及 `sr-dependencies.json`，SR 仅显示自己的规格。右侧选中依赖 JSON 时，复用现有图画布与缩放控件显示只读依赖图，不展示 JSON 正文：节点为稳定 SR ID 与标题，箭头从前置 SR 指向依赖方，支持平移及点击连线查看原因，独立 SR 也显示；无效或过期材料报错，不绘制旧图。不混入旧开发阶段报告，不提供复制、下载或带入讨论按钮。流程操作位于提案材料底栏；材料缺失、未生成和读取失败明确区分，失败保留目标和草稿，重试不自动重放动作或回退样例。

## 7. 配置、多人访问与模型职责

项目只配置名称、Git 仓库地址和默认分支，Release 沿用项目配置；平台管理内部工作副本。保存设置不拉取仓库、不创建分支或推送。原型格式校验不证明仓库可访问或分支存在。

Git URL 必须含主机；`https://`、`https:///` 不可保存，合法 URL 与 SCP 地址仍只作格式校验。分析间隔及下一周期超出安全整数／可表示日期范围时在修改配置前拒绝，不污染原调度。

以下为目标共享部署约定，不代表本轮已实现服务或安全认证：

| 项目 | 约定 |
| --- | --- |
| 业务数据 | `omp dev_db` 固定端口 18321，统一管理 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`；Web 经服务访问，不各自直接打开 NFS SQLite |
| Web | 只启动一个共享 `omp dev_web`，所有人访问同一地址；`--port <端口>` 指定端口，省略时选可用端口并输出地址，不按访问者启动个人 Web |
| Token | 所有访问者使用启动者的 OMP Token／profile；切换浏览器工号不切换宿主或凭据 |
| 工号 | 小写 `a`–`z` 字母加 8 位数字，保留前导零；仅格式检查，不是完整认证 |
| 共享查看 | 项目、Release、提案、正式需求及全部设置对所有人可见 |
| 提案讨论 | 所有访问者在同一共享 Web 提需求和讨论，无需个人 Git 目录；讨论归该宿主，宿主不可用不自动接管 |
| 设置权限 | 外观和 Skill 设计所有人可用；其余设置仅启动该 Web 的人可修改，其他人只读，可切换、搜索、筛选和复制；草稿、保存、快捷键及全部写入口使用同一权限，不隐藏页面 |
| 设置分组 | 先“个人工具”（外观、Skill 设计），后“平台配置”（项目与 Release、模型、个性化、技能、需求进度分析等有效设置）；两组全员可见，分组不改变权限 |

模型职责为业务需求、需求评审 A／B／C、综合评审、方案、需求进度分析及 Skill 设计。不提供计划、执行或 IR 验收 Agent 配置。评审前三者使用不同模型，综合评审独立选型；模型、思考强度及追加提示词按会话／评审轮次保存快照，修改只影响新会话或新轮次，不覆盖历史。不新增提示词预览。

个性化追加提示词与模型配置均在离开前提供保存／丢弃／取消；保存读取最新草稿，长文本连续输入不循环更新。每个 Agent 按 UTF-8 最多 100 KiB，超限保留内容但禁止普通保存、快捷键及保存并离开，缩短后恢复。技能管理提示共享 Web 启动者维护，不要求访问者另启个人 Web。

技能页及独立 Skill 设计保留为辅助能力，不代表 Dev 接管编码。所有访问者可填写 Skill 设计表单，把实际值及临时路径填入原聊天草稿，明确发送后预览并确认保存；不因此获得模型、提示词或技能管理的修改权。目标明确展示为共享 OMP 当前 profile 的 `skills/<name>/` 或有效项目 `.omp/skills/<name>/`，不冒充访问者的个人后端；没有项目绑定不阻止 profile 目标，不覆盖同名技能或写目标外目录。这不引入 Dev 个人开发目录要求；原型仅演示固定文件及内存保存状态。

Skill 左右两栏同步显示当前版本的生成／保存状态；重新生成后清除旧版保存标记和过期通知。通用定时任务列表与详情区分“已启用 · 等待执行”“执行中”“已暂停”，启用不代表正在执行，暂停任务不计入执行中筛选。

## 8. 原型与真实运行边界

独立预览与 OMP 正式入口共用 `app/DevApplication.tsx` 及 Dev UI，分别注入内存样例或真实宿主数据。正式适配层仅使用宿主现有 HTTP／WS／RPC 能力，错误不得回退样例；已有宿主协议不等于最新平台业务已接通。

本轮仅维护文档和独立原型。四 Agent 报告、`design.md`、`sr-dependencies.json`、排期建议、Git 推送、SR 分支、代码证据和进度报告均为演示数据；材料和编辑只改变页面内存，不真实写文件，刷新恢复。提案后台演示每 5 秒读取内存预置结果，关页即停止，不能当作真实服务。未实现真实共享数据库、AI 调用、Git／PR 集成、权限认证或后台进度分析。

原型隐藏自由会话、新建会话和正在开发入口，不删除底层会话、草稿或原生能力，也不修改原 WebGUI。**Dev 只考虑电脑端浏览器：设计、原型及验收不覆盖手机、平板或触屏专用布局。** 电脑端窄窗口及拖窄分栏仍须可用，底部操作在栏内换行，不能裁切；外观控件关联可见标签并支持键盘操作。本机 Chromium 的截图与交互记录见前端 README，Firefox 128、真实读屏软件及真实宿主仍需独立验证，不能互相代称通过。

可编辑聊天输入框保留两项原型辅助输入：

- **画图**：全屏覆盖现有 Sketch 页面，发送时只把完整画布 PNG 回填原输入框附件，不自动发送消息或推进阶段。取消不改变草稿；失败保留绘图。仅独立预览启用，不连接真实 Sketch 服务。
- **语音转文字**：麦克风入口演示录音及可编辑示例文字，确认后追加草稿，不自动发送；不申请麦克风权限、不采集音频、不调用识别服务。
