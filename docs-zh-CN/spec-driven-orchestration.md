## OpenSpec 文件约定

一个 IR 对应一个 OpenSpec Change；一个 SR 对应一个能力的 `spec.md`，文件内可包含多条 Requirement 和 Scenario，整份 IR 共用一份 `design.md`。

```text
/tmpdata/DFT_LAB/omp/{project_name}/{原提交人工号}/{提案id}/
└── openspec/
    └── changes/
        └── {change-id}/
            ├── proposal.md                    # IR：业务需求与范围
            ├── specs/
            │   ├── {capability-a}/spec.md      # SR A：能力增量规格
            │   └── {capability-b}/spec.md      # SR B：能力增量规格
            └── design.md                      # 共享技术方案、SR 顺序及依赖
```

先在固定临时目录生成，不直接写项目工作区；由已确认版本准备提案分支。`design.md` 说明技术设计、架构、模块、文件、函数、SR 实施顺序及依赖。IR、SR、Change 与 capability 使用稳定映射；标题、列表筛选和显示顺序不是业务身份。

提案合入表示需求和方案正式入库，不代表实现完成。未实现的 Change 增量规格不能在提案 PR 中提前同步为 `openspec/specs/` 的已实现规格。

## 并行与冻结

- 同一仓库一次只有一个进入开发的 IR；按仓库身份统一判断，跨项目登记、工号、clone、worktree、Release 或目录别名不能绕过。
- 当前 IR 内满足依赖的独立 SR 可以并行，默认最多 2 个；不限制同一工号只能开发一个 SR。不同仓库和提案讨论可并行。
- 方案阶段明确依赖及实施顺序。前置 SR 的 PR 真实合入、默认分支核验后，依赖它的 SR 才可开始；不只依据 Agent 声称完成或分支已推送。
- 每个 SR 从开发人的 Git 开发仓库，以启动时最新默认分支创建独立分支和 worktree，记录确切基点提交。后续对齐默认分支保留更新记录，不隐式改写启动基点。
- SR 的开发人、目录、分支、worktree、会话固定；一个 SR 不能重复接手。切换浏览对象或修改个人设置不重绑已经开始的工作。
正式需求入库后可在自己的 Git 项目自由修改和提交；保留历史版本，旧报告不自动适用于新提交。
- 准备中、开发中、等待评审或合并均占 SR 名额；真实合并且工作结清后释放该 SR 名额。仓库 IR 占用一直保留到最终验收／归档 PR 合并并核验。
- 准入与占用通过共享状态原子检查。暂停、断线、关闭页面、重启或删除列表显示不释放占用，不自动删除 worktree 或分支。

## 业务流程

### 1. 需求讨论与业务评审

业务需求 Agent 整理 IR、拆分 SR，写 `proposal.md` 与增量规格。需求评审仍为一个阶段：评审 A／B／C 使用三个不同模型并行只读审查同版 IR／全部 SR，第四个综合评审 Agent 汇总意见并保留来源与分歧。人默认查看综合意见，自行判断通过进入方案或返回业务补充；模型不决定是否通过。

业务人员通过与 AI 对话明确业务判断；评审 Agent 只读报告问题，需改需求时自行返回业务 Agent，不新增裁决表单，不无限循环。提交给开发人员接手不要求已有技术方案，但业务评审须通过。

### 2. 技术方案

开发人员明确接手后，方案 Agent 生成共享 `design.md`，解决技术问题并确定 SR 顺序与依赖。需要业务补充时附原因打回业务需求 Agent；保留历史，旧方案和受影响确认失效，重新评审并生成本轮方案。

提案状态与当前讨论阶段分开：草稿可以处于业务需求或正在生成方案；确认方案完成后才可准备提案 PR，提交后仍为 PR 待合并。没有独立“待评审”状态。提案内仅点击 IR 的“需求讨论”进入当前阶段的整份提案会话；业务需求和方案各保留自己的历史。点击 SR 只阅读自身 spec.md，中间显示返回 IR 讨论或修改的提示，不挂载聊天或阶段操作。

### 3. 提案入库

人工确认需求及方案 → AI 在授权范围内提交、推送提案分支并提供 PR 标题、正文 → 人工创建、评审、合并 PR → 告知平台。

平台核对默认分支已包含确认版本的 `proposal.md`、全部 SR 增量规格与 `design.md`，才转为正式提案，进入现有“正式需求”导航。提案文件仍位于 `openspec/changes/{change-id}/`，此时不归档、不提前更新已实现规格。通知、PR 链接或勾选不能替代 Git 事实；核验应兼容 squash／rebase。

### 4. 按依赖开发 SR

明确开始 SR → 校验自己的 Web 与 Git 路径、本 Web 内的并发及依赖 → 本 Web 内预留名额 → 获取最新默认分支 → 创建独立分支与 worktree → 开发计划 → 开发与验证 → 交付 PR。

Superpowers 提供计划、开发、测试和代码审查方法，OMP 唯一负责原生会话、工具、子任务及状态。计划与执行使用相应职责，测试／代码审查使用 OMP 原生子代理，不另建重复顶层 Agent 或第二执行器。阶段推进需要明确批准，并绑定当前阶段、轮次和完整材料版本；未执行、失败或环境受限的验证如实记录。

**代码、测试以及将该 SR 增量落实到 `openspec/specs/{capability}/spec.md` 的更新放在同一个 PR**，保留源 Change／SR／版本映射。提交前不改写当轮记录的 Change 需求。合并前对齐最新默认分支并重跑受影响验证；需求冲突、Git 合并冲突暂停交人工，普通实现问题由 Agent 修复。

AI 提交／推送并给出 PR 标题和正文；人工创建、评审、合并并告知。平台核验默认分支的代码、测试和规格后完成该 SR、释放其名额，允许依赖就绪的下一 SR 开始；IR 继续占用仓库。

### 5. IR 验收与归档

全部 SR 已合入后，IR 验收 Agent 按固定正常流程生成通过报告；当前简化设计不发现问题、不返工或复验。随后由 AI 准备归档 PR，人工评审合并并核验归档后，IR 才完成。

验收报告绑定最终候选及默认分支基点；归档前核对各 SR 代码、测试和已实现规格的合并记录。默认分支变化属于版本核验，不新增业务返工阶段。

**最后一个 PR 只做 Change 归档**。将 Change 目录移入原生归档位置，使用不再同步规格的归档方式（`--skip-specs`），不重复执行规格同步。

人工创建、评审、合并最终 PR 并告知，平台核验最终默认分支的成果与归档结果后，IR 才完成并释放仓库占用。不自动删除开发目录、worktree、分支或历史。

## 界面及运行边界

Dev 面向桌面浏览器，不要求手机适配；保留 Chromium 与 Firefox 128 的后续验证目标。原 WebGUI 自有的手机要求与实现本次不改。

现有原型预览与 OMP 正式启动共用同一套 Dev UI，由不同入口注入样例或真实宿主数据；预览启动命令保持不变，正式资源不加载样例，真实错误不回退演示。此次只实施数据源分离与现有原生接口挂载，不新增原型功能，不补做下述完整业务，也不恢复旧 Dev 流程。


左侧继续为当前项目的“自由会话”“正式需求”“需求提案”。自由会话功能与 WebGUI 原“单项目”一致，只显示当前开发项目，默认右侧审查，仅查询最近 5 条历史，进入后才加载消息；不绑定 Release 或走提案流程。新建只打开未发送草稿，重复点击保留正文、附件和模型选择，首次发送成功后才显示历史记录。访问他人的 OMP Web 时仍显示自由会话行及按钮，不显示历史，点击操作提醒进入自己启动的 OMP Web、以自己的工号登录并配置开发项目路径。正式需求和提案使用同一 IR／SR 控件，IR 展开 SR；三栏尺寸与 WebGUI 相同；刷新后右侧默认展开，自由会话显示审查，需求会话显示只读材料。左侧自由会话及需求栏目展开到 IR 层，IR 下 SR 默认收起，不因恢复会话自动展开；手动折叠偏好在本页按当前浏览上下文保留。

自由会话是正式 Dev 必需能力，必须接入 OMP 原生会话的新建、历史读取、发送与流式回复、停止、重命名、置顶、归档及文件／审查，并按原生规则持久化。数据源分离不得成为取消或隐藏入口的理由；真实失败保留目标与草稿，不回退样例或以空列表冒充成功，不自动重放操作。当前独立原型保留入口和样例，正式适配层仍关闭自由会话且尚未接入；本次仅更新原型边界及文档要求，不修改正式代码、不运行测试，也不宣称真实功能已恢复。

项目与依赖它的 Release 在左下角工作区菜单相邻展示，切换项目重选其 Release，不改变运行中的任务。正在开发入口须容纳本 IR 的多个开发 SR，分别显示阶段与开发人；浏览他人的开发只读。选中、搜索、筛选、查看历史或重试读取均不启动 Agent、推进阶段或重新绑定目录。

模型及追加系统提示词涵盖业务需求、业务需求评审、方案、计划、执行、IR 验收、Skill 设计七个职责，沿用每个开发者自己的 OMP 配置目录／profile，个性化、模型、Agent 和个人技能互不共用，不落共享业务数据库；只作用于新建角色会话，历史保留创建时快照。不增加追加提示词预览。现有技能页保留，独立 Skill 设计页复用原生聊天能力：表单将全部实际填写值按“字段名称：内容”组合，连同临时技能目录及主文件路径填入右侧聊天输入框；无需填写技能标识，由模型推荐并用于预览及保存路径，保留原有草稿，由用户直接发送或继续补充后发送；不根据表单直接生成技能。所有人看见同样的 Skill 设计页面；业务人员点击填入时弹出不支持提示，不改变输入框；开发者填入时保留原草稿，成功写入后才提示。实际发送后由大模型澄清并在临时目录生成技能，用户可预览文件清单、路径和内容，继续讨论修改，最后明确选择并保存整份技能目录到自己的当前开发项目 `.omp/skills/<skill-name>/` 或个人 OMP profile `skills/<skill-name>/`。缺少项目绑定只阻止项目目标，不影响有效个人目标；不写共享只读目录或他人目录，不覆盖所选目标中的同名技能。Skill 设计会话与临时文件也仅属于当前开发者后端。当前会话仅修改文档与前端原型，不改真实实现、不跑测试；原型使用明确标注的固定产物样例，不代表模型生成或真实文件写入。

### 聊天输入框画图（本轮仅文档与原型）

Dev 中间聊天输入框在模型选择器左侧增加画图按钮。点击后在当前网页全屏覆盖显示现有 Sketch 页面，覆盖整个三栏工作区，不另开标签页。画完点击画布的“发送”，完整画布作为 PNG 图片附件加入打开它的原输入框；成功后关闭画布，保留原有文字、附件和模型选择。这里的“发送”只回填附件，绝不自动发送聊天消息、调用模型、创建会话／提案或推进阶段，仍由用户在输入框明确发送。

取消只关闭画布，不添加附件或改变原草稿；回填失败保留绘图并显示原因。没有可编辑输入框的只读页面不增加入口。本轮只在独立原型演示，不接正式 OMP 宿主或 Sketch 服务，不改原 WebGUI 与原生 `/sketch`。


材料缺失、读取失败、目录失效、仓库不符或发送失败须明确原因，保留原目标和未发送输入；重试不自动重放命令、创建对象或回落固定样例。退出前结清自有主任务及递归子工作；浏览器关闭不退出服务。跨机器接管须先结清原宿主，不凭超时、PID 或文件可见性自动夺取占用。

团队长期 Web 与开发者各自的本地 Dev 同时存在，各自运行 OMP 原生能力，业务元数据跨后端共享，开发者配置独立；原先仅本机的 Dev 访问假设不再定义本部署。原 WebGUI 的访问边界、普通 OMP、独立 OpenSpec／Superpowers 和 TUI 独占准入保持原约定；本次不实现新的服务或网络接入。

桌面聊天头部显示标题、居中阶段条、Agent／职责状态；提案不重复标题，提出人在左侧及提案信息固定展示，当前处理责任合并到状态行，人工操作独立放在右侧文档底部。提案 IR：业务需求→需求评审→技术方案→需求入库；SR：开发计划→开发与验证→交付合并；正式 IR：SR 开发→整体验收→完成归档。评审使用独立只读 Agent 聊天，人工 PR 节点使用流程说明；交付继续使用执行 Agent 职责，不新增交付 Agent。阶段点击只查看历史，人工检查右侧文件后点下一步才推进；回退弹窗说明影响并保留代码和历史，既有文档、依赖、版本与 PR 核验门槛不变。历史查看仅提供返回当前阶段；提案辅助信息和记录通过更多菜单查看，流程动作只在文档底栏。右侧为文件路径、正文及固定底部阶段操作栏。只考虑桌面，浏览器截图走查不代表真实 Agent、Git 或测试已执行。

评审阶段中间保留原生聊天及输入框，评审 Agent 只读报告问题与对应文件依据，用户可直接询问；右侧仍通过文件目录阅读，不另建静态评审页面。文件选择器保留完整路径并换行，使文件名可见；正文与表格、代码块中的复制、下载、展开等操作不显示，保留读取失败时的重新读取入口。右侧仍仅有文件路径、正文与独立阶段操作底栏，不增加材料管理卡片。聊天继续使用原型假数据，本轮不重写讨论内容或实现真实服务。

### 以 AI 为中心的提案补充循环

人通过对话提供业务信息、代码理解和意见，检查只读产物并确认流程；业务需求 Agent 生成和修改 IR 的 proposal.md、全部 SR 的 spec.md，方案 Agent 生成和修改 design.md。平台不以人工编辑、复制或修补这些文件作为正常流程入口。本文“开发修改需求／方案”均指开发与对应 AI 对话，由 AI 执行文件修改。

业务讨论、需求评审、技术方案全在管理员 A（j00808874）的 OMP 上，临时目录内完成，不要求方案开发人已启动自己的 Web 或配置个人项目。需求文件完整后人工发起评审；当前版本综合意见完整后，人点击“通过，进入技术方案”，记录本轮方案参与人，不再要求先“交给开发”再单独接手。评审只提供问题、建议与依据，不按模型评分或阈值判定通过；是否通过由人阅读综合意见后决定。

方案 Agent 提问时，开发能回答则继续对话；回答不了，由开发自己复制 Agent 的原文，点击右侧底栏“退出方案，退回业务补充”，在大输入框中粘贴并可编辑后确认。取消或关闭不改变阶段。平台不自动识别、拆分、分派问题或判断逐项已解决。确认后立即回业务需求 Agent，不先进入需求评审；IR 讨论上方醒目显示最新待处理意见的完整原文、提交开发人工号，长内容可滚动。业务通过聊天补充，由 AI 更新 IR／SR；人工再发起当前版本评审，通过后开发再次进入方案 Agent，结合最新文件与补充意见继续。此循环可重复，保留每轮意见及会话历史；旧方案和旧确认不能用于新版本入库。Agent 的上下文必须带入最新意见，原型仅演示数据与界面，不代表真实模型已连接。

左侧提案 IR 以紧凑双行显示名称、固定提出人工号及当前状态，SR 仍为单行；提出人不随方案参与人或入库人改变。IR 头部显示当前轮到业务提出人、方案开发人还是具备条件的入库开发人员处理；这是工作责任提示，不新增自动分派或角色权限系统。最新意见在业务补充及重评期间保留，开发重新进入方案后转为历史，在操作记录中查看，不要求人工逐题勾选。

只有最终需求入库要求开发登录自己启动的 OMP Web，配置自己可写且属于同一仓库的 Git 项目。入库开发人可以与方案开发人不同；确认后由 AI 将 A 的 NFS 提案临时目录中 IR、全部 SR、design.md 的当前版本复制到自己的项目分支，提交、推送，人工创建、评审、合并 PR 后核验。其他 Web 仍不能讨论或修改 A 的提案，但符合条件时可处理已完成方案的入库；确认候选由确认人继续操作，不代用他人候选。浏览器原型的各入口为独立内存样例，不冒充真实跨 Web 共享或文件复制。`?demo=proposal-intake&backend=colleague` 可查看方案已就绪、由 B 自己的 Web 准备入库的场景。

最新待处理意见须兼容长文本：页面内正文限制高度、独立滚动并支持键盘聚焦，不撑开页面或挤掉聊天；提供只读全屏阅读，标题和返回操作固定，全文独立滚动。保留段落、列表及换行，长链接和连续字符可换行，不产生横向页面溢出。打开／关闭不发送消息、不改变阶段或意见状态，返回原讨论及原滚动位置。大输入框支持长意见粘贴及内部滚动，不截断原文。

### 需求评审 Agent：工具只读，对话可用

需求评审包含四个独立只读 Agent 会话：A／B／C 使用三个不同模型并行审查同版 IR／SR，第四个综合评审 Agent 等待三份报告完成后汇总来源、依据和分歧。中间默认打开综合意见及可发送输入框，A／B／C 会话用于按需追溯；“只读”指不修改需求或其他项目文件，不是禁用聊天。是否通过只由人判断，模型有建议、阻塞标签或分歧不自动禁用人工通过，也不按投票或分数放行。右侧底栏“通过，进入技术方案”记录当前报告版本的人工决定并进入方案；“返回业务补充”直接返回业务 Agent，无裁决表单和额外已读勾选，由 AI 修改文件后重新评审。四个 Agent 的追问都不修改需求、不自动批准或推进。历史会话仅供只读查看，旧报告及旧人工决定不适用于新版本。原型为固定报告和会话样例，不代表真实多模型执行。

需求提案 IR 与正式 IR／SR 的聊天顶部固定为三行：第一行原生标题和工具图标，第二行居中阶段条，第三行单行显示当前 Agent、状态与必要处理人。删除重复标题、单独人员／目录行及协作按钮；正式 IR／SR 的简洁“…”菜单紧邻问号左侧，没有聊天会话时仍显示原生标题。所有流程操作仍在右侧文档底栏。本轮仅改文档和原型，未运行测试。

### 正式需求筛选简化及五份 IR 样例

当前简化约定：IR 验收 Agent 只走正常流程并生成通过报告，不发现问题、不返工、不复验。筛选只保留“全部需求、待开发、开发中、验收与归档、已完成”五项，按当前 Release 的 IR 整体进度聚合，不能按某一个 SR 是否正在运行判定。“全部需求”不是业务阶段。

- 待开发：没有任何 SR 开始。
- 开发中：已有 SR 开始或完成，尚未全部合并核验；即使当前没有运行中的 Agent，也不回到待开发。
- 验收与归档：全部 SR 合并核验后，覆盖等待验收、正在验收、通过后准备归档及最终 PR 等待合并核验的整个阶段。
- 已完成：最终归档 PR 已合并，成果与归档均已核验；不能仅凭全部 SR 完成就判断 IR 完成。

原因：在验收不会失败的假设下，待验收、验收中、待归档只是同一条固定后续流程的内部进度，不需要再占据多个筛选项；行内仍可说明待验收、验收中等具体进度，不新增问题／返工分类。SR 的开发计划、开发与验证、交付合并继续作为 SR 阶段，不混入 IR 筛选。

默认 Aurora 项目当前 Release 共五份正式 IR：团队数据总览（待开发）；账号与权限体验（开发中）；报表导出（全部 SR 已合并，待验收）；通知中心（验收中）；操作审计（最终 PR 与归档均已核验，已完成）。因此各筛选数量为全部 5、待开发 1、开发中 1、验收与归档 2、已完成 1。五个 IR 的具体进度不同，但不为匹配五个选项而虚构一个“全部”阶段。提案和其他项目样例保持独立。

这些都是静态内存数据，未执行真实模型、测试、Git 或归档。待验收和验收中的共享摘要使用不同 OMP 标识，不占当前 A 的开发名额；并发准入仍只检查当前 OMP Web。

### 需求提案列表只展示 IR

需求提案左侧列表仅展示 IR，不显示展开箭头、下属 SR 或展开／收起全部按钮。点击整行直接进入该 IR，并显示当前选中状态；保留提出人、阶段／待处理提示，以及搜索、筛选和排序。

原因：提案的讨论、评审、方案和入库均以 IR 为单位，SR 没有独立阶段操作，树形列表容易让用户误以为可以单独推进 SR。SR 数据及文档不删除：在 IR 右侧文件选择器中查看 `proposal.md`、各 SR 的 `spec.md` 和 IR 的 `design.md`。正式需求仍保留 IR 展开 SR，因为开发后各 SR 有独立流程。

### 新提案首发权限

“新建需求提案”的未发送草稿尚无 IR 编号，仍属于提案讨论。A（j00808874）的 Web 上，业务人员首次发送需求文字或附件不要求拥有该 Web，也不要求配置个人 Git 开发路径；其他 Web 仍不能发起提案讨论。首次发送成功后才加入提案列表，重复点击新建不会生成空提案，发送失败保留草稿供重试。

修正原因：旧权限检查未区分草稿，且首条消息发送时从普通列表读取，遗漏了尚未公开的提案，误用了正式需求开发限制，导致业务人员首次发送失败。此修正仅涉及原型的讨论权限判定，不放宽正式需求开发、个人配置或最终需求入库权限。

### 只读材料：类型、路径与正文分层

所有 IR、SR、提案及开发阶段共用的只读材料面板，依次展示材料类型下拉框、所选文件完整路径、文档正文、底部阶段操作按钮。下拉框使用“IR 原始需求、SR 系统需求、IR 方案设计、开发计划、完成报告、UT 报告、ST 报告、交付说明”等业务名称，不显示文件名或路径。IR 内存在多份 SR 规格时，使用“SR 系统需求 · 需求标题”区分，不能把文件路径放回选项。

路径独立显示，使用已记录的工作区与材料路径，长路径完整换行、不截断；已归档材料显示实际归档路径。路径与正文在同一阅读滚动区，阶段操作固定在面板底部，保持原有权限和流程。原因：先按材料用途选择，再查看来源和正文，避免长路径挤占下拉框并妨碍识别。

### 原生动态工作流时间线

需求提案、正式 IR、SR 的聊天顶部统一复用 ZCode `WorkflowTimeline`，替换自制数字阶段条及底部进度线；仅在独立 Dev 前端中投影现有阶段状态，不接入或伪造工作流执行引擎。

- 提案：业务需求 → 需求评审 → 技术方案 → 需求入库。前三站分别展示业务、只读评审、方案 Agent；入库为人工流程，不虚构入库 Agent。
- 正式 IR：SR 开发 → 整体验收 → 完成归档。SR 开发是计划／执行 Agent 的汇总，整体验收展示 IR 验收 Agent，归档仍需人工合并核验。
- SR：开发计划 → 开发与验证 → 交付合并。展示计划 Agent 与执行 Agent，交付继续由执行 Agent 准备，不增加新 Agent。

原生轨道、Agent 头像、完成标记和运行灯沿用站点风格。当前阶段与正在查看的历史阶段分别标记；只有现有运行状态为工作中时才显示运行动画，等待人工确认时保持静止。提案有开发退回记录时显示技术方案返回业务需求的回路线与轮次，保留反馈及历史。

点击已进入节点仅查看对应阶段，未进入节点不可操作；阶段推进和回退仍从右侧文档底部发起，权限、文件版本门槛及入库条件不变。窄桌面聊天列复用原生横向滚动与边缘导航，并定位所选阶段，不缩小文字、不改三栏比例。提案 SR 的材料页继续无独立阶段流。

### 需求评审：三路并行、第四个 Agent 综合、人工判断

**职责与归属。** 业务需求 Agent 生成完整 `proposal.md` 和全部 SR `spec.md` 后，人工发起一次需求评审。A（j00808874）的 OMP 先运行三个独立只读评审 Agent，各用不同模型审查同一文件集合、内容版本和需求轮次，不先参考彼此结论。三份报告完成后，由第四个“综合评审 Agent”读取全部原始报告及本轮需求，归并重复意见，保留来源、依据、原文和分歧。这里的评审 A／B／C 是 Agent 槽位，与访问者 A、B、C、D 无关。业务人员不需要个人 Git 路径。

**人看综合意见并作决定。** 综合意见是第四个 Agent 的产物和独立会话，不是纯汇总视图，也不假装三个模型共享一段聊天。业务默认只需读这一份，需要时可切换原始评审追溯。模型给出的意见、问题严重度、分歧、票数或评分不能自动判定通过或不通过；全部报告完成也不自动推进。人可接受有分歧或有建议的需求进入设计，也可要求继续补充。只有当前需求材料、三份同版原始报告和综合报告完整且可读，才提供本轮人工决定入口；这属于材料完整性，不是模型代替人判断。

**原生工作流展示。** 主线仍为“业务需求 → 需求评审 → 技术方案 → 需求入库”。沿用 ZCode 原生时间线、Agent 头像、状态与会话组件；顶部紧凑显示当前查看的评审 Agent，中间默认“综合意见”，可切换“评审 A、评审 B、评审 C”。通过明确的“评审流程”入口展开原生大图：A／B／C 是三条并行轨道，汇入综合评审节点，再指向人工判断节点；不能画成 A 后 B 后 C 的串行调用，也不能把人工判断画成第五个 Agent。显示实际模型名称，区分运行、报告完成和人工批准。

**操作与版本。** 右侧文档底部由人选择“通过，进入技术方案”或“返回业务补充”。通过仅记录当前工号、时间、评审编号及其需求版本，再进入 A 的方案流程；不额外要求裁决表单、处理每个模型的问题或逐项勾选。返回后与业务 Agent 对话，由 AI 更新 IR／SR，四份旧报告和旧人工决定随文件版本变化全部失效，保留历史；人工对新版本重新发起完整一轮。单纯追问评审依据不修改需求、不自动批准。原始报告仍在同轮时可单独重试失败 Agent；原始报告改变后综合意见须重做，旧人工批准失效。真实重试、并行执行与综合调用仍需后端接入，当前原型仅演示完整报告样例。

**模型与个性化。** 现有需求评审职责内有 A、B、C、综合评审四个配置项；前三者要求不同模型，综合评审独立选型，可与其中一个模型相同。模型设置、追加提示词和写权限继续属于 A 的 Web 所有者；每轮保存四个模型和提示词快照，配置修改只作用于新建轮次，不替换运行中的配置。不为其他阶段增加 Agent。

**原因。** 三个不同模型独立检查减少单模型遗漏；第四个 Agent 把重复意见与分歧组织成一份人能阅读的结论，减少人员翻阅三份长报告的负担。人了解业务背景，保留最终通过权可避免少数模型意见、投票或评分取代业务判断。独立来源和版本绑定便于追溯，紧凑默认视图与原生展开图兼顾阅读空间和流程解释。

**原型边界。** 已提供四个模型／提示词配置、四份独立会话及报告、综合意见默认入口、原生并行汇合图和人工决定的内存状态样例。未调用真实模型、运行工具、修改项目文件、执行 Git 或测试；当前完整报告状态不代表真实并行任务已执行。
