# Lander／Sailor：Release／IR／SR 浏览器研发协作指南

> 本文是新 Dev 的操作指南，原文件路径保留以维持链接。当前流程为完整需求整理、需求 PR 合入冻结，再按 SR 执行四阶段开发；不是旧八阶段流程，也不是旧四阶段 TUI。本文描述功能合同，不将说明、局部检查或历史证据当作完整集成验收。

## 1. 先分清项目、Release、IR 和 SR

| 对象 | 用途与边界 |
| --- | --- |
| 项目 | 登记 OMP 宿主已有的 Git 仓库；同仓库各 worktree 共用项目状态及开发名额 |
| Release | 组织交付范围及进度，不等同 Git 分支；本地新建使用当前 Release，导入时选择目标 Release |
| IR | 完整业务需求：背景、目标、场景、范围、非目标、规则、边界、讨论结论及验收预期 |
| SR | 完整、可测试的系统要求，是开发单位；一个 IR 至少含一个 SR，小需求不必强拆多条 |

IR、SR 的标题、正文及拆分由 AI 通过对话生成和修改，稳定内部 ID 不随标题变化；导航显示标题，不要求用户填写变更 ID、重命名表单或拖拽拆分。项目名称、宿主目录和 Release 名称仍在设置中填写，不属于需求正文编辑。

**IR 不进入技术开发流水线。** 必须先将完整 IR 与全部 SR 作为同一组需求交付；需求 PR 合入默认分支并核对后，整组冻结，之后才能选择 SR 开发。

Dev 是独立模块：前端完整复制 WebGUI 后在 Dev 副本中改造，源码位于 `packages/dev-frontend`，不挂载或改写原 WebGUI。普通 OMP、TUI、`/webgui`／`omp webgui`、独立 OpenSpec、Superpowers、JCH 和现有用户配置保持各自语义；无需绕到原 WebGUI 整理需求。

## 2. 启动、地址与安全退出

### 2.1 两个入口

- 在普通 OMP 输入 **`/dev`**：普通模型、工具、任务须先结清，Loop 须先退出，普通 Collab 须先停止共享或离开 `join` 会话；Dev 不暗中替用户停止这些工作。进入后当前 TUI **只接受再次 `/dev` 结清退出**，不与浏览器同时操作普通聊天。
- 在目标目录运行 **`omp dev`**：使用有效目录、profile、模型和运行环境直接启动工作台，不要求先进入 TUI，也不要求额外启动前端开发服务器。独立进程启动后在终端输入完整一行 **`/dev`** 并回车，可结清全部 Dev 自有资源后正常退出；输入 EOF 本身不退出，未知普通输入不交给模型。

两个入口均输出完整可复制地址。非 offline 默认尝试打开本机浏览器，失败时保留真实地址并报告原因；`OMP_DEV_NO_OPEN=1` 可明确跳过自动打开。**offline 不自动打开浏览器**，请手动打开终端显示的完整地址，包括随机能力路径。Linux offline 的剪贴板尝试及 SSH／X11 注意事项见[内网快速上手](quick-start-intranet.md#devwebguisketch-手动打开网页)。

非 offline 仅本机访问；offline 输出 loopback 及实际内网接口／主机名的完整地址，监听范围不保证防火墙、路由或 SSH 转发可达。远端电脑的 `127.0.0.1` 不是 OMP 宿主，不要自行删改路径。能力地址不是公司账号认证系统，不能随意公开转发。

### 2.2 页面不拥有后台任务

打开、刷新、关闭页面或断线不批准任务、不重发输入，也不停止宿主已接受的工作。宿主必须存活；重连只读取事实，运行状态未知、历史缺失或任务失败须按页面真实错误处理，不能凭旧画面认定成功。

再次 `/dev` 或显式停止须等待所属主 Agent、任意深度子代理、工具、队列及 Goal 真正结清。退出失败保留占用与错误，处理原因后重试，不能将强杀进程当作成功结清。成功退出不取消需求、不回滚 Git、不删除材料；会话内入口恢复原普通聊天，独立 `omp dev` 正常结束进程。

## 3. 三栏工作台、原生会话与配置

- **左栏**：Release 选择、本地新建、浏览器新建、导入 ZIP；当前 Release 的正式 IR 平铺显示，草稿另列；左下角切换项目和打开设置。
- **中栏**：当前对象的 OMP 原生 AI 会话。SR 开发后顶部显示实际阶段及四阶段导航。
- **右栏**：完整只读材料。可选择 IR、SR、方案、计划、完成报告、UT、ST、交付说明和历史版本，支持收起、重开、复制、下载及带入讨论。

先在设置登记**宿主机器已存在的 Git 目录**与项目名称，再添加、选择 Release；不自动 clone、不创建所填目录。多个项目共享本实例监听端口，但每页独立选择，切换不会停止原项目任务、迁移附件或将迟到结果接到新项目。无效项目不会静默回落到另一目录。

### 3.1 有 Agent 与无 Agent 时怎么操作

| 当前情形 | 正确操作 |
| --- | --- |
| 只打开页面、仅选择项目、查看未启动 SR | 读取状态或配置，不自动创建 Agent、调用模型、建开发 worktree 或批准 |
| 明确新建需求并开始讨论 | 使用绑定该项目及 IR 的需求会话；输入事实、资料和需要澄清的问题 |
| 已有可用的当前阶段会话 | 在原生输入框续聊，保留其消息、工具事件、附件、问答、停止和历史语义 |
| 导入包后尚无本机需求会话 | 查看不启动模型；明确发送合入前需求修订请求时建立全新的本地需求会话，见第 5 节 |
| 选择尚未开发的 SR | 查看完整 SR；只有点击“开始开发”才进入技术方案并建立开发 worktree |
| 历史文件缺失、身份不匹配或会话不可恢复 | 保留有效材料和状态，显示不可用原因；不能猜测另一个会话或自动重放旧任务 |

聊天中的“同意”“继续”、Agent 自报完成和文件存在均不是阶段批准。正式动作由页面明确按钮执行，并绑定对象、材料版本、会话、阶段及执行轮次；过期页面或迟到回复不能批准另一个版本。

沿用复制后的原生设置、模型、Skill、MCP、工具及问答界面，不另建聊天正文库、执行器、权限系统或额外账号。Team 与模型角色配置继续使用既有方式（如普通 OMP 的 `/team configure` 及原生角色模型设置），没有新的 Dev Team 配置或多候选方案管理；普通 TUI 配置操作需先成功退出 Dev。工具授权、deny、受限目录及阶段写入边界仍适用。

同一 Dev 的登记项目、需求、草稿和需求会话共享可见，修改串行；不能把姓名或会话 ID 当认证身份。业务浏览器整理无需加入 Collab；需要现有同会话协作时可按原生 Collab 共享／`join`，但加入、离开不会替换本页本地需求或阶段绑定，也不自动跨阶段跟随。

## 4. 两种新建入口，共用完整需求检查

### 4.1 本地新建：开发人员自己的 clone

选择项目和 Release，点击 **“本地新建”**，从默认分支建立需求分支及独立 worktree，直接与需求 Agent 讨论。无需先去远程整理宿主，不填名称、分类或背景表单。已有资料通过原生输入、附件等能力提供给 Agent，**不是上传一份 Markdown 就直接放行**。

### 4.2 浏览器新建：共享宿主整理业务需求

开发人员长期运行 Dev，业务人员只需浏览器访问其完整地址，选择登记项目和 Release，点击 **“浏览器新建”**。业务人员无需安装 OMP、Git 或 clone 仓库，使用与开发人员相同的界面。

浏览器新建只保存服务端需求草稿及原生会话，**不创建需求分支或 worktree，不提交、不推送**。完成整组确认审核后下载 ZIP，由接手开发人员在自己的 Dev 导入。不要将“浏览器新建”理解为自动在业务人员电脑开发，也不要用“本地新建”代替无 Git 草稿整理。

### 4.3 需求讨论与格式

需求 Agent 结合授权资料和当前项目背景，澄清业务目标、场景、范围、非目标、规则、异常、约束及验收，区分事实、假设和待确认事项。每份 SR 都要有实质内容，不是标题列表；全部 SR 合起来需覆盖 IR，检查遗漏、重复和冲突。可以要求停止访谈，但未决事项须保留，停止不是批准。

正式 IR、SR 为 Markdown，至少有一级标题、三个二级章节及验收内容；同时检查稳定 ID、文件路径及整组关系。正文需真正说明业务和可观察行为，不能以凑章节代替质量。附件可随整组资料保留，是否能解析及如何使用受现有工具能力与授权限制。

当前需求权威位于 `docs/dev/requirements/<irId>/`，其中 `requirements.json` 记录标题、正文路径和全部 SR 关系；由程序维护，不能手工改清单绕过对话与审核。项目原有 Markdown／递归 OpenSpec 权威仍按原位调查和引用，不建立竞争性主规格，也不把 Dev 强制变成 OpenSpec 同步归档流水线。

### 4.4 人员确认、固定整组检查与独立审核

1. 阅读完整 IR、全部 SR 和附件，明确点击 **“确认需求与全部拆分并审核”**。
2. 程序先检查完整结构、引用关系及当前文件版本；不通过时显示具体问题，不启动语义 review，也不开放导出或开发。
3. 需求会话派发独立 reviewer，审查**同一固定快照的整组 IR／SR**：目标、边界、未确认假设、可测试性、遗漏、重复、冲突和整体覆盖，不逐条另起 SR 撰写流程。
4. 保存人员确认及只读审核结论；全部通过才内部确认，进入正式 IR 导航并允许下载当前需求包。草稿能保存、恢复，但不冒充正式 IR。

审核意见是内容审查，不是公司批准或软件测试。需要修改时由需求 Agent 修订，再由人重新确认；格式与 review 都针对新版本重新执行。审核期间或采用结果前材料变化，旧结果不得套用；失败不会把已写文件、原生历史或实际错误抹掉。

## 5. 导出、导入与合入前本地修订

### 5.1 导出完整 ZIP

**“下载需求 ZIP”** 仅提供当前内部确认及检查通过的一个完整 IR，包含全部 SR、必要附件、人员确认、独立审核记录及 JSON 清单。清单记录格式版本、稳定 ID、来源项目、Release／包来源、文件列表、摘要和引用关系；不是局部 SR、标题列表或示例产物。

包不含源聊天正文、OMP 凭据、配置、进程锁、端口或服务器绝对运行路径。接手人无需恢复业务源会话。确认后若 AI 实际修改材料，当前成品下载资格及旧审核权威失效，必须重新确认与检查。

### 5.2 在自己的 Dev 导入

1. 接手开发人员选择明确的目标项目及 Release，使用 **“导入 ZIP”**。
2. 程序确定性检查版本、完整性、摘要、引用和安全路径等，再建立目标项目默认分支上的需求分支与 worktree，保存独立材料副本及原始来源记录。
3. 导入不启动 SR、不调用模型或再次自动 review，不创建 PR，也不把来源记录当当前代码兼容性或公司批准。
4. 包损坏、缺文件、来源仓库不适用、稳定 ID 冲突或越界时按真实错误处理，不覆盖已有冻结需求。重复请求不重复创建对象；已删除的 ID 也不能被重复导入复活。

### 5.3 导入副本还能修改吗？

**需求 PR 合入前可以。** 在导入 IR 中明确向 AI 提出修订，由本机创建全新原生需求会话，以当前完整 IR、全部 SR、实际元数据和附件为输入；不是恢复另一宿主的聊天，也不伪造源会话文件。

未变化的资料可保留原确认来源；真正改变内容、标题或拆分后，当前确认、review 和需求 PR 版本依据失效，须本地重新确认、格式检查及独立审核，再更新需求分支和人工 PR。原始包、快照及 provenance 保留，不以修订覆盖来源历史。

源草稿、已导出快照和开发端导入副本互相独立：不自动跨 clone 同步、不自动传播合入通知，重新导出不能覆盖已经冻结的开发需求。

## 6. 需求 PR：人工创建，Git 核对后整组冻结

内部确认只表示需求资料可交接，**不是 SR 开发许可**。

1. 在需求 IR 的 **“Git 发布范围与授权”** 查看整组正文、清单、确认／审核依据及本次拥有的删除路径，填写提交说明。
2. 明确选择仅提交，或提交并推送。提交、推送分别记录；不强制每次状态变化都提交，也不把普通确认解释为 Git 授权。
3. 在公司平台**手动创建、评审、合并需求 PR**，以同仓库真实默认分支为目标；通常是 main 或 master，但不猜名称，不直推默认分支。
4. 在 Dev 填写人工 PR 地址，点击 **“登记已人工提交 PR”**。Dev 检查实际已提交并推送的资料；URL 是人员登记，不代表已查询平台审核状态。
5. 平台合入后再明确标记并核对 Git 合入。Dev 获取实际默认分支，检查整组 IR、全部 SR、清单、确认依据及删除内容是否对应批准版本，支持按内容核对 merge／squash／rebase，不能只凭源分支 SHA 或一句“已合入”。

核对成功立即冻结**整个 IR 与全部 SR 的标题、正文和成员关系**，不是等首个 SR 开始才锁定。主 Agent、递归后代、工具及正式发布都不能绕过冻结；本流程不提供解冻、冻结需求改版或关联修复 IR 管理。

无可用远端时可以讨论、整理、准备材料，但不能宣称公司 PR 已合入或放开 SR。需求 PR 评审要求修改时仍按第 5.3 节修订、重新确认并更新 PR。

## 7. SR 的四阶段开发

### 7.1 点击开始才占用开发名额

选择 SR 只展示完整需求。点击 **“开始开发”** 时，整组必须已 Git 核对合入并冻结，且项目没有其他开发 SR。程序从启动时最新默认分支创建该 SR 固定开发分支及 worktree，之后四阶段持续复用。

**同一项目跨全部 Release、IR 和 worktree 最多一个开发中 SR。** 等待评审、等待代码 PR 合入、暂停 Agent、关闭网页、重启或切换项目均不释放名额。其他 SR 很久后启动时，仍用冻结需求配合新的代码基线；发现不兼容须披露并阻塞，不能改需求迁就代码。

### 7.2 四阶段及人员决定

| 实际阶段 | 产物与工作 | 明确决定 |
| --- | --- | --- |
| 技术方案 | 基于冻结的完整 IR、当前 SR、审核及背景，调查真实代码、接口、测试与约束；仅维护一个当前推荐方案，写清理由和取舍 | “确认方案进入计划” |
| 开发计划 | 具体修改范围、步骤、接口、依赖及验证安排；不提前写实现代码 | “确认计划进入开发与验证” |
| 开发与验证 | 在批准范围内实施，实际运行 UT／ST、进行必要审查；分别形成完成报告、UT 报告和 ST 报告 | “确认开发与验证进入交付 PR” |
| 交付 PR | 读取已批准方案、计划、完成与 UT／ST 记录，形成交付说明，准备人工代码 PR | 明确范围 commit／push、人工 PR 登记、实际合入核对 |

阶段只提供适用操作，批准绑定当前材料摘要、阶段和轮次。完整上游文件及人员决定交接，不用聊天摘要替代要求；技术方案不重新走一遍业务需求撰写。方案或计划确认只授权下一阶段，不授权自动提交、推送或创建 PR。

技术材料位于 `docs/dev/development/<srId>/`：`solution.md`、`plan.md`、`completion.md`、`ut.md`、`st.md`、`delivery.md`；历史版本在其 `history/` 下保留。它们是可读正式资料，不是旧候选 JSON／候选 ID 选择流程。

### 7.3 UT、ST 和等待确认

UT、ST 合并在“开发与验证”工作阶段，但**分别记录真实结果**：实际被测代码版本、命令、工具／电路／环境、覆盖范围、结果和可访问证据。失败、未运行、缺许可证、数据或权限都如实披露；报告存在、格式合法、AI 审核或人员点击不证明测试全部通过，也不替代公司后续验收。

执行会话先完成实际验证及 UT／ST 报告，最后交付完成报告；完成报告形成后停止自主可写推进并等待人员动作。普通询问、查看或讨论影响不重新授权实施。交付 PR 阶段仅准备交付说明，不重新实施代码、代建平台 PR 或调用 PR API；需要修正先按下一节明确返回。

### 7.4 查看历史和 Back 不是同一件事

点击阶段导航只改变右侧查看的材料，顶部始终区分“查看阶段”与“实际阶段”，中间仍是当前阶段会话；不停止工作、不改变批准。

明确点击 **“返回技术方案（保留代码）”** 或 **“返回开发计划（保留代码）”** 才返工：先结清当前 SR 的主 Agent、递归任务、工具、队列和 Goal，再改变阶段及轮次，撤销目标阶段与下游批准／报告资格。**已有代码、材料和历史全部保留，不执行 Git 回滚**；依据现有代码调整后重新确认、验证，不能因旧文件仍在就当作重新通过。

在代码 PR 合入前，范围内修正可点击 **“返回开发与验证／继续修正（保留代码）”**：保留仍未变化的方案和计划批准，旧完成、UT、ST、交付材料失效，修复及验证后重新确认。若需改方案或计划，返回对应阶段；任何返回都不能改冻结业务要求。停止失败保持原阶段与真实错误，不在后代仍写入时伪报已返回。

### 7.5 有范围的发布与代码合入终点

在 **“Git 发布范围与授权”** 选择当前 SR 的真实源码、测试及技术材料变更，每项绑定具体路径、摘要与大小（含删除）；文件变化后重新选择，不能只提交几份报告冒充交付。发布不得夹带其他需求、冻结权威或运行资料，也不能污染其他 worktree 的 index；未授权祖先提交不能因 push 一并发布。

仅提交与提交并推送是不同明确授权；commit 成功而 push 失败时保留实际提交和步骤，不能重复提交或假报推送成功。原有暂存、未暂存及无关变更须保留。错误和实际副作用见“操作记录”，响应丢失先核对事实，不盲目重做。

开发人员在公司平台手动创建代码 PR，人工评审、合并。登记前须有实际提交的报告、干净 worktree 和已推送 HEAD。平台合入后明确确认，Dev 获取默认分支并核对本轮代码、测试、资料、模式及删除内容的真实合入，不以 URL 或人员声明冒充 Git 证明。

代码核对合入、自有工作结清后，**SR 结束并释放开发名额**。保留材料、原生历史、代码分支和 worktree，仅提醒检查未保存变更后自行清理，不自动删除。Dev 不管理合入后测试、复测、关联修复或同 SR 再次开发；公司既有后续流程独立处理。独立 OpenSpec 同步／归档仍为另行明确操作，不是 Dev 固定前置或自动收尾。

## 8. 状态、锁、删除与顺序换机

- **Git 中**：完整需求 Markdown、关系 JSON、净化后的确认／审核依据、方案、计划、已产生的报告和交付说明。
- **非 Git 工作流状态**：同仓库 Git commonDir 的 `omp-dev-workflow-v1/` 下，以带版本、原子写入的共享 JSON 保存阶段、占用、操作步骤、PR 事实及原生会话引用；同仓库 worktree 不各自另建矛盾的开发占用。Dev 不新增专用 SQLite／WAL，也不复制原生聊天正文。
- **原生历史**：OMP 管理消息和会话文件，Dev 保留精确引用；Git pull 只能取得已提交材料，不能迁移聊天、运行任务、端口、锁或接管远端 Agent。重新打开和只读查询不恢复执行授权。
- **互斥与防重**：同项目的 Dev／WebGUI owner、工作流变更及 SR 名额分别按实际归属校验；子目录、路径别名、profile 或另一个 checkout 不能绕过。操作记录及版本校验防重复建 worktree、提交和输入；过期请求明确失败。
- **删除不是撤销**：仅未冻结、未合入且所有 SR 都未启动的整组 IR 可明确删除。先结清其原生递归工作，再保留删除记录并从活动导航移除；文件、代码、分支、worktree、快照、来源及原生历史均不删。已有人工 PR 时提示由人关闭，Dev 不调用平台关闭接口。开始过开发的 SR 所属 IR 不可删除，删除不能释放开发名额；无旧 `drop` 别名。
- **NFS 仅顺序换机**：先结清并退出旧机器使用同配置／profile 的全部 OMP，再在新机器读取共享配置、材料、状态及历史。未知旧宿主、未结清操作或遗留锁必须人工处理，不按超时抢占，不拿另一机器 PID 当本机进程，也不能以本机 socket 锁证明跨机安全。

旧八阶段、旧 Dev TUI 子操作、旧状态兼容／迁移及恢复入口已退役；用户已有文档、代码和 Git 历史不因此删除。不要用历史指南中的命令或旧状态文件手动拼接新流程。
