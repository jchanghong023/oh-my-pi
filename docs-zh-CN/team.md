# `/team` 多模型方案规划命令

> **状态：已实现（2026-09-18）。** 本文档是 `/team` 的完整需求与设计契约：第 2 节为行为需求，第 5 节为实现与集成约束，第 6 节为验证要求，三者对实现同等强制。`fork.md` 记录对应的用户可感知契约条目；本文档保留为完整需求依据。

## 1. 背景与用户目标

### 1.1 背景

用户在开始修改代码前，可能只有一份初步需求、一段问题描述，或者一个尚未确定的设计方向。理解任务需要同时查看需求文档、公司内部 wiki 和现有代码，确认目标、现状、内部约束及相关调用关系。

本命令要解决的是：不要让方案只建立在一个代理的一次调查和第一份设计上。不同模型分别接触一手资料、独立形成判断，再检查彼此的遗漏与错误，最后得到能够说明依据和取舍的方案。

典型使用环境中，只有一个模型的综合能力较强，其他模型能力不完全一致。因此，多个模型负责提供独立调查、候选思路和反例，最强主代理负责核实证据和最终综合；不能用多数票代替判断。

### 1.2 用户目标

- **把问题弄清楚：** 明确需求、现状、约束，以及仍然缺少的信息。
- **把方案想充分：** 获得不同模型独立形成、经过交叉审查的方案。
- **把取舍看明白：** 知道方案为什么成立、主要差异是什么、风险在哪里。
- **把选择变简单：** 有明确优势时给出推荐及理由，不人为增加备选方案。
- **把完成条件说清楚：** 在实施之前明确验收标准和需要先核对的关键前提。

用户不需要手动创建团队、分配审查任务或转发各代理的讨论内容，也不需要在流程中途回答问题。日常只需要提出问题，并在结果落地后选择方案或追问。

### 1.3 范围

`/team` 负责分析问题、讨论设计和形成计划，不负责执行计划。用户选择方案后，本次规划流程结束，后续实施不属于本命令的功能范围；选择 MUST NOT 被解释为修改代码的授权。

## 2. 功能需求与规则

### 2.1 功能入口与运行模式

命令形式为：

```text
/team <问题或需求>
```

用户可以直接描述问题，不要求填写固定表单，也不要求先指定分析、诊断、规划等子模式。`/team` 是用户主动选择的多模型讨论入口，不设按任务大小自动分流为单模型流程的规则。

运行模式约束：

* 仅 Main 主代理下可用。Discuss 模式下输入 `/team` 只返回提示（用 `Shift+F2` 切回 Main），不派发、不执行，与 `/tan` 的 Discuss 门禁同等待遇。
* 输入只有 `/team` 而未说明任务时，提示补充问题或目标，不猜测用户要分析什么。
* 运行中 MUST 让用户看见当前阶段和各参与模型的完成、失败状态，并允许用户取消本次讨论（见 5.4）。

### 2.2 参与者与模型配置

参与模型由一个专门的设置项定义：

* **设置项 `team.members`**：模型 ID 列表（完整 ID，如 `company/GLM-5.2-public`）。未设置或设置为空数组均视为**未配置**。
* **未配置 + `--offline` 进程**：默认取 company lane 当前全部可用聊天模型（运行时快照，即 `DeepSeek-V4-Flash-public`、`GLM-5.2-public`、`MiniMax-M2.7`、`Qwen3.6-27B-public`、`Qwen3.6-35B-A3B`、`Qwen3.8-27B`）。
* **未配置 + 普通启动**：company lane 不存在，`/team` 直接报错并提示配置方法（给出 `team.members` 示例），MUST NOT 静默降级为单模型流程，MUST NOT 自动拉入同家族模型冒充多模型。
* **显式配置优先**：两种环境下，已配置的 `team.members` 都覆盖环境默认名单。

参与者集合与角色：

* **提案者集合 = 去重（`team.members` 解析结果 ∪ 当前会话模型）**。去重按解析后的具体模型实例判断，同一模型的不同名称不算不同模型。会话模型不在名单内时，作为额外提案者加入（落实"最强模型也通过子代理独立调查"）。
* **主代理 = 发起 `/team` 的当前会话模型**。"最强"是使用前提而非机制判断：系统不存在模型能力排序，用户应在综合能力最强的模型会话中发起 `/team`；该约定记录入 `fork.md`。主代理承担阶段二对齐子调用与阶段五综合子调用，本身不充当审查者或修订者。
* 配置中的模型不存在或不可用时，报错指出具体项，MUST NOT 静默剔除后继续。

### 2.3 只读边界（机械保证）

从命令发起到方案输出，以及后续澄清、追问和方案选择，均属于只读规划过程：

* 所有子代理（提案、审查、修订、对齐、综合）的工具集由代码**机械限制为只读**（读文件、`wiki` 检索、代码检索类；不含写文件、bash/eval 执行、task 委派等）。这是程序保证，不是提示词要求。
* 不创建、修改、删除或移动项目文件、需求文档、公司文档和项目配置；不安装依赖、不运行构建或测试、不更新文档索引、不提交或推送。
* 可以读取资料、检索内部 wiki、检查代码及接口定义，并在回复中提出修改建议和验证方法。
* "修订方案"是修改讨论中的方案内容，不是修改项目文件。
* 用户选择方案不等于授权立即实施。

正常的会话记录不属于项目修改。原稿、证据和修订结果 MUST 能在本次讨论中回查（见 5.5）。

### 2.4 编排形态：全程序化编排器

`/team` 采用**代码驱动的编排器**实现，五个阶段全部由命令代码推进；用户交互只发生在两端——命令输入，以及结果落地后的普通聊天轮次。流程中 MUST NOT 向用户提问或等待用户输入。

代码机械保证（不是指令约束）：

| 保证 | 实现方式 |
| --- | --- |
| 独立调查隔离 | 各提案子代理由代码以相同输入并行创建，互不可见，不存在共享摘要 |
| 审查匿名 | 审查 prompt 由代码构造，不含作者模型名、支持人数或推荐顺序 |
| 两轮上限 | 修订轮数由代码计数，第三轮直接拒绝 |
| 阻断门禁 | 审查意见与修订回应为结构化输出，代码追踪未解决阻断问题；受影响方案无论综合文本如何，机械标注"尚不可采用" |
| 只读边界 | 子代理工具集机械限制（见 2.3） |

需要模型判断的环节（对齐、综合）由代码以**当前会话模型**发起拼装上下文的子调用完成；编排器不经过主代理的 Task 工具派发（程序化调用路径直接指定各子代理的模型）。

### 2.5 固定工作流程

```text
独立调查 → 对齐与比较 → 交叉审查 → 修订与复核 → 汇总方案
```

#### 阶段一：独立调查

**目标：** 让每个模型从一手资料形成自己的判断。

代码为每个提案者并行启动新的提案子代理（受 `task.maxConcurrency` 约束），各自独立完成：

1. 阅读用户指定的需求文档及相关用户说明。
2. 搜索公司内部 wiki，查找与任务相关的规范、历史方案和接口约定。
3. 阅读相关代码、接口定义和调用关系，确认现有行为与影响范围。
4. 提出方案或诊断结论，说明依据、关键假设、主要风险及验收建议。
5. **显式记录自己对需求歧义的理解与假设**（哪些需求点存在多种解读、本方案采用哪一种）。

各子代理接收相同的用户问题、明确约束和资料入口，但检索路径与分析结论分别形成。不能先由一个代理调查，再让所有模型只依据它的摘要出方案。

初稿必须区分事实、推断和假设。没有足够依据时，可以报告未形成可行方案；MUST NOT 为了交出答案虚构接口、规范或代码行为。

**阶段结果：** 各模型的原始方案（结构化输出，全文 ≤ 4000 汉字），含证据、关键假设、风险、未知项、验收建议与歧义理解记录。

#### 阶段二：对齐与比较（后置澄清，不中断）

**目标：** 统一可查清的部分，把不可查清的理解差异显式化，让真实差异可见。

代码以当前会话模型运行一次**对齐子调用**，输入为用户原始问题与全部提案，结构化输出：

1. **统一的需求理解（可查清部分）与共同验收标准。** 各提案的验收建议用于发现遗漏，但不能各自定义一套较容易满足的标准。
2. **事实差异清单：** 各提案在接口存在性、规范适用性等事实上的矛盾，标注需回查的来源位置（交由阶段三审查者回查、阶段五核实）。
3. **需求理解差异清单：** 无法通过现有资料查清的歧义，列出各提案的不同理解及其对方案与验收的影响。

本阶段 MUST NOT 向用户提问、MUST NOT 中断流程。对方案差异的处理：

* **事实差异**回查来源确认，查不清的标为未知，不靠辩论决定真假。
* **设计取舍**（如少改代码与更清晰的模块边界）保留到最终比较。
* 相似方案可以归类展示，但 MUST 保留原稿、依据和重要差异；不能仅因标题、技术选型或表格中几项相同就认定方案等价并删除候选。

理解差异的处理后置到阶段五呈现（见 2.9）：实质影响选择的差异，由结果尾部提示用户带答案重跑 `/team`。

**阶段结果：** 统一的需求理解与验收标准、事实差异清单、理解差异清单。

#### 阶段三：交叉审查

**目标：** 检查方案是否有事实错误、遗漏或不能成立的关键前提。

每份拟作为最终选项的方案安排 **1 名新的审查子代理**。分配规则由代码机械执行：按提案者顺序轮转指派给**下一个不同模型**的参与者；仅存在一个参与模型时，由同模型的新子代理审查。

审查者可见：共同需求、统一验收标准、待审方案、关键假设、事实差异清单（协助回查）、原始资料入口；可回查完整提案、wiki 和代码。审查 prompt 由代码构造，MUST NOT 包含作者模型名、支持人数或预先推荐顺序。

即使所有模型只提出同一种方向，也要审查其共同前提；不能以"大家一致"代替审查。审查重点：

* 是否误读或遗漏用户需求、适用规范和必须保持的行为。
* 对接口、代码、调用关系的判断是否有事实错误。
* 哪些关键假设一旦不成立，就会使方案失败。
* 是否存在影响正确性、兼容性或可实施性的实质风险。
* 方案是否能够满足共同验收标准。

每条反驳必须说明对应方案、具体问题、影响及依据，并区分**阻断**、**重要**和**次要**问题。已有事实应提供可回查的资料位置；新设计可以使用明确的逻辑推导或反例，但 MUST NOT 冒充已运行的验证结果。允许返回"未发现实质问题"，不必凑问题数量；没有发现问题也不等于证明方案绝对正确。

**阶段结果：** 结构化审查意见（每份 ≤ 1500 字），问题分级、有依据、有影响说明，或明确记录未发现实质问题。

#### 阶段四：修订与复核

**目标：** 处理有效问题，确认关键修改没有引入新的错误。

代码将审查意见路由回该方案的**提案模型**（新子代理），逐项回应：接受并修订、举证说明不接受、保留为真实取舍，或说明仍无法解决。对不成立的质疑，不要求修改原本正确的方案。不能只回复"已解决"，不能降低验收标准绕过问题。

修订回应为结构化输出，包含：修订后的方案、修改内容与理由，以及**复核标志**——

* 是否修改了核心设计、接口、数据变化或兼容策略；
* 是否声称解决了已确认的阻断（或严重）问题；
* 是否有新证据改变了关键假设、需求理解或适用约束。

代码按标志机械决定复核：任一标志为真时，安排**新的审查子代理**复核受影响部分；全部为假时不复核，不强凑修订轮次。复核结论由代码收集后交综合阶段使用，作者 MUST NOT 自行宣布关键问题已关闭。

**轮数规则：** 每份方案最多两轮"修订与必要复核"，由代码计数；达到两轮仍有阻断问题时，停止循环并将该方案标为**尚不可采用**。"没有新增问题"不等于旧问题已解决；"达到轮数上限"不等于通过；MUST NOT 通过重命名方案或重开讨论绕过上限。

**阶段结果：** 最新方案、审查意见处理结果、复核结论，以及已解决或仍未解决的关键问题。

#### 阶段五：汇总方案

**目标：** 给用户提供能够据此作出选择的结果。

代码以当前会话模型运行**综合子调用**，输入为：用户问题、统一验收标准、全部最新提案（含修订）、审查处理结果、事实差异回查结果、理解差异清单、各方案未解决阻断问题标记。综合先核实关键证据、检查硬约束，再比较真实取舍：

* **硬约束**来自用户明确要求、确认适用的强制规范、必须保持的兼容约定和共同验收标准。违反硬约束或仍有未解决阻断问题的方案，MUST 标注"尚不可采用"——该标注以代码的结构化追踪为准；综合文本与此矛盾时，以结构化追踪覆盖。
* 通过硬约束后，再比较风险、复杂度、修改范围、兼容性、维护负担和可验证性等取舍。比较必须说明理由，不采用多数票，不能用低工作量抵消正确性缺陷。
* 只能汇总经过审查的方案；MUST NOT 在最后拼接多个候选生成未经审查的新设计再称其已通过。
* 最终方案数量不固定：有一个就输出一个；存在多个实质不同且有选择价值的方案时分别输出；没有可采用方案时明确说明原因，MUST NOT 为多样性制造备选。
* 有明确优势时，将最合适的方案标记为 **【推荐】**，说明推荐成立的前提和理由；没有明确优选时，直接说明取舍条件，不勉强指定赢家。

**阶段结果：** 最终 markdown 消息（见 2.9），交由用户决定。

### 2.6 证据与关键假设

#### 2.6.1 不混淆现状、目标和规范

需求文档说明目标，代码说明现状，确认有效的公司规范说明必须遵守的约束。三者冲突时应识别冲突及适用范围，不设"代码永远高于需求"之类的固定覆盖顺序。计划新增能力，不应因现有代码尚未提供而被直接否决；但方案 MUST NOT 把尚不存在的能力当作已存在且可直接调用的能力。

#### 2.6.2 不把意见当证据

模型之间相互同意、作者自评有信心、综合子调用的设计偏好，都不能代替事实依据。反驳的严重程度也不是自动否决理由；问题必须真实且影响成立，才据此要求修订或排除方案。

#### 2.6.3 关键假设必须说明状态

关键假设指"一旦不成立，方案就需要明显改变或不能采用"的前提。每项必须说明内容、现有依据、验证状态和错误时的影响。能通过只读资料核查的，应在流程中核查；只能在实际执行环境验证的，列为执行前检查。有执行前待验证条件的方案可作为**有条件方案**展示，但 MUST 清楚标出条件；已被证伪的前提 MUST NOT 仅通过列入"执行前检查"变成可接受条件。

#### 2.6.4 内部资料检索的边界

各模型应独立搜索与任务相关的 wiki 内容，保留用于判断的来源位置。未搜索到资料不等于公司没有相关规定；历史文档不自动代表当前有效规范。无法访问资料、结果不完整或有效性不明时，MUST 说明证据缺口及其影响，不填补成确定事实。

### 2.7 用户可见结果与方案选择

最终结果以**一条 markdown 聊天消息**呈现，用户不需要阅读各子代理的中间过程：

| 内容 | 要求 |
| --- | --- |
| 需求与验收标准 | 说明共同目标、必须满足的条件及如何确认完成；共同内容不在每个方案中反复抄写 |
| 核心方案 | 说明采用什么方向、主要实施步骤和影响范围，不输出详细实现代码 |
| 关键依据 | 列出支持方案的重要需求条款、wiki 或代码位置 |
| 主要取舍 | 说明与其他候选的实质区别及适用条件 |
| 风险与关键假设 | 说明已确认风险、未验证前提和仍有分歧的事项 |
| 执行前检查 | 说明采用方案前还需要核对什么、检查失败意味着什么；没有时不制造检查项 |
| 推荐理由 | 仅在标记【推荐】时给出，说明依据和前提 |
| 需求理解差异 | 阶段二识别的理解差异清单；实质影响选择的差异 MUST 置顶提示 |
| 未采纳方向 | 必要时简述重要候选被淘汰或暂不可采用的原因，不倾倒讨论记录 |

消息尾部固定附带**收尾契约**（原文形式）：

> 选择方案请直接回复（如"选择方案 A"）。选择仅确认该方案、其验收标准与执行前检查，不触发实施；如需修改代码，请另行明确要求。若存在影响选择的"需求理解差异"，请先回答该差异并带答案重跑 `/team`，不要在不同前提的方案间盲选。

后续交互规则：

* 用户的选择与追问由主代理在**普通聊天轮次**中处理，依据落在会话里的最终结果消息作答；不重跑无关调查，不把追问当成执行授权。
* 对"原因是什么"类诊断请求，先回答根因是否已确认，再说明证据和后续核查方法；未经验证的根因不作为让用户任选的方案。
* 追问或补充约束导致核心方案变化时（实质需求变化），MUST 提示带约束重跑 `/team`，MUST NOT 沿用旧方案的通过结论或旧推荐。

### 2.8 异常与结束规则

| 情况 | 必须呈现的结果与行为 |
| --- | --- |
| 输入只有 `/team`，未说明任务 | 提示补充问题或目标，不猜测 |
| 普通启动且未配置 `team.members` | 报错并给出配置示例，不运行任何阶段，不降级单模型 |
| `team.members` 中模型不存在或不可用 | 报错指出具体项，不静默剔除 |
| 指定文件缺失或位置不明确 | 说明缺失或歧义并结束本次运行，由用户修正后重跑；不编造文件内容 |
| 内部 wiki 不可用或未取得关键资料 | 说明哪些约束尚未核实及对结论的影响；影响方案成立时不得判通过 |
| 某个提案/审查/修订子代理失败、超时或未完成 | 该参与者如实标失败，其余参与者的结果继续处理；参与不完整 MUST 在结果中标明；失败 MUST NOT 被理解为同意或"未发现问题" |
| 对齐或综合子调用（会话模型）失败 | 报告流程未完成并结束，不输出半成品结论 |
| 无法完成必要审查（如审查模型全部失败） | 明确报告流程未完成，不静默改成单模型并宣称团队流程完成 |
| 理解差异实质影响选择 | 结果尾部置顶提示"先回答差异、带答案重跑"，不在不同前提的方案间让用户盲选 |
| 只剩一个可采用方案 | 输出一个方案及依据，不补造第二个 |
| 所有候选均不可采用 | 输出原因和需要补充的信息，不制造推荐，不自动重开讨论 |
| 两轮后仍有阻断问题 | 该方案标"尚不可采用"并保留未决问题，排除在已通过选项之外 |
| 用户中途取消 | 停止本次讨论，取消传播到所有在跑子代理，不继续调查、修订或选择 |
| 用户事后改变需求或关键资料已变化 | 受影响结论不标有效；实质变化按重跑处理 |

正常完成指：独立调查、对齐、必要审查和修订已结束，编排器输出有依据的方案结果或明确的不可行结论。流程完成不代表必须存在推荐方案；资料缺失、模型失败或用户取消导致必要步骤未完成时，MUST 与"已完成分析但没有可行方案"区分。

## 3. 需求验收条件

以下条件用于判断 `/team` 是否满足本规范：

1. 用户通过一个自然语言命令即可发起完整流程，不需要管理团队成员、转发消息或在中途回答问题。
2. 各参与模型从一开始独立读需求、查 wiki、查代码，不依赖任何代理的统一分析摘要——由代码以相同输入、并行、互不可见的方式机械保证。
3. 所有最终方案在各自**显式声明的需求理解**下比较：可查清部分使用统一验收标准；无法查清的理解差异在结果中作为一等输出呈现，实质影响选择时提示带答案重跑；相似方案归类不丢失原稿和重要差异。
4. 每份最终选项经过新子代理的交叉审查（代码轮转分配、匿名构造 prompt），允许"未发现实质问题"结论；有效反驳得到处理，无依据意见不自动否决方案。
5. 修订与复核最多两轮（代码计数，第三轮拒绝），关键修改按结构化标志触发新子代理复核，未解决阻断问题的方案机械标注"尚不可采用"。
6. 综合子调用依据证据与硬约束比较，不多数投票、不强凑方案、不在汇总时增加未经审查的新设计；"尚不可采用"标注以结构化追踪为准。
7. 结果能让用户看清方案、依据、取舍、风险、验收标准、执行前条件与需求理解差异；有明确优势时给出推荐理由。
8. 澄清、追问和选择不触发实施，全程不修改项目文件（子代理只读工具集机械限制）；失败、未知和未完成状态如实说明。

## 4. 用户用例与命令

### 4.1 按初步需求形成实现方案

**用户输入：**

```text
/team 按 api.md 的初步需求，给出实现方案
```

**预期行为：** 各参与模型并行独立阅读 `api.md`、搜索内部 wiki、查看相关代码并提出方案（各 ≤ 4000 字、显式记录歧义理解）；对齐子调用统一可查清部分并列出事实与理解差异；每方案 1 名不同模型审查；修订按标志复核；综合子调用输出结果。全程不向用户提问。

**结果：** 一个或多个有依据的方案，包含主要步骤、差异、风险、验收标准和执行前检查；有明确优势时标记【推荐】；存在实质影响选择的理解差异时置顶提示带答案重跑。

**用户选择：**

```text
选择方案 A
```

**选择结果：** 主代理确认采用方案 A 及共同验收标准，说明尚未验证的前提，结束本次方案选择；不修改代码。

`api.md` 只是示例文件名。用户可以指定其他需求文档，也可以直接在命令中描述需求。

### 4.2 分析问题原因

```text
/team 这个接口偶尔返回重复结果，结合相关代码和内部文档分析原因
```

预期输出已确认的事实、可能的原因、各原因的证据和缺口。只有证据充分时才确认根因；证据不足时给出需要补充的资料或验证方法，不为凑答案认定根因。

### 4.3 提出问题解决方案

```text
/team 这个模块处理大文件时内存占用过高，给出解决方案
```

各模型独立调查相关路径与约束，再比较可行处理方式。结果说明各方案的依据、预期影响、需要保持的行为和验证要求；MUST NOT 虚构尚未实测的性能提升。

### 4.4 比较设计方向

```text
/team 新功能应该扩展现有模块，还是增加独立模块？结合需求、wiki 和代码给出方案
```

重点核查两条路径分别依赖什么条件、能否满足同一目标，以及变更范围与维护成本等差异。用户提出两个方向不代表最终必须保留两个；调查发现其他合理方向时，同样进入审查流程。

### 4.5 对方案追问或补充条件

```text
方案 A 为什么比方案 B 更适合当前需求？
```

主代理基于结果消息回答具体比较依据，不重跑无关调查，不把追问当成执行授权。

```text
补充一个约束：旧接口行为必须保持不变。
```

该约束属于实质需求变化：主代理提示带约束重跑 `/team`（如 `/team 补充约束：旧接口行为必须保持不变。<原问题>`），MUST NOT 直接沿用旧审查结论或旧推荐。

## 5. 实现与集成约束

### 5.1 命令与编排器

* 命令名 `/team` 为有意决策（非 `jch*` 前缀）：接受未来上游同名命令的注册冲突风险，发生时再处理（改名或合并），不预防性改名。
* 命令经 fork 自有命令注册路径注册；编排器为代码驱动的阶段状态机，经程序化子代理生成路径创建子会话（`runSubprocess` 层的 `modelOverride` 直指各子代理模型），不经主代理 Task 工具。
* 对齐子调用与综合子调用使用当前会话模型、拼装上下文；其余子代理使用各自配置模型。
* 结构化输出贯穿全程：提案、审查意见、修订回应（含复核标志）、对齐与综合结果均为 schema 约束输出；输出预算（提案 ≤ 4000 汉字、审查 ≤ 1500 字）由 schema 机械执行。

### 5.2 审查分配与轮次

* 审查者按提案者顺序轮转指派给下一个不同模型；单一参与模型时同模型新子代理审查。
* 复核仅在修订回应的结构化标志为真时触发；轮数代码计数，第三轮拒绝并标"尚不可采用"。

### 5.3 只读工具集与失败处理

* 全部子代理工具集机械限制为只读（读文件、`wiki`、代码检索类）。
* 提案/审查/修订子代理失败不自动重试、不自动替补：该参与者标失败，其余继续，结果如实标注参与不完整。
* 对齐/综合子调用失败即流程未完成，报告结束。

### 5.4 取消、进度与并发

* 取消走命令取消信号并向所有在跑子代理传播；取消后不执行任何后续阶段。
* 进度：阶段级状态（当前阶段、各参与者完成/失败）经现有状态展示机制呈现；子代理明细经 Agent Hub 查看，不新造 TUI 面板。
* 并发受 `task.maxConcurrency`（fork 默认 8）约束；默认 6 参与者的阶段一可全部并行。

### 5.5 结果落地

最终结果为一条 markdown 消息落入会话（内容结构见 2.7 表格，尾部附收尾契约）；各子代理的结构化原稿保留在本次任务结果中可回查。不写计划文件、不创建 Todo、不修改任何外部状态。

## 6. 验证要求

按 fork 验证体系执行（UT 验局部逻辑，E2E 从真实公开入口到可观察结果）：

* **UT（桩 runner，确定性）：** 覆盖阶段流转与顺序、审查者轮转分配（含单模型回退）、两轮上限拒绝、标志触发复核、审查 prompt 匿名构造（不含作者模型名）、阻断门禁与"尚不可采用"标注、输出预算 schema、配置解析（offline 默认名单、未配置报错、空数组、去重 ∪ 会话模型、不可用模型报错）、无参数提示、Discuss 拒绝。
* **进程内集成测试：** 脚本化模型响应跑通五阶段到最终输出，断言结果结构（含收尾契约、理解差异呈现、阻断标注）。
* **UI 冒烟扩展：** 在现有 PTY TUI 冒烟中加入 `/team` 用例——真实 TUI 入口，`zcode-api` 指向本地 stub HTTP 服务，跑到可观察的最终结果。
* **合入前一次真实人工运行：** `--offline` 公司模型全流程跑一遍并如实记录；不冒充为自动化验证。
* 测试清单加入 `scripts/fulltest.ts` 白名单；TypeScript 修改后 `bun run fastcheck` MUST 通过；`bun run fulltest` / `slowtest` 按仓库规则仅在用户明确要求时运行。

## 7. 已知边界与已接受代价

* **上游撞名 `/team`：** 已接受；上游引入同名命令时处理注册冲突。
* **复核触发依赖自我报告：** 修订者漏设标志时不发生复核；以结构化 schema 降低漏报率，不引入全量复核。
* **同步成本：** 编排器直驱子代理生成路径（`runSubprocess` 层），上游重构该层时 fork 同步成本偏高。
* **延迟量级：** 默认 6 参与者的全流程（6 提案 + 1 对齐 + 6 审查 + 修订复核 + 1 综合）为分钟级到十分钟级；company 模型价格为 0，代价主要是时间。
* **综合子调用无会话现场：** `/team` 问题自包含，拼装上下文的损失有限；事后追问由主代理基于结果消息回答，深度不及过程记忆。
* **并发取消传播：** 多子代理并发的取消传播行为需在实现与 UI 冒烟中验证。
