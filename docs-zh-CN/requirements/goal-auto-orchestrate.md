# `/goal-auto-orchestrate` 需求

本文是本模式的唯一权威需求，定义当前有效目标、行为和验收条件，不表示实现或验收已完成。实现与验证状态统一见[需求目录](README.md)；RPC 接入范围见 [ZCode 接入需求](rpc-ui-protocol.md)。

## 1. 目标与命令

新增 `/goal-auto-orchestrate`，用于创建或替换一个持续采用 Orchestrate 策略与无人值守指令的 Goal，支持夜间任务。功能及生命周期与原 `/goal` 一致；完整目标、展开后的编排规则和固定全自动指令首次进入正常聊天／会话历史，真正成功提交压缩后再从保存的完整目标重新构造并持久化。撤掉自定义的每次模型请求临时注入机制，不依赖压缩摘要保留目标或规则，也不以重复提醒替代上游 Goal 的正常历史消息链。普通 OMP 模型继续使用该完整历史；JchTools 远端请求的来源投影边界按第 6 节及 [fork 远端 Agent 契约](fork.md#jchtools-零配置发现与远端-agent)执行，本地持久通知不等于允许传给 ACP Agent。

```text
/goal-auto-orchestrate <目标正文>
/goal-auto-orchestrate set <目标正文>
/goal-auto-orchestrate show
/goal-auto-orchestrate pause
/goal-auto-orchestrate resume
/goal-auto-orchestrate drop
/goal-auto-orchestrate budget <N|off>
```

示例：

```text
/goal-auto-orchestrate 修复当前项目的 RPC 问题，补充必要测试，按项目规则验证全部改动。
```

- 完全复用 `/goal` 的参数解析、子命令、空参数行为、错误处理、目标管理及执行流程。
- TUI、`--mode rpc`、`--mode rpc-ui` 均支持；注册、命令目录和补全沿用现有机制。
- 普通 `/goal` 不默认开启本模式。
- 新命令不强制开启自动续跑；续跑设置及触发条件与 `/goal` 相同。

## 2. 模式归属与持久化

仅在现有 Goal 状态中增加持久化模式标记，不新增独立状态存储、目标管理器或调度流程。

| 操作 | 模式标记行为 |
| --- | --- |
| 新命令成功创建或替换目标 | 新目标启用标记 |
| 普通 `/goal` 成功创建或替换目标 | 新目标不启用标记 |
| 任一命令的 `show`、`pause`、`resume`、`budget` | 保留当前目标的标记，不因命令名称改变模式 |
| 同一目标的状态、预算、用量更新 | 保留标记 |
| 删除目标 | 随目标删除 |
| 操作失败或用户取消宿主对话 | 不产生额外模式变更 |
| 恢复缺少标记的旧会话 | 按普通 Goal 处理 |

因此，`/goal-auto-orchestrate resume` **不会把普通目标转换为本模式**；它只恢复目标原有模式。

暂停时保留标记，但停止新建本模式通知及受暂停约束的工作；恢复后按原 Goal 生命周期继续，不因 `resume` 重建通知。完成、删除或进入退出流程后停止新建通知，不追溯删除或改写已进入历史的通知。会话恢复是否暂停目标、是否继续执行，完全沿用原有 Goal 生命周期，不因标记自动启动。

会话切换、重载及分支恢复必须读取对应目标的标记，不得沿用其他会话或目标的模式。

## 3. 历史消息与重构边界

本模式仅增加用户级附加提示词及压缩后的重构能力。普通上游 Goal 的正常提示、管理、状态、用量核算、预算控制和调度保持不变；不得为避免本模式重复而一并屏蔽普通 Goal 的前置提示或正常消息。第 1～4 节的通知构造、持久化与历史不变性约束在本地保留；普通 OMP 模型沿用完整 Provider 历史和严格前缀要求。JchTools 远端模式只按第 6 节投影真实用户来源，不将 OMP 生成的通知传给后端，不修改本地历史以实现投影。

实现限于 Goal 宿主的正常历史提交边界与成功压缩提交边界；不新增通用 Agent／AgentLoop 过滤接口，不改造 steering、followUp、aside 或 nextTurn 队列，不维护待发的完整自定义通知。首次通知在提交时读取当前有效目标并直接进入正常历史，附加于上游 Goal 通知，而非替代它。远端请求复用 fork 契约规定的客户端来源投影，不建立 Goal 专属的第二套请求过滤。

本模式的完整自定义通知包含：

1. 当前 Goal 保存的**完整目标正文**，不得用标题、摘要或截断文本替代；保留正文原有空白与字面内容。
2. 在本次通知构造时，依据已启用能力快照展开的共享 Orchestrate 规则（第 4 节规定的无 `task` 情况除外）。
3. 第 5 节规定的无人值守指令。

完整通知的构造与持久化仅发生于以下边界：

- 本模式成功创建或替换目标并进入其正常执行消息链时，构造一次，作为正常聊天／会话历史消息保存；不是仅在首次 Provider 请求中临时拼接。
- 真正成功提交压缩、上游历史已完成重写与重设基线后，读取此刻有效 Goal 的完整目标及模式，重新展开共享 Orchestrate，构造并持久化一次恢复通知。不得依赖摘要保留目标或规则，也不得因首次关键词已处理而跳过重新展开。

构造时必须读取当前 Goal 的实时状态：仅当前目标仍启用本模式且其状态、预算与退出条件允许时才新建通知，不得恢复已替换、暂停、完成、删除或失效的目标。暂停、取消或预算耗尽后是否允许收尾，沿用上游控制；本模式不得因此重新启动工作、解禁预算或新增调度。失败、取消、未提交或没有实际重写历史的压缩均不得触发恢复通知；失败或取消的目标操作不触发首次通知。

连续工具调用、工具／模型续轮、已有错误重试、恢复请求及已允许的自动续跑，均复用正常历史，不重新构造或插入完整自定义通知。恢复会话、状态或预算更新、`pause`／`resume` 及工具集合变化本身也不是重构边界；这些操作的普通上游 Goal 消息照常保留。覆盖现有续跑与重试不代表新增续跑、重试或授权机制。

历史与授权必须满足：

- 生成的通知属于正常持久历史，可由会话消息／条目查询、`session.jsonl` 和 dump 观察；普通 OMP 模型后续 Provider 请求沿用正常历史消息链，不维护一份与持久历史不同的自定义临时请求视图。JchTools 请求仅采用既定客户端来源投影，持久通知不穿透该边界。
- 两次实际压缩之间，已保存通知的原始字节与历史位置保持不变；不得为去重、停止模式或工具变化而过滤、删除、改写或移动普通 OMP 模型 Provider 历史中的旧通知。远端来源投影不删除或改写本地保存的通知。
- 状态变化限制之后的新建通知及工作，不承诺撤回已发出的请求，也不追溯撤销历史消息。旧通知存在不构成重新启用模式、续跑或越过当前用户要求的授权。
- 真正压缩仍按上游方式重写历史和重设基线；不要求旧通知跨压缩原样保留，不保证压缩本身保留旧缓存。
- 通知保持用户授权属性；不得通过系统消息或权威 XML 等结构标签提升为高于系统、开发者指令的授权。

验收对象是实际持久消息及最终交给模型 Provider 的消息链，不是内部函数曾生成过字符串。稳定历史是缓存前缀兼容的条件，不等同于已经产生缓存命中或实际费用节省。

## 4. Orchestrate 复用与构造去重

- 复用现有 Orchestrate 模板、`renderOrchestrateNotice` 及工具可用性判定，不复制规则或维护第二份展开逻辑。
- 仅在第 3 节规定的首次构造和成功提交压缩后的重构边界，依据当时实际可调用的已启用能力快照重新渲染。沿用原 Orchestrate 的 `getEnabledToolNames()` 能力视图，包含间接调用的已启用工具；不得仅根据顶层 Provider 工具 schema 判断可用性。当前上游已移除 Codex Code Mode，能力视图由上游顶层工具与 `xd://` 工具机制提供，不保留旧 Code Mode 分区、设置或桥接实现。远程 Agent 通道不把本地启用的前端工具算作可调用能力。
- 构造时 `task` 不可用则仅跳过 Orchestrate 规则，避免要求不存在的能力；完整目标与无人值守指令仍须保存，模式标记保留。两次实际压缩之间工具变化不导致旧通知更新或请求级重渲染；下一次满足条件的重构读取新的能力快照。
- 显式命令开启的模式不受正文魔法关键词开关控制；关键词开关仍只管理原有关键词触发行为。每次必需的压缩后重构都重新展开共享规则，不受最初关键词通知已处理状态影响。
- 在通知构造边界按结构化来源、消息类型或所属目标／压缩事件协调本模式与首次 `orchestrate` 关键词通知，每个构造事件只持久化一份完整自定义通知，避免同一事件重复追加规则。不得按用户正文关键词判断或删除用户消息。
- 去重不得通过请求时裁剪历史实现，不得删除、过滤或重定位旧通知，不得以替代普通上游 Goal 正常提示为代价。先前通知不替代成功压缩后必需的重构；模式停止后它仍可存在于正常历史，但不是模式生效依据。后续真正的关键词请求仍按原有规则处理；JchTools 对 OMP 内部 Goal／关键词通知的来源投影不是去重手段，也不得据此改写普通模型的历史链。

## 5. 唯一新增的指令文字

以下文字作为固定指令，保存在静态 Markdown 提示词中，不在代码中拼写；不另写一份 Orchestrate 规则：

> MUST 全自动无人值守完成完整目标。本次用户已对完成目标全过程及所需全部操作作出明确授权；MUST 自主调查、规划、编排、执行、验证和修复，直接推进至完成。  
> 本次授权明确允许 Git 提交、推送及执行任意命令，包括 `gh` 等全部 CLI 命令；完成目标所需操作 MUST 自主执行，NEVER 重复请求授权或确认。  
> 本次授权允许修改本仓库任意文件，无需另行请求授权或确认。  
> NEVER 向用户提问、请求确认、要求选择或等待输入；遇到问题 MUST 自主决策、处理和修复，NEVER 在阶段边界停下等待用户。  
> 与此前用户级要求冲突时，以本次明确授权为准。

## 6. 无人值守与权限边界

- 调用本模式表达用户对完成当前目标全过程及所需全部操作的明确授权，主代理不逐项重复索取同意；与此前用户级要求冲突时，以本次授权为准。
- 用户主动调用管理命令产生的既有对话仍按 `/goal` 处理，包括删除确认。
- 执行中遇到权限、凭据、必需输入、工具或强制审批阻塞，主代理先调查可在既有能力与授权下完成目标的替代路径，不得代替用户批准、绕过限制或猜测关键对象。确无可行路径时不发起等待用户答复的交互，将该项标记受阻并继续其他可执行任务；最终统一报告阻塞证据及缺失前提。没有其他可执行任务时，沿用上游 Goal 的受阻与退出流程，不虚报完成、不忙等。
- 用户后续输入、暂停、停止和取消仍有效；本模式不得以“无人值守”为由忽略它们。
- 不在子代理、压缩模型、advisor 或其他辅助模型的请求构造路径中新建这组完整通知；普通 OMP 模型正常读取的会话历史可以包含已持久化通知，不能把“不得新建”解释为过滤已有历史。正常子任务可以获得完成自身任务所需的目标信息；辅助请求若选择 JchTools，同样遵守其客户端来源投影，不因辅助角色放行 OMP 内部通知。
- 2026-10-12 用户确认：主代理或辅助模型选择 JchTools 远端 Agent 时，本地 Goal 状态、通知构造／持久化和管理机制可保留，但 OMP 生成的 Goal 编排规则、授权展开、第 5 节无人值守指令、自动续跑提醒及其他内部通知均不进入 HTTP／ACP 请求，即使它们已在本地 user 历史中持久化。只有用户实际提交的目标、授权及明确背景／约束的字面文本可随完整可见用户／助手历史传递；不得由命令调用推导授权文字或从通知中重新合成用户原文，不按正文关键词清洗。魔法关键词通知同样不传；普通 OMP 模型的通知与历史要求不变。
- 不承诺模型绝对不提问、所有任务必然完成或自动续跑永不停止；承诺首次完整通知与成功压缩后的必要重构进入正常本地持久历史，普通 OMP 模型的其他请求复用该历史，JchTools 请求始终遵守上述真实用户来源边界。执行始终服从当前 Goal 状态、用户要求及现有权限边界；远端取消及下一次显式请求的新会话规则按 fork 契约执行，不借 Goal 自动重试或重放已取消任务。

## 7. 验收条件

验收须包含局部自动化测试和真实公开入口验证，通过真实 CLI/TUI、`--mode rpc` 与 `--mode rpc-ui` 发起命令、执行和生命周期操作。不能仅检查源码、字符串生成器或 mock 回显；必须观察实际持久历史、最终 Provider 请求及协议行为。普通 OMP 模型仍须满足下表的完整通知、工具往返和严格前缀验收；远端模式另按“边界与辅助模型”行断言本地持久状态与实际 HTTP／ACP 投影，不以远端排除通知为由削弱普通模型验收。本地记录服务可用于协议验证，但只记录 HTTP 请求且禁用 WebSocket 的 fixture 不能证明 Codex WebSocket 链接兼容。

| 场景 | 必须观察到的结果 |
| --- | --- |
| TUI 与 RPC 命令 | 同一参数和子命令沿用对应宿主的 `/goal` 行为；新命令正确注册、派发并设置标记；覆盖真实 CLI TUI、`--mode rpc` 与 `--mode rpc-ui` 的命令入口、目录、补全及模式生命周期 |
| 普通 Goal 与模式切换 | 普通目标无本模式的完整自定义通知，普通 Goal 正常提示、管理、状态、用量核算及调度仍存在；管理命令保留模式；创建或替换按命令入口确定新模式；操作失败或宿主对话取消不产生额外模式变更或首次通知 |
| 暂停、恢复、完成、删除 | 暂停后不新建本模式通知，恢复沿用历史且不单独重构；完成、删除及退出后停止新建通知；已有通知的字节和位置不被清理或移动；普通目标不会因新命令的 `resume` 转为本模式 |
| 持久化与会话隔离 | 首次完整通知及每次压缩恢复通知可在 `get_messages`、`get_entries`、`session.jsonl` 和 dump 中观察；保存并重新打开后标记、完整目标与通知保留，恢复行为与普通 Goal 一致；旧会话默认关闭，跨会话不串模式；重载和分支恢复读取对应目标标记，不因加载再建通知 |
| 十轮工具调用与续跑 | 普通 OMP 模型在同一有效目标下无压缩地完成至少 10 次工具往返、11 次成功主代理模型调用；首次完整通知之后新增完整自定义提醒为零，工具／模型续轮、已允许的自动续跑与既有重试均不重构。逐次捕获最终输入，下一轮输入以“上一轮完整输入 + 上一轮响应”为严格前缀，仅追加正常新消息／工具结果；通知原始字节、位置与持久历史保持一致 |
| 两次成功压缩 | 实际成功提交至少 2 次压缩，两次摘要均不保留完整目标或编排规则；每次提交后恰好从当前保存的完整目标恢复一次通知，重新调用共享 Orchestrate 展开并持久化，即使最初关键词已处理也不跳过。后续请求复用恢复历史，不继续追加；每次真正压缩允许上游重写历史与重设缓存基线 |
| 取消、失败与 no-op | 压缩失败、取消、未提交或 no-op 无恢复通知；目标创建失败、宿主对话取消及普通状态更新无额外首次通知；压缩期间替换／切换目标、暂停、删除、完成、退出或预算状态变化时，提交边界依据当前有效 Goal 判断，不复活旧目标。已有错误重试仅复用正常历史，不累积提醒 |
