# Fork 与上游差异

本仓库是个人自己使用的 fork 维护仓库：持续同步上游最新 `main`，保留个人功能和默认值，不以对外发布为目标。

本页面向本人和 AI agent，维护项目定位、共同使用目标及**相对当前上游基线仍有效、对使用者有影响的功能差异**，不记录实现细节或同步历史（随日常开发沉淀、上游尚未包含的缺陷修复统一记录在「上游缺陷散点修复」一节，并在上游等价修复合入后删除对应条目）。开发规则及仓库专属同步参数见仓库根 `AGENTS.md`，通用同步流程与受限 Git 执行脚本由 JCH 仓库维护并分发的 `jch-upstream-sync` Skill 提供；需求域划分见[目录索引](README.md)。当前有效范围：模型选择与验证编排跟随上游规则（fork 不维护模型硬排除或手工测试白名单），诊断日志继续复用上游 logger，覆盖契约见本文「运行诊断日志」；`/team`、`/repo`、`/wiki`、company、`/jch*`、fullsend、Codex 策略与分发能力完整保留（各域验证状态见[目录索引](README.md)）。代码定位索引的独立契约见[代码定位索引](repo-index.md)。

## 项目定位与使用场景

两种主要使用场景统一使用本 fork 的 OMP 作为 Agent 核心，目标均为零配置文件、开箱即用。独立 RPC 客户端场景已退役：上游 `--mode rpc-ui` 保留为上游原样的单会话 RPC，fork 不扩展、不依赖，桌面接入唯一入口是 ZCode 协议：

| 场景 | 使用目标 | 具体契约 |
| --- | --- | --- |
| 终端 TUI | 直接使用 OMP 原生终端交互入口，跟进上游能力，并带有本 fork 的个人默认值；公司无互联网环境通过 `OMP_OFFLINE=1` 使用本地资源和公司内部模型服务，日常启动与核心任务不依赖公网 | 本文「默认设置」「快捷键与状态栏」「公司内网模型（仅 `OMP_OFFLINE`）」「安装与运行」；[新手快速指南](../quick-start-intranet.md) |
| ZCode 桌面 | 使用 ZCode 的界面框架与风格，以本 fork 的 OMP 替换其 Agent 核心，复用同一套 OMP 执行能力与状态 | [ZCode 接入](rpc-ui-protocol.md) |

- **零配置文件**：默认使用不要求用户手工创建、填写或修改 OMP 配置文件；所需默认值由内置行为、场景启动参数和已有环境信息提供。模型服务可达及必要认证仍是使用前提；公司环境复用既有 Claude Code 配置的具体约定见下文，不要求另配一份 OMP 凭据。
- 用户仍可主动调整偏好并由程序持久化，例如通过 ZCode 保存 role；可选设置不能成为默认使用的必经步骤。零配置不禁止程序保存会话、缓存或用户主动选择。
- **共同验收目标**：在未手工提供 OMP 配置文件、对应服务与认证已就绪的条件下，两种场景分别从真实入口完成消息发送、模型响应和工具执行；公司场景在无公网条件下完成。ZCode 的具体能力范围与验收按其独立契约执行，不由本节扩大。
- 高频同步与最小业务代码差异的维护原则统一见 [AGENTS.md](../../AGENTS.md)；这些目标不代表当前两种场景均已实现或验收通过，具体状态以各功能域记录为准。

## 当前功能差异

### Git 钩子

- 本 fork 不保留或使用任何 Git 钩子，包括提交、推送、签出及外部工具跟踪钩子；安装、开发和上游同步不得恢复钩子或其自动安装步骤。
- 现有 checkout 删除全部钩子文件，并在本仓库设置 `git config --local core.hooksPath /dev/null`；不修改用户全局 Git 配置。
- `git commit` 与 `git push` 不自动运行检查或外部跟踪程序。既有验证命令及通过标准保持不变，仅按任务授权显式执行。


### 工具参数自纠正提示

- 工具参数 JSON 解析失败时，保留原始错误，并明确告知模型本次工具未执行，要求修正参数后重新调用，不只解释错误，也不重复已成功的调用。复用既有工具错误反馈与后续模型回合，不新增重试机制、次数配置或模型特判，不放宽校验或隐藏失败状态。

### `/loop` 轮次间隔

- 支持 `/loop [次数或总时长] [间隔] [任务内容]`，间隔无需参数名，仅在有效限制参数后紧接的位置识别完整时长标记，支持秒、分钟、小时及组合时长；正文中的时长不再解析。条件参数仍可放在间隔后、正文前。
- `/loop 10 30s xxx` 首轮立即执行，总计最多 10 轮，每轮结束后等待 30 秒再启动下一轮；`/loop 10m 30s xxx` 最多运行 10 分钟，等待计入总时长，到期不再启动下一轮。
- 不指定间隔保持上游原行为，包括数字限制为首轮后的重复次数（`/loop 10 xxx` 最多 11 轮）及默认中断窗口；指定间隔时数字限制包含首轮。
- TUI 与 ZCode 命令宿主共用解析和语义，等待期间可以暂停、关闭或切换会话，旧定时器不得继续提交；首轮、条件检查及 compact/reset 沿用现有执行链，不允许重叠提交。


### Markdown 文档索引

- **Wiki 数据目录**：CLI、TUI 和 `wiki` 工具的创建、读取、导入、迁移及删除统一使用当前 profile 数据目录下的 `docs.db`，不设置独立 Wiki 数据根或平行副本。数据根调整遵循[安装与运行](#安装与运行)的统一目录契约；目录按既有建库流程创建，不自动迁移旧数据，不据此承诺 NFS 多机并发安全。验证状态见[需求目录](README.md)。
- **Rust 文档索引内核**：`crates/pi-natives/src/wiki/` 负责 Markdown 文件发现、忠实移植既有共享解析器语义的词法解析／章节切分、文档哈希、数据库 schema／旧库迁移、索引生命周期与导入／发布／回滚，以及查询分析、技术名称边界与切分上下文恢复、SQLite FTS5／BM25、全量排名、完整排名缓存、快照版本、游标、正文／来源读取、页预算、同页去重、证据渲染、展示控制字符过滤和可取消的成功时长下限等待；异步操作复用 `grep` 的 native/N-API blocking-task 机制，不保留 TypeScript 实现或回退。保留的 TypeScript engine／service／tool 仅适配宿主路径、参数 schema、会话、IPC／服务子进程、UI、logger 与取消／释放边界。算法、数据库格式、结果顺序、正文／引用及有效旧游标身份不得因语言迁移变化，现有索引无需重建；DB-only、成功时长 ≥500ms 与错误契约保持不变。
- **共享数据库页读取**：wiki 查询连接默认请求最多 500 MiB 的 SQLite 内存映射读取；多个进程访问同一实际数据库文件时，由操作系统复用文件页面、按需加载并回收。保留原有 SQLite 私有页缓存与进程内排名缓存规则，不为每个进程新增大额堆缓存，不改变导入／删除、读快照、完整结果或游标。映射范围受 SQLite／平台支持限制，不是单进程或整机内存硬上限；正常关闭服务须释放映射与数据库句柄。
- **数据库与构建身份**：打开连接前后须确认同一实际数据库文件；导入租约、隐藏构建回收与创建、提交、发布与回滚须绑定原数据库身份，不能仅凭可复用的行 ID 操作其他构建或已发布索引。取得租约后替换数据库必须在回收或创建前拒绝；回调期间替换数据库、取消或关闭服务不得修改替换库中的既有证据。
- 索引管理只有两个命令：`omp docs init "<dir>" --name "<name>"` 新建（同名已存在直接报错）与 `omp docs remove <name> --force` 删除；没有 list/status/更新/重建等其他命令入口（`/wiki` 面板会列出已有索引供检索，并可直接发起这两个动作），索引也不记录状态或时间戳。删除只删数据库中的索引，不删源文件。
- 文档重新导出后，刷新方式固定为「先 remove 删除旧索引，再 init 新建」。本 fork 只维护这两个命令：新增其他索引维护入口属于超出当前契约的范围，NEVER 引入。
- **技术相关性（默认 `mode="search"`）**：固定使用 SQLite FTS5 全文检索，关键词或自然语言问题均可直接输入，无布尔、引号或通配符语法（`AND`/`OR`/`*` 等按普通字符处理）；不根据输入自动启用正则。优先返回同时覆盖所问技术主题、连续词组与当前章节标题的实质正文，不能让泛化描述、功能词或仅因全部词元出现的章节压过技术证据；代码片段（包括围栏及缩进代码）中形似标题的文字不算当前章节标题，技术主题不能误当功能词。同级使用相关性及 BM25 排序。拉丁词与数字按整词匹配，中英粘连仍保留拉丁词；汉字串按原样相邻 bigram 分析，功能词整词丢弃，超过 32 个词元等距取样保留首尾。排序覆盖整个匹配集，并用存储正文补足完整名称召回；NEVER 因有界候选窗口、评分文本截断或单页预算遗漏后续证据。
- **完整名称**：识别用户输入的文件名、标识符、选项、路径等技术名称（如 `mbist_check.rpt`、`std::vector`、`--flag`、`foo_bar`、`E123`、`ERR-123`、`C++`）；独立输入的非汉字标识符／命令（如 `hisms`、`scan`）同样按完整名称处理，普通多词文本（如 `git status`）仍按词组／自然语言检索，不新增语法。名称保留内部标点，忽略大小写；自然语言句子的结束标点不属于名称（如 `Explain mbist_check.rpt.` 的末尾句点），独立输入的 `mbist_check.rpt.` 则仍保留字面句点。完整名称边界须结合数据库中保存的相邻切分语境判断，不能把人为分段边缘当作名称结束；更长标识符、扩展名、命名空间或版本中的局部字串不能冒充完整命中（如切分后的 `C++` 仍不能冒充 `C++17` 的完整名称）。`match=exact-name` 的完整名称证据排在所有 `match=related` 相关章节之前；散落词元、去掉内部标点或只匹配部分名称只能算相关命中。没有完整名称命中时明确输出 `未找到完整名称命中`，即使存在相关章节也不能改称完整命中。
- **显式 grep 模式（`mode="grep"`）**：`query` 按正则表达式处理，复用现有 grep 的 Rust 正则／PCRE2 引擎；Rust 不支持的合法表达式交给 PCRE2，两个引擎均拒绝时明确报非法正则，不采用文件 grep 的转义修复或字面量回退。`case` 默认 `true`（区分大小写），`false` 忽略大小写，仅用于 grep 模式。扫描所选已导入语料的数据库原始 Markdown，不依赖 FTS 候选、归一化文本、原文件或文件 grep 的 4MiB 上限；只返回实际正则命中的章节，标注 `match=regex`，按索引／文档／章节的固定来源顺序分页，不混入相关章节或完整名称判定。
- **grep 匹配边界与范围**：逐原始行匹配，不提供跨行模式、布尔查询语言或精确出现次数；`AND`／`OR`／`NOT` 不是布尔运算符，正则分组、`|` 和边界按引擎语义解释。恢复同一文档存储切片之间的连续原始行并去除重叠，不能把人为切分点当作 `^`／`$`、漏掉跨切片的单行匹配或只靠 500 字符重叠保证召回；命中范围涉及的存储章节均可到达。grep 保留表达式首尾空格，不静默截断；超过 500 个 UTF-16 单元明确报错。合法零命中正常成功，数据库扫描与页后等待均可取消，不预先承诺性能提升。
  - 原生 `crates/pi-natives/src/wiki/database.rs` 的 grep 校验拒绝空字符串及纯空白 query；这与将有效正则原样传给 matcher 是不同边界。含非空白内容的合法正则仍保留首尾空格，GUI 不得通过 trim 改写其匹配语义；不需要修改 Rust 原生语义。
- **连续分页**：只读 `wiki` 工具接受必填 `query: string` 与可选 `mode: "search" | "grep"`、`case: boolean`、`cursor: string`；多个索引时覆盖全部已导入索引，`/wiki` 面板只搜索所选索引，`/` 发起默认检索、`g` 发起 grep。页脚给出命中章节总数及「还有结果 + 下一次调用参数」或明确耗尽。继续查询必须保持原 query、模式和有效大小写选项并原样传回游标。游标绑定有效查询、检索模式／大小写选项、索引范围与数据库逻辑版本；原默认检索的有效旧游标身份保持不变，关闭再打开服务仍可续页。损坏、跨查询／模式／选项／索引或过期游标报错，不伪装成零命中。每页的版本、命中、计数、完整正文与来源来自同一读快照，数据库变化不能拼接旧来源与新正文。
- 分页顺序固定且与单页预算无关；连续页按序推进，每个匹配章节及来源恰好到达一次，不跳过放不下的下一节。常规工具页目标约 8000 字符（正文、定位、页头与续页信息均计入），每次最多 200 节；每页第一节即使超限也完整返回并标注，其他节放不下就留至下一页，不截断正文。默认检索 `query` 超过 500 字符先截断并带省略号，再检索与回显，续页使用该有效 query；grep 不适用此截断规则。入库章节上限仍为 18000 字符。逐字重复的长正文（超过 200 字符）可指向**同页**已完整展示的正文，但每个来源定位仍须保留；跨页重新提供完整正文，重复来源、仅标题章节及旧库结构标签都必须可遍历，不能被折叠或预算永久隐藏。
- `/wiki` 命中详情须能遍历完整存储正文：长行按当前宽度折行，通过方向键、PgUp/PgDn、Home/End 滚动，缩放终端后仍可到达正文尾部；来源与列表标签可以限宽，不能用限宽丢弃正文。
- **非阻塞与取消**：查询、续页及索引列表／删除不能在交互线程执行数据库工作或阻塞输入和渲染；`/wiki` 显示加载、搜索、删除或导入的实际操作状态，任何操作进行期间均可用 `c` 或 `Esc` 直接取消，不等待关闭确认，关闭面板也取消未完成操作。工具与对话宿主传递调用方取消信号；取消须及时结束该调用，不重试、不回落到交互线程同步搜索，迟到结果不能覆盖新请求。排队请求的取消不影响正在执行的其他请求；会话结束、切换 profile／数据库或服务关闭须释放其自有执行资源，不能泄漏后台进程或继续交付结果。续页失败／取消保留原结果页及所选命中的存储正文，不清空已有证据。
- **完整排名复用**：服务在存续期间有界保留按有效查询、索引范围和数据库快照绑定的**全部**匹配排名；同一未变化查询的再次读取或续页不重复全库扫描／排序，只读取当前页所需的完整正文与来源。容量限制只能淘汰整个查询，不能截掉证据尾部；不以时间 TTL 代替真实数据库变更判断。导入／删除、原始 SQL 或 FTS 修改、外部提交、数据库文件替换以及关闭再打开后，必须重新确认逻辑版本和读快照，不能复用陈旧／混合证据或把并发变化后的版本标给旧排名。缓存淘汰或服务重开不改变游标身份：版本未变仍可续页，版本变化则明确报过期；页间不持有读事务。
- **持久化查询投影**：新导入文档在原有文档事务内预计算并保存查询无关的 Markdown 评分字段、规范化名称轨道及压缩的原字节来源映射；查询不再重复解析全部 Markdown。旧库首次打开时仅从数据库内已保存的原文自动迁移至 schema 12，不要求源目录或重新导入；schema 11 升级不重建未变化的 FTS。投影会增加数据库空间并产生一次性准备成本，必须与迁移后的查询耗时分开报告，不隐藏首次准备等待。
  - 预计算与即时算法须在完整召回、排名、完整名称边界、Unicode 规范化、跨切片／重叠／缺口、链接标签与目标及旧版坐标语义上等价；不截断候选或正文，不保存逐命中位置数组。数据库内容未变时，既有游标与完整证据摘要保持一致。
  - 原始 SQL 对章节的增删改、归属变更及 ID 替换必须使受影响文档的投影失效，包括关闭外键或递归触发器的写入；缺失投影按原有算法现算，不能使用陈旧投影。无效版本、损坏或非法来源映射明确报错，不静默伪造结果。FTS 修改继续使排名缓存失效；文档事务失败／取消和索引回滚不留下已发布的派生数据。
- **成功查询时长下限**：对外每次成功搜索（工具与 TUI，含续页和正常零命中）的总时长必须 **≥500ms（不少于 500ms，并非不超过 500ms）**。实际查询与页预算完成后，仅在不足下限时以可取消的异步等待补足，并按单调时钟复核；不能阻塞交互线程、在等待时持有数据库事务、将等待伪装成数据库工作或将下限用作缓存 TTL。运行诊断日志须区分真实执行工作、下限等待与对外总时长，沿用现有日志，不新增永久审计记录。错误和取消立即返回，不补足 500ms。
- **零命中与错误**：已有可查询索引时，正常无匹配返回成功结果，明确说明「在本次检索的已导入语料中 0 matches」及结果已耗尽，不证明知识或规定不存在；技术名称无完整命中仍按上条标注。缺少／空白 query、非法 cursor、无索引、数据库损坏及其他操作故障仍报错；缺 query 的错误指出收到的参数名和示例，无关额外键按现有宽松参数处理忽略。
- 默认非受限会话在 `tools.xdev=true` 时将 `wiki` 作为低频只读设备挂载：通过 `read xd://wiki` 按需读取说明与 schema，通过 `write xd://wiki` 携带 JSON 参数执行查询，不在顶层工具 schema 中常驻；`tools.xdev=false` 时仍作为顶层工具提供。显式工具清单继续按原生顶层工具暴露，受限清单不被扩大；仅改变展示与派发入口，不改变权限、查询、分页、取消或生命周期语义。
  - 设备查询保留原生只读工具的独立审批和共享调度：`tools.approval.wiki` 的显式策略仍生效，未配置时不继承 `tools.approval.write` 的拒绝／询问策略；同轮独立查询可以并发，不因 `write` 传输变为独占。普通文件写入和其他设备仍沿用原有审批及调度规则。
- 非受限会话中，显式声明 `read` 的工具清单会自动附加只读 `wiki` 与 `repo`（含自定义 agent 的 `tools:` frontmatter 与 SDK/RPC 传入的清单）；受限清单（如 `/team` 子代理的工具集）不附加。
- 被强杀的中断导入留下的隐藏半成品索引（面板不可见、无法按名称删除）会在下一次 `init` 枚举到非空语料后回收，避免它长期占用空间。

### JCH 命令

保留以下个人命令及其核心语义：

- `/jchfix`：定位根因并最小修复，不提交、不推送。
- `/jchdiagnose`：只读诊断根因、影响和修复边界。
- `/jchfuncreview`：独立只读功能审查，仅报告高置信问题。
- `/jchfuncreviewfix`：审查后最小修复。
- `/jchverify`：只读验证指定修改是否可交付。
- `/jchfuncreview`、`/jchfuncreviewfix`、`/jchverify` 的范围参数：三命令都支持 `uncommitted`（未提交改动）与 `commit <ref>`；`/jchfuncreview` 与 `/jchverify` 另支持 `path <路径>`，`/jchfuncreviewfix` 另支持 `repo`（全仓）；空参或非法 verb 在执行前报用法错误。
- `/jchci`：只读分析当前 HEAD/PR 的 GitHub Actions。
- `/jchcifix`：修复当前有效 CI 失败，并仅提交、普通推送相关修改；push 后 CI 不会自然触发新 run 时，仅对已定义 `workflow_dispatch` 的 workflow 以 `--ref` 指向已推送分支执行 `gh workflow run`。
- `/jchcatchup`：查看本地状态/最近提交；`full` 时深入比较远端差异。
- `/jchgs`：`fetch --all` 后显示状态。
- `/jchgitpull`：直接按当前 upstream/pull 配置执行 `git pull`。
- `/jchgitdiscardall [--ignored=true|false]`：始终无交互确认，先执行 `git fetch --all --prune`、`git reset --hard @{upstream}`。无参数或 `--ignored=false` 时以 `git clean -df` 清理未跟踪内容，保留 ignored；`--ignored=true` 时以 `git clean -xdf` 同时清理 ignored 文件和目录。clean 以 `git rev-parse --show-toplevel` 解析的仓库根为工作目录，会话位于仓库子目录时同样清理整个工作树（reset 本就是全仓生效）。该命令在交互界面（TUI）执行；ACP/RPC 通道返回提示、不派发；print/SDK 通道没有内置命令派发，命令文本会原样作为用户消息进入模型。非法、重复或多余参数在任何 Git 操作前报用法错误；任一步失败即停止。重置目标是当前分支配置的跟踪分支，不是本仓库名为 `upstream` 的分支。
- `/jchdftexplain`：面向 DFT 新手解释文件、目录、代码和业务概念，命令参数为待解释对象。只读：可读取文件、搜索代码和调用 `wiki`，不修改文件、不执行待解释脚本、不启动 EDA 流程；内部术语主动用 `wiki` 核对并标注来源，代码解释按命令去重、结论先行。
- `/jchime [故障现象]`：内置提示词恢复命令，面向内网较小模型提供完整可执行步骤及有边界的自主恢复空间；不是无模型的本地动作。默认环境为 CentOS 7、GNOME Terminal、SSH X11/Exceed、IBus 1.5.17 与 `libpinyin`；运行时重新核实，不使用快照中的历史地址或 PID。
  - 首选恢复块使用 Bash + 系统 Python 3.6+（本次调用显式 UTF-8 标准流编码），核对当前 UID、DISPLAY、唯一 daemon、地址文件归属和 PID、引擎可用性后，请求一次 `ibus restart`，重新发现实时总线并切回、核验 `libpinyin`。覆盖仅切引擎不能解决的 daemon/XIM 状态异常；同 daemon 的客户端会短暂中断，未提交的预编辑文字可能丢失。

### `/clear` 已结束待办清理

- `/clear` 原地清空对话上下文时，若当前 TODO 的所有任务均为 `completed`（已完成）或 `abandoned`（已放弃），同时清空当前生效的清单并立即移除 TODO 显示，不等待自动隐藏延迟；手动展开或禁用自动隐藏不阻止此次清理。
- 只要仍有 `pending`、`in_progress` 或 `blocked` 任务，就保留整份清单，包括已完成／已放弃任务、阶段与阻塞说明，不部分删除。
- 清理通过既有会话记录持久化空清单，不删除此前任务历史，不改变会话 ID、标题、目录、模型与设置；刷新、重新展开或重启恢复会话后，不得重新出现已清理的清单。
- 复用共享会话重置链路与已有 `isClosedTodo` 状态定义，不新增配置或第二套终态判定；TUI 重置后同步刷新当前 TODO 面板。

### `/wt` 会话工作树

- 保留 `/wt [分支名]` 与别名 `/worktree`，切换的是当前会话的工作目录，不新建聊天会话；未指定分支名时沿用上游自动命名。以下规则仅约束该命令，不改变 task 隔离、PR checkout 或其他 worktree 入口。
- 指定的本地分支已存在时直接使用，不因同名报错、不重建或重置分支：已有对应工作树时把会话切到该目录；尚无对应工作树时为该分支创建工作树，检出该分支自身的提交，而不是当前分支的 `HEAD`。目标就是当前工作树的分支时保持当前位置，不重复创建。
- 指定的分支不存在时，从当前 `HEAD` 创建新分支与工作树。
- 新建工作树的根目录放在当前会话工作目录的父目录下，与当前目录平级，不放入 `~/.omp/wt`，也不由全局 `worktree.base` 或 `OMP_WORKTREE_DIR` 改变这一位置规则；已有工作树直接复用其原位置，不为满足平级要求搬迁它。目录冲突沿用现有可用路径选择机制，不覆盖已有目录。
- 新建工作树的代码以目标分支的已提交内容为准，不携带源目录的已暂存、未暂存、未跟踪改动或删除状态；当前分支及原目录的这些内容、暂存状态保持不变，不自动 stash、提交、reset 或 clean。`worktree.cleanSource` 不得让 `/wt` 清理原目录。
- 切换到已有工作树时保留该工作树自身的未提交改动，不用源目录覆盖它，也不为切换而清理它。
- 其余会话迁移、运行中限制及退出策略继续复用上游机制。验收须从真实 `/wt` 入口覆盖新分支、已有分支无工作树、已有工作树复用及当前位置四种情况，并核对新建目录的同级关系、目标提交与两端未提交状态；实现与验证状态见[需求目录](README.md)。

### `/display` 界面显示模式

- TUI 提供内置命令 `/display [clean|compact|detailed]`，接入现有 slash 命令注册、帮助与参数补全，不调用模型。无参数按 `clean → compact → detailed → clean` 循环切换；非法参数只显示用法，不修改当前选择。
- 默认使用 `compact`。用户主动切换后复用当前 profile 的全局配置持久化，并立即刷新当前对话；重新启动及恢复会话后沿用所选模式，不要求手工创建配置文件。设置的项目／启动覆盖仍遵循既有优先级；覆盖使所选档位不能完整生效时，必须说明当前实际的思考／工具呈现及覆盖项来源，不得提示请求的档位已生效。
- **已压缩历史的紧凑呈现**：紧凑模式不再整段隐藏已压缩历史；按当前分支既有压缩切点及重置边界，仅保留旧区段的用户原文与助手普通正文，包含工具前后及中途失败前已经输出的正文。不显示旧工具调用／结果（含文件预览与 diff）、思考、通知、错误卡片、用量及耗时行、压缩摘要或其他历史 UI；只有思考／工具而没有正文的助手消息不占位。用户亲自调用的技能只保留原始调用及参数，不展示展开的技能正文。
- 以上投影仅作用于紧凑模式的已压缩区段，不受“折叠已压缩历史”开关影响；未压缩尾部、活动工具、实时思考及当前 TODO／输入区继续遵循现有规则。干净／详细模式仍按该开关选择折叠或完整历史，显式历史查看器保留原始详情。恢复会话、重复压缩、缩放及切换模式须保持旧对话顺序且不重复；不改写原始会话、模型上下文或压缩算法，不新增配置项。
- 旧区段中的用户消息须排除 `synthetic` 或 `agent` 归属的系统注入；用户技能请求以普通 `message` 或 `custom_message` 条目存储时须等价保留。仍在运行的后台工具不按已结束历史隐藏：前台空闲、压缩及模式／焦点重建后仍须保留单一可更新卡片与后续进度、完成回执；终态工具在再次重建时恢复历史收起规则。

| 模式 | 思考内容 | 模型发起的工具调用与结果 |
| --- | --- | --- |
| `clean`（干净） | 不显示正文，仅保留忙碌状态 | 隐藏调用及结果 |
| `compact`（紧凑） | 单一实时尾窗，仅显示当前思考最新三个屏幕行 | 真实文件的写入与编辑沿用上游内容预览、diff 及展开／折叠；其他工具每条可见调用最多占一行，连续紧凑工具段保留最近两条成功调用，更早成功调用与普通失败调用汇总为一行计数；运行中调用保留，失败不再逐条显示；单行调用只显示状态、操作摘要与耗时，不显示完整参数、输出正文或图片；连续单行工具块之间不额外插入空行，文件更改与正文的分隔沿用上游 |
| `detailed`（详细） | 不显示实时尾窗；完整思考原文保留在会话数据，经显式历史查看器查看 | 显示调用与结果，沿用现有详情展开／折叠能力，不强制展开全部内容 |

- 正常主界面任何时刻最多只有一个思考块，仅紧凑模式显示，干净与详细模式不显示；只投影当前被查看会话的真实活动思考块，后台代理并发不抢占。窗口位于输入区上方、固定 TODO 面板之前，底部顺序为实时思考 → TODO → 状态行／输入区；不作为聊天记录或终端 scrollback 输出，不另留思考脉冲、已完成折叠块或历史正文。显式历史查看器保留原始详情能力，不改写会话数据。
- 仅在接口返回非空思考正文时显示；使用真实 `thinking_start`／`thinking_delta`／`thinking_end` 与流运行态判断阶段，不以尾块类型、固定等待时间或网络静默猜测。思考结束且回合仍在运行时收起为单行暗色存根（`…` 前缀加思考最后一个非空行，按宽度截断，不改写原始内容），工具执行与自动重试等待期间保留存根；正文开始（`text_start`）、取消、错误、流结束、新回合开始、会话切换与隐藏设置须清空存根，旧流通知、显示队列及旧焦点回调不能重开旧窗或清掉新窗。聚焦仍在运行的会话须从真实消息与活动索引同步恢复，历史回放不激活窗口。
- 三行上限按当前终端宽度折行后的正文屏幕行计算；非空尾窗另加一行静态“思考”头行，标题使用主题强调色与粗体，宽度允许时带暗色 `╭─` 连接线；头行和正文引导条统一留两个终端列的左边距。正文带左侧 `│ ` 引导条，按扣除左边距与引导条后的可用宽度折行，不增加上下空行。极窄宽度无法同时容纳左边距、引导条与正文时省略装饰，不新增动画、计时或速率。所有终端高度均使用三行正文上限，其余折行与空白规则不变；存根始终为单行且不保留头行与引导条，宽度允许时保留相同的两个终端列左边距。仅在显示层删除全部空行（包括仅含空格或 Tab 的行），再取最新行，原始思考不裁剪或改写。流式空白追加不得挤掉既有正文，后续正文须保留原始缩进。中文、emoji、组合字素、Tab、控制字符和缩放须保持宽度安全，ANSI 与 native 呈现一致。复用已有刷新节奏与文本宽度工具，以增量尾部和缓存避免每个 Token 重新排版完整历史，不新增轮询或动画计时器；宽度、高度钳制、字形宽度配置或主题变化时按实际需要更新。
- 最新可见非空行使用当前主题正文色 `text`，其引导条使用强调色 `accent`；其余正文及结束后的存根使用次级色 `dim`，旧行与标题连接线使用暗色边框 `borderMuted`，避免思考过程与正式回答争夺视觉重点。不写死 RGB 颜色；流式追加和主题切换时更新强调位置与颜色，ANSI 与 native 使用相同结果，不新增动画。
- 实时尾窗同样遵循 `proseOnlyThinking`（默认开启）：复用既有代码围栏省略规则，先过滤正文，再按上述空白规则取最新三个屏幕行；关闭时不省略代码围栏，空白处理与行数上限不变，活动流中切换须立即生效，不能修改原始消息或重开已结束／已隐藏的窗口。
- 已完整处理的 CRLF／ANSI 不得让后续普通追加永久退回完整历史归一化与折行；未闭合控制序列、跨分片 CRLF 和代理对仍须安全处理。
- 紧凑模式的普通单行工具失败调用只计入当前活动段的失败数，不再单独显示红色 `error`、失败原因、路径或调用意图；失败状态、原因及原始输出保留在会话记录，详细模式／显式历史查看器可查看，不把失败计为成功或推断已恢复。真实文件更改的参数流、运行中、成功与失败结果均沿用上游渲染；干净模式仍隐藏全部工具活动。
- 连续紧凑工具段不跨真实文件更改、助手普通正文或其他可见非工具消息合并；隐藏的思考／工具调用宿主块与独立用量行不切断工具段。较早成功调用显示为单行 `… 已收起 N 次成功调用`；存在失败时优先显示 `… 失败 F 次`，宽度允许才附加 `· 已收起 N 次成功调用`，没有较早成功调用时附加 `（已收起）`，不显示零次成功。窄屏先省略成功部分及收起说明；能够容纳最短失败标识与完整数字时，不得因成功计数而截掉失败数；完整失败计数放不下时只保留失败标识，不显示截断的部分数字。读取分组按实际调用计数，失败与真实文件更改不计入成功数。单行工具的运行中、待确认提案及读取警告仍保留各自单行。仅折叠显示，不删除或改写会话数据，切回详细模式恢复全部工具详情，不新增配置、模式或快捷键。
- **紧凑模式专属降噪**：以下错误协调、后台通知汇总及 TODO 层级仅作用于 `compact`；`clean`、`detailed`、工具执行／重试、TODO 状态及原始记录保持不变。失败与重复 Warning 仅在结构化 `toolCallId` 明确对应同一次实际失败且该失败已计入紧凑活动时合并；不同执行、独立警告及缺乏关联者不合并。失败原因、TODO 进度可能陈旧的提示保留在详细／历史查看入口，迟到结果、历史重建与模式切换不得丢失失败计数。没有明确关联证据时处理状态仍未知，不凭后续其他成功标记恢复，不新增自动恢复判断。
- `async-result` 中有非空执行 ID 且实际状态为 `completed`／`failed` 的普通 `task`／`bash` 通知，在连续活动段中汇总为一条原地更新的完成／失败计数；重复投递同一执行不重复计数，同名不同执行分别计数。失败只以低强调的计数呈现，不再逐条显示红色后台失败日志与内部执行 ID，不计为成功、不推断已恢复。汇总不切断连续工具段，仍只保留该段最近两条普通成功调用。取消、身份／状态未知事件及独立 artifact／schema 警告分别保留，不算普通成功；助手正文、真实文件预览／diff 和独立可见异常仍为真实边界，不跨边界合并。不改变监督进程通知、桌面通知或原始会话消息，详细／显式历史视图恢复逐项记录。
- TODO 在紧凑模式中用非颜色的 `[active]`／`[blocked]` 标识突出进行中与阻塞，待办使用正文色，关闭项降低视觉权重但仍可读；已放弃项明确标识，不当作成功。保留已有折叠、关闭项上下文、手动展开、计数和活动子代理匹配 `pending` 的 active/current 呈现，不修改持久状态或自动选择唯一主任务。矮终端的 TODO 单行也不得把阻塞或放弃显示成完成；ANSI 与 native 使用同一状态含义，切换档位即时刷新。
- 紧凑模式下工具折叠或底部面板收缩后，允许输入区自然上移，不为维持底部贴边而在工具记录与实时思考／TODO 之间补出大段空白；不清空或重复输出已有滚动历史，干净与详细模式保持原有布局策略。
- 紧凑模式在视口不足时按对话顺序显示连续的末尾屏幕行，仅从顶部裁切，不把每条用户消息或助手正文分别压成一行；前序活动组件阻塞历史提交时同样适用。不伪造组件结束、不越过历史提交顺序、不改写会话原文；干净与详细模式保持既有视口分配策略。
- 紧凑工具摘要优先使用已有意图字段 `i`；普通文件目标优先显示文件名（保留行号选择器），完整路径与参数在详细模式查看。Bash 未提供意图时显示执行程序名，不用整段脚本挤占摘要。普通单行工具的操作摘要使用正文色，ANSI 与 native 文本回退中的工具名、普通状态和耗时降低强调，不再用粗体突出工具名；警告保留既有强调，native 语义工具节点保留终端负责的标题呈现。内部 URL 保留既有设备身份与专用摘要。AST 编辑的未应用提案显示“待确认”，不标作成功写入；应用提案的实际回执显示“已应用”，原提案记录仍表达当时的提案阶段，不改写原始历史。
- 真实文件的 `write`、`edit` 与 `apply_patch` 不强制压缩为单行，也不纳入成功调用计数折叠；直接路径及 `local://`、`ssh://` 等文件目标均复用上游内容预览、diff、流式更新与详情展开／折叠，不另建渲染器。`write agent://…`、`write proc://…`、`write cfg://…`、`write xd://<tool>`（包括 LSP）及其他工具继续遵循单行限制，展开快捷键不显示其参数、正文或 diff；干净模式仍隐藏真实文件更改。
- 无专用摘要的工具按 `command → pattern → query → path → input` 选取首个非空字符串作为操作摘要，使检索词优先于搜索目录；继续复用单行清洗、截断和耗时呈现，不追加结果正文。
- 紧凑模式的 `eval` 优先使用已有意图字段 `i`，其次使用本次调用的 `title` 作为操作摘要；不展示代码或输出，继续复用统一的状态、截断和耗时呈现。
- 紧凑模式的 `wait` 单行须从最新后台任务快照显示任务类型、ID 与命令／任务标签；多任务优先显示仍在运行的任务，并标出其余任务数量。仅显示标签首行，不泄露任务输出；进度更新、完成快照、模式切换与窄屏均沿用同一摘要，没有任务快照时保留通用等待提示。
- 耗时仅使用实际可用的执行计时；历史消息没有单次调用计时信息时省略耗时，不根据恢复时间或消息间隔伪造数值，也不为显示模式改写既有历史格式。
- 切换后显示一行中文状态提示；紧凑档生效时在提示中指明 `/display detailed` 工具详情入口，补全与配置覆盖说明须准确表达普通工具单行、真实文件修改保留预览与 diff，不改输入区帮助。实时输出、已完成工具调用及恢复会话须遵循所选模式；切回详细模式可重新查看原始工具详情，但不在正常主聊天记录恢复旧思考块。用户手工发起的 shell／Python 执行即使不在模型回合中，也必须保留运行中的组件及后续输出，不因切换显示模式而消失。
- 模式只改变 TUI 呈现，不改变模型、推理档位、工具执行、审批、取消或错误处理。助手普通正文中的进度说明仍正常显示，不承诺“只显示最终答案”；不扩展 ZCode 客户端显示协议。

- 宿主驱动的 Loader、工具和状态栏 spinner 共用 160ms 字形步进；TSP 终端自行驱动的动画不受该宿主间隔限制。助手正文及工具参数的累计 `message_update` 使用 50ms 合并窗口，仅处理窗口内最新快照；非更新事件处理前须先提交待处理快照，保持最终内容与事件顺序，不延后到达即处理的思考阶段通知和逐 delta 语音。普通 TUI 绘制上限及输入处理节奏保持不变。

### 运行诊断日志

- 项目 MUST 提供可落盘的诊断日志，主要用于运行时问题定位和 Agent 故障分析；fork 功能复用上游统一 logger、目录、级别与轮转，不建立平行日志系统或新增必填配置。
- 异常、超时、重试、降级与部分提交等分支 MUST 留下可识别的阶段和结果；关键调用 MUST 记录安全的结果摘要及耗时。可能阻塞的调用、网络请求、IPC 和子进程 MUST 有开始与成功/失败/取消终态，不能仅依赖 UI、stdout/stderr、协议回包或会话 JSONL。
- 运行日志使用单行结构化记录，MUST 写入 `.log` 文件，每条记录具有含时区的毫秒时间戳、级别和 PID；业务边界补充稳定事件、组件、阶段与 `elapsed_ms`。默认路径由 `getLogsDir()` 解析为当前数据根的 `logs/omp.<日期>.<PID>.log`，随 `OMP_CONFIG_ROOT`、profile 和适用的 Linux XDG 状态目录迁移；沿用现有日期/大小轮转与保留规则。
- 一个日志文件 MUST 仅属于一次进程运行；重启／重跑（包括 PID 被复用）MUST 创建新文件，NEVER 追加已有日志。遇到同名旧日志时沿用数字后缀选择未占用文件；目录、级别、日期／大小轮转、保留与刷新规则不变。
- 级别约定：INFO 记录关键开始、完成和状态变化；WARN 记录可恢复异常、重试或降级；ERROR 记录当前操作失败；DEBUG 仅承载额外细节。正常取消、服务缺席和协议预期拒绝不能冒充故障；必要诊断不得全部藏在可关闭的 DEBUG 中。
- 内网日志例外：`OMP_OFFLINE` 启用时仅记录 ERROR，优先于 `OMP_LOG_LEVEL`；WARN／INFO／DEBUG 在统一 logger 入口直接丢弃，不合并或序列化其上下文、不写本地日志，也不投递日志接收器。正常启动／退出不另写 INFO，日志回退不插入 WARN；真实 ERROR 仍沿用原目录、轮转与刷新。此项适用于全部 offline 平台，不改变界面提示、工具结果或协议输出；非 offline 保留原有级别与诊断覆盖。内网不再要求上文的正常阶段与成功起止日志，接受相应诊断缺口。
- 同一操作 MUST 通过 `operation_id` 及现有 request/job/goal/session/tool-call 标识关联起止和阶段；异步分支继承关联上下文，内部跨进程调用尽可能透传现有标识，不为日志改变外部协议。
- 对话终态须区分用户取消、本地/宿主超时、abort、断连和失败，独立响应仍继承发起操作的标识；后台面板吞掉的异常、已保存但 reload 降级、Goal 工具激活/恢复失败与无效持久状态不得被完成/协议成功日志遮盖。
- 会话删除须区分主文件删除、备份清理和附件清理，明确已提交、部分清理及未知状态；team 通知发送与后续 UI 更新分别定位，内部终止仅记录安全原因分类；repo 整代读取失败使用文件指纹定位，不记录原路径或源码。
- 离线 models/bench 的 cache-only 日志仅描述目录发现/刷新，不代表模型请求离线；初始化及后续 selector-miss 刷新保留起止关联。WSL helper 预检拒绝记录有界原因码，不复制 helper 输出正文。
- 凭据、Authorization/Cookie、URL 认证与敏感查询参数、用户输入、提示词、源码、文档/响应正文 MUST NOT 直接入日志。仅记录有界、脱敏的类型、代码、状态、计数、长度和必要栈帧；不得无限复制 stdout/stderr 或大对象。
- 日志目录不可写时 MUST 尝试合理的用户级目录回退；适用的 Linux offline shm 模式下，回退仍须限定在运行根内，不得转写原始持久根或其他磁盘目录。仍失败则向 stderr 有界报告日志初始化故障；日志失败不能递归、掩盖业务结果或使业务崩溃。启动/退出须可追踪并刷新关键记录。
- 本契约覆盖已保留的 fork 功能及其公共边界：JchTools、team、Goal、docs/wiki、repo/AST 通知、company 与向量请求、Codex 压缩、JCH Git、门禁和安装/更新；补日志不改变业务控制流、权限、重试次数或超时。验收包含真实入口的成功/失败、适用的网络与 IPC/子进程异常、关联重建及生成日志的敏感信息检查。

### 安装与运行

- 维护面向公司内网 Linux/tcsh 使用者的简洁[新手快速指南](../quick-start-intranet.md)：最前面说明 `OMP_OFFLINE`、`OMP_CONFIG_ROOT` 与 `OMP_SKILLS_DIR`，随后说明先执行 `ma dmas_ide`、`ide agent` 启动 IDE 和模型代理，再覆盖常用终端命令、内置命令、快捷键及可复制的任务示例（含 `/loop`、`/goal`、`/team`、代码定位索引 `/repo`、`/advisor`，以及可直接携带任务文本的 `/ultrathink`、`/orchestrate`、`/workflowz`、`/fullsend`）。内容依据当前实现，明确循环/目标的停止方式及内网限制，不扩展为上游文档翻译或站点。
- 日志框架复用上游，fork 的日志目录与诊断覆盖遵循上文「运行诊断日志」，数据根遵循下述约定；启动参数除下述 fork 扩展外沿用上游。
- fork 新增 `-P <name>`，复用上游 `--profile <name>` 语义，无需配置 shell alias；启动前选择 profile，认证、会话、设置与缓存隔离及环境变量优先级沿用上游。`-p` 仍为非交互 print 模式，不新增会话共享行为。
- offline 模式只由环境变量 `OMP_OFFLINE` 触发（取值 `1`/`true`/`yes`/`on`，忽略大小写；未设置、空串、`0`/`false` 等其余值不触发），不存在 offline 命令行参数：环境变量对所有 omp 进程及其子进程一致生效，这是把触发入口统一到环境变量的原因（多进程数据根与 lane 状态不能因 spawn 透传遗漏而分裂）。
- `OMP_CONFIG_ROOT`（绝对路径，支持 `~` 展开；相对值被忽略）统一调整 OMP 原始数据根：agent 数据、Wiki／Repo 数据库、会话、日志、缓存、运行状态及 profiles 等目录沿用根下相对布局，项目级 `.omp/` 不受影响。未设置有效值时复用上游默认目录解析和目录名规则，不硬编码 `.omp`；与 `PI_CONFIG_DIR` 同时设置时由 `OMP_CONFIG_ROOT` 决定根位置。非 offline 时直接使用该根；适用的 offline shm 模式按下述契约区分运行根与原始持久根。
- **统一数据根**：删除 `OMP_WIKI_DIR` 环境变量的读取、路径优先级和专用透传，不保留兼容别名或专用 Wiki 目录配置项；环境中遗留该变量也不得影响路径。所有平台及 offline／非 offline 模式均只通过 `OMP_CONFIG_ROOT` 统一调整 OMP 数据根，Wiki 等子目录沿用 profile 内布局，不再单独指定活动目录或备份目标。此项是通用目录需求变更，不受下述 shm 功能的启用条件限制。
- **Broker native 生命周期**：broker 自有 native 缓存位于既有 scope runtime 的 `natives/` 下，随现有 profile／config root／项目（含 global service scope）身份隔离和 runtime 回收机制管理，不以创建者进程为所有者。一个 core 的显式 `PI_NATIVES_DIR` 仍用于该 core 及普通子 worker，但不约束可供其他 core 合法共享的 detached broker；不要求宿主永久保留其临时叶，不通过 `client.close()` 关闭共享 scope。Linux offline 继续使用既有 profile shm native 根。验收须实际加载 native、关闭 creator 并立即删除其独占叶（Windows 不出现 EPERM），另一已连接 client 仍能访问 broker，最后 client 关闭后通过 broker 正常退出释放自有缓存；两个独立 worker 同时冷提取／加载完整 DLL，发布后内容不变且无 staging 残留。实现与新增回归当前未运行验证，不以源码用例替代编译二进制的真实生命周期验收。
- **Linux offline shm**：已实现将 OMP 自有运行数据统一放在 `/dev/shm`，前台就绪满 10 分钟后首次异步备份回原始数据根，之后按周期备份；原始根优先采用有效 `OMP_CONFIG_ROOT`，未设置时沿用上游默认解析，目录名不写死。启动不复制、不恢复，不改变工具读写 NFS 项目文件的能力。完整行为与验收条件以[离线 shm 运行与异步备份](offline-shm.md)为准；非 offline 和非 Linux 不启用该运行根映射或备份。实现不等于 Linux 验收通过，当前验证结果及未验收边界统一见[需求目录](README.md)。
- **offline 用户配置保存（Settings／Team／CLI 已接入，实机尚未整体验收）**：TUI、配置命令及 Agent 代配的 shm／原始 NFS 同次双写、跨主机保护与成功标准统一以[用户配置双写权威要求](offline-shm.md#23-用户配置的-shmnfs-双写权威要求程序实现待验收)为准；不得以周期备份或局部入口约定替代，不改变启动不恢复和运行数据的既有路由。Windows 定向回归与真实入口证据见[需求目录](README.md)，不替代 Linux／公司 NFS 跨主机锁及 CentOS 实机验收；当前没有主动 provider 保存 API，Agent 新增 provider 仍须遵循该权威要求。
- `OMP_OFFLINE` 进程中若未设置 `FS_SCAN_CACHE_TTL_MS`，进程内设为 `30000` 毫秒；该变量只影响 `@` 文件补全的目录重扫间隔，非 offline 进程完全不变，用户显式设置的值（含 `0`）优先。
- **内网交互减负**：仅 Linux offline 将普通后台 TUI 重绘合并到最多 10 FPS；输入回显与取消沿用原输入优先调度，强制最终刷新、终端输出反压与自适应限速不变。品牌渐变刷新降为 250ms，活动计时装饰刷新降为 1000ms。Git 状态缓存由普通模式的 10 秒延长到 60 秒，沿用 HEAD／工作目录／显式失效；未显式失效的外部工作树修改可能延后显示，不新增工具修改通知或修改 Git 配置。非 Linux 和非 offline 保持原行为，不要求改变企业远程软件，不预先承诺公司实机提速。

- 二进制必须携带 fork 版本、构建时间和更新仓库信息。
- 本地构建脚本 `packages/coding-agent/scripts/build-binary.ts` 同样注入本 fork 更新仓库：本地构建产物的 `omp update` 指向本 fork Release，不会回退官方渠道（版本号不注入，`--version` 无 `+fork.N` 后缀属预期）。
- `omp update` 先比较正常 SemVer，再比较同基线的 fork build counter；本地构建未带 `+fork.N` 时按 counter 0 比较，因此可取得同基线的新 fork Release，而不把更高上游基线降级。支持 `%2B` 编码的 `+` 版本 URL；GitHub 元数据和资产统一优先环境令牌，再尝试本机 `gh auth token`，无凭据才匿名请求。

- 运行时代理与安装器同序：Windows 主进程内所有经全局 `fetch` 的出网请求（含 LLM 流、OAuth/usage 探测、模型发现、更新检查与 web 请求）按「请求自带显式 `proxy`（`PI_PROXY_<PROVIDER>`/`PI_PROXY`）→ 标准代理环境变量（`HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY`，Bun 原生应用）→ 当前用户 Windows 系统代理 → 直连」解析。系统代理仅取 HKCU Internet Settings 的静态 `ProxyEnable`/`ProxyServer`（含 `http=`/`https=` per-protocol 形式，`socks=` 条目与 PAC/WPAD 不支持），每进程读取一次并缓存；未启用或读取失败时行为与无此改动一致。`NO_PROXY` 与回环/内网硬 bypass 同样约束系统代理。仅 win32 生效；worker 子进程入口（本地服务）不经此链路。系统代理层另有 fork 内网绕行清单（`packages/ai` proxy.ts 的 `FORK_SYSTEM_PROXY_BYPASS`，抄自公司代理 override 清单）：公司域名后缀、点名内网主机、CGNAT/RFC1918 式 IP 前缀（`10.`、`100.64.`–`100.126.`、`172.16.`–`172.32.`、`7.` 等）与 `*` 通配条目命中的目标不走系统代理、直连；清单只约束系统代理层，不约束 `PI_PROXY` 与环境变量代理（它们的绕行机制仍是 `NO_PROXY`）。条目语义与来源格式对应：前导 `-` 剥离、数字开头为 IP 前缀、含 `*` 为整机名 glob、首尾皆点为点号标签包含、仅前导点为域名后缀、其余为精确或点后缀。
- 零配置 TLS 默认：主进程网络引导时，未显式设置即默认 `NODE_TLS_REJECT_UNAUTHORIZED=0`（Bun fetch 认可，覆盖全部 fetch 请求的证书验证）与 `GIT_SSL_NO_VERIFY=true`（主进程拉起的 git 子进程继承），使拦截代理/私有网关的自有根证书场景免配置可用。显式设置的值均优先于此默认，不被改写；`NODE_TLS_REJECT_UNAUTHORIZED=1` 与 `GIT_SSL_NO_VERIFY=false` 分别恢复对应的严格校验，显式 `0`／`true` 则仍放宽对应校验。agent 目录 `.env` 同样先于此默认生效；worker 子进程入口不经此默认。这是个人 fork 的安全姿态取舍：采用该放宽默认时，TLS 不再验证端点身份，凭据在可劫持网络下有被截获风险，仅在个人受控环境接受。
- 安装器替换目标二进制时不中断运行中的 omp：Linux 用同目录原子 `mv`；Windows 先把旧 `omp.exe` 重命名到唯一的 `.omp.old.*` 再换入（换入失败自动回滚），仅当重命名失败（如杀软锁定）才回退为按安装路径精确匹配强杀，`.omp.old.*` 残留由下次安装尽力清扫。Windows 的已验证下载在替换失败时保留为 `.omp.tmp.*`，包括旧安装已成功回滚的情况；回滚失败同时保留旧映像供恢复。
- Windows 下载成功后，校验、旧映像重命名/强杀回退、换入、回滚或 PATH 设置失败，MUST 打印失败阶段、原始错误、错误类型/代码、安装目标及可用的诊断日志路径，并输出正确引用路径的可执行 PowerShell 命令：未通过验证的二进制不能引导运行；已验证的保留下载可直接启动；旧映像恢复只在目标不存在时执行；重试固定本次 Release 与安装目录，最后核对目标文件及 PATH 命中的版本。二进制已换入但 PATH 设置失败时明确标为部分完成，不能提前报告安装成功。非致命清理失败须说明具体错误和安全重试命令；仍被旧会话占用的映像可留待会话退出后清理，不影响新版安装结果。详细错误仅向终端展示，落盘日志继续遵循脱敏契约。

- 模型筛选、可用性、角色解析和显式选择统一采用上游规则；各 fork 功能复用这些规则，不维护 fork 专有的模型硬排除契约。

本节是三层本地门禁与独立公开 Bazel 适配器的唯一需求位置；具体权限、命令与缓存纪律见 `AGENTS.md`「验证」「构建与缓存纪律」，验证状态见[需求目录](README.md)。门禁只复用现有检查、测试与编译原语，不改写上游质量定义、通过标准、产品行为或 CI 工作流。

- 当前平台的无改动热缓存验收须保持同一源码、约 400 个完整必需目标与稳定 Bazel 配置，连续两次真实 `bun run fulltest` 成功；第二次从启动该命令子进程到退出的外部总墙钟必须**严格小于 30 秒**。发现、源码身份核验、配置隔离、缓存判定、报告及清理全部计时，必要准备不得移到计时外；不以内部门禁时钟遗漏顶层 import、启动或退出开销，不通过缩范围、弱化检查或放宽原有三层硬上限达标。双轮须核对同一组目标、配置与持久 Server 身份，并保留各轮原生 profile、BEP、执行日志及外部墙钟证据；实现变更或诊断 probe 不能代替验收。
- 正式门禁直接按风险批次调用真实 `bazel build`／`bazel test`／`bazel run`，由 Bazel 判定输入失效与成功结果复用；不在相同目标的正式执行前叠加 freshness probe。独立诊断不改变必需目标或成功判据，也不把未派发的计划命令登记为缺失的实际 invocation。

- 保留适配桥接须有原执行语义依据：TS 使用 Bun 特有的测试、worker 与 TSX 行为，不以 Node／`tsc` 替换；本地 Rust 保留既有 Cargo／nextest／rustdoc 的 affected 选择、失败即停及报告，不能仅换成普通 `rust_test` 丢失这些边界。桥接只声明输入、调用原语及接收结果；执行、并发和结果缓存仍归 stock 规则与 Bazel，已有 `rules_rust` 继续负责 native 产物构建。
- 降低 Loading／Analysis 开销须修改实际 Bazel 规则与生成图：精简无关依赖、过宽 `glob` 和复杂宏，复用已有精确输入及 stock 规则，不只调整命令参数。不得删除真实传递依赖、保守加载边界或必需目标，不得用缩小完整 fork 范围、放松断言／预算或禁用应有失效替代优化；以同轮原生 profile 区分 Loading／Analysis 与执行开销，未取得证据时不声称已提速。
- 以下受支持的 root scripts 默认经 Bazel 执行，显式适配器 `bun run bazel -- <existing-task> [task arguments]` 同样可用；这不是第四层门禁，不从 Bazel 目标递归调用 fastcheck/fulltest/slowtest。检查／类型族包含 `check`、`check:ts`（含原 package 类型检查）、`check:tools`、`check:rs`、`lint`、`lint:ts`、`lint:tools`、`lint:rs`、`lint:py`；构建族包含 `build`、`build:native`、`collab:web:build`、`robomp:web:build`；测试族包含 `test`、`test:ts`、`ci:test:ts` 及既有 workspace/native/coding-agent 分片、`test:scripts`、`test:rs`、`test:py`、`robomp:test:integration`、`sdk:test:go`／`sdk:test:go:smoke`／`sdk:test:rust`、`ci:test:smoke`、`ci:test:install-methods`。原叶子命令的选择、顺序、并发、平台限制、工具前置与报告语义不变；仅接受相应适配器明确支持的原参数（Rust `--affected`／`--dry-run`、Go `--smoke`），不扩展命令授权。已在真实 Bazel payload 内的嵌套原语直接执行，避免重入同一 lane；原始命令只保留一处，不建立可绕过默认路由的第二套公开入口。会写源码的 `fmt`／`fix` 族保持原入口，不纳入只读静态检查路由。
- 独立任务报告 `scope=standalone-public-task`，不冒充 `scope=fork-affected`，不将 Python、独立 SDK、安装测试、无关 workspace 构建或完整上游 TS 套件自动加入 fulltest。声明闭合的输入与真实产物可复用 Bazel 成功结果；`lint:tools`／`lint:ts` 保留现有本地 TS lint 原语并可复用结果，未声明完整 Rust 闭包的 `lint:rs` 及包含它的聚合 `lint` 禁用结果复用、每轮真实执行。未闭合的 Python／Go／独立 Rust SDK 工具与依赖、真实 CLI／集成环境、安装等树外状态或副作用须禁用相应结果复用：测试使用原生 `external`，非测试使用每轮实际执行原命令的 `bazel run`，只复用启动器构建。可达不等于环境可用、已获执行授权或已经通过；三层预算及上述无改动双轮、第二轮外部总墙钟严格小于 30 秒的验收均不变。
- workspace 构建保留六个原有生产者及其依赖顺序：browser-relay、collab-web、stats、robomp-web 的独立目录归档与 coding-agent CLI 可执行文件归档由真实 Bazel action 声明，native 保留既有三个原生产物。新执行与缓存命中均从本轮真实 BEP 产物恢复输出，不能以成功标记冒充构建产物；native 安装、版本戳与宿主加载核验每轮执行。CLI 缓存保留产物的真实编译日期，不伪造请求时刻的新构建；未闭合的自定义编译器或 macOS 签名环境仍禁用相关结果复用。Windows ZIP 生产者使用已安装系统 bsdtar，不为此自动安装工具。
- native 安装每轮仍从真实构建产物执行版本戳及宿主加载核验；最终版本戳后的 addon 字节与 bindings 内容均未变化、且已有文件可写时，保留安装文件及其修改时间，避免无内容变化的写入触发下游图重算。版本或内容变化时仍使用既有替换、权限恢复与失败处理，不以时间戳或自建成功标记代替字节比较。

- 三层均在一个单调累计时钟下计费，排除实际观测到的**纯编译区间之并集**；编译和非编译并行时重叠仍计费一次。发现、准备、下载、同步、非编译等待、汇总和清理计费；不能把混合检查/测试命令整段排除。fulltest/slowtest 另有包含编译及全部收尾的总墙钟硬上限，不因纯编译排除而延长；嵌套阶段共享外层剩余额度，并保持更严格的内层上限。`--limit-seconds` 同时下调本入口的非编译与总墙钟上限。
- 到限主动终止本次拥有的普通进程树，Bazel 仅取消本轮自有 invocation/actions、保留 Server（生命周期边界见下文）；非零退出并报告 `TIMEOUT`，不在阶段间重置时钟、不放宽上限。所有退出路径（成功、失败、缺工具、超时、中断、参数错误）都输出 status、total、compile_excluded、budgeted、limit 与退出码，秒至少一位小数。fastcheck 按 budgeted 判断到限；fulltest/slowtest 在 budgeted 或 total 任一到限时退出，独立线程须能在主线程同步阻塞时执行总墙钟强退。
- 首个实际用例、检查、编译、执行、前置准备或结果核验失败后，fulltest/slowtest 立即非零退出，终止本次拥有的普通并行任务、嵌套运行器与进程树；Bazel 仅取消自有 invocation/actions，不终止 Server。不得等待 afterAll、其他用例、WSL、本机剩余测试、清理钩子或报告 I/O。嵌套运行器在识别失败时立即通知外层，不等自身退出。保留首个失败与原退出码（失败状态附带 0 时归为 1），未启动/被取消工作不算通过；允许绕过退出钩子直接结束进程。
- 原生 driver 的准备、客户端、BEP／产物核验失败必须先通知外层，再收尾自有客户端；缺失工具与缺失证据／产物分别报告，不能把所有 `ENOENT` 归为缺工具。Windows 必须先独立启动截止监督，再在主线程准备非阻塞管道，最后才输出生命周期事件／启动工作；fatal 写入不得临时更改可能被挂起同步写占用的管道模式。初始化期间收到首错／中断时立即锁定原始退出码并禁止工作，未完成的管道准备最多等待到「原绝对截止」与「首错后 100ms」的较早者，不能把它变为额外工作预算；已就绪路径仍立即退出。背压或不支持有界写的输出端可缺失最终诊断，但不能延迟独立截止或改写首个失败码。
- 构建脚本能力探针的预期非零编译退出作为探针答案原样返回，不单独触发门禁失败；Cargo 正式编译单元及 Go 工具的失败仍须即时上报并保留原退出码，不能依赖外层进程转发失败。
- 门禁的进程监督须在命令仍运行时回收已退出的孤儿后代，不得截获由运行器持有的主命令退出码；宿主直接退出或 IPC 断开时，监督进程仍须停止并回收普通自有后代，含逃逸的独立 session，Bazel Server 不在清理范围内，其自有工作按下文取消。跨 Windows/WSL 的取消命令须在强退前独立发起，不等待其收尾。Windows 隔离临时目录的正常清理须能解除带拒绝读取 ACL 的目录 junction，且不得遍历或删除其目标；清理失败不得降级成通过。
- 独立且安全的检查/测试/Windows与WSL两端必须并行；改写共享生成文件的构建、打包或代码生成须先于其静态/测试读取者，避免共享文件竞争。编译项目必须保留正常增量缓存、固定同平台配置与路径；NEVER 在连续 fastcheck 之间清缓存、切换 target/profile/flags 或制造冷样本。Windows 与 WSL 使用各自稳定的原生缓存。
- native 生成完成后，fulltest 的静态检查与测试须进入同一 Bazel 图和 invocation：Rust 测试直接依赖 Rust fmt／clippy 的实际 action 完成，不以不同 lane 的优先级或 Cargo 隐式构建锁实现顺序。仅争用根 `target/` 的 Cargo 阶段串行；TS 静态检查、TS 测试和不持构建锁的格式检查不增加额外等待依赖。保留既有 target、profile、features 与 flags，不新增锁、轮询队列或调度成功标记。无法复用的 clippy action 须声明既有实时执行上下文以防增量跳过，不能只依赖 `no-cache` 标签；不将其结果报告为有效缓存。
- 共享图中的 fastcheck 仍有独立的 180 秒非编译预算，观察同一调用的真实活动事件，全部静态目标获得成功 BEP 后结束，不等待剩余测试。外部作业占用 Cargo 构建目录时保留原始等待输出、继续计入原预算；不得杀其他 Agent 的 Cargo 进程或放宽时限。验收须检查原生执行日志：本轮 clippy 启动不再因本轮 Rust 测试出现 `Blocking waiting for file lock on build directory`，Rust 测试在 clippy 成功后完整执行既有 affected 范围（含 doctest）。
- 三层均使用真实 Bazel 文件/action/test 依赖追踪与本地成功结果缓存，按既有独立检查原语声明传递源码、共享库、fixture、生成数据、配置、工具链、平台、相关环境和命令参数。Bazel 已提供的摘要、传递依赖、增量判定、并发、结果缓存和测试产物管理直接复用，删除项目平行实现，不以手写内容指纹或成功清单代替。每轮选完整必需目标，缺失、失败、中断或依赖失效的目标须重跑，输入仍有效的成功结果可跨层复用。禁止用 HEAD、随机运行 ID 或临时报告路径作语义输入；不能可靠表达的外部依赖和副作用目标禁用相应结果复用并说明。报告必需目标、实际执行、有效缓存、未完成目标及原生 BEP／执行日志／测试产物来源；缓存是覆盖证据，不复制重放旧用例冒充新执行。
- fulltest 的范围选择和全部脚本／静态／测试读取者必须绑定同一 post-native 源码快照；准备阶段及后续执行期间的源码或 HEAD 变化立即拒绝。native 生成阶段仅允许两个已跟踪普通文件 `packages/natives/native/index.js`、`index.d.ts` 的内容更新，不能借此接受其他文件、类型、模式或 HEAD 变化；随后重取完整 fork 差异并在结束时核对快照。Rust affected 分析／计划异常须保留原因并非零退出，不能改跑全 workspace 将分析失败转成 PASS；选择器明确返回保守全量范围的正常分支保持不变。
- TS 测试与仓库脚本测试按测试文件建立独立结果目标；复用 Bun 原生 metafile 的模块输入与 chunk 依赖，转换为路径稳定的 Bazel filegroup 图，不执行生成的 bundle，不以 bundle 内容哈希代替 Bazel 文件摘要。字面模块相对资源、worker、对象形式子进程命令和继承的 TypeScript 配置须纳入实际输入及模块依赖；相对子进程工作目录无法可靠定位时保留全仓边界，无法静态确定的其他本地加载保留原有包级/全仓保守边界，第三方不透明加载（含 `createRequire` 工厂及别名）保留已安装依赖边界，发现失败不得当作空依赖命中。报告器只依赖轻量失败通知与清理标记读取，不因错误转发引入完整 native 门禁运行时；报告标签、对象属性名不作为文件路径来源。Rust 测试保留现有 affected 选择与测试原语，仅从其输入中去除无关 TS 业务源码；资源和工具链依赖不省略。验收须通过真实报告入口验证局部业务模块、资产和 npm 依赖编辑后的实际消费者重跑、无关目标有效缓存复用，以及继承配置、跨包子进程和动态加载输入变更后的失效，不以完全无改动的热运行代替增量验收。
- 包级不透明加载的保守闭包须保留完整所属包及其声明的传递工作区依赖；传递依赖及原生发现的包循环域须继续链接对应回退组，不得经普通 `pkg_*` 构建组重新引入全部根共享文件与 Rust 源码。真实跨包资源、已安装依赖和必须保留的全仓回退照常声明；粗粒度构建／检查目标的既有 shared／crates 输入不变。
- worker、子进程入口及动态导入与 Bun chunk 图形成的循环，由 Bazel 原生查询确定各独立循环域；每域单独声明去重的文件输入和全部域外依赖，不合并互不相连的循环，不删除依赖边。增量验收须包含两个独立 worker 循环，修改一侧业务、资产或 npm 依赖后，另一侧仍有效复用缓存。
- Windows 测试子进程的 PATH 排除 WindowsApps 执行占位程序，复用已安装的真实 Python，并为 Bazel 显式提供本机 Git Bash；Python 夹具的 UTF-8 标准流协议不依赖宿主 ANSI 代码页。环境覆盖遵循 Windows 变量名大小写不敏感语义，不修改系统 PATH 或宿主配置。
- 无法可靠声明外部状态或树外产物的非测试原语使用 `bazel run`，每轮执行原命令，仅复用启动器构建；不能把 action 的 `no-cache` 执行标签误当成禁止增量跳过。相应测试使用原生 `external` 标签禁止结果复用；fastcheck 不调用 `bazel test`，不执行测试。
- Windows 的 Rust 测试在 Cargo/Rustup home 稳定且已声明实际工具链/sysroot、依赖源码、Cargo 配置、nextest 与平台工具/SDK 输入时复用原生测试缓存；仅有 rustup 代理或 Cargo.lock 不构成完整工具链声明。精确 `CI=1` 的 Rust fmt／clippy 静态检查在 Windows 稳定 Cargo/Rustup homes，且工具、SDK、被忽略配置及动态定义输入闭合时可复用成功结果；非 CI 公开 `check:rs`、Linux 及未闭合原生系统依赖的平台仍保守禁用对应复用。native producer 的可缓存真实产物与每轮安装／版本戳／宿主加载核验分开，不将安装副作用当作 action 缓存。
- 独立调用按工程风险选择就绪目标的优先批次，不虚构历史失败率。fulltest 在 native 生成完成后先运行其范围内的仓库脚本阶段（并发一），再将全部静态检查与 fork 测试放入同一 Bazel 图、同一次 invocation；该共享图不拆风险批次，Rust 测试对 clippy 的依赖及 TS 安全并行按本节前述契约执行。批次内由 Bazel 原生依赖与并发调度，不另建任务许可队列。记录风险依据、批次与原生实际执行日志，不能仅排序命令标签；调度元数据不进入 action 输入，调整风险顺序不应使有效结果失效。
- 每次原生 Bazel invocation 保留现有保守资源配置：按当前空闲内存扣除 2 GiB 的 JVM／宿主预留后取一半声明内存，并取扣除两个宿主 CPU 后的一半 CPU 预算；每个测试树默认申领 1 GiB 与两个 CPU，覆盖其子进程，fulltest 测试并发上限为四。使用 `--local_test_jobs=0` 保持 CPU／内存资源准入有效，并用原生 `--local_resources=omp_test_slots=<并发上限>` 与 `--default_test_resources=omp_test_slots=1` 同时约束测试树数量；Bazel 9.2 的非零 `local_test_jobs` 会绕过 CPU／内存估算，不能用它替代这一组合（[原生实现](https://github.com/bazelbuild/bazel/blob/9.2.0/src/main/java/com/google/devtools/build/lib/analysis/test/TestTargetProperties.java)）。含测试的 invocation 保留既有最多 16 个分析／缓存评估并发。由 Bazel 原生资源调度约束安全并发，不按整机安装内存或仅 Bun 入口低估多进程测试。不改变用例、超时、覆盖或成功标准，资源调度参数不作为源码指纹或自建缓存键。
- 原生资源预算是准入估算，不是操作系统硬限制：Bazel 9.2 默认允许某项资源当前未被使用时单个 action 超预算执行，CPU 准入还按申领值的 60% 判断；低空闲内存预算不代表可同时放行多个超预算测试，测试树数量仍受独立 slot 资源约束（[ResourceManager 实现](https://github.com/bazelbuild/bazel/blob/9.2.0/src/main/java/com/google/devtools/build/lib/actions/ResourceManager.java)）。原生 UI 的 `running` 与 profile 的 `local action execution` 包含资源等待，不能据此认定测试进程同时运行；实际并发以 `Local execution process wall time` 中 `TestRunner` 的重叠区间和 `Resources acquired` 区间核对（[本地执行边界](https://github.com/bazelbuild/bazel/blob/9.2.0/src/main/java/com/google/devtools/build/lib/exec/local/LocalSpawnRunner.java)）。
