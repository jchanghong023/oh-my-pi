## 1. 背景与用户目标

### 1.1 背景

用户在开始修改代码前，可能只有一份初步需求、一段问题描述，或者一个尚未确定的设计方向。理解任务需要同时查看需求文档、公司内部 wiki 和现有代码，确认目标、现状、内部约束及相关调用关系。

本命令要解决的是：不要让方案只建立在一个代理的一次调查和第一份设计上。多个代理分别接触一手资料、独立形成判断，再检查彼此的遗漏与错误，最后得到能够说明依据和取舍的方案。代理可以使用不同模型，也可以使用同一模型的独立上下文；模型数量不等于代理数量。

典型使用环境中，各模型能力可能不完全一致。因此，多个代理负责提供独立调查、候选思路和反例，用户选定的最强主代理负责核实证据和最终综合；不能用多数票代替判断，也不要求必须配置多个不同模型。

### 1.2 用户目标

- **把问题弄清楚：** 明确需求、现状、约束，以及仍然缺少的信息。
- **把方案想充分：** 获得多个代理独立形成、经过交叉审查的方案。
- **把取舍看明白：** 知道方案为什么成立、主要差异是什么、风险在哪里。
- **把选择变简单：** 有明确优势时给出推荐及理由，不人为增加备选方案。
- **把完成条件说清楚：** 在实施之前明确验收标准和需要先核对的关键前提。

用户不需要手动创建团队、分配审查任务或转发各代理的讨论内容，也不需要在流程中途回答问题。日常只需要提出问题，并在结果落地后选择方案或追问。

### 1.3 范围

`/team` 负责分析问题、讨论设计和形成计划，不负责执行计划。用户选择方案后，本次规划流程结束，后续实施不属于本命令的功能范围；选择 MUST NOT 被解释为修改代码的授权。

`/team configure` 是用户主动操作的配置管理入口，不属于只读讨论流程，不启动模型调用；用户确认保存只授权修改当前 profile 的 Team 成员配置。它不开放讨论子代理的写权限，也不授权实施任何讨论方案。

## 2. 功能需求与规则

### 2.1 功能入口与运行模式

命令形式为：

```text
/team <问题或需求>
```

用户可以直接描述问题，不要求填写固定表单，也不要求先指定分析、诊断、规划等子模式。`/team` 是用户主动选择的多代理讨论入口，不设按任务大小自动分流为单代理流程的规则。

运行模式约束：

* 输入只有 `/team` 而未说明任务时，提示补充问题或目标，不猜测用户要分析什么。
* 运行中 MUST 让用户看见当前阶段和各参与代理的完成、失败状态，并允许用户取消本次讨论（见 5.4）。
* 提交携带的图片不进入讨论（子代理不接收图片）：Enter 与 Ctrl+Enter 路径均在等待异步 input hook 前分离本次提交的图片；压缩队列和循环重放保留该草稿所有权。派发成功时随命令一并消费，不泄漏到用户下一条消息；派发失败时连同提交文本完整还原，并与派发期间的新草稿合并，保持文本与图片标记对齐，不覆盖用户新输入的文本或图片。

### 2.2 参与者与模型配置

参与者名单由一个专门的设置项定义：

* **设置项 `team.members`**：有序模型 ID 列表（完整 ID，如 `company/GLM-5.2-public`，或已有的精确别名）。解析遵循既有完整 ID／别名规则，MUST 保留输入顺序及重复项；同一模型的多个名称解析到同一实例时也不合并。未设置或设置为空数组均视为**未配置**。
* **未配置时**：以当前会话模型作为单项基础名单；`OMP_OFFLINE=1` 与普通启动行为相同，不自动选择 company 或同家族模型名单。
* **显式配置时**：只使用配置的有序基础名单，不自动追加当前会话模型，也不与会话模型取并集或去重。

提案者槽位与角色：

* 基础名单长度为 `M`（未配置时为 `1`），提案代理数为 `N = max(3, M)`。从 `i = 0` 开始，槽位 `i` 使用基础名单的第 `i % M` 项，按顺序循环分配：`A → AAA`、`AB → ABA`、`ABC → ABC`、`ABCD → ABCD`；这里字母表示模型，右侧每个字母表示一个独立提案代理。配置中的重复项仍占据自己的槽位。
* 每个槽位都有唯一索引与标签（`A`…`Z`、`AA`…`AZ`、`BA`…），不设置 26 槽位上限；标签与阻断 ID、审查路由及报告归属一致，并创建独立子上下文。相同模型的多个槽位 MUST NOT 共享调查上下文或复用提案结果。模型种类数不决定代理数；并发限制只影响排队，不截断名单或减少槽位。
* **主代理 = 发起 `/team` 的当前会话模型**。"最强"是使用前提而非机制判断：系统不存在模型能力排序，用户应在综合能力最强的模型会话中发起 `/team`。主代理承担阶段二对齐子调用与阶段五综合子调用，本身不充当审查者或修订者；当前会话模型可以不在显式提案名单内。
* 配置中的模型或当前会话模型不存在、不可用或被禁用时，报错指出具体项，MUST NOT 静默剔除后继续；模型可用性与筛选统一采用上游规则，不维护 fork 专有的硬排除策略。当前会话模型即使不在提案名单内，仍必须单独通过身份与可用范围校验。
* 所有槽位模型及当前会话模型必须支持前端机械限制的只读工具集与结构化 `yield` 输出。JchTools 等由后端 Agent 自行执行工具的通道不满足该能力边界：当前会话模型或配置成员命中时，必须在任何讨论子调用开始前明确报错，不静默剔除、降级或派发后端执行；当前会话模型不在显式名单内也不能绕过此检查。

### 2.3 只读边界（机械保证）

从命令发起到方案输出，以及后续澄清、追问和方案选择，均属于只读规划过程：

* 所有子代理（提案、审查、修订、对齐、综合）的工具集由代码**机械限制为只读**（`read`、`grep`、`glob`、`wiki`、`repo`、`ast_grep` 与 yield；其中工具仍受各自 enabled 设置限制，不含写文件、bash/eval 执行、task 委派等）。`ast_grep` 是已注册的 read 审批级别工具，不是可变更源码的 `ast_edit`。这是程序保证，不是提示词要求。
* 不创建、修改、删除或移动项目文件、需求文档、公司文档和项目配置；不安装依赖、不运行构建或测试、不更新文档索引、不提交或推送。
* 独立子代理只可读取自己的会话材料；普通文件路径、内部 URL、选择器、目录检索及符号链接均不得绕过其他代理原稿与转录的隔离。自己的材料与普通项目源码仍可读取；包含其他代理材料的祖先目录不得用于枚举或递归搜索。
* 禁用 MCP 的受限子会话不得通过进程全局 manager、未注册 scheme 或未知 `skill://` 回退读取 MCP 资源；普通会话已启用的原有资源读取能力不变。
* 只读子会话初始化不得改变 Repo 索引的新鲜度、变更序号或未核验状态；允许查询既有索引，不因启动会话挂载写入类索引生命周期。
* 可以读取资料、检索内部 wiki、检查代码及接口定义，并在回复中提出修改建议和验证方法。
* "修订方案"是修改讨论中的方案内容，不是修改项目文件。
* 用户选择方案不等于授权立即实施。

正常的会话记录不属于项目修改。原稿、证据和修订结果 MUST 能在本次讨论中回查（见 5.5）。

### 2.4 编排形态：全程序化编排器

`/team` 采用**代码驱动的编排器**实现，五个阶段全部由命令代码推进；用户交互只发生在两端——命令输入，以及结果落地后的普通聊天轮次。流程中 MUST NOT 向用户提问或等待用户输入。

代码机械保证（不是指令约束）：

| 保证 | 实现方式 |
| --- | --- |
| 独立调查隔离 | 各提案子代理由代码以相同输入并行创建，互不可见，不存在共享摘要 |
| 审查匿名 | 审查 prompt 由代码构造，不含作者模型名、支持人数或推荐顺序 |
| 两轮上限 | 修订轮数由代码计数，第三轮直接拒绝 |
| 阻断门禁 | 审查意见与修订回应为结构化输出，代码追踪未解决阻断问题；受影响方案无论综合文本如何，机械标注"尚不可采用" |
| 只读边界 | 子代理工具集机械限制（见 2.3） |

需要模型判断的环节（对齐、综合）由代码以**当前会话模型**发起拼装上下文的子调用完成；编排器不经过主代理的 Task 工具派发（程序化调用路径直接指定各子代理的模型）。

### 2.5 固定工作流程

```text
独立调查 → 对齐与比较 → 交叉审查 → 修订与复核 → 汇总方案
```

#### 阶段一：独立调查

**目标：** 让每个提案代理从一手资料形成自己的判断。

代码为每个提案槽位启动新的提案子代理（受 `task.maxConcurrency` 约束，超限槽位排队而不省略），各自独立完成：

1. 阅读用户指定的需求文档及相关用户说明。
2. `wiki` 可用时优先搜索企业内部文档 Markdown 数据库，查找与任务相关的规范、术语、历史方案和接口约定。
3. `repo` 可用时优先查询代码仓索引定位实现，再读取当前代码、接口定义和实际调用，确认现有行为与影响范围。
4. 提出方案或诊断结论，说明依据、关键假设、主要风险及验收建议。
5. **显式记录自己对需求歧义的理解与假设**（哪些需求点存在多种解读、本方案采用哪一种）。

各子代理接收相同的用户问题、明确约束和资料入口，但检索路径与分析结论分别形成。不能先由一个代理调查，再让其他代理只依据它的摘要出方案；即使全部槽位使用同一模型，也必须独立调查。

初稿必须区分事实、推断和假设。没有足够依据时，可以报告未形成可行方案；MUST NOT 为了交出答案虚构接口、规范或代码行为。

**阶段结果：** 各提案代理的原始方案（结构化输出，所有文字字段合计 ≤ 4000 字，含证据来源，不计布尔值与状态枚举；字段上限保留，解析端超预算整份拒绝，不截断正文或证据），含证据、关键假设、风险、未知项、验收建议与歧义理解记录。审查输出另受 ≤ 1500 字正文预算约束，计入摘要、全部 findings 文字与逐条裁决依据，详见 5.1。

#### 阶段二：对齐与比较（后置澄清，不中断）

**目标：** 统一可查清的部分，把不可查清的理解差异显式化，让真实差异可见。

代码以当前会话模型运行一次**对齐子调用**，输入为用户原始问题与全部提案，结构化输出：

1. **统一的需求理解（可查清部分）与共同验收标准。** 各提案的验收建议用于发现遗漏，但不能各自定义一套较容易满足的标准。
2. **事实差异清单：** 各提案在接口存在性、规范适用性等事实上的矛盾，标注需回查的来源位置（交由阶段三审查者回查、阶段五核实）。
3. **需求理解差异清单：** 只列各提案实际不同的理解及其对方案与验收的影响；仅当资料无法消除且不同理解会改变选择时标为实质差异。共同未知项保留在统一理解中，同义表述或补充细节不算理解差异。

统一需求与验收标准是对原始要求及已确认适用约束的解释，不是新的上位要求。审查、修订与综合均 MUST 区分用户原始要求、已确认适用的强制约束和对齐阶段的解释；对齐解释 MUST NOT 静默增加、删除或放宽前两者。出现冲突时回查原始请求与来源、确认适用范围；仍无法消除的歧义保留为差异，不盲从对齐摘要，也不采用“用户要求无条件覆盖一切规范”的规则。

统一理解、验收及差异描述只陈述需求、事实与观点；方案标签仅用于说明事实或观点归属，不夹带作者身份、模型名、支持人数、共识或推荐排序，避免对齐摘要向匿名审查泄露支持关系。

本阶段 MUST NOT 向用户提问、MUST NOT 中断流程。对方案差异的处理：

* **事实差异**回查来源确认，查不清的标为未知，不靠辩论决定真假。
* **设计取舍**（如少改代码与更清晰的模块边界）保留到最终比较。
* 相似方案可以归类展示，但 MUST 保留原稿、依据和重要差异；不能仅因标题、技术选型或表格中几项相同就认定方案等价并删除候选。

理解差异的处理后置到阶段五呈现（见 2.7）：实质影响选择的差异，须在结果正文前置顶提示用户先回答差异、带答案重跑 `/team`。

**阶段结果：** 统一的需求理解与验收标准、事实差异清单、理解差异清单。

#### 阶段三：交叉审查

**目标：** 检查方案是否有事实错误、遗漏或不能成立的关键前提。

每份拟作为最终选项的方案安排 **1 名新的审查子代理**。分配规则由代码机械执行：按提案槽位顺序轮转指派给**下一个不同模型**的参与者；所有槽位都使用同一模型时，由同模型的新子代理审查，仍不复用提案上下文。

审查者可见：用户原始问题及明确约束、共同需求与统一验收标准（标明其属于对齐解释）、待审方案、关键假设、事实差异清单（协助回查）、原始资料入口；可回查完整提案、wiki 和代码。审查 prompt 由代码构造，MUST NOT 包含作者模型名、支持人数或预先推荐顺序。

即使所有代理只提出同一种方向，也要审查其共同前提；不能以"大家一致"代替审查。审查重点：

* 是否误读或遗漏用户需求、适用规范和必须保持的行为。
* 对接口、代码、调用关系的判断是否有事实错误。
* 哪些关键假设一旦不成立，就会使方案失败。
* 是否存在影响正确性、兼容性或可实施性的实质风险。
* 方案是否能够满足共同验收标准。

每条反驳必须说明对应方案、具体问题、影响及依据，并区分**阻断**、**重要**和**次要**问题。已有事实应提供可回查的资料位置；新设计可以使用明确的逻辑推导或反例，但 MUST NOT 冒充已运行的验证结果。允许返回"未发现实质问题"，不必凑问题数量；没有发现问题也不等于证明方案绝对正确。

**阶段结果：** 结构化审查意见（每份正文 ≤ 1500 字），问题分级、有依据、有影响说明，或明确记录未发现实质问题。模型新报的问题不携带 ID；整份审查校验通过后，由代码为每条问题分配提案内唯一、不可变的 ID（如 `A-F1`、`A-F2`），不按问题文字匹配或合并；同样文字的问题也可以是不同 ID。初审 `blockingResolutions` 必须为空。

#### 阶段四：修订与复核

**目标：** 处理有效问题，确认关键修改没有引入新的错误。

代码将最新成功审查的问题与仍未解决的阻断问题按 ID 取并集，路由回该方案的**提案模型**（新子代理）。作者通过 `responses[].findingId` 对每个给定 ID 恰好回应一次：接受并修订、举证说明不接受、保留为真实取舍，或说明仍无法解决，并提供非空解释；未知、重复、缺失 ID 或空解释的回应无效，不回退到自由文字匹配。对不成立的质疑，不要求修改原本正确的方案。不能只回复"已解决"，不能降低验收标准绕过问题；作者回应本身不关闭任何阻断。

修订回应为结构化输出，包含：修订后的方案、修改内容与理由，以及**复核标志**——

* 是否修改了核心设计、接口、数据变化或兼容策略；
* 是否声称解决了已确认的阻断（或严重）问题；
* 是否有新证据改变了关键假设、需求理解或适用约束；
* 是否举证反驳已有阻断问题（原 fork 契约中的第四标志，同样必须触发复核）。

代码按标志机械决定复核：任一标志为真时，安排**新的审查子代理**复核受影响部分；全部为假时不复核，不强凑修订轮次。复核结论由代码收集后交综合阶段使用，作者 MUST NOT 自行宣布关键问题已关闭。**必需复核失败（子代理失败、超时或输出不合法）时，当前修订版 MUST 标为"尚不可采用"并附原因，MUST NOT 沿用修订前审查的可采用状态；后续轮次的复核成功可以恢复其资格。**"初次审查没有记录阻断"不等于"修订版已经过审查"。

复核基线是最后成功完成审查的方案。必需复核失败后，不推进基线、不丢弃待核实的修订；下一次复核同时获得该基线、其后全部修订与审查材料，不能仅检查第二轮新增部分就恢复资格。

复核与阶段五综合均仅在历史修订正文与提示词已展示的当前正文相同时使用 `current` 引用；复核还可对与最后成功审查正文相同的历史修订使用 `previous` 引用，两处展示正文相同时不再重复。其余历史正文不做全局去重；累计未复核的中间版本、逐 ID 回应、审查依据与失败状态 MUST 保留。去重只作用于提示词投影，不改变原始会话材料、输出 schema 或阻断追踪。

每次复核必须在 `blockingResolutions` 中对传入的每个未决阻断 ID 恰好裁决一次，字段为 `findingId`、`status`（`resolved` 或 `unresolved`）及非空 `basis`。只有对应 ID 的有效 `resolved` 裁决才能关闭该问题；部分修复仍为 `unresolved`，依据须说明残余问题。复核发现的新问题另行报告，由代码分配新 ID；MUST NOT 自造或复用 ID。`noSubstantiveIssues` 只表示没有新增实质问题，`findings=[]` 或“没有新增问题”不能关闭历史阻断。

未知、重复或缺失裁决 ID、空白依据、格式错误或旧版整体状态字段均使整次复核无效，保守保留原阻断并走既有必需复核失败路径，占用本轮，不分配新问题 ID、不推进成功基线、不覆盖历史证据；第二轮有效复核仍可按上述规则恢复资格。

**轮数规则：** 每份方案最多两轮"修订与必要复核"，由代码计数；达到两轮仍有阻断问题时，停止循环并将该方案标为**尚不可采用**。必需复核未完成时同样占用轮数：允许用第二轮修订再争取一次复核，但两轮结束时仍未复核完成的方案保持"尚不可采用"。"没有新增问题"不等于旧问题已解决；"达到轮数上限"不等于通过；MUST NOT 通过重命名方案或重开讨论绕过上限。

**阶段结果：** 最新方案、审查意见处理结果、复核结论，以及已解决或仍未解决的关键问题。**提案的结构化字段（关键假设及其"若不成立"影响、主要风险、未知项、证据）MUST 原样传递给对齐、审查（含复核）与综合提示词**——这些子代理是新建且上下文隔离的，未显式传入的材料等于丢失。

#### 阶段五：汇总方案

**目标：** 给用户提供能够据此作出选择的结果。

代码以当前会话模型运行**综合子调用**，输入为：用户问题、统一验收标准、全部最新提案（含修订）、审查处理结果、事实差异回查结果、理解差异清单、各方案未解决阻断问题标记。综合先核实关键证据、检查硬约束，再比较真实取舍：

综合输入保留每一轮修订的逐项 ID 回应、理由、证据、复核的逐 ID 裁决与依据及失败状态；后续成功不会覆盖历史材料，历史失败也不等于当前方案仍然受阻。综合 MUST 在最终选择前重新核对用户原始要求及已确认适用的强制约束，不以对齐解释替代原文。

* **硬约束**来自用户明确要求、确认适用的强制规范、必须保持的兼容约定，以及据此形成的共同验收标准；对齐解释本身不能改变其范围。违反硬约束或仍有未解决阻断问题的方案，MUST 标注"尚不可采用"——该标注以代码按 ID 追踪的状态为准；综合文本与此矛盾时，以结构化追踪覆盖。
* 综合输出中实际展示的正文、推荐理由或推荐前提自行写入 `【推荐】` 标记，或声称结构化追踪已否决的方案可采用时，视为综合结果无效，报告流程未完成；不得把相互矛盾的文字与状态表一起交给用户。门禁与 TUI Markdown 共用一次 HTML 实体解码的可见文字语义。明确否定采用或说明解除阻断后方可采用的条件语句不属于肯定推荐；条件只作用于对应分句，不覆盖其后的无条件采用声明。
* 综合新确认的硬约束违例 MUST 通过 `hardConstraintViolations` 提交已有方案标签、具体问题与依据；代码使用该提案的同一 ID 分配器追加带 ID 的阻断，保留问题与依据并补充影响及针对部分，不新增候选、不解除既有阻断、不绕过追踪。标签不存在或问题、依据为空时，综合结果无效。
* 通过硬约束后，再比较风险、复杂度、修改范围、兼容性、维护负担和可验证性等取舍。比较必须说明理由，不采用多数票，不能用低工作量抵消正确性缺陷。
* 只能汇总经过审查的方案；MUST NOT 在最后拼接多个候选生成未经审查的新设计再称其已通过。
* 最终方案数量不固定：先直接回答用户问题，共同结论、依据与验收只写一次；同方向方案可归类展示并保留标签、适用条件和重要差异，不因侧重点不同制造独立备选。存在多个实质不同且有选择价值的方案时分别展开；没有可采用方案时明确说明原因，不拼接未经审查的新设计。
* 综合正文默认以 ≤ 2000 字为写作目标；只展开影响选择的差异，必要的阻断、歧义、依据与采用条件不得因篇幅省略。保留现有 12000 字硬上限，不新增截断或失败路径。
* 有明确优势时，将最合适的方案标记为 **【推荐】**，说明推荐成立的前提和理由；没有明确优选时，直接说明取舍条件，不勉强指定赢家。

**阶段结果：** 最终 markdown 消息（见 2.7），交由用户决定。

### 2.6 证据与关键假设

#### 2.6.1 不混淆现状、目标和规范

需求文档说明目标，代码说明现状，确认有效的公司规范说明必须遵守的约束。三者冲突时应识别冲突及适用范围，不设"代码永远高于需求"之类的固定覆盖顺序。计划新增能力，不应因现有代码尚未提供而被直接否决；但方案 MUST NOT 把尚不存在的能力当作已存在且可直接调用的能力。

#### 2.6.2 不把意见当证据

模型之间相互同意、作者自评有信心、综合子调用的设计偏好，都不能代替事实依据。反驳的严重程度也不是自动否决理由；问题必须真实且影响成立，才据此要求修订或排除方案。

#### 2.6.3 关键假设必须说明状态

关键假设指"一旦不成立，方案就需要明显改变或不能采用"的前提。每项必须说明内容、现有依据、验证状态和错误时的影响。能通过只读资料核查的，应在流程中核查；只能在实际执行环境验证的，列为执行前检查。有执行前待验证条件的方案可作为**有条件方案**展示，但 MUST 清楚标出条件；已被证伪的前提 MUST NOT 仅通过列入"执行前检查"变成可接受条件。

对需要运行时验证的关键假设，验证建议 MUST 给出**待验证主张、具有区分力的输入或观察、哪些结果支持／反驳／仍不足以判断，以及各结果对采用方案的影响**。方法应能区分相关竞争解释或检查关键前提，不能只写“重跑看看”。不强求每项检查都能双向证明，不把未复现当作不存在；结果不能区分解释时如实保留未决状态及采用条件。只读流程只提出方法，不因此获得执行测试、命令或修改环境的权限；没有必要的检查不凭空制造。

#### 2.6.4 内部文档与代码仓索引检索

* **必须使用与优先级：** 所有阶段的子代理（包括对齐、修订、复核与综合）均须在提示词中强调：`wiki` 可用时 MUST 优先搜索企业内部文档 Markdown 数据库；`repo` 可用时 MUST 优先查询代码仓索引。各独立提案代理必须自行检索，不能以其他代理摘要替代。
* **Wiki 证据：** 直接依据数据库返回的入库正文、索引名、路径与行号，不为核实命中重读原 Markdown 文件。未命中不证明公司没有相关规定；历史文档不自动代表当前有效规范。
* **Repo 证据：** 用于定位代码文本与 Python 定义候选；依赖命中内容前 MUST 读取当前源码。索引不提供调用图，不能据此推断调用关系、修改影响或代码不存在；穷尽结论仍用当前源码及 `grep` 核实。
* **禁止猜测：** 不懂或未确认的术语、规范、接口和代码行为 MUST 先检索核实；仍无依据 MUST 标为未知并说明证据缺口及影响，NEVER 用猜测补齐事实。
* **不可用与错误：** 工具禁用、缺索引、查询失败和正常零命中必须区分并如实说明；必要时改用可用的只读工具。不因检索需要创建、更新、重建或删除索引。
* **本子调用内止损：** 各代理仍自行检索；确认缺索引后不重复探测。命中明显偏题时定向调整，仍无相关证据则转当前源码；无新线索不重复等价查询。不得将此结论扩展为整个 Wiki 无关或不存在规范，也不共享其他提案代理的调查摘要。

### 2.7 用户可见结果与方案选择

最终结果以**一条 markdown 聊天消息**呈现，用户不需要阅读各子代理的中间过程：

| 内容 | 要求 |
| --- | --- |
| 需求与验收标准 | 说明共同目标、必须满足的条件及如何确认完成；共同内容不在每个方案中反复抄写 |
| 核心方案 | 说明采用什么方向、主要实施步骤和影响范围，不输出详细实现代码 |
| 关键依据 | 列出支持方案的重要需求条款、wiki 或代码位置 |
| 主要取舍 | 说明与其他候选的实质区别及适用条件 |
| 风险与关键假设 | 说明已确认风险、未验证前提和仍有分歧的事项 |
| 执行前检查 | 说明待验证主张、判别性输入或观察、支持／反驳／仍不足以判断的结果及其采用影响；没有时不制造检查项 |
| 未解决阻断 | 展示代码追踪的 ID 与具体问题；部分修复保留残余问题，不以作者回应或综合文字替代关闭裁决 |
| 推荐理由 | 仅在标记【推荐】时给出，说明依据和前提 |
| 需求理解差异 | 阶段二识别的理解差异清单；实质影响选择的差异 MUST 置顶提示 |
| 未采纳方向 | 必要时简述重要候选被淘汰或暂不可采用的原因，不倾倒讨论记录 |

消息尾部固定附带**收尾契约**（原文形式）：

> 选择方案请直接回复（如"选择方案 A"）。选择仅确认该方案、其验收标准与执行前检查，不触发实施；如需修改代码，请另行明确要求。若存在影响选择的"需求理解差异"，请先回答该差异并带答案重跑 `/team`，不要在不同前提的方案间盲选。

后续交互规则：

* 用户的选择与追问由主代理在**普通聊天轮次**中处理，依据落在会话里的最终结果消息作答；不重跑无关调查，不把追问当成执行授权。
* 对"原因是什么"类诊断请求，先回答根因是否已确认，再说明证据和后续核查方法；未经验证的根因不作为让用户任选的方案。
* 追问或补充约束导致核心方案变化时（实质需求变化），MUST 提示带约束重跑 `/team`，MUST NOT 沿用旧方案的通过结论或旧推荐。

### 2.8 异常与结束规则

| 情况 | 必须呈现的结果与行为 |
| --- | --- |
| 输入只有 `/team`，未说明任务 | 提示补充问题或目标，不猜测 |
| 未设置 `team.members` 或设置为空数组 | 两种启动模式均以当前会话模型建立三个独立提案槽位，不要求先配置，不自动加入 company 名单 |
| `team.members` 中模型或当前会话模型不存在、不可用或能力不受支持 | 在首个子调用前报错指出具体项，不静默剔除；会话模型不在显式名单内也必须检查 |
| 指定文件缺失或位置不明确 | 说明缺失或歧义并结束本次运行，由用户修正后重跑；不编造文件内容 |
| 内部 wiki 不可用或未取得关键资料 | 说明哪些约束尚未核实及对结论的影响；影响方案成立时不得判通过 |
| 某个提案/审查/修订子代理失败、超时或未完成 | 该参与者如实标失败，其余参与者的结果继续处理；参与不完整 MUST 在结果中标明；失败 MUST NOT 被理解为同意或"未发现问题" |
| 对齐或综合子调用（会话模型）失败 | 报告流程未完成并结束，不输出半成品结论 |
| 无法完成必要审查（如审查模型全部失败） | 明确报告流程未完成，不静默改成单代理并宣称团队流程完成 |
| 理解差异实质影响选择 | 结果正文前置顶提示"先回答差异、带答案重跑"，不在不同前提的方案间让用户盲选 |
| 只剩一个可采用方案 | 输出一个方案及依据，不补造第二个 |
| 所有候选均不可采用 | 输出原因和需要补充的信息，不制造推荐，不自动重开讨论 |
| 两轮后仍有阻断问题 | 该方案标"尚不可采用"并保留未决问题，排除在已通过选项之外 |
| 用户中途取消 | 停止本次讨论，取消传播到所有在跑子代理，不继续调查、修订或选择 |
| 用户事后改变需求或关键资料已变化 | 受影响结论不标有效；实质变化按重跑处理 |

正常完成指：独立调查、对齐、必要审查和修订已结束，编排器输出有依据的方案结果或明确的不可行结论。流程完成不代表必须存在推荐方案；资料缺失、模型失败或用户取消导致必要步骤未完成时，MUST 与"已完成分析但没有可行方案"区分。

| 模型选择器 | 搜索名称、ID、provider 及已核实的中文别称／简称；同名跨 provider 的候选明确显示来源，由用户确认具体项 |
| 运行预览 | 通过共享服务的只读草稿预览同时展示当前生效配置、拟保存用户名单及考虑高层覆盖后的预计有效槽位，按 `N = max(3, M)` 保留顺序、重复及默认回退；不写盘、不把预览当成已保存 |
| 操作区 | 保存、恢复默认、取消；恢复默认把草稿设为 `[]`，仍需保存确认，不立即写盘 |

* 同一模型可反复添加或复制，新增时明确提示这是另一个独立代理槽位，不自动去重；排序只影响草稿，不逐次写配置。
* 已保存但失效、被禁用或目录中消失的成员保留其原始 selector 并标错，允许替换／删除，不因候选过滤而静默丢失。主模型不受支持时显示独立问题，不擅自替换主模型；成员配置可保存不等于当前会话已具备运行条件。
* 搜索只筛选真实候选；自然语言辅助匹配沿用第 4.6 节，不按相似度自动选第一项。可唯一核实的映射可供普通 Agent 代配直接采用，TUI 搜索仍由用户确认；多解或缺失不能拼造 ID。保存及落盘使用具体模型身份，不使用自然语言字符串。
* 打开面板后仅编辑本地草稿，保存时一次提交完整有序列表；取消不写盘。有未保存修改时退出须明确保留在面板或放弃，不隐式保存。支持键盘完成全部操作、滚动和窄终端显示，长 ID 不得导致来源、状态或关键操作不可辨认。
* 保存版本冲突时保留草稿，允许重新读取并比较后再次提交，不自动覆盖外部更新。收到外部设置变化通知且草稿已修改时只提示变化，不直接替换草稿；切换会话／profile 后丢弃迟到响应，不把旧草稿写入新上下文。
* GUI 草稿变化调用只读草稿预览（字段契约即 `omp-config-extension` 的 `get_team_config` preview data 结构，见 [ZCode 接入需求](rpc-ui-protocol.md#team-模型配置接口规划未实现)），由共享服务计算结果；TUI 调用同一只读方法，不在两端复制运行模型选择／槽位算法。请求携带并回传草稿 `clientRevision`，只展示仍匹配当前会话和草稿版本的结果；无法解析的保留槽位可参与只读诊断，但修复／移除之前不能作为具体模型写入。
* 完整保存、保存但被高层覆盖、部分保存、结果未知须有可区分提示；Linux offline 展示活动与持久两处结果。保存只影响随后启动的 Team，不改变正在执行的讨论及当前主模型。

#### 2.9.3 与 GUI 的职责边界

TUI、GUI 与普通 Agent 代配共用模型目录资格、成员校验及保存服务。GUI 管理布局和草稿，OMP 返回候选、有效来源、版本、槽位与保存结果；GUI 不读写 YAML、不推导 shm 路径、不访问数据库或复制凭据。RPC v3 wire 已随独立 RPC 场景退役；ZCode 协议侧经 `omp-config-extension`（`session/configure` operation）接入，GUI 待外部 ZCode 侧实现，字段契约与细节见 [Team 模型配置接口（规划）](rpc-ui-protocol.md#team-模型配置接口规划未实现)。

## 3. 需求验收条件

以下条件用于判断 `/team` 是否满足本规范：

1. 用户通过一个自然语言命令即可发起完整流程，不需要管理团队成员、转发消息或在中途回答问题。
2. 各提案槽位从一开始独立读需求、查 wiki、查代码，不依赖任何代理的统一分析摘要——由代码以相同输入、独立上下文、互不可见的方式机械保证；并发超限仅排队。
3. 所有最终方案在各自**显式声明的需求理解**下比较：可查清部分使用统一验收标准；无法查清的理解差异在结果中作为一等输出呈现，实质影响选择时提示带答案重跑；相似方案归类不丢失原稿和重要差异。
4. 每份最终选项经过新子代理的交叉审查（代码轮转分配、匿名构造 prompt），允许"未发现实质问题"结论；有效反驳得到处理，无依据意见不自动否决方案。
5. 修订与复核最多两轮（代码计数，第三轮拒绝），关键修改按结构化标志触发新子代理复核；阻断按代码生成的不可变 ID 逐条裁决，部分修复仍未决，无效复核占用轮次且不丢历史，作者不能自关闭；未解决阻断问题的方案机械标注"尚不可采用"。
6. 综合子调用回查原始要求与适用硬约束、区分对齐解释，依据证据比较，不多数投票、不强凑方案、不在汇总时增加未经审查的新设计；"尚不可采用"标注以结构化追踪为准，综合发现的违例只追加带 ID 阻断、不解除既有阻断。
7. 结果能让用户看清方案、依据、取舍、风险、验收标准、执行前条件与需求理解差异；运行时关键假设附有可区分解释的验证方法及支持／反驳／不足以判断的采用影响，有明确优势时给出推荐理由。
8. 澄清、追问和选择不触发实施，全程不修改项目文件（子代理只读工具集机械限制）；失败、未知和未完成状态如实说明。
9. 提案槽位严格保留基础名单顺序和重复项，按 `N = max(3, M)` 循环分配；`A/AB/ABC/ABCD` 分别生成 `AAA/ABA/ABC/ABCD`。两种模式的空／未配置名单都使用当前会话模型生成三个独立槽位；显式名单不自动追加会话模型。
10. 当前会话模型继续执行对齐与综合，即使不在提案名单内也通过身份、可用范围、只读工具及结构化输出能力检查；槽位标签唯一，同模型多槽位的原稿与审查路由不混淆。
11. 五阶段及复核子代理实际允许使用启用的 `wiki`／`repo`，并遵守 2.6.4 的优先检索、当前源码核实与未知信息处理规则；增加索引查询能力不开放任何项目写入或索引管理权限。

## 4. 用户用例与命令

### 4.1 按初步需求形成实现方案

**用户输入：**

```text
/team 按 api.md 的初步需求，给出实现方案
```

**预期行为：** 各提案代理独立阅读 `api.md`、搜索内部 wiki、查看相关代码并提出方案（各 ≤ 4000 字、显式记录歧义理解，超并发上限时排队）；对齐子调用统一可查清部分并列出事实与理解差异；每方案 1 名新代理审查，优先按规则轮转到不同模型、全部同模型时使用同模型的新上下文；修订按标志复核；综合子调用输出结果。全程不向用户提问。

**结果：** 一个或多个有依据的方案，包含主要步骤、差异、风险、验收标准和执行前检查；有明确优势时标记【推荐】；存在实质影响选择的理解差异时置顶提示带答案重跑。

**用户选择：**

```text
选择方案 A
```

**选择结果：** 主代理确认采用方案 A 及共同验收标准，说明尚未验证的前提，结束本次方案选择；不修改代码。

`api.md` 只是示例文件名。用户可以指定其他需求文档，也可以直接在命令中描述需求。

### 4.2 分析问题原因

```text
/team 这个接口偶尔返回重复结果，结合相关代码和内部文档分析原因
```

预期输出已确认的事实、可能的原因、各原因的证据和缺口。只有证据充分时才确认根因；证据不足时给出需要补充的资料或验证方法，不为凑答案认定根因。

### 4.3 提出问题解决方案

```text
/team 这个模块处理大文件时内存占用过高，给出解决方案
```

各提案代理独立调查相关路径与约束，再比较可行处理方式。结果说明各方案的依据、预期影响、需要保持的行为和验证要求；MUST NOT 虚构尚未实测的性能提升。

### 4.4 比较设计方向

```text
/team 新功能应该扩展现有模块，还是增加独立模块？结合需求、wiki 和代码给出方案
```

重点核查两条路径分别依赖什么条件、能否满足同一目标，以及变更范围与维护成本等差异。用户提出两个方向不代表最终必须保留两个；调查发现其他合理方向时，同样进入审查流程。

### 4.5 对方案追问或补充条件

```text
方案 A 为什么比方案 B 更适合当前需求？
```

主代理基于结果消息回答具体比较依据，不重跑无关调查，不把追问当成执行授权。

```text
补充一个约束：旧接口行为必须保持不变。
```

该约束属于实质需求变化：主代理提示带约束重跑 `/team`（如 `/team 补充约束：旧接口行为必须保持不变。<原问题>`），MUST NOT 直接沿用旧审查结论或旧推荐。

### 4.6 内置使用指南与 Agent 代配

* 提供 [Team 使用指南](../../docs/team.md)，由既有 `docs/**/*.md` 收集与打包机制暴露为 `omp://team.md`；说明命令用法、主模型与参与名单区别、多模型配置和默认槽位规则，并按第 2.9 节已实现的 `/team configure` 入口说明配置操作及其验收边界。
* 用户在普通聊天中授权代配后，Agent 须查询目标环境及 profile 的真实模型目录，将用户自然语言名称、简称、版本及规模解析到实际可用的完整 selector；唯一匹配直接采用，实质歧义列出候选并确认，缺失项如实报告，不拼造 ID、不静默替换版本或 provider。保留用户顺序及明确重复项，检查允许范围与主模型能力，不能把配置任务派给只读 `/team`。
* 指南须区分主设置 `config.yml` 与 provider 定义 `models.yml`，说明 profile、项目及 overlay 覆盖；配置只修改授权字段并读回有效值，不为代配自动发送真实模型请求。
* offline 代配的双端保存必须遵循[用户配置的 shm／NFS 双写权威要求](offline-shm.md#23-用户配置的-shmnfs-双写权威要求程序实现待验收)，覆盖同一 profile 的授权字段；涉及自定义 provider 时其模型文件变更也按该要求处理。代配不能以后台备份代替原始配置写入，不能引入启动回源或自动恢复。

## 5. 实现与集成约束

### 5.1 命令与编排器

* 命令名 `/team` 为有意决策（非 `jch*` 前缀）：接受未来上游同名命令的注册冲突风险，发生时再处理（改名或合并），不预防性改名。
* 命令经 fork 自有命令注册路径注册；编排器为代码驱动的阶段状态机，经程序化子代理生成路径创建子会话（`runSubprocess` 层的 `modelOverride` 直指各子代理模型），不经主代理 Task 工具。
* 对齐子调用与综合子调用使用当前会话模型、拼装上下文，不要求该模型出现在显式提案名单中；提案、审查与修订按各自槽位及既有轮转规则选择模型，不增加角色或人格要求。
* 结构化输出贯穿全程：提案、审查意见、修订回应（含复核标志）、对齐与综合结果均为 schema 约束输出。提案所有文字字段（含证据来源）合计 ≤ 4000 字，不计布尔值与状态枚举；超预算整份拒绝，不截断正文或证据。综合指定非空推荐标签时，推荐理由必须非空白，否则沿用综合失败流程；无推荐且理由为空仍合法。审查正文 ≤ 1500 字，合计 `reviewSummary`、全部 findings 的问题／影响／依据／针对部分文字及 `blockingResolutions[].basis`。schema 字段上限与解析端合计预算共同执行；审查摘要超限时先带截断标记截断，截断后合计仍超预算则整份拒绝，结构化 findings 和逐条裁决均不静默截断。新问题最多 10 条；两轮累计裁决及作者回应须容纳累计待处理集合（上限 30 条），不得只保留前 10 条。
* 提案因全部文字超预算被拒绝时，用户可见的排除原因须包含实际合计与上限；保留整份拒绝、不截断、不自动重试或替补的规则。
* 提案必须提交 `investigationBlockedReason`：必要调查完成时为空字符串；指定资料、关键约束或访问条件缺失导致必要调查未完成时，填写具体原因并设 `noViableProposal=true`，本次流程以未完成结束，不进入对齐或综合。已完成调查但确认无解时仍使用空原因与 `noViableProposal=true`，允许正常输出不可行结论；该原因计入提案全部文字的 4000 字预算。

### 5.2 审查分配与轮次

* 审查者按提案槽位顺序轮转指派给下一个不同模型；全部槽位使用同一模型时，同模型新子代理审查。
* 复核仅在修订回应的结构化标志为真时触发；轮数代码计数，第三轮拒绝并标"尚不可采用"。
* 原始模型审查 `TeamReviewOutput` 的 findings 为不含 ID 的 `TeamFinding`；接受后才转为含 `TeamTrackedFinding` 的 `TeamReviewRecord`。模型在新问题中自行填入 ID 或提交旧版 `priorBlockingStatus` 均拒绝，不设置兼容回退。
* 每提案维护从 1 开始单调递增的 `nextFindingNumber`，整份审查有效后才为所有严重级别分配 ID；已接受的 ID 永不回收，不依赖问题文字。历史审查、修订复核及 `unresolvedBlocking` 均保留带 ID 的记录；原始模型输出与程序追踪状态不得混为一谈。
* 未决阻断按 ID 从有效审查历史计算：仅删除有效 `resolved` 裁决对应的旧阻断，保留其他旧阻断，再追加新阻断；同文不同 ID 独立追踪。作者回应、`noSubstantiveIssues`、空 findings、综合文本及轮数上限均不能清空该集合。
* `parseTeamReview` 接收当前预期未决阻断 ID 集合，初审为空；`parseTeamRevision` 接收最新成功审查 findings 与未决阻断的 ID 并集。两者都要求精确逐 ID 对应，不接受未知、重复或缺失项及空白依据／解释；无效必需复核沿用 `pendingRecheck`／`recheckFailed` 状态，保留最后成功基线与全部其后待复核修订材料。

### 5.3 只读工具集与失败处理

* 全部子代理工具集机械限制为只读（读文件、`wiki`、`repo`、代码检索类）。
* 提案/审查/修订子代理失败不自动重试、不自动替补：该参与者标失败，其余继续，结果如实标注参与不完整。
* 对齐/综合子调用失败即流程未完成，报告结束。

### 5.4 取消、进度与并发

* 取消走命令取消信号并向所有在跑子代理传播；取消后不执行任何后续阶段。
* 任务、运行依赖、报告交付与界面回调绑定发起会话；成功恢复或切换到另一会话后取消原任务，丢弃迟到结果，不向新会话追加旧问题、报告或状态。
* 进度：阶段级状态（当前阶段、各参与者完成/失败）经现有状态展示机制呈现；子代理生命周期、进度和事件沿根观测总线进入现有 TUI／RPC 明细、转录与 ownership 控制路径，子代理明细经 Agent Hub 查看，不新造 TUI 面板。
* 并发受 `task.maxConcurrency` 约束（上游默认值，fork 不另行覆盖）；上限只控制同时运行的子代理数，超限槽位排队，不截断 `N = max(3, M)` 的参与名单。

### 5.5 结果落地

最终结果为一条 markdown 消息持久落入会话（内容结构见 2.7 表格，尾部附收尾契约）；各子代理的结构化原稿保留在本次任务结果中可回查。成功及失败报告都等待当前模型回合空闲后，以带取消信号的 durable custom message 追加，不启动模型回合、不进入仅存于内存的 nextTurn 队列；默认不设任意十分钟交付期限。若显式设置交付超时，超时必须报告未完成，不能把易丢失的排队消息当作成功。取消后不得追加或确认交付；只有持久提交成功才能 acknowledge，再重建 GUI。会话持久化仍属于正常会话记录，不写计划文件、不创建 Todo、不修改项目或其他外部状态。

各子代理完整工件的发布必须先确认 UTF-8 字节数、落盘大小与可读性，再原子替换；Windows 深层会话目录（含超过传统 MAX_PATH 的暂存路径）不能导致原稿丢失或截断，中文正文及尾部证据须可通过原有 `agent://<id>` 完整回查。写入、校验或发布失败必须如实报告工件保存失败，不得因最终摘要或 GUI 报告可见就认定完整材料已保存；失败保留此前有效工件，并清理本次暂存残片，路径、文件名和只读隔离规则不变。

### 5.6 模型配置实现方案（规划，未实现）
