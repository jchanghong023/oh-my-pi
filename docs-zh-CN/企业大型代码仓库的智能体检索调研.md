# 企业大型代码仓库的智能体检索：技术路线、产品实践与建设取舍

调研日期：2026 年 9 月 19 日

## 摘要

企业代码仓库积累到几十万行源码，并包含大量配置和测试后，编程智能体能否完成修改，很大程度上取决于能否找到相关实现、追踪影响范围，并获得可靠的验证依据。命中一个文件，只完成了其中的一步。

公开产品采用了不同的检索组合。Claude Code 按任务探索当前文件系统，也能接入语言服务器和企业搜索；GitHub Copilot 将语义检索、文本搜索和符号导航配合使用；Cursor 当前的搜索文档介绍了本地索引式正则搜索。[1](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)[2](https://code.visualstudio.com/docs/agents/reference/workspace-context)[3](https://cursor.com/docs/agent/tools/search) 全仓库向量化并非这些产品共同要求的前置步骤。

企业可以先用现有文件搜索、符号工具和构建测试环境建立可用方案，再根据实际瓶颈增加能力。重复扫描过慢，可以评估索引式全文搜索；引用定位不准，应检查语言分析与构建配置；业务描述难以对应代码名称，再试验向量语义检索。建设顺序应由真实任务中的遗漏、耗时和维护成本决定。

## 一、大型仓库给检索带来什么问题

### 1.1 规模与复杂度要分别衡量

几十万行代码与几十万个文件，是两种不同的规模。文件数增加会提高目录遍历和元数据访问的开销；文本总量增加会提高内容扫描的开销。参数化测试、快照和生成文件还可能占据大部分搜索结果，使真正需要的实现难以辨认。ripgrep 的直接扫描与索引式搜索，对这些成本采用了不同处理方式。[5](https://github.com/BurntSushi/ripgrep)[6](https://cursor.com/blog/fast-regex-search)

选型时应分别观察搜索规模和理解难度。前者包括文件数、总字节量、仓库数量与变更频率；后者包括语言种类、构建变体、动态注册、配置覆盖和测试生成方式。结构清楚的单语言工程，即使代码较多，也可能只需简单的检索工具。配置和生成机制复杂的工程，则可能在更小规模时就需要补充关系信息。

### 1.2 一次修改需要哪些信息

以“调整超时行为，同时保持旧平台兼容”为例，智能体需要找到下列信息：

| 信息 | 需要查清的问题 | 常见遗漏 |
| --- | --- | --- |
| 实现与入口 | 目标逻辑在哪里，如何进入？ | 同名实现位于不同平台或版本目录 |
| 影响范围 | 谁调用它，哪些配置和构建目标依赖它？ | 接口、默认值或错误处理变化影响了其他文件 |
| 约束与意图 | 为什么保留现有行为，哪些兼容要求仍然有效？ | 设计决策或硬件约束没有写在当前代码中 |
| 验证依据 | 哪些测试覆盖目标场景，新行为如何验收？ | 找到了测试文件，却没有检查场景、参数和断言 |

因此，检索过程通常还要继续追踪引用、查找配置和测试，并阅读当前文件。VS Code 的工作区上下文文档和 Claude Code 的实践指南都包含这类多步调查。[2](https://code.visualstudio.com/docs/agents/reference/workspace-context)[38](https://code.claude.com/docs/en/best-practices)

本报告依据公开文档、工程文章、论文和问题记录整理，未进行统一环境下的产品实测。文末的建设建议属于工程判断；厂商测试和论文结论各有适用条件。

## 二、检索、索引与上下文的分工

### 2.1 查找信息、组织数据与选择模型输入

检索负责找到与当前任务有关的信息。索引预先保存可查询的数据结构，减少重复扫描，或支持按符号和关系查找。上下文组织则决定哪些结果应在何时提供给模型。

智能体可以直接使用路径搜索、grep 和语言服务器，逐步定位代码；也可以先查询索引，再读取当前工作区的文件。Anthropic 将保留路径等定位线索、需要时才加载内容的做法称为“即时上下文加载”。[4](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 自建持久索引并非开展仓库调查的必要条件，已有索引也仍需与原文阅读配合。

检索增强生成（RAG）指利用检索到的外部材料辅助生成回答或代码，检索端可以采用词法、向量或混合方法。评价检索结果时，召回率衡量所需信息找到了多少，精确率衡量返回信息中有多少相关内容。统计单位可以是文件、符号或代码片段，比较时必须统一。[33](https://arxiv.org/abs/2602.05892)

### 2.2 两类“语义”回答不同问题

| 技术 | 分析依据 | 典型问题 |
| --- | --- | --- |
| 编程语言语义分析 | 声明、作用域、类型和构建配置 | 这个名称引用了哪个声明？ |
| 向量语义检索 | 问题与代码或文本的向量相似度 | “失败后重新尝试”的逻辑可能在哪里？ |

clangd 的符号与引用分析属于前一类；代码向量检索属于后一类。[11](https://clangd.llvm.org/design/indexing)[18](https://cursor.com/blog/semsearch) 相似度高的片段可能处理相近业务，却没有调用关系。具备语义分析能力的符号工具可以解析名称，但仅凭它也很难把没有代码词汇的业务需求映射到实现。

### 2.3 索引的内容决定查询能力

路径索引记录文件位置；倒排索引记录词项或字符片段的出现位置；符号索引记录声明、定义和引用等信息；关系图记录实体间的连接；向量索引服务于相似度查询。

这些结构还需要相应的解析和更新机制。解析出 YAML 的字段，并未解释字段由哪段代码消费；抽取出静态调用关系，也未必覆盖动态派发和运行时注册。选型时要检查索引保存了什么、关系如何取得，以及哪些内容未被覆盖。

## 三、代码检索的主要技术路线

### 3.1 文本与正则搜索

grep、ripgrep 按文本或正则表达式查找内容，不依赖语言解析或向量模型。ripgrep 默认遵循相应的忽略规则，并跳过隐藏文件和二进制文件。[5](https://github.com/BurntSushi/ripgrep)

已知函数名、错误码、配置键、日志、测试编号或宏名称时，精确搜索往往能直接提供入口。自定义领域语言缺乏专门工具支持时，也能先通过文本定位。

文本匹配会同时命中同名函数、注释和字符串，无法确定它们是否指向同一个程序实体。业务描述与代码命名相差较大时，还需要改写查询、追踪已有线索，或借助其他检索方法。

“没有找到”只能针对本次搜索范围成立。忽略规则、权限、搜索失败和输出截断都可能造成遗漏。需要列出全部使用位置时，应检查范围与结果完整性，不能用相似度检索返回的前若干项代替完整查找。

### 3.2 文件名、路径与元数据筛选

文件名、目录、扩展名、模块和文件类别可用于缩小搜索范围。例如，先限定平台目录，再找实现；先找到测试目录，再搜索场景与断言。路径匹配可以直接遍历文件系统，也可以查询缓存的清单或持久索引；使用 `glob` 并不要求数据库。[2](https://code.visualstudio.com/docs/agents/reference/workspace-context)[5](https://github.com/BurntSushi/ripgrep)

测试、配置和生成输出远多于源码时，分类筛选能减少无关结果。不过，测试未必与源码同目录，配置也可能跨层继承。筛选范围过窄会隐藏依赖，所以默认降低优先级的内容仍应能在任务需要时被查询。

### 3.3 索引式全文搜索

索引式全文搜索预先记录词项或字符片段出现的位置，查询时先筛选候选，再验证实际匹配。Zoekt 使用面向代码搜索的索引；Cursor 的正则搜索工程文章介绍了倒排索引、三字符片段和稀疏字符片段等方法。[6](https://cursor.com/blog/fast-regex-search)[7](https://github.com/sourcegraph/zoekt/blob/main/doc/design.md)

| 方法 | 作用 |
| --- | --- |
| 倒排索引 | 根据词项或字符片段，查找包含它们的文件或位置 |
| 三字符片段索引及其他字符片段索引 | 把字符串拆成连续片段，过滤不可能匹配的候选 |
| BM25 | 根据词频、词项稀有程度和文档长度等因素，对匹配结果排序 |

三字符片段通常称为 trigram，更一般的长度为 n 的片段称为 n-gram。候选文件包含所需片段，并不保证满足完整查询，仍需进行实际匹配。BM25 是排序方法，可以与倒排索引配合。SQLite FTS5 提供全文检索、trigram 分词和 BM25 等能力，无需额外引入向量数据库。[8](https://www.sqlite.org/fts5.html)

这条路线适合查询频繁、重复扫描较慢或多人共享的代码搜索。代价是索引构建、存储和更新；正则表达式缺少可用于筛选的字面量时，加速效果也可能减弱。用于代码搜索的分词需要照顾标识符、缩写与字段特点。排序后只返回前 K 项的接口，同样不保证列出全部匹配。

### 3.4 符号索引

符号索引提取函数、类、方法、类型和模块等实体，记录名称、类别及位置。Universal Ctags 可以生成用于导航的标签；编译器或语言服务器索引还能提供更深入的关系信息。[9](https://docs.ctags.io/en/latest/man/ctags.1.html)[11](https://clangd.llvm.org/design/indexing)

这类工具适合查找定义、列出接口和生成模块概览，能减少为找一个函数而读取整个文件的次数。但不同索引器的分析深度差别很大：按名称找到的候选定义，可能仍需借助作用域和类型信息确认。重载、别名、模板和动态绑定尤其需要区分“名称匹配”与“引用解析”。

### 3.5 语言服务器与编译器索引

语言服务器协议（LSP）规定编辑器或智能体如何与语言服务器通信，支持定义跳转、引用查找和符号查询等能力。具体能力由服务器实现，协议本身不规定索引的存储方式。[10](https://code.visualstudio.com/api/language-extensions/language-server-extension-guide)

语言服务器可以使用项目级、持久化或远程索引。clangd 会组合多个索引层：动态索引处理已打开文件及相关头文件的信息，后台索引依据编译数据库分析项目并缓存结果，也可以加载预建索引或使用远程索引。[11](https://clangd.llvm.org/design/indexing)

这类分析有助于区分同名实体、查找已解析的引用，以及追踪类型和接口关系。它仍受语言、服务器实现与工程配置限制，不能保证列出全部运行时调用目标。C/C++ 的头文件路径、宏、语言标准和编译命令都会影响解析；单一构建配置的索引也无法证明覆盖了其他平台和条件编译分支。[12](https://clangd.llvm.org/design/compile-commands)

SCIP 是语言无关的代码智能索引格式，可表示符号、出现位置及相关关系，方便索引生产者和查询工具交换数据。项目仍需使用合适的索引器完成分析。[13](https://github.com/scip-code/scip)

企业已有成熟语言服务器时，可以先让智能体复用，并检查编译数据库是否正确。现有解析环境不完整时，应先评估修正编译数据库能否解决问题，再考虑另建关系图。

### 3.6 语法树与结构化搜索

抽象语法树（AST）用节点表示程序结构。Tree-sitter 构建的是可增量更新的具体语法树（CST），上层工具可据此提取需要的结构信息；ast-grep 则提供按语法结构匹配代码的能力。[14](https://tree-sitter.github.io/tree-sitter/)[15](https://ast-grep.github.io/guide/introduction.html)

查找“使用某种参数结构的 API 调用”、特定导入、声明或重复实现模式时，结构化搜索能够避开部分空格、换行和嵌套差异，适合为批量修改提供候选。

语法树主要描述代码结构。名称绑定、类型关系和实际运行行为仍可能需要额外分析。Tree-sitter 支持增量解析，也不代表使用它的工具自动具备全仓库持久索引；缓存、关系抽取和更新都由上层系统负责。

### 3.7 调用、依赖与测试关系

关系图以文件、符号、构建目标或测试为节点，以特定关系为边。不同来源的边有不同含义：

| 关系 | 表达的事实 | 用途 |
| --- | --- | --- |
| 导入与模块依赖 | 模块声明依赖另一模块 | 导航和影响范围调查 |
| 调用与引用 | 分析工具解析出的实体引用或调用 | 接口修改和调用链追踪 |
| 构建依赖 | 目标依赖其他目标或输入 | 查找依赖方、关联构建及测试目标 |
| 测试覆盖 | 某次运行中，测试执行过某段代码 | 辅助选择测试 |
| 配置与业务关系 | 字段被某实现消费，场景由某测试验证 | 连接配置、实现与验收条件 |

Bazel 的查询工具支持反向依赖和测试集合查询。[16](https://bazel.build/query/guide) coverage.py 在启用动态上下文，或由测试运行器显式设置上下文后，可以记录测试与所执行代码的对应关系。[17](https://coverage.readthedocs.io/en/latest/contexts.html) 配置消费和业务关系则可能需要项目专用规则补充。

静态调用图会受到动态派发、反射、插件和生成机制影响；构建依赖也不能直接当作运行时调用。一次测试没有覆盖某行，只能说明这次执行未经过它。RepoGraph 在其研究设置中验证了仓库关系图的辅助价值，实际覆盖程度仍需按项目检查。[32](https://arxiv.org/abs/2410.14684)

查询结果最好保留关系出处，便于回到代码、构建声明或运行记录核验。启发式推断的边也应有明确标记。规模有限的关系可以保存在普通数据结构或现有数据库中，使用关系图并不要求部署独立图数据库。

### 3.8 向量语义检索

向量嵌入模型把查询和代码片段转换为向量，再根据相似度返回候选。当用户知道业务行为，却不知道实现名称时，这类检索能帮助寻找相关模块、类似实现或文档。Cursor 在 2025 年的工程文章中讨论了向量检索与 grep 的互补，以及代码片段排序和训练方法。[18](https://cursor.com/blog/semsearch)

向量检索的效果受切块方式、路径与外围定义是否保留、模型对目标语言的适应程度等因素影响。相近概念可能分布在互不相关的模块，关键依赖也可能与查询描述缺乏相似性。因此，配置键、错误码、芯片型号和测试编号等查询仍需要词法检索；要求找全使用点的修改，还要进行引用或依赖调查。

向量相关建设可拆成三个独立决策：

| 决策 | 建设内容 | 可选方式 |
| --- | --- | --- |
| 使用向量嵌入 | 为查询与候选内容生成向量 | 先验证能否改善实际召回 |
| 加速向量查询 | 使用专门的相似度检索结构 | 数据量允许时直接精确搜索；延迟不足再考虑近似索引 |
| 部署向量数据库 | 管理持久化、更新、元数据、并发和服务接口 | 使用本地库、现有数据库扩展或独立服务 |

Faiss 提供向量相似度搜索库；pgvector 在 PostgreSQL 中支持精确向量搜索和可选的近似索引。[19](https://github.com/facebookresearch/faiss)[20](https://github.com/pgvector/pgvector) 企业可以先验证语义召回的价值，再决定存储和运维方式。

### 3.9 仓库地图

仓库地图提取重要文件、符号和签名，再按任务相关性及上下文预算选择展示内容。Aider 的 Repo Map 在文件依赖图上进行排序，为当前对话选取重要接口和代码位置。[21](https://aider.chat/docs/repomap.html)

这种概览适合智能体初次进入项目时寻找入口和复用接口。需要更多细节时，再沿地图读取文件。它比逐文件生成自然语言摘要更接近导航工具，但同样会省略信息；签名无法完整表达副作用、实现细节和业务约束。

### 3.10 历史、规范与文档检索

提交记录、合并请求、问题讨论和设计文档，能帮助解释兼容分支为何保留、配置为何废弃，以及类似功能过去如何接入。Git 已支持按路径、提交信息和变更内容查找历史，可先按需查询。[22](https://git-scm.com/docs/git-log)

这些材料需要保留时间与适用范围。旧讨论可能被后续决定替代，旧补丁可能不适用于当前分支；经常共同修改的文件也只能作为依赖线索。

当前代码用于确认实现，有效需求与规范用于确定目标行为，历史材料用于解释决策经过。发生冲突时应查清哪项决定仍然有效，避免把旧实现或旧讨论直接当成本次修改的要求。

### 3.11 自主探索与混合检索

智能体可以根据上一次结果选择下一步工具：先找文件，再查符号，遇到配置键就搜索配置，发现调用方再继续追踪依赖。SWE-agent 的研究表明，搜索、导航、编辑和反馈接口的设计会影响软件任务表现。[23](https://arxiv.org/abs/2405.15793)

混合检索有两种常见组织方式。一种是在单次查询中合并词法与向量候选，去重后重新排序；另一种是在多轮调查中选择不同工具。重排只能改变已有候选的顺序，未被召回的依赖仍需其他查询补充。

探索过程可能重复搜索、过早锁定错误模块，或读入大量最终未使用的内容。子智能体可以隔离调查上下文、并行处理独立问题，也会增加调用和协调成本。[4](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)[33](https://arxiv.org/abs/2602.05892) 已知符号的小修改与跨模块功能设计，需要的调查深度不同，无需让每个任务都调用全部检索工具。

### 3.12 工具与服务接入

模型上下文协议（MCP）提供客户端与服务端之间的工具、资源等交互机制。插件可以封装工具、配置和工作流程。这些接口能够连接代码搜索服务，后端仍需选择具体的检索算法和数据结构。[24](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)

评估代码检索插件或 MCP 服务时，应检查索引范围、分支与工作区支持、语言分析深度、关系来源和更新机制。接口接通后，还需要用真实查询验证结果质量。

## 四、主流产品如何获取代码上下文

### 4.1 产品路线对照

| 产品或入口 | 公开资料描述的做法 | 适用范围与限制 |
| --- | --- | --- |
| Claude Code | 按任务探索文件系统，可接入语言服务器和内部搜索 | 本地探索无需用户预建全仓库索引，外接服务可使用索引。[1](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start) |
| Codex CLI | 阅读和编辑本地代码、执行命令，并使用项目指令及外部工具 | 公开本地工作流未要求自建向量服务；其他产品入口需分别考察。[25](https://developers.openai.com/codex/cli/)[26](https://developers.openai.com/codex/guides/agents-md/) |
| GitHub Copilot | 使用仓库索引支持语义代码搜索 | 索引可用性受产品入口、仓库托管方式和策略影响。[27](https://docs.github.com/en/copilot/concepts/context/repository-indexing) |
| VS Code 中的 Copilot | 组合语义、文本、文件搜索与符号使用位置查询 | 语义索引不可用时，仍可使用不依赖该索引的工具。[2](https://code.visualstudio.com/docs/agents/reference/workspace-context) |
| Cursor 当前智能体搜索 | 本地 Instant Grep 索引与探索子智能体 | 当前搜索说明与 2025 年的语义搜索文章应按时间区分。[3](https://cursor.com/docs/agent/tools/search)[18](https://cursor.com/blog/semsearch) |
| Gemini Code Assist Enterprise 代码定制 | 检索私有仓库索引，为代码建议提供相关片段 | 服务于代码补全和生成，有明确的文件类型与更新周期限制。[28](https://docs.cloud.google.com/gemini/docs/codeassist/code-customization-overview) |
| JetBrains Context | 增量语义索引及检索，可接入多个编程智能体 | 发布时为早期访问；跨仓库能力在发布文章中列为推进中的功能。[29](https://blog.jetbrains.com/ai/2026/07/introducing-jetbrains-context-repository-intelligence-for-coding-agents/) |
| Sourcegraph Cody | 关键词搜索、Sourcegraph 搜索及代码关系信息 | 借助代码搜索平台，具体上下文入口因客户端而异。[30](https://sourcegraph.com/docs/cody/core-concepts/context) |
| Aider | 按预算选取符号和依赖信息，生成仓库地图 | 提供导航概览，细节需继续读取源码。[21](https://aider.chat/docs/repomap.html) |

### 4.2 现场探索：Claude Code

Anthropic 在 2026 年 5 月的大仓库文章中介绍了无需预建仓库索引的探索方式，也介绍了语言服务器和企业搜索的接入。[1](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start) 其大仓库文档进一步说明，代码智能插件可连接语言服务器，帮助查找定义、引用和类型问题。[37](https://code.claude.com/docs/en/large-codebases)

企业可以先提供可搜索的工作区、有效的工程配置与验证入口，让智能体利用现有开发工具工作。跨仓库调查频繁，或每次任务都在重复探索相同内容时，再评估共享搜索服务。这条路线降低了起步所需的基础设施，但没有消除后续的搜索和阅读成本。

### 4.3 本地开发工具：Codex CLI

Codex CLI 的公开工作流包括在本地仓库阅读、编辑和运行代码。`AGENTS.md` 等文件可提供项目指令，外部工具可补充其他能力。[25](https://developers.openai.com/codex/cli/)[26](https://developers.openai.com/codex/guides/agents-md/)

项目指令的发现与合并有具体规则。官方文档描述了启动时构建指令链、按目录读取指令以及适用的覆盖规则，不能假定编辑到某个目录时，其全部嵌套指令都会自动加载。[26](https://developers.openai.com/codex/guides/agents-md/)

采用这类命令行智能体时，企业可以分别评价模型、工具接口、语言服务器和索引后端。遇到检索问题，先确定缺口发生在哪一层，再决定是否连接额外服务。

### 4.4 多种搜索工具配合：GitHub Copilot

GitHub 为 Copilot 提供仓库索引和语义搜索。VS Code 的文档同时列出了文本搜索、正则搜索、文件搜索、符号使用位置查询和文件阅读，智能体可据此继续调查。[27](https://docs.github.com/en/copilot/concepts/context/repository-indexing)[2](https://code.visualstudio.com/docs/agents/reference/workspace-context)

语义检索适合从需求描述中寻找候选，精确搜索和语言工具用于定位符号及追踪细节，读取当前文件则用于确认实际代码。已有 IDE 能提供这些能力时，应先核对覆盖范围、索引状态和企业策略，避免重复建设相同功能。

### 4.5 本地索引式正则搜索：Cursor

Cursor 在 2025 年 11 月 6 日发表的文章中讨论了向量语义搜索与 grep 的互补。2026 年 3 月的工程文章介绍了索引式正则搜索；截至本次核验，其搜索文档明确写明，Instant Grep 在本机建立和查询索引，且不为该搜索保存代码库向量嵌入。[18](https://cursor.com/blog/semsearch)[6](https://cursor.com/blog/fast-regex-search)[3](https://cursor.com/docs/agent/tools/search)

这几份资料对应不同时间和范围。当前文档可以用于说明公开搜索入口，旧工程文章则保留了语义检索路线的技术与评测记录，不能据此推断 Cursor 全部系统的内部架构。

Cursor 还说明，智能体打开搜索命中后，文件内容仍可能被放入模型请求。[3](https://cursor.com/docs/agent/tools/search) 本地索引解决的是搜索数据结构的存放位置，模型请求的数据去向需要另行确认。

### 4.6 企业私有代码检索：谷歌代码定制服务

Gemini Code Assist Enterprise 的代码定制服务检索已纳入索引的企业私有仓库，将相关片段加入补全或生成请求。它能够搜索当前本地文件夹之外的仓库，文档规定每 24 小时重新索引。[28](https://docs.cloud.google.com/gemini/docs/codeassist/code-customization-overview)

支持范围包括 Markdown 文档，以及列出的编程语言，其中包含 Verilog 和 SystemVerilog；其他语言不纳入该代码定制索引。[28](https://docs.cloud.google.com/gemini/docs/codeassist/code-customization-overview) 这种支持表示可以索引并用于代码建议，不应进一步解释为具备完整的硬件设计展开、引用或依赖分析能力。

配置和测试密集的仓库，需要逐类核对文件是否被索引，并检查更新周期能否满足开发过程。代码建议使用的远程索引也不能直接当作当前工作区的实时状态。

### 4.7 可接入多个智能体的检索层：JetBrains Context

JetBrains 在 2026 年 7 月的发布文章中介绍了 Context：增量建立语义索引，提供检索工具，并与 Claude Code、Codex CLI、Junie CLI 等集成。发布时为早期访问，文章将跨仓库搜索描述为正在推出的能力。[29](https://blog.jetbrains.com/ai/2026/07/introducing-jetbrains-context-repository-intelligence-for-coding-agents/)

这种分工使仓库检索可以独立于某一个智能体维护。发布文章还报告了内部基准收益，但这些结果只能说明相应测试条件下的表现，不能直接作为企业仓库的成本或质量承诺。

### 4.8 共享搜索与仓库概览：Sourcegraph 和 Aider

Sourcegraph Cody 的上下文文档列出了关键词搜索、Sourcegraph Search 和代码关系图，也列明不同客户端支持的文件、符号和远程内容入口。[30](https://sourcegraph.com/docs/cody/core-concepts/context) 已部署代码搜索平台的企业，可以考察如何让智能体复用这些服务。

Aider 的仓库地图则侧重组织模型输入：从重要符号和文件关系中选择当前任务需要的概览，帮助模型决定下一步读取哪些文件。[21](https://aider.chat/docs/repomap.html) 两种能力分别解决共享检索与导航问题，可以配合使用。

## 五、研究与实践提供了哪些证据

### 5.1 检索工具需要放回开发任务中评价

| 研究 | 主要结果或方法 | 对企业评估的意义 |
| --- | --- | --- |
| SWE-agent，2024 | 研究面向智能体的搜索、导航、编辑和反馈接口。[23](https://arxiv.org/abs/2405.15793) | 接口设计也会影响最终表现，不能把系统收益全部归给搜索算法 |
| Agentless，2024 | 采用定位、修复与验证流程完成软件修复任务。[31](https://arxiv.org/abs/2407.01489) | 可将分阶段流程纳入基线，但不能据此否定其他编排方式 |
| RepoGraph，2024 年首次提交 | 在所测系统中，仓库级关系图能辅助软件工程任务。[32](https://arxiv.org/abs/2410.14684) | 关系信息值得验证，收益取决于抽取质量和任务类型 |
| ContextBench，2026 | 分别测量上下文召回、精确率和效率。[33](https://arxiv.org/abs/2602.05892) | 能够检查搜索过程中遗漏和无效阅读发生在哪里 |
| 仓库级上下文文件评估，2026 年 6 月修订版 | 在所测设置下，上下文文件未普遍提高任务成功率，平均推理成本增加超过 20%。[34](https://arxiv.org/abs/2602.11988v2) | 项目说明的内容与成本需要实测，不能默认越多越好 |

这些研究采用的任务、模型和工具各不相同，不构成产品排名。企业需要同时检查检索质量与最终修改结果：搜索更快或输入更少，若伴随关键证据遗漏，就未必改善开发效率。

### 5.2 检索到的信息是否真正被使用

ContextBench 收录了来自 66 个仓库、覆盖 8 种编程语言的 1,136 个问题解决任务，并提供人工标注的目标上下文。作者在所测模型和智能体组合中发现，系统往往偏向召回而牺牲精确率，已探索内容与实际利用内容之间也存在明显差距。[33](https://arxiv.org/abs/2602.05892)

企业评测可据此区分几种现象：必要文件没有被找到，找到了却没有被利用，或读入了大量无关信息。只统计命中文件数，无法识别这些差异。增加工具或调查子智能体后，也应检查额外探索是否改善补丁，而不只记录调用次数。

### 5.3 项目文档应提供什么

OpenAI 的工程案例采用较短的 `AGENTS.md` 作为导航入口，把详细设计和规则保存在结构化文档中，并使用自动检查维护文档与架构约束。[36](https://openai.com/index/harness-engineering/)

《Evaluating AGENTS.md》的 2026 年 6 月 23 日修订版则报告：在其测试设置下，模型生成和开发者提交的上下文文件均未普遍提高任务成功率，平均推理成本增加超过 20%。论文同时指出，上下文文件可用于说明非标准的项目约定。[34](https://arxiv.org/abs/2602.11988v2)

这两类证据关注的目标有所不同。项目需要明确特殊构建方式、兼容约束和其他不能从源码推导的要求；是否通过增加仓库概览来提高解题成功率，则应单独验证。重复代码内容或强制无关流程的长文档，会增加阅读负担。

### 5.4 索引维护也是实际成本

Cursor 的历史语义检索文章和 JetBrains Context 发布文章都包含厂商内部评测。由于模型、任务、权限与统计口径不同，不能将这些数字直接放在一起排名。[18](https://cursor.com/blog/semsearch)[29](https://blog.jetbrains.com/ai/2026/07/introducing-jetbrains-context-repository-intelligence-for-coding-agents/)

公开故障记录则能补充部署层面的观察。VS Code 的问题 #320915 于 2026 年 6 月 11 日报告：非 GitHub 仓库上传语义索引后，在完成处理阶段收到 HTTP 412。核验时，页面已标记补丁进入 Insiders。[35](https://github.com/microsoft/vscode/issues/320915) 这是一次具体故障记录，说明索引构建状态和失败恢复需要被纳入运维；它不能代表当前普遍故障或故障率。

产品文档与研究反复涉及的实际问题包括：如何按任务选择材料、减少无效阅读、保留准确定位能力，以及用当前源码和执行反馈检查修改。[2](https://code.visualstudio.com/docs/agents/reference/workspace-context)[4](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)[23](https://arxiv.org/abs/2405.15793)[38](https://code.claude.com/docs/en/best-practices) 企业评测应围绕这些问题建立自己的基线。

## 六、企业建设的优先级与取舍

### 6.1 先建立可用的检索与验证基线

起步方案应保证文件和文本搜索可用。智能体能按路径、模块和文件类别缩小范围，查找精确文本，并读取当前文件；搜索排除了哪些内容、结果是否截断、工具是否失败，也应可见。

主要语言已有成熟工具时，优先复用语言服务器、编译器索引或符号工具。缺少支持的语言和文件可先采用结构化搜索或文本搜索，但应说明分析深度。无需等所有语言都具备精确导航后才开始使用智能体。

同时提供构建和测试入口、生成文件的修改来源、平台兼容要求与有效规范。信息可以保存在项目已有文档中，避免为接入智能体另建一套内容重复的说明。

修改完成后，通过与任务相关的构建和测试检查目标行为及保留行为。这样既能检验代码生成，也能暴露检索中的遗漏。Claude Code 的探索方式、Copilot 的多种搜索工具和现有语言索引说明，这套基线可以不使用向量嵌入或独立向量数据库。[1](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)[2](https://code.visualstudio.com/docs/agents/reference/workspace-context)[11](https://clangd.llvm.org/design/indexing)[38](https://code.claude.com/docs/en/best-practices) 是否足以支撑企业任务，再由实际结果判断。

### 6.2 分清源码、配置与测试的检索需求

大量配置和测试会改变仓库的检索重点。可以先通过目录分类、清单和结果元数据区分内容，无需为每类文件建设独立数据库。

| 内容 | 优先查找的信息 | 容易出错的处理方式 |
| --- | --- | --- |
| 手写源码 | 定义、引用、接口、构建归属和当前实现 | 只提供自然语言摘要，无法读取原文 |
| 配置 | 结构定义、默认值、覆盖关系、解析入口和消费位置 | 把语法相似的配置当作业务等价 |
| 集成测试 | 入口、场景、参数、夹具、断言和运行条件 | 仅凭文件名判断覆盖范围，或默认排除全部测试 |
| 生成器与生成文件 | 生成来源、可修改位置和必要输出样本 | 一律排除生成物，遗漏头文件或绑定关系 |
| 快照、基准输出和大型数据 | 生成及比较机制、任务所需片段 | 将全部输出默认放入模型上下文 |

配置密集的工程尤其需要连起几个位置：字段在哪里定义、默认值如何覆盖、由谁解析和消费、受哪些平台或构建条件控制，以及哪些测试检查对应结果。

部分连接可以复用构建查询与测试覆盖记录。[16](https://bazel.build/query/guide)[17](https://coverage.readthedocs.io/en/latest/contexts.html) 自定义领域语言、字符串注册表和企业回归清单，可能还需小范围的专用抽取规则。先补齐反复影响修改的连接，通常比给全部文件生成摘要更容易检查成效。

搜索结果的优先级与编译分析的输入范围也要分开处理。生成文件可以减少默认展示，但编译器需要的头文件和绑定文件仍应参与分析。

### 6.3 修改既有代码时，沿影响关系检索

有跨文件影响的修改，可以按以下顺序调查和验证：

1. 明确目标行为、代码版本、适用平台和完成条件，列清需要保留的行为。
2. 找到候选实现，读取当前工作区原文；存在同名实体时，用符号或类型信息确认。
3. 追踪调用方、配置、构建目标与相关测试，记录尚未确认的关系。
4. 完成修改，执行获准且相关的检查，并复核差异是否遗漏关联变更或引入无关修改。

范围清楚的小改动可以简化调查，复杂任务则需要更多探索。[38](https://code.claude.com/docs/en/best-practices) 交付时说明实际改动、验证结果和未检查的范围即可。

检索找到的测试是验证起点。索引未返回某项测试，并不能证明它与修改无关；项目要求的集成测试、跨平台检查和其他质量门仍需按既定规则处理。

### 6.4 新增功能时，优先寻找扩展点与复用方式

新功能往往没有现成的函数名可查。检索应先帮助确定功能所属的模块边界，再寻找可复用能力及已有接入方式，最后查清新旧行为如何验证。

注册入口、工厂或插件机制、公共接口、配置扩展点、测试夹具与验收模式，都可能比一段概念相似的代码更有用。仓库地图、符号导航和规范检索可以提供这些线索；业务表述与代码命名差异明显时，再补充向量召回。[21](https://aider.chat/docs/repomap.html)[38](https://code.claude.com/docs/en/best-practices)

候选实现仍需结合当前代码与有效规范确认。代码、需求和测试发生冲突时，要先澄清目标行为，不能只按相似实现决定新功能的要求。

### 6.5 文档保留难以从代码获得的信息

值得维护的内容包括特殊构建方式、测试命令及运行条件、兼容约束、生成入口、架构边界和有效规范链接。它们应有明确的适用范围，并随工程变化更新。

函数签名、目录清单和引用位置适合从代码提取。难以从实现推导的设计意图，再用经过核验的文字补充。不建议把“为每个文件生成摘要”设为统一前置步骤；自动生成的说明需要标明来源与版本，并能在过期后失效或重建。这一取舍结合了上下文文件研究与文档维护案例，仍需在具体项目中检验。[34](https://arxiv.org/abs/2602.11988v2)[36](https://openai.com/index/harness-engineering/)

`AGENTS.md`、`CLAUDE.md` 等指令文件应遵循宿主的加载与作用域规则。能自动验证的要求，可以交给构建、静态检查或专用脚本执行，减少仅靠文字提醒维持约束的负担。[26](https://developers.openai.com/codex/guides/agents-md/)[36](https://openai.com/index/harness-engineering/)

### 6.6 哪些能力需要增加，哪些可以暂缓

| 能力或组件 | 建议 | 增加的条件 | 暂不增加的代价 |
| --- | --- | --- | --- |
| 精确文本、路径搜索与原文阅读 | 保证可用，优先复用现有工具 | 所有任务都需要基本定位和核验 | 缺失时难以确认修改依据 |
| 语言服务器或符号导航 | 主要语言有成熟支持时优先接入 | 同名实体多，接口和类型关系复杂 | 更多依赖文本查找与人工核验 |
| 独立全文索引服务 | 按需建设 | 重复扫描过慢，跨仓库或共享查询频繁 | 承担更多扫描与重复查询成本 |
| 结构化代码搜索 | 按任务接入 | 经常查找语法模式或批量修改结构 | 部分模式用正则难以准确表达 |
| 向量语义召回 | 可以暂缓 | 业务描述与代码词汇长期不一致，已有工具经常漏掉候选 | 需要更多查询改写与探索 |
| 向量近似索引 | 可以暂缓 | 已确认需要向量，精确搜索达不到延迟或吞吐目标 | 向量查询可能较慢；未使用向量则无此成本 |
| 独立向量数据库 | 可以暂缓 | 已有向量需求，规模与服务管理要求超出现有存储能力 | 由本地库或现有数据库承担管理工作 |
| 全仓库调用图或知识图谱 | 不作为统一前置步骤 | 关系被反复用于影响分析，且抽取覆盖率可验证 | 跨模块关系需逐次追踪 |
| 独立图数据库 | 可以暂缓 | 图规模与多跳查询超出现有工具能力 | 复杂关系查询和管理可能较繁琐 |
| 全量历史及问题讨论预索引 | 先按需查询 | 历史调查频繁，原生检索成为瓶颈 | 历史定位可能更慢 |
| 全仓库自动摘要 | 不建议默认建设 | 对反复使用、难以从代码取得的知识做小范围验证 | 缺少部分概览便利，但减少重复与过期材料 |
| 每次固定启动多个调查智能体 | 不建议默认启用 | 子问题可独立分解，并行收益超过调用与协调成本 | 串行调查可能耗时更长 |
| 将全仓库放入超长上下文 | 不作为大型仓库常规方案 | 候选材料本来就少，任务确需整体内容 | 需要分步检索和阅读 |

索引、向量和独立数据库应分别决策。索引式全文搜索可以完全不使用向量；向量检索也可以采用本地库或现有数据库扩展。[7](https://github.com/sourcegraph/zoekt/blob/main/doc/design.md)[19](https://github.com/facebookresearch/faiss)[20](https://github.com/pgvector/pgvector) 产品内置能力已经满足需要时，企业无需再自建相同服务。

### 6.7 让索引版本与覆盖范围可见

查询结果至少应标明所属仓库和版本，并说明是否覆盖当前分支及未提交修改、哪些目录或语言未被索引、结果是否截断，以及查询是否成功。跨仓库结果还需保留完整的仓库身份。

远程主分支索引与本地工作区不一致时，可以用它寻找候选，但编辑前应读取本地原文并核实符号。clangd 的动态与后台索引组合，以及企业代码服务的周期更新，代表了不同的更新方式。[11](https://clangd.llvm.org/design/indexing)[28](https://docs.cloud.google.com/gemini/docs/codeassist/code-customization-overview) 接入时应确认实际行为，尤其是分支切换和本地改动如何反映到结果中。

索引故障需要与“没有匹配”区分开，并保留直接搜索等替代路径。索引构建和完成状态也应可检查，避免智能体在索引未就绪时误判代码不存在。[35](https://github.com/microsoft/vscode/issues/320915)

### 6.8 核对企业数据的访问与传输范围

搜索排除规则用于控制检索范围，代码访问权限则应由相应的系统或服务实施。`.gitignore` 无法代替访问控制。Claude Code 文档也明确说明，其文件拒绝规则不覆盖所有自行打开文件的子进程。[37](https://code.claude.com/docs/en/large-codebases)

索引、缓存、日志和返回片段应按源码的敏感程度控制访问。检索在本机执行时，还需核对哪些内容会进入远程模型请求；Cursor 对这一点有明确说明。[3](https://cursor.com/docs/agent/tools/search) 内网部署应分别确认检索服务与模型调用的数据边界。

### 6.9 用真实任务判断新增组件是否有效

选取一组企业任务，覆盖缺陷修复、功能扩展、配置变更和测试维护。固定模型与基础工作流后，逐项增加检索能力，再比较必要的组合。若同时更换模型、提示词、工具和索引，就难以判断收益来自哪里。

| 评价层面 | 应记录的内容 |
| --- | --- |
| 定位质量 | 必要文件、符号、配置和测试的命中与遗漏 |
| 上下文质量 | 相关片段比例、重复内容、过期结果和截断 |
| 任务结果 | 验收与回归结果、人工审查发现、无关修改 |
| 成本和延迟 | 全程耗时、工具轮次、模型费用、索引建设及更新成本 |
| 运行可靠性 | 分支切换、本地改动、索引故障和权限变化时的行为 |

ContextBench 提供了观察召回、精确率和利用效率的研究方法；业务是否正确，还需要项目自身的测试和审查来判断。[33](https://arxiv.org/abs/2602.05892) 搜索结果多可能包含噪声，输入少也可能遗漏信息，单次查询快则可能被索引维护或额外工具轮次抵消。

回放历史任务时，应使用当时的代码基线，排除答案补丁、后续修复提交和已公开的解决方案，避免信息泄漏。重要比较应保留多次运行结果或相应的不确定性说明。

一个组件是否值得保留，取决于它能否稳定解决已观察到的问题，以及这项收益是否覆盖建设和维护成本。

### 6.10 建议的建设顺序

优先保证精确搜索、现有符号导航、当前原文阅读和修改验证。随后按实际问题补充能力：

| 主要问题 | 优先评估的改进 |
| --- | --- |
| 大量时间花在重复扫描 | 索引式全文搜索 |
| 同名实体难区分，引用结果不准 | 语言分析支持与构建配置 |
| 经常遗漏跨模块影响 | 有出处、可核验的依赖和测试关系 |
| 业务描述难以匹配代码名称 | 向量语义召回 |

向量库、全量知识图谱和自动摘要都可以暂缓。先测清现有方案在哪些任务上失败，再决定增加哪种能力。

## 七、工具方案：为 omp 补齐仓库检索能力

前六章是技术调研，本章把其中的建议落成一份可执行的方案。

### 7.1 方案针对的环境与目标

先固定环境前提，它们与第一章的问题直接对应：

| 环境事实 | 对工具的要求 |
| --- | --- |
| 企业内部老项目，主体语言为 Python 3.6 | 能直接解析既有代码，不要求改造代码或补写类型标注 |
| 源码几十万行，配置文件与测试文件很多 | 检索要能区分源码、配置、测试；不能每次任务都全仓重扫 |
| 源码、用户目录、缓存都在网络文件系统上 | 减少重复的文件遍历与读取；索引更新低频、批量 |
| 离线环境，要求零额外安装、开箱即用 | 能力随工具内置，不依赖外部服务、数据库或账号 |

omp 是我们选用的 AI 编程助手：在终端里以对话方式接收任务，自己读文件、改代码、运行命令。它“找代码”靠的就是检索工具，给它什么检索工具，直接决定它在大型仓库里的表现。本方案不更换 omp，只补齐它的检索层，让它在下列任务上先定位、后动手：新增功能、修改旧代码、查找相关实现、寻找调用关系、寻找相关配置、寻找相关测试、分析修改影响范围。

状态、关键词、符号、关联、影响面五种查询，连同索引的建立与增量更新，全部包含在本方案里，一次到位。多人共享一份索引、向量语义召回等扩展项不在本方案内，需要时按 6.6 / 6.10 的触发条件另行评估。

### 7.2 五个检索能力分别是什么

| 能力 | 是什么（通俗解释） | 适合回答的问题 | 举例 |
| --- | --- | --- | --- |
| grep（文本搜索） | 把整个仓库当作一个大文档做“查找”：给定词语或模式，逐文件扫描，返回所有出现的文件和行 | 已知函数名、错误码、配置键、日志文本时直接定位 | 搜 `ERR_TIMEOUT`，得到它出现的全部位置 |
| glob（文件搜索） | 按文件名或路径模式列出文件 | 先圈定范围再看内容 | 列出所有 `test_*.py`，或 `configs/` 下的全部文件 |
| ast_grep（结构化搜索） | 先读懂代码的语法结构，再按“代码的形状”匹配，换行与缩进差异不影响结果；匹配任意变量要用通配写法（`assert $X == 0`），名字写死则只按字面匹配 | 找某种写法的所有出现 | 用 `assert $X == 0` 找出所有“结果与 0 判等”的断言 |
| lsp（语言服务器） | IDE 里“转到定义”“查找引用”背后的引擎：按语言规则分析，而不是按文字匹配 | 这个名字定义在哪；哪些地方引用了它 | 列出 `run_pattern()` 已解析出的引用位置 |
| repo（仓库索引，新增） | 提前为整个仓库建好的“地图加索引页”，类似书末的索引：建好之后直接查，不必逐页翻 | 仓库有哪些模块、类、函数；谁导入谁；谁可能调用谁；相关测试、配置在哪 | 修改 `flow/base.py` 之前，先查它的影响面 |

前四项 omp 已具备，本方案不重做；第五项是新建的核心能力。这个组合与第三章的技术路线一一对应：文本与路径搜索（3.1、3.2）、结构化搜索（3.6）、语言服务器（3.5）复用现有；索引式全文搜索（3.3）、符号索引（3.4）与关系图（3.7）合并为新的 repo 工具。它对应 6.10 节列出的两条触发条件：大量时间耗在重复扫描上（网络文件系统把这一点放大），以及跨模块影响经常被遗漏（需要带出处的关系信息）。

语言服务器要工作，需要一个针对 Python 的分析程序（如 Pyright）。本方案不把它打进工具包：公司环境里已安装则自动启用，未安装也不影响其余能力——repo 不依赖它。工具包因此保持离线、零额外安装。

### 7.3 仓库索引的工作原理

repo 的数据流只有三步：

```text
仓库源码
   ↓ 解析：识别模块、类、函数、导入、调用，并把文件区分为源码、测试、配置
   ↓ 存储：写入一个单文件数据库（带全文检索能力），放在用户自己的目录
   ↓ 查询：AI 在任务中按需查询，每条结果都带文件路径和行号
```

五个关键设计：

**解析。** 解析器用 Tree-sitter（GitHub 网页代码导航、Neovim 等编辑器同源），内置 Python 语法库，覆盖 3.6 时期的语法特性，具体写法的实际覆盖以公司代码为准。解析产出结构信息：每个文件定义了哪些类和函数、写了哪些导入语句、调用了什么。这些信息全部来自代码文本，属于静态可见的部分。

**存储与并发。** 索引存放在一个单文件数据库里（SQLite，大量软件内置的同款技术，不需要安装数据库服务）。网络文件系统上，数据库的并发锁与常用的 WAL 日志模式都不可靠，因此存储遵循三条原则：同一时间只允许一个写入者，多个实例并存时其余实例只读；日志模式避开依赖跨进程共享内存的 WAL；写入合并为低频批量事务，不在网络盘上产生碎小写入。

**全文检索。** 检索按代码标识符的特点组织：下划线、点号算作词的一部分，`ERR_TIMEOUT` 是一个词，不是 `ERR` 加 `TIMEOUT`；子串类查询用三字符片段方法实现。每条索引记录都带行号范围，所以结果能给出文件和行号。索引式检索先按词定位、再验证，与逐文件扫描的文本搜索在极端写法上可能给出不同结果；需要穷尽式清单时，仍以文本搜索为准。

**关系。** 索引里“谁和谁有联系”的记录来自四类规则：

- 导入：`import`、`from ... import` 语句本身可以直接、精确地提取；这条语句实际导入哪个文件，则要另行判断——`flow.base` 可能对应 `flow/base.py`，也可能是包的 `flow/base/__init__.py`，还受模块搜索路径和相对导入影响。索引记录导入语句原文，目标文件按规则解析，解析不确定的地方如实标注。
- 调用：从函数体里的调用写法取出名字，与被导入模块中定义的符号名对上号。这一步只做了名字匹配，没有追踪程序运行，所以这类记录是候选。
- 测试：测试文件导入了某模块，就记录一条“该测试与此模块相关”；文件命名的对应关系（`test_flow_base.py` 对 `flow/base.py`）作为辅助线索。两条规则都是推断，记录时标注依据。
- 配置：来源包括显式的配置路径和加载入口，以及配置键与消费代码的对应关系；只凭名称或关键词相同建立的关联记为候选。运行时动态生成、拼接出的配置关联，静态分析发现不了，允许留空。

**增量更新。** 增量分两层：发现变化，重新解析。发现变化优先用已有线索——omp 自己改过哪些文件、版本控制给出的变化清单——先筛出候选再校验内容；线索覆盖不到的外部修改，靠补充扫描发现。修改时间不能保证内容一致，判定变化时必要时读取内容确认；只有确认内容变了的文件才重新解析。文件的删除和重命名同样进入增量处理，随之失效的符号与关系记录一并失效。

### 7.4 五种查询能力

| 查询能力 | 回答的问题 | 结果形态 |
| --- | --- | --- |
| 状态查询（repo status） | 索引覆盖哪些目录、多少文件；索引对应的版本、已知待更新文件与未检查范围 | 状态摘要 |
| 关键词查询（repo search） | 仓库级关键词搜索：查索引，不重扫全仓 | 文件、行号、片段 |
| 符号查询（repo symbol） | 按名称找模块、类、函数的定义位置 | 定义点列表，同名可区分 |
| 关联查询（repo related） | 给一个文件或符号，找相关实现 | 同模块、相互导入、同名的候选清单 |
| 影响面查询（repo impact） | 改动影响面：谁导入或调用了它、相关测试、相关配置 | 候选清单，每条带出处 |

对应到日常任务：

| 日常任务 | 用到的能力 |
| --- | --- |
| 新增功能，先看现有实现和接入方式 | 符号查询、关联查询 |
| 修改旧代码，确认同名实现是哪一个 | 符号查询、关键词查询 |
| 评估一处改动的影响范围 | 影响面查询 |
| 找相关测试 | 影响面查询、关联查询 |
| 找相关配置 | 关键词查询、影响面查询 |
| 找调用关系 | 影响面查询（静态候选），需要进一步核查时用语言服务器 |

### 7.5 能力边界

- 静态分析有边界：“谁调用谁”“哪个测试相关”“哪个配置相关”，答案都来自对代码文本的分析。运行时拼接的调用、动态替换（monkey-patch）、反射，静态分析看不见；语言服务器同样属于静态分析，也不能保证找全动态调用。所以关联查询和影响面查询给的是带出处的候选清单，不是最终结论；确认要回到代码，或用语言服务器进一步核查。
- 索引是快照：低频更新意味着尚未扫描到的修改可能未进入索引。状态查询报告索引对应的版本、已知待更新文件和未检查范围，不承诺与当前文件系统完全一致。
- 找到测试不等于跑过测试：执行测试和判定回归仍按项目既有规则，顺序与 6.3 节一致。
- 不做向量语义检索：维持 6.6 节的结论，先把关键词、结构、关系做扎实；业务描述与代码命名长期对不上时，再按 6.10 节评估。

### 7.6 与公司环境的逐项对应

| 公司环境事实 | 本方案的处理 |
| --- | --- |
| 全部在网络文件系统上 | 查询走索引，不重复扫描网络盘；存储与更新按 7.3 的并发与增量原则设计 |
| 离线、零额外安装 | 解析与索引能力随工具内置，不引入任何需要部署、采购或运维的组件 |
| Python 3.6 老项目 | 解析器内置 Python 语法支持，不要求改造代码 |
| 多人各自使用 | 索引每用户一份、单写入者；多人共享一份索引作为后续可选项单独评估 |
| 语言服务器未统一安装 | 不打包；环境已装则自动启用，未装不影响其余能力 |

omp 本身能不能在公司旧系统上运行（操作系统版本、系统依赖），和它能不能解析老代码，是两个独立的兼容性问题，要分别确认。索引不改动代码库里的任何文件，只是旁边的独立数据，删除索引文件即完全清除。

明确不引入的组件：搜索服务（如 Elasticsearch）、图数据库（如 Neo4j）、向量数据库（如 Milvus、Chroma）、云服务与外部账号。本方案新增的能力全部在 omp 进程内完成。
