# 单元测试正确性验证与修复

为测试提供结构化的编译和运行时错误修复流程，确保测试的编译正确性和运行时正确性。相比临时调试，本技能提供更高效、更可靠的解决路径。

## 核心原则

1. **仅修复测试代码**：不修改生产代码、构建配置文件、第三方库
2. **错误分类优先**：先对错误进行分类，再匹配修复策略，避免盲目尝试
3. **渐进式修复**：一次修复一类错误，修复后重新验证，避免引入新问题
4. **上下文驱动**：围绕被测函数所在文件和定义展开上下文收集，避免盲目搜索
5. **循环验证**：修复后必须重新验证，直到无错误或遇到无法解决的问题

## 反模式禁令

反模式禁令（断言误用、Mock误用、代码修改禁令）详见各语言reference中的反模式禁令或硬性约束章节。

## 用户自定义经验（可选）

1. 使用 `read` 工具读取目标项目根目录下 `.dtagent/experience.json`
2. 如果文件存在，解析 JSON 数组，过滤 `phases` 包含 `"fix"` 的条目
3. 对每个匹配的条目，使用 `read` 工具读取 `path`（绝对路径）指定的经验文件
4. 将用户经验内容作为对应语言 references 的**补充约束**

**优先级规则：**
- 本 SKILL.md 中的**硬性约束**：用户经验**不可覆盖**
- 对应语言 references 中的**策略建议**：用户经验**优先于**内置策略
- 项目特有的**补充知识**：用户经验作为**额外上下文**

如果 `.dtagent/experience.json` 不存在，跳过此步骤。

## 语言路由（强制执行）

检测测试代码语言后，**必须读取对应语言的专属reference**获取语言特定的错误类型、修复策略和验证命令：

本 skill 的 `references/` 和 `scripts/` 路径相对于加载时返回的 baseDir；用 `read` 读取资源时可用 `skill://fix-ut/<路径>`。reference 中的相对链接以该 reference 所在目录为基准，不依赖项目工作目录。脚本命令使用 baseDir 的绝对路径并加引号。

| 语言 | 触发条件 | 必读reference |
|------|----------|---------------|
| **Java** | 测试文件以 `.java` 结尾 | `references/java/fix-rules.md` |
| **C/C++** | 测试文件以 `.c`/`.cpp`/`.cc`/`.h`/`.hpp` 结尾 | `references/cpp/fix-rules.md` |
| **Go** | 测试文件以 `.go` 结尾 | `references/go/fix-rules.md` |
| **Python** | 测试文件以 `.py` 结尾 | `references/python/fix-rules.md` |

语言检测后，若入口文件中引用了子文件则按需读取；若入口文件为自包含（无子文件引用），则直接按入口文件内容执行，不报错。新增语言时只需创建入口文件即可完成基本流程，子文件可后续按需补充。

## 执行步骤

### Step 1: 获取当前错误信息

1. **目标**：获取当前测试文件的错误信息，包括编译错误或执行错误。

2. **动作**：编译测试代码并捕获编译输出，或运行测试并捕获执行输出，获取错误信息。若语言专属reference中提供了意图识别路径或专用工具命令，优先按其执行。

3. **输出内容**：错误信息原文及错误分类。

4. **下一步**：如不存在错误则结束；如存在错误需修复则进入 Step 2。

### Step 2: 上下文信息收集

1. **目标**：根据 Step 1 的错误信息，深入分析导致错误的根本原因，识别需要额外收集的上下文。

2. **原则**：所有上下文信息的收集都围绕被测函数所在的文件以及被测函数的定义展开。

3. **收集策略**（按优先级）：
    - **Step 2.1**：如果多个上下文信息位于同一个方法文件中，优先使用 `read` 一次性读取该文件
    - **Step 2.2**：若 Step 2.1 无法获取所需的 identifier 定义，使用 `grep` 查询出现位置，再用 `read` 获取定义
    - **Step 2.3**：对于构造困难或未提供设置方法的参数/变量/fields，在支持通过 Mock/反射等能力构造的情况下，考虑使用这些方式构造和设置

4. **错误分类**：将错误归类为以下类型之一：编译错误（语法/类型/头文件缺失）、链接错误（undefined reference）、运行时错误（段错误/断言失败/异常）、Mock配置错误（参数不匹配/返回类型不一致）。若语言专属reference中提供了更详细的错误分类表或路由规则，按其执行。

5. **上下文收集完成后**进入 Step 3。

### Step 3: 生成修复后的测试代码

1. **输出要求**（必须）：必须通过 Edit 工具输出修复后的测试文件。

2. **修复原则**：
    - 针对错误分类匹配的修复策略进行修复，具体策略详见语言专属reference
    - 一次修复一类错误，避免混合修改
    - 仅修复测试代码，不修改生产代码
    - 保持已有通过的测试用例不变（除非该用例本身有错误）

3. **修复后**进入 Step 4。

### Step 4: 校验修复结果

1. **目标**：测试文件修复后务必再次验证修复结果。

2. **动作**：使用与 Step 1 相同的方法获取错误信息。

3. **判定**：
    - 如不存在错误 → 修复完成，输出修复总结
    - 如存在错误需要修复 → 返回 Step 2，继续修复循环

4. **修复循环限制**：最多 10 轮修复。达到限制后，使用语言对应的禁用机制禁用无法修复的用例，保留完整代码并注明原因。

## 修复总结输出

修复完成后，输出以下信息：
- 修复前错误概要（错误类型和数量）
- 修复轮次
- 每轮修复的错误类型和修复策略
- 修复后状态（全部通过 / 部分禁用 / 仍有未解决问题）
- 被禁用的用例列表及禁用原因（如有）
- 遇到的无法解决的问题（如有）

## 错误处理

| 场景 | 处理 |
|------|------|
| 测试文件不存在 | 输出错误信息，提示用户提供正确的文件路径 |
| 项目无法编译（非测试代码问题） | 标注为环境问题，提示用户检查项目构建配置 |
| 错误信息无法获取 | 提示用户手动提供编译/运行错误信息 |
| 修复后引入新错误 | 回退到上一个通过状态，重新分析修复方案 |
| 所有错误类型均已修复但测试仍失败 | 检查是否为被测代码本身的问题，若是则标注并结束 |
