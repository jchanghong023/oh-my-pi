# 单元测试断言有效性评审与修复

为测试提供结构化的断言有效性评审，检查断言质量问题并按规范逐步修复，输出修改后的测试文件。

## 核心原则

1. **正确性优先**：修改时优先保证正确性和稳定性，不引入依赖未验证实现细节或第三方内部机制的断言
2. **可观测行为**：只断言可观测的行为，不断言不可检索的内部状态
3. **逐步评审**：按规范顺序逐步评审，前一步的修改结果作为后一步的输入
4. **结合源码**：深度评审需结合被测源码，理解断言目标与业务逻辑的关系
5. **不过度断言**：不为追求更强断言而引入对实现细节的依赖

## 语言路由（强制执行）

检测测试代码语言后，**必须读取对应语言的专属reference**获取语言特定的断言规范、检查清单和修复策略：

| 语言 | 触发条件 | 必读reference |
|------|----------|---------------|
| **Java** | 测试文件以 `.java` 结尾 | `references/java/review-checklist.md` |
| **C/C++** | 测试文件以 `.c`/`.cpp`/`.cc`/`.h`/`.hpp` 结尾 | `references/cpp/review-checklist.md` |
| **Go** | 测试文件以 `.go` 结尾 | `references/go/validity-rules.md` |
| **Python** | 测试文件以 `.py` 结尾 | `references/python/validity-rules.md` |

语言检测后，若入口文件中引用了子文件则按需读取；若入口文件为自包含（无子文件引用），则直接按入口文件内容执行，不报错。新增语言时只需创建入口文件即可完成基本流程，子文件可后续按需补充。

## 评审流程（严格按顺序执行）

执行流程时，不要显示"step1"、"step2"等文字标记，直接执行评审。

### 评审1：规范条款评审与修改

1. **评审**测试文件，检查以下维度：
    - **缺失断言**：无assert、Then阶段无断言、使用System.out/cout手动判断
    - **伪断言**：恒为真、与SUT输出无关、依赖人工观察
    - **异常断言合规**：expected/assertThrows使用、try-catch无断言
    - **断言可读性**：缺失失败消息
    - **Mock/Test Double对断言有效性的影响**
    - **门禁和测试通过标准**
    - **评审关注点**：是否有断言、覆盖关键场景、能检测异常逻辑
2. **修改**：对不合规项进行针对性修改（添加断言、修复异常断言风格、添加消息、调整Mock使用等）
3. 保留修改后的版本作为中间结果，进入评审2

若语言专属reference中提供了更详细的断言规范条款，优先按其执行。

### 评审2：静态特征评审与修改

1. **评审**当前测试文件（评审1修改后的版本），检查：
    - **缺失断言**：是否存在Assert/expect/verify等断言
    - **伪断言**：恒为真断言、仅存在性断言无内容验证
    - **提前退出**：循环/if内return导致后续断言未执行
2. **修改**：修复伪断言、仅存在性断言、可移除的提前退出
3. 保留修改后的版本作为中间结果，进入评审3

若语言专属reference中提供了更详细的静态特征检查清单，优先按其执行。

### 评审3：断言目标与步骤评审与修改（需结合被测源码）

1. **定位被测源码**：从测试类名推断被测类（如 `MockServiceTest` → `MockService` 或 `MockServiceImpl`），在工作区找到对应源文件并读取被测方法及其直接上下文（同文件中调用的方法、实例/静态字段）
2. **结合被测源码**评审当前测试文件，按规范检查：
    - **断言目标**：值变更维度、可观测状态转换、核心逻辑被破坏时断言是否失败
    - **必须断言的内容**：非局部变量、输入对象、返回值的字段级/内容级断言
    - **必须避免的内容**：仅存在性、伪断言、与状态/业务无关
    - **响应式断言**（如适用）：生命周期、终止信号、策略对齐
    - **经验与典型修复**：仅verify不断言返回值、分支返回新实例、多次调用无绑定stub、仅存在性、伪断言等
    - **修改注意事项**：正确性优先、不可检索时不断言、只断言可观测行为、显式约束注释
3. **修改**：对不合规项应用规范的"推荐修复"和"提示"；不引入依赖未验证实现细节或第三方内部机制的断言

若语言专属reference中提供了更详细的断言目标与步骤规范，优先按其执行。
4. 产出最终版本

## 输入

- **测试文件路径**：完成的测试文件路径
- **工作区根目录**：当前项目/工作区根（用于定位测试文件和被测源码；语言专属reference在本skill目录下，无需从工作区根读取）

## 输出

1. **修改后的测试文件**：将最终版本写回用户提供的测试文件路径（或用户指定的路径）。输出必须是有效的、可编译的源代码，不破坏语法或引入未定义符号。
2. **简要修改总结**：在对话中或同目录下，简要列出按规范做了哪些类型的修改（如添加Then断言、移除恒为真断言、添加返回值字段级断言等），用于追溯。

## 约定与注意事项

- 三个评审步骤不得重排：先规范条款（评审1），再静态特征（评审2），最后断言目标与步骤（评审3，依赖被测源码）
- 如果评审3中无法在工作区定位被测源码，仍可基于测试代码和评审1/2规范进行修改，并在总结中注明"未读取被测源码；未进行基于值变更的深度补全"
- 被测代码（业务类、服务、仓库及所有非测试源文件）严格只读，仅修改测试代码，不修改生产代码、构建配置文件、第三方库
- 路径使用正斜杠；从本skill目录的references/读取语言专属规范，避免Windows反斜杠问题
