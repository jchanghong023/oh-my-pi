# 华为云开发者测试规范（断言有效性）— 审查参考文档

本文档遵循 DT 断言有效性审查参考的结构，将 **华为云开发者测试规范** 中与 **断言/验证/测试有效性** 直接相关的条款提炼为审查参考，可供本 Skill 或其他工具使用。  
**目的**：仅作为参考使用；并非 Skill 主体。

---

## 一、缺失断言（规范明确禁止“始终通过”）

**目标**：识别缺乏断言、因此无法自动验证结果的测试用例。

| # | 审查点 | 描述（来自规范） |
|---|--------------|-------------------------|
| 1 | 用例中无断言调用 | 规范指出“始终通过”的用例通常**没有 assert**，无法有效验证被测对象 |
| 2 | Then 部分缺失断言 | 规范强调 given-when-then；**Then 代表测试结果 assert**；若 Then 无断言，风险增加 |
| 3 | 通过 `System.out` 进行人工判断 | 规范**禁止**使用 `System.out`（或类似方式）进行人工判断；**必须使用 assert** 进行自动验证 |

**判定**：若满足 1/2/3 中的任意一项，标记为**断言缺失/不充分**（补充可自动化的断言）。

---

## 二、虚假断言（断言存在但“始终为真/无意义”）

**目标**：识别形式上有断言但缺乏区分能力（对质量防护网无价值）的用例。

| # | 审查点 | 描述（来自规范） |
|---|--------------|-------------------------|
| 1 | 断言条件始终为真 | 规范指出“始终通过”的用例：**assert 条件始终为真**，因此无法有效验证被测对象 |
| 2 | 断言与 SUT 输出无关 | 规范中“始终通过”的描述隐含：断言未引用关键产物（返回值/状态变更/副作用/外部交互） |
| 3 | 依赖人工观察而非断言 | 与“System.out 人工判断”同源：即便有断言，可能仅存在弱检查，关键结论仍依赖对输出的人工观察 |

**判定**：若满足 1/2/3 中的任意一项，标记为**虚假/弱断言**需修复（使断言与关键输出强绑定）。

---

## 三、异常断言合规性（必须可自动验证）

**目标**：当场景预期抛出异常时，确保用例以标准方式断言异常，而非通过日志/人工判断/吞掉异常。

| # | 审查点 | 描述（来自规范） |
|---|--------------|-------------------------|
| 1 | 预期异常但未使用 `expected` / `assertThrows` | 规范要求：测试异常时**必须使用 expected**；JUnit 4.13+ / JUnit 5 可使用 `assertThrows` |
| 2 | 异常被捕获但未断言 | 若 `try/catch` 吞掉了异常且未断言失败，等同于“始终通过”的风险（与规范一致） |

**判定**：若存在预期异常路径但未遵循 1，或满足 2，标记为**异常断言不合规**。

---

## 四、断言可读性与可诊断性（建议项）

**目标**：提升失败诊断能力，降低误解与维护成本。

| # | 审查点 | 描述（来自规范） |
|---|--------------|-------------------------|
| 1 | 断言缺少错误信息 | 规范建议在 assert 中包含错误信息，以帮助读者理解测试意图与失败原因 |

**判定**：若断言普遍缺少信息，标记为**可读性待改进**（不一定是阻断项，但建议补充）。

---

## 五、Mock / Test Double 对“断言有效性”的影响（规则 + 风险提示）

**目标**：识别因不当 Mock 导致断言失真、测试有效性下降的风险。

| # | 审查点 | 描述（来自规范） |
|---|--------------|-------------------------|
| 1 | 滥用 Mock / 任意 stubbing | 规范要求合理使用 Test Double，**禁止滥用 Mock**；过度 Mock 会降低测试有效性 |
| 2 | 在适用 Stub 的场景使用 Mock | 规范强调“优先使用 Stub”；作为审查点：可使用 Stub 的场景不应严重依赖 Mock |
| 3 | Mock 引入非真实行为并扭曲断言 | 规范指出 Mock 的非真实性会降低测试有效性；具体表现为：断言验证的是 stubbed 行为而非真实业务约束 |

**判定**：若满足 1/2/3 中的任意一项，标记为**断言可能失真/有效性下降**；考虑细化测试粒度或使用更真实的依赖（嵌入式中间件/真实实现等）。

---

## 六、门禁与客观“测试通过”标准（与断言结果绑定）

**目标**：将“断言有效性”结果与门禁标准对齐；避免“运行但未验证”或“验证失败但仍然合入”。

| # | 审查点 | 描述（来自规范） |
|---|--------------|-------------------------|
| 1 | MR 门禁要求所有用例验证成功 | 规范给出“所有测试通过”：Errors = 0 且 Failures = 0（Failures 直接对应断言失败） |
| 2 | Flaky 处理稀释断言覆盖 | 规范允许 flaky 用例在门禁中被禁用（例如 `@Disabled`），但要求及时修复；大量被禁用的用例会稀释断言防护网 |

**判定**：若 Failures/Errors ≠ 0 仍可合入，或 flaky 被禁用比例高且长期未修复，标记为**断言防护网失效**。

---

## 七、Committer 关注点（规范对“测试有效”的定义）

**目标**：与人工审查标准对齐，形成可操作的自动/半自动检查。

| # | 审查点 | 描述（来自规范） |
|---|--------------|-------------------------|
| 1 | 测试有效必须“有断言” | 规范：测试有效包括“测试具有断言” |
| 2 | 断言必须覆盖关键代码/关键场景 | 规范：覆盖设计输出要求的关键代码与场景 |
| 3 | 断言应能检测变更引入的异常逻辑 | 规范：能够检测代码修改时引入的异常逻辑（可理解为：关键分支/异常路径具有明确断言） |

**判定**：若用例存在但未满足 1，或 2/3 明显缺失（关键路径无断言/异常路径未断言），标记为**测试有效性不充分**。
