# Dev 阶段性前端原型

这是分阶段开发的**第一阶段 UI/UX 原型**，继续使用本目录已复制的 WebGUI Root、组件、样式和聊天输入框，不是第二套界面或最终产品。当前暂停业务开发与真实后端对接；用户确认前端体验后，再恢复真实 OMP 对接，既有业务目标与最终真实验收要求不取消。

## 界面范围

Dev 仅面向桌面浏览器，不要求手机布局、触屏交互或手机实机验证；检查桌面窗口下的内容可达性与深浅主题。WebGUI 继续按自身要求考虑手机适配，本轮不修改原 WebGUI。

## 独立运行

需要 **Bun >= 1.4.4** 和现代浏览器。在另一台机器拉取仓库后，进入 `packages/dev-frontend` 再执行以下命令；也可以只复制整个 `packages/dev-frontend` 目录到普通可写目录，不需要复制 `node_modules` 或 `build`。

```sh
bun ./standalone.ts install
bun ./standalone.ts start
```

浏览器打开 **http://127.0.0.1:4173/**；按 `Ctrl+C` 停止。默认只监听本机，端口被占用时会明确报错，不自动切换端口。安装需要访问 npm 包源；依赖安装完毕后，原型不需要 OMP 服务、模型/API 密钥、Rust、根仓库安装或 postinstall、原始 vendor 前端以及个人机器配置。

**即使在完整仓库内，也使用上述命令，不要直接运行 `bun install`。** 启动器仅在系统临时目录用本包清单和 `bun.lock` 执行冻结安装，禁用安装脚本，然后把生成依赖复制回本包 `node_modules` 并清理临时目录。源码、样例数据和运行入口始终来自本目录，不复制界面，也不执行祖先 workspace 的安装脚本。重新安装前先停止预览；安装会替换本包 `node_modules`。

等价脚本：`bun run install:standalone`、`bun run start`。可选静态构建：`bun ./standalone.ts build`，输出在本包 `build/dev`；不要直接用 `file://` 打开源码。依赖清单或锁文件变化后重新执行安装命令；不要复制其他机器的 `node_modules`。

## 自由会话

左侧以原 WebGUI 单个项目行显示“自由会话”，直接展开当前项目最近 5 条自由聊天；不再套“项目”分区或重复显示项目名。保留原行内更多、文件、新建会话按钮，以及会话重命名、置顶、归档等操作和展开动画。项目仍由左下角工作区菜单切换。

自由会话不绑定 Release、IR、SR，不创建提案或推进阶段；复用原聊天输入、消息、文件与审查能力。进入自由会话右侧默认打开“审查”；正式需求和需求提案仍默认“只读材料”，两种上下文独立。会话保留创建时的目录身份，查看或切换项目不重绑他人的执行目录。

样例每项目提供 8 条轻量记录，目录列表按更新时间倒序只返回最近 5 条；较早记录保留，不因截取而删除。后续真实实现需在服务查询层限制元数据数量，选中会话后才加载消息，不能先读取全部历史再在前端截断。当前仅内存样例，无真实模型、文件、Git、共享数据库或后端调用；原 WebGUI 不变。

## 提案状态与讨论阶段（原型）

状态与阶段分开，不恢复旧的“草稿”导航分区。提案仍统一显示在“需求提案”中；移除“待评审”状态。

| 提案状态 | 讨论阶段 | 允许的下一步 |
| --- | --- | --- |
| 草稿 | 业务需求 | 使用业务需求 Agent 补齐 IR／SR，提交评审；不要求已有方案 |
| 草稿 | 方案 | 由评审需求的开发人员使用方案 Agent 完成方案，或填写原因打回业务补充 |
| 方案完成 | 方案 | 提交包含 IR、全部 SR 和本轮有效方案的需求 PR；尚未转正 |
| PR 待合并 | 方案 | 查看提交记录；合并并核对默认分支文件后转为正式需求 |
| 正式需求 | 开发流程 | SR 从开发计划开始，随后开发与验证、交付 PR，不再启动方案 Agent |

“提交评审”仅把草稿从业务需求阶段交给开发，切换到方案阶段并记录工号、时间，状态仍为草稿。开发人员点击“生成方案（演示）”后产生静态样例文件并变为方案完成；不声称调用模型或已经真实审核。提交 PR 前若缺少本轮有效方案，动作层和按钮均阻止提交。

“打回业务补充”必须填写原因；记录开发人工号、UTC 时间和反馈，回到草稿的业务需求阶段并增加轮次。IR／SR、目录和各阶段讨论保留；旧方案标记失效，即使文件还在也不能用于 PR。补充后重新提交评审、由开发人员生成本轮方案，才能继续。此处只演示 PR 提交前的打回；提交后的变更或关闭 PR 流程不在本轮扩展。

IR 与全部 SR 在当前阶段共用同一会话，业务需求和方案各有一份提案级会话；历史阶段只读，当前 Agent 不因点击 SR 改变。预置“自动化工作流探索”为业务需求草稿，“团队通知与提醒”为方案阶段草稿。

PR 示例提交后仍留在提案列表。演示合并需确认默认分支已包含 IR、全部 SR 与本轮方案，之后才移入正式需求。正式实现必须由服务端核对真实默认分支提交及完整文件版本，不能凭页面勾选、平台状态或文件存在直接转正。模型调用与 PR 提交仍使用服务账号 A 的配置／凭据，操作人工号另行记录；工号格式检查不是本人或开发权限验证。

正式实现的数据至少包括提案状态、当前讨论阶段、轮次、开发交接记录、方案文件版本及其绑定的 IR／SR 快照、生成／确认开发人、打回原因／时间／工号、PR 信息、默认分支提交及文件核对记录。状态变更应事务化并防重、拒绝旧轮次和迟到结果。数据库仍为 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`，提案目录规则不变。本轮不实现这些后端能力。

## Skill 设计原型

“Skill 设计”是与“技能”并列的独立设置入口，不改造原技能页面的布局或操作。4 项必填为核心任务、适用场景、所需输入、期望输出与成功标准；边界／不适用场景、流程／参考资料、真实例子为选填。桌面左侧填写说明，右侧以“补充讨论／文件预览”标签切换，分别滚动；必填项显示完成数量、具体缺项和定位入口。不设置技能分类或模板下拉选择；“填入示例”按钮只补齐空白，不覆盖已有内容。目标沿用当前 Dev 项目，示例保存位置为 `<项目根>/.omp/skills/<name>/SKILL.md`，属于项目技能，不混入个人级模型／追加提示词配置。

右侧补充讨论直接嵌入现有 `SessionPane`、`V4PaneConversationProvider`、消息流及原输入组件，仅收起窗格标题，不另写简化输入框或聊天执行器。每个项目的技能设计有独立演示会话 ID，与主工作区 IR/SR 会话分开；表单与补充消息共享设计草稿，问题、缺口和建议直接在聊天中说明，不提供字段建议面板或回填按钮；表单由用户自行修改，补充消息进入下一次文件预览。切换右侧标签保留会话与未发送消息。切换其他设置分区后草稿仍可读回；样例回复不表示真实理解、模型调用或工具执行。

“生成预览”仅用静态模板呈现 `SKILL.md` 和 3 个待试用的验证例子。内容、标识或补充消息修改后保留旧预览，列出变更字段并可查看修改前后，重新生成前不能保存；保存区集中展示项目、完整路径、名称冲突和保存结果，禁止覆盖与重复保存。演示保存检查名称和同名冲突，只将项目技能加入本页内存样例；不改变原技能页的作用域、加载方式或操作。刷新恢复初始样例，不写入真实项目文件、不提交 Git、不改变正式 OMP 技能加载状态。生成模板／回复位于 `mock/skill-design*.md`，草稿交互位于 `mock/skill-design.ts`。
