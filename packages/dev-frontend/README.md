# Dev 共享前端与独立预览

本目录维护同一套 Dev 页面、组件、样式和聊天输入框。独立预览注入仓库内样例，OMP 正式入口注入真实宿主数据与原生 RPC；两者共用 `app/DevApplication.tsx`，不复制界面。本轮只分离数据来源及启动装配，不新增原型功能或实现完整 Dev 业务后端。

**最新 Dev 规则已由用户确认为权威需求，见[流程说明](../../docs-zh-CN/spec-driven-orchestration.md)与[OpenSpec 总提案](../../openspec/changes/refactor-dev-webgui-requirement-intake/proposal.md)。此前已更新需求文档；已对齐六个 Agent 设置、IR 验收收尾、仓库级开发准入／并行占用，以及正式入库与开发冻结时点演示；其余差异仍待更新。下述现有样例行为不等于最新需求已经实现。**

## 数据来源与 OMP 挂载

- `packages/ui/src/dev/types.ts`、`data-source.ts` 定义中立视图与注入合同；UI 不直接导入样例模块，纯显示派生由 `domain.ts` 统一维护。
- `preview/main.tsx` 与 `preview/prototype-data-source.ts` 仅供独立预览，继续使用现有内存样例与启动命令，不访问 OMP、真实模型、Git 或业务数据库。
- `runtime/main.tsx` 与 `runtime/omp-data-source.ts` 使用当前 Dev 能力地址内的 HTTP／WS／RPC，读取真实项目、Release、需求和材料，绑定真实工作区及原生会话；网络或读取失败不回退样例，也不自动重放操作。
- 在仓库根执行 `bun run gen:dev` 生成供 `/dev`／`omp dev` 使用的正式内嵌资源；正式模块依赖图禁止加载预览适配器与 mock 模块，运行时不依赖 Vite。预览与正式入口共用 `vite.config.ts`，均以 Firefox 128 为目标。
- 真实入口只开放当前宿主已提供的能力；新版需求评审、方案、并发／冻结、交付、IR 验收、自由会话及角色设置等完整业务仍须按权威规格实施。不把旧协议事实冒充新版业务成功，不新增旧流程界面；原 WebGUI 不变。

## 界面范围

Dev 仅面向桌面浏览器；不要求手机布局、触屏或手机实机验收。后续真实实现保留 Chromium 与 Firefox 128 验证目标。WebGUI 自有手机要求不受影响。

## 独立运行

需要 **Bun >= 1.4.4** 和现代浏览器。在另一台机器拉取仓库后，进入 `packages/dev-frontend` 再执行以下命令；也可以只复制整个 `packages/dev-frontend` 目录到普通可写目录，不需要复制 `node_modules` 或 `build`。

```sh
bun ./standalone.ts install
bun ./standalone.ts start
```

浏览器打开 **http://127.0.0.1:4173/**；按 `Ctrl+C` 停止。默认只监听本机，端口被占用时会明确报错，不自动切换端口。安装需要访问 npm 包源；依赖安装完毕后，原型不需要 OMP 服务、模型/API 密钥、Rust、根仓库安装或 postinstall、原始 vendor 前端以及个人机器配置。

**即使在完整仓库内，也使用上述命令，不要直接运行 `bun install`。** 启动器仅在系统临时目录用本包清单和 `bun.lock` 执行冻结安装，禁用安装脚本，然后把生成依赖复制回本包 `node_modules` 并清理临时目录。源码、样例数据和运行入口始终来自本目录，不复制界面，也不执行祖先 workspace 的安装脚本。重新安装前先停止预览；安装会替换本包 `node_modules`。

等价脚本：`bun run install:standalone`、`bun run start`。可选静态构建：`bun ./standalone.ts build`，输出在本包 `build/dev`；不要直接用 `file://` 打开源码。依赖清单或锁文件变化后重新执行安装命令；不要复制其他机器的 `node_modules`。

本包显式锁定与 React 19 运行时匹配的 `@types/react`／`@types/react-dom`，避免被间接依赖的 React 18 类型覆盖。更新这些依赖后仍按上述独立安装命令准备环境，不需要安装根仓库依赖。

## 自由会话

左侧沿用原 WebGUI 单项目行，命名“自由会话”，不额外套项目层级。展示当前项目最近 5 条记录，保留更多、文件、新建、重命名、置顶及归档操作。选中后右侧默认审查；正式需求和提案默认只读材料。

自由会话不绑定 Release、IR、SR，也不推进提案流程。真实实现须查询时限制元数据数量，选中后才加载消息，不先读取全部历史再截断。当前样例每项目包含 8 条轻量记录，不执行真实聊天或文件操作。

## 工号入口与共享部署

入口固定深色、居中单列表单，只校验小写 `j` 加 8 位数字，例如 `j00808874`；不是身份认证。支持回车、格式错误反馈、同标签页刷新恢复及工作区菜单切换工号。切换后读取该工号的个人开发路径样例，不切换 A 的 OMP Token、模型或 profile。

目标部署为 A 长期运行共享服务，约 200 位同事访问；所有项目共用 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`，项目／Release 清单全员可见。共享项目路径只读，个人开发路径按项目和工号登记，真实开发前须校验服务端可访问、同仓库与可写。原型只有内存样例，无真实共享或权限检查。

## 左侧导航与项目选择

“自由会话”“正式需求”“需求提案”三个分区首次展开，内部 IR 默认收起；导航到目标 SR 时展开所属 IR，用户手动折叠优先，刷新不反复强制打开。正式需求在提案上方，两者复用 WebGUI 项目式标题、IR／SR 行、类型标签和展开动画；IR 点击展开 SR，需求讨论由按钮进入。

搜索沿用 WebGUI 命令中心弹窗，筛选沿用下拉菜单。项目及依赖它的 Release 相邻放在左下角工作区菜单，不显示“OMP”文字；项目变化重选该项目 Release，无 Release 时清空旧值。浏览选择和折叠仅属浏览器偏好，不改变后台执行。

“正在开发”按仓库展示最多两个开发中的 SR、各自阶段和开发人，自己的可继续，其他人的只读；名额跨工号和 Release 统一。IR 验收开始后，“正在开发”显示 IR、验收人和验收／最终 PR 状态，跨 Release 可返回；最终合并核验完成才移除。查看他人开发或验收只读。

## 业务流程帮助

左下角工作区菜单的项目与 Release 下方增加“帮助”，打开沿用现有样式的流程说明弹窗。用业务语言展示提出需求、检查需求、制定方案、确认入库、逐项开发、评审合并、整体验收、完成归档八步，解释 IR／SR／PR 及人工确认边界，不包含登录操作。内容可滚动，支持关闭按钮、我知道了和 Esc；查看帮助不切换项目、会话或推进流程。

## OpenSpec 提案文档与临时工作区

目标为一个 IR 一个 Change，一个 SR 一个 `specs/<capability>/spec.md`，共享 `proposal.md` 和 `design.md`。初始文件先生成于 `/tmpdata/DFT_LAB/omp/{project_name}/{原提交人工号}/{提案id}/openspec/changes/{change-id}/`；目录绑定原提交人和稳定项目标识，不随查看人或个人路径更改。

原型已有提案目录展示／复制、两阶段讨论、业务补充打回、PR 文件交接和默认分支核对视图，全部静态。提案内 IR 的“需求讨论”与任意 SR 进入同一当前阶段的整份提案会话，业务需求与方案分别保留历史，不为每个 SR 重建 Agent。

草稿／方案完成／PR 待合并与讨论阶段分开展示，不增加待评审状态。提案 PR 合入后为正式提案，并不代表实现或归档；冻结、并行与 IR 完成应按上方差异表更新，不能从旧样例推导规则。

### 新建提案与 IR／SR 生成（原型）

点击“新建需求提案”后，在原聊天框输入业务描述，或点击“生成 IR／SR（演示）”填写描述。首次输入以首行为 IR 标题，按固定模板生成 `proposal.md` 及两个能力 `spec.md`，分别展示业务操作与结果、异常处理与恢复；输入原文保留在整组材料中。左侧立即出现 SR，右侧可阅读对应内容，不需要刷新或预置 SR。

后续聊天、顶部“补充 IR／SR（演示）”及评审弹窗的补充入口共用需求更新动作：保留 SR 标识、路径与已有内容，追加说明到 IR 和全部 SR，更新轮次、文件版本及快照。旧评审保留但失效，旧方案不可继续使用；不自动评审、交接、生成方案或提交 PR。

生成后明确发起业务评审，先展示待补充的静态意见；补充异常与验收说明后重新评审，才演示当前版本通过，并允许交给开发、接手方案、生成方案和沿现有提案 PR 演示转为正式需求。普通样例仓库已有其他开发 IR 时，新的正式提案仍受单仓库单 IR 门槛限制；可在 `?demo=empty-requirements` 的空需求场景从头体验新建、生成、补充、重评、入库及 SR 开发准入。

以上均为本页内存演示，不按输入语义智能拆分，不写入真实 OpenSpec 文件、调用模型或连接后端；后续真实能力边界不变。

### 提案确认与交付（原型）

方案完成后，按“确认需求与方案 → AI 提交并推送 → 人工创建需求 PR → 核验 PR 合并”依次明确操作。弹窗绑定打开时的具体文件版本，逐项确认 IR、全部 SR 与 design.md 后才生成候选；推送与人工 PR 登记分开。PR 标题与正文包含候选及完整文件版本，合并核验再次逐文件检查。重新生成方案或修改需求后，旧确认、推送和 PR 不能复用，历史交付记录保留。旧“更多”里的单独材料提交／推送入口已移除，不能绕过统一交付。


## 阶段推进、历史与工作区样例

现有正式 SR 展示开发计划、开发与验证、交付 PR，阶段推进核对演示材料及轮次；历史会话只读，返工保留文件样例并使后续样例材料失效。聊天、文件、审查和暂存按启动时记录的工作区隔离，修改个人开发目录不重绑进行中的 SR。真实停止、递归任务结清、Git 或默认分支校验尚未接入。

## 仓库开发准入与并行占用（原型）

单仓库同时只允许一个开发中的 IR；同一 IR 内依赖就绪的 SR 默认最多两个，并非每个工号一个。同一人可开发两个独立 SR，同事切换工号不获得额外额度。顶部显示仓库额度、前置依赖和具体阻塞原因，左侧列出全部进行中的 SR；点击切换仅返回既有工作区／会话。

开始开发前统一校验正式提案与方案的合并记录、仓库 IR 归属、依赖图、前置 SR 的真实合并记录样例、并行上限及个人目录。依赖缺失或循环、只标完成却无合并记录均不能启动。方案材料展示同一份 SR 依赖映射。工作树与会话仍按 SR 独立固定。

等待评审／合并或停止 Agent 不释放 SR 名额；SR 合并核验只释放该 SR 名额。第一个 SR 开始记录 IR 占用，即使全部 SR 合并、尚未开始验收或等待最终 PR，也继续阻止同仓库其他 IR；最终验收与归档 PR 合并核验后才释放。不能通过删除已开始 IR 绕过占用。不同仓库独立计算。

正常样例已改为 Aurora 同时两个 SR 开发，其他 SR 按依赖等待，不再出现四个 SR 超额。`?demo=parallel-admission` 从一个开发中 SR 开始，另有独立 SR 可由同一工号接手，用于演示第二名额、第三个阻塞及前置合并后解锁。原有 `?demo=ir-acceptance` 演示仍保留。

以上只使用本页内存及登记的样例 repositoryId；不探测真实 clone／远端、不提供多浏览器原子准入或共享锁，也不执行 Git。正式入库与冻结已按下节对齐；SR 代码／测试／规格同 PR 等其他差异仍以上方表格为准。

## SR 代码、测试与规格同 PR（原型）

主界面交付阶段只保留状态和“准备／处理交付 PR”入口，操作收在现有风格弹窗中，避免挤占聊天；关闭弹窗保留状态并可阅读右侧材料。SR 的交付 PR 阶段统一准备代码、测试与 `openspec/specs/<capability>/spec.md` 的交付清单，并在右侧提供 PR 标题、正文、源 Change／SR／冻结版本、候选与对齐默认分支基点；不改写冻结增量，不提前归档。原“更多”里的单独 SR 材料发布不再提供另一个交付入口。

当前轮次完成报告、UT、ST、交付说明完整且可读后才能准备清单。通过当前候选的合并前验证后，明确演示提交、推送分支，再登记人工创建的 PR；只登记链接不代表 SR 完成。告知合并时仍核对当前候选、默认分支基点及代码／测试／规格三类文件，完整后才释放该 SR 名额；IR 占用继续保留。

默认分支更新或材料变化使旧验证失效，须重新准备并验证新候选，已有 PR 重新登记当前候选即可，不强制另建 PR。重新准备及阶段返工保留原交付历史；SR 工作树、分支及启动基点不随重新准备而重绑。后续新 SR 则使用该仓库当前样例默认分支基点。

普通实现问题演示修复后复验；Git 或需求冲突暂停并禁用自动重新准备，必须记录人工处理说明且确认不改变冻结需求和方案。业务或方案需要变化时重新提案。验收和前置依赖都使用包含代码／测试／规格的 SR 合并记录，不只检查“已完成”标签。

`?demo=sr-delivery` 可直接进入当前工号的交付阶段；“演示异常场景”可模拟验证失败、Git／需求冲突或默认分支更新。清单、验证、人工处理记录及合并核验仅为本页静态内存样例，不实际提交、推送、运行测试、同步规格或访问 PR 平台，也不能证明代码正确；真实原生 Git／测试工具与人工流程待后端对接。

## 必经的业务需求评审（原型）

业务需求 Agent 整理 IR 与 SR 后，必须先完成当前版本的业务需求评审，才可“提交给开发”。未评审、发现阻断问题、评审过期或需求材料不全时，界面与动作入口均拒绝交接、开发接手、生成方案、提案 PR 准备与合并核验；正式提案开始开发也检查对应业务评审版本。

评审绑定 proposal.md 与全部能力 spec.md 的实际样例路径、摘要、大小、需求轮次及文件集合，不依赖一个“通过”标签；漏文件、增加或修改能力规格、补充需求与打回都会要求重评。技术 design.md 单独生成不会使业务评审过期，业务评审不代替方案／代码审核或人工确认。

`?demo=requirements-review` 直接打开“自动化工作流探索”提案：首次评审演示发现异常场景不足；补充验收说明后旧评审失效，再明确发起评审，才演示当前版本通过并允许交给开发。原生聊天继续承担业务讨论，不增加字段建议或提示词预览。已入库和已交接的提案提供明确标注的预置通过记录。

评审仅由明确操作发起，不自动循环；失败与旧版本记录可在评审弹窗的历史中查看。“人工业务争议处理”单独记录意见、依据、处理结果、工号、时间及原 AI 评审版本；可要求补充、保留 AI 原结论或暂缓交接，不改写 AI 报告或伪造通过。暂缓及要求补充不会因同材料重评而自动解除；明确新处理结果或更新材料并重评后再按当前结论判断。通过样例仍是预置演示结果，不代表真实模型审核；真实争议协作与共享持久化未接入。

## 正式入库与开发冻结（原型）

提案 PR 合并并核对文件后进入“正式需求”，需求与方案尚未冻结，也不占用仓库开发名额。全部 SR 尚未开发时可明确“修订正式提案”：保留原文件、快照、AI 评审、候选及合并记录，同一 IR／SR 返回需求提案补充。修订期间全部 SR 禁止开始开发；须重新评审、接手方案、人工确认新版本、提交推送和提案 PR 合并核验后，才能恢复开发准入。已开始或冻结的提案不能原地修订，须重新提案。

首个 SR 明确开始且准入检查成功时，整组状态才变为“开发已冻结”，记录冻结人、时间、确认摘要、IR／全部 SR／共享 design.md 文件版本、SR 成员及依赖。第二个并行 SR、阶段推进、停止或浏览切换均不重建快照。后续发现冻结版本、成员或依赖改变时，拒绝继续依赖旧版本的开发和验收；冻结记录缺失不能静默补造。

标题区明确区分“正式提案已入库 · 尚未冻结”与“首个 SR 开始后已冻结”，未冻结的正式 SR 同样有开始开发入口。`?demo=proposal-freeze` 可从全部 SR 尚未开始的正式提案体验第一次冻结，再接手第二个独立 SR；普通开发中及 IR 验收样例保留原冻结记录。

当前只验证与保存内存样例快照，不实现真实文件权限、工具写入拦截、修订提案 PR 执行或 Git 校验；实际冻结正文、集合及版本保护仍待后端实现。

## IR 整体验收与最终 PR（原型）

正式需求每个 IR 行新增“IR 验收”图标，IR 讨论顶部也提供同一入口。全部 SR 完成且有合并核验样例后启用；否则鼠标悬停说明尚未合并的 SR。SR 三阶段导航不变，全部 SR 完成不再让 IR 自动进入“已完成”筛选。

点击入口先查看验收准备状态，由开发人员明确“开始 IR 验收（演示）”。创建独立的 IR 会话及固定修复／归档工作区，模型使用创建时的 IR 验收 Agent 配置；复用现有聊天框、消息和只读材料面板，不把系统提示词当作聊天预览。右侧可选择 IR、全部 SR、共享方案、验收报告和最终 PR 信息。

顶部为“整体验收 → 最终 PR → 完成”。可演示发现问题、修复并复验，或无需修复直接通过。报告绑定当前候选，旧报告保留但失效。确认验收后生成最终 PR 标题与正文，再登记人工创建的 PR 链接；会话只读，仓库仍占用。演示核对最终候选成果及 Change 归档后才完成 IR、释放占用；归档不重复同步规格，不删除分支或 worktree。完整真实 Git／测试／模型／PR 核验仍待接入。

验收报告绑定当前候选、默认分支基点、全部 SR 的合并提交及文件版本。准备最终 PR、推送、登记及合并核验均重复检查这些事实；默认分支或 SR 记录变化后旧验收失效，会话只读。明确“重新对齐并验收”后生成新候选，保留原模型快照、会话、工作树与启动基点；旧报告／PR 清单失效并保留历史，已有 PR 链接可在新候选重验、推送后重新登记。

最终 PR 的详细操作收在弹窗内，右侧显示修复／测试和逐文件归档移动清单。清单从冻结的 Change 文件集合推导，目标为 `openspec/changes/archive/{日期}-{change-id}/`，文件必须全部移动且路径对应、内容版本不变，明确跳过规格同步。无修复时只归档，有修复时只把本轮已验收的实现修复、测试与归档放入同一 PR；冻结的增量需求不改写。

最终候选验证通过且清单完整后，明确演示提交／推送，再登记人工创建的最终 PR。只有当前候选、当前清单和有效报告全部匹配，才允许演示核验合并；完成记录包含修复／测试、目标归档文件、源目录不存在及未重复同步规格等事实，再释放 IR 占用。归档历史材料显示目标路径，不把旧源路径冒充当前默认分支位置。这些都不是实际 Git 或文件系统操作。

“演示异常场景 → 默认分支变化”可验证旧候选无法完成 IR，必须重验及更新原 PR 登记。归档遗漏、字节版本变化、错误目标或再次同步规格的清单也会被动作校验拒绝，不提供靠勾选或仅登记链接强制放行的路径。

预览地址追加 `?demo=ir-acceptance` 可直接打开“账号与权限体验”IR 的准备页，所有 SR 已合并核验为静态样例。正常预览保留原有开发中数据，可查看按钮禁用和等待说明。刷新恢复样例；此参数不修改真实需求、文件或数据库。

## 设置与 Skill 设计

保留原技能页和自动化页，独立增加 Skill 设计，固定字段与简化聊天协同；没有技能说明下拉、字段建议或追加提示词预览。目标复用原生聊天能力，生成的技能存入当前个人开发项目中 OMP 默认可加载路径，无有效绑定时不得写共享只读目录。当前不调用真实模型、不写目录、不执行技能或脚本。

现有模型及个性化设置以服务账号的 OMP 配置为目标，跨项目共用，保存只用于新建角色会话；历史展示创建时模型快照，未保存草稿与取消操作保留。当前已展示六个角色，包括 IR 验收 Agent；个性化页面按角色显示职责并提供独立追加提示词样例，保存、取消及清空沿用原逻辑。真实配置保存、提示词注入与 IR 验收执行仍待实现。

## 空态、失效目录与错误恢复

未选择会话时不再使用固定的样例任务作为后备，也不挂载可发送的聊天框；没有项目、没有 Release、没有需求、失效 IR／SR 和缺失会话分别展示明确状态。没有项目时可直接使用原项目设置组件登记已有 Git 项目，再明确选择；没有 Release 时可添加版本，仍可新建自由会话。空需求列表提供新建提案和自由会话入口，不把空态自动转成提案或模型调用。工作区绑定期间显示读取状态，不留空白。

目录不存在、不可访问、仓库不符或绑定缺失时阻止进入原工作区，不借用共享项目、当前查看人的目录或其他样例。恢复页保留目标上下文，提供重试读取、项目选择和原项目设置；重试只读，不自动重建 worktree、切换项目、重发消息或推进阶段。失效的已开始 SR 应恢复原 worktree，修改个人开发目录只影响之后的新 SR。原型的“恢复目录样例（演示）”只清除故障样例，不检查磁盘、修复权限或移动真实文件。

材料读取失败时保留所选路径与元数据并披露原因，正文不可用时禁用复制、下载、带入讨论及使用该材料的阶段批准；不能仅凭有效摘要或文件名放行。重新读取可恢复暂时读失败的样例，但缺失文件不会因重试凭空出现，需要恢复原文件，或由当前阶段开发人明确生成新的材料样例。尚未生成材料使用中性等待状态，不冒充读取错误；旧版本仍可按原规则只读查看。

发送拒绝发生在接纳消息之前，草稿保留，用户明确重试才再次提交；同一命令结果仍可查询，不伪装成已接纳后又失败。动作失败在修改业务状态之前返回，弹窗内的打回说明、项目路径和名称等输入保留，原阶段不变，成功后才关闭弹窗。恢复读取不自动重放失败操作。文字草稿沿原工号／工作区／会话作用域保存；目录恢复后可读回已保存草稿，不承诺浏览器存储不可用时跨刷新保存，附件沿用原聊天规则。

### 可复现的原型情景

在预览地址后添加 `?demo=<情景>`，每次刷新重新初始化该情景，故障只存在于当前页面的内存样例中；不使用真实文件或数据库：

| 情景 | 展示和验证内容 |
| --- | --- |
| `empty-projects` | 无项目，复用原设置添加已有 Git 项目 |
| `empty-releases` | 当前项目无 Release，可配置或开始自由会话 |
| `empty-requirements` | 当前 Release 无需求，不回落样例聊天 |
| `missing-requirement` / `missing-sr` | 失效目标阻塞，明确返回项目查看 |
| `missing-directory` / `unreadable-directory` / `wrong-repository` | 原目录失效、不可访问、仓库不符；重试不改绑 |
| `missing-material` / `material-read-failure` | 缺失文件与暂时读失败，恢复方式不同，禁止复制和批准 |
| `session-read-failure` | 原阶段会话暂时读取失败，重新读取原记录，不新建会话 |
| `send-failure` | 首次发送拒绝、输入保留、手动重试仅接纳一次 |
| `operation-failure` | 首次打回动作失败、说明与阶段保留、再次明确提交后成功 |

正常地址不启用这些故障；浏览器偏好与已保存草稿仍沿原作用域保留，清除站点数据可完全复位。恢复页沿用已有主题和控件，检查桌面深浅主题及常见窗口宽度；原 WebGUI 不改。所有恢复、重试和生成仍是原型行为，不提供真实网络、目录、Git、模型、PR、数据库或任务生命周期能力。
