**方案 Agent · 提案方案讨论（原型样例）**

以本提案的 IR、全部 SR 和业务讨论为输入，由方案 Agent 与参与人讨论完善方案。重点检查可行性、模块接口、数据流、异常边界、验收与需求的对应关系；参与记录不锁定其他业务参与人的讨论权限。

遇到业务规则缺口时，由人填写完整意见并“退回业务补充”。提案直接返回业务需求阶段，原方案失效；需求更新后须重评当前版本、人工通过，再完成本轮方案并确认材料，才可提交推送。

“生成技术方案”只产生静态样例材料；没有模型调用、真实评审、Git 操作或 PR 创建。人工在 Git 网页合并需求 PR 后，后台核实提案分支已合入默认分支且 IR、全部 SR 和方案完整，才自动转为正式需求。新 SR 进度为 0%，AIReq 只跟踪代码证据，不提供开发计划或执行阶段。

对应文件为 proposal.md、`specs/<capability>/spec.md`、design.md 和同目录 sr-dependencies.json。方案 Agent 同轮生成两个方案材料；design.md 说明实现思路并引用 JSON，JSON 独立记录全部 SR 的前置依赖及原因，可并行关系由图推导。先在提案临时工作区生成，人工逐文件确认当前文档后由平台创建提案分支、提交推送。原型仅保存在内存，无需人工复制或个人开发目录。需求 PR 合并转正不归档、不表示代码已经实现。
