# OMP fork 知识库要求

本项目是 oh-my-pi 的个人 fork。Wiki 面向需要维护、开发和使用本 fork
的读者：在说明必要的上游基础架构的同时，优先深入分析本 fork
新增、修改或重点维护的功能与行为。

## 证据和归属

- 以当前源码和测试确认实际行为；以 `openspec/specs/` 中的已批准规格
  理解 fork 的目标和约束。待定变更不能视为已实现或已批准的事实。
- `openspec/specs/fork-upstream-baseline/spec.md` 记录当前集成的
  上游基线，但它不是 fork 全部工作或个人贡献的完整清单。
- 区分“当前 fork 特有或有差异”“沿用上游但被本 fork 重点使用或
  修改”“已贡献上游”“归属尚未确认”。证据不足时明确标注，
  不要根据功能名称、提交作者或规格名称推断归属。
- 当前生成环境不能直接读取 Git 历史或自行执行上游 diff。
  如有仓库内可读取的历史对比资料，可将其作为线索，但仍需对照
  当前源码和测试；没有证据时不要编造差异或归属。

## 优先分析领域

根据当前源码和规格确认各领域的实际范围，不要把下面的主题
直接当作“全部为 fork 独有”的结论。

1. 内网及离线运行：公司模型、认证与配置来源、离线资源、
   默认行为和限制。
2. Dev 规格驱动工作流：需求、方案、计划、执行四阶段，
   产物、用户批准、状态恢复，以及与 OpenSpec、
   Superpowers 的边界。
3. Team 与 Goal：配置、启动条件、协作流程、状态和失败处理，
   以及它们与 Dev、原生会话和任务的关系。
4. 知识索引与生成：Knowledge、OpenWiki 各自的用途、入口、
   数据所有权、更新和查询方式，以及彼此的边界。
5. TUI 与个人默认行为：显示模式、关键交互、配置覆盖和
   与上游行为的已证实差异。
6. Fork 维护与验证：上游同步基线、功能保留边界、
   fastcheck/fulltest 等门禁的实际职责与适用范围。

## 每个重点功能需要回答

- 解决什么问题，用户从哪里进入，适用于什么场景。
- 入口到核心实现的主要流程、关键模块及状态所有者。
- 关键配置、默认值、优先级、持久化位置和必要前提。
- 重要边界与失败、取消、恢复行为。
- 哪些差异有证据支持，哪些仅是继承能力或归属未确认。
- 对应的规格、源码和行为测试位置。

优先解释跨模块关系和实际运行流程，而不是罗列文件或提交。
对复杂且独立的功能，可设置独立页面；相关页面之间建立链接，
避免把多个重要子系统压缩成一段概述，也不要重复拆页。

Wiki 仍需覆盖理解整个项目所必需的核心架构和流程，但篇幅和
分析深度应优先服务于上述重点功能。不要臆造实现、配置、测试
结果或上游差异；资料不足时如实说明。
