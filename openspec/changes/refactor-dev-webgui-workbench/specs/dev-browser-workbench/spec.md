# Spec Delta

## MODIFIED Requirements

### Requirement: Dev 网页原生浏览器边界

Dev 工作台 MUST 以 Firefox 128 默认启用的原生能力作为最低运行环境及浏览器技术上限；现代浏览器使用同一实现及同一生产资源集，不再以 Firefox 68 为兼容或验收目标。MUST NOT 引入 polyfill、API shim、浏览器专属回退、双构建或现代浏览器专属增强分支。允许开发期编译，但交付的全部脚本、样式、依赖及 Worker MUST 遵守此边界，并保持现有布局、四阶段 SR 流程与交互，不改变宿主权限、人员确认及网络安全边界。

#### Scenario: 同一原生实现完成需求流程
- **WHEN** 用户在 Firefox 128 或现代浏览器中打开同一 Dev 工作台地址
- **THEN** 均能查看需求列表、四阶段及真实只读材料，切换查看阶段而不推进流程，使用共享会话的消息、命令、工具过程和适用问答，并完成 Markdown 上传／下载、当前阶段明确推进／返回、当前方案确认及人工标记／确认
- **AND** 缺失材料、不可用操作与实际执行错误须如实呈现；不得以静态演示、只读替代页或要求升级浏览器代替完整功能

#### Scenario: 连接恢复与安全边界不因浏览器改变
- **WHEN** 任一目标浏览器参与 offline 同会话协作、刷新或断线重连，或在非 offline 环境访问 Dev
- **THEN** 按现有 offline 普通 HTTP／WS 或非 offline 安全策略处理；重连只读取实际状态，不重放消息、工具调用或确认
- **AND** 不以兼容旧浏览器为由降低非 offline 的传输或权限要求，不新增绕过身份、确认或宿主限制的通道；浏览器缺少安全能力且现有策略无法满足时须明确拒绝，不伪称功能成功

#### Scenario: 兼容性检查与证据边界
- **WHEN** 评估 Dev 网页的 Firefox 128 原生能力边界
- **THEN** 检查实际交付的完整脚本、CSS、依赖、资源 URL 及适用 Worker，并通过生产 HTTP(S) 入口使用 Selenium＋geckodriver 驱动本机已安装的真实 Firefox 128（当前版本 128.14.0）、隔离临时配置及默认能力／安全设置，观察布局并操作加载、材料、会话、文件、阶段控制与人工确认；其他浏览器、构建成功或静态检查不能代替本机 Firefox 128 验证
- **AND** 记录实际可执行路径、精确版本、发布通道、操作系统、生产入口及流程结果；无法观察的中文输入法、真实桌面输入或其他交互须标记未验证，不自动安装浏览器、不改写个人浏览器配置、不把未观察到的结果报告为通过

#### Scenario: 工作台图标随生产资源交付
- **WHEN** 浏览器加载 Dev 工作台
- **THEN** 页面显式引用同一能力路径下的内嵌图标资源，真实图标请求成功；不依赖不存在的根目录 favicon，也不为图标放宽原有能力路径或访问限制

### Requirement: 浏览器连接不拥有后台任务生命周期

工作台 MUST 将页面连接与原生 OMP 任务生命周期分开。关闭、刷新页面或临时断线 MUST NOT 停止已确认工作；重连 MUST 展示真实持久事实及仍存活的运行事实，不重放操作。OMP 宿主进程必须存活，本要求不承诺脱离宿主继续执行。

#### Scenario: 关闭页面后继续工作
- **WHEN** 原生 Agent 或获授权任务仍在运行，用户关闭或刷新浏览器
- **THEN** 宿主继续已有工作；再次打开同一工作台后显示所属需求的实际进度、结果和错误，不创建第二任务或自动再次提交输入

#### Scenario: 刷新恢复查看位置而非执行授权
- **WHEN** 同一工作台页签选择一个真实需求及某个查看阶段后刷新
- **THEN** 在读取宿主真实需求列表后恢复该需求和查看阶段；查看阶段可不同于实际进行阶段，恢复只读取和订阅现有状态，不启动会话、不加入共享房间、不重发消息、操作或人员确认
- **AND** 保存位置按工作台入口隔离；不存在的需求、无效阶段或不可用的浏览器存储不得导致误选其他需求或崩溃，未保存选择的新入口仍显示空状态


#### Scenario: 宿主退出或执行事实不可用
- **WHEN** 宿主退出、原生任务失败，或重连时无法确认原运行状态
- **THEN** 如实显示中断、失败或不可用，不因旧画面、旧 running 标记或文件存在推断任务仍在运行或成功
- **AND** 需要停止时复用原生显式停止及结清能力，关闭页面本身不是停止命令

#### Scenario: 当前 TUI 与网页互斥及退出
- **WHEN** 用户从普通 OMP 的 `/dev` 进入工作台，或再次 `/dev` 请求退出
- **THEN** 普通任务未结清时拒绝进入，提示先停止或等待，不暗中取消普通工作；成功进入后当前 TUI 只接受再次 `/dev`，拒绝所有普通命令及输入，不同时操作网页 Dev 与普通 TUI
- **AND** 再次 `/dev` 通过既有 native stop／settlement 结清 Dev 后恢复普通原会话；失败不提前解锁。退出不取消需求、不撤销 Git、不删除材料，关闭网页不退出 Dev 或停止任务
- **AND** 不为普通 `/new`／move／dispose 与 Dev 并存保留会话快照、克隆或额外生命周期；不要求私有 Provider／MCP 克隆，实际借用资源必须避免污染 root，原生生命周期及安全 Git 边界保持

#### Scenario: Dev 终端地址与当前反馈
- **WHEN** Dev 独占当前 TUI，用户查看工作台地址、提交普通输入或按 Esc／Ctrl+C
- **THEN** 地址独立完整显示，窄终端换行不丢失字符，保留终端原生鼠标选择复制及 Ctrl 点击链接能力，不启用该界面的鼠标捕获
- **AND** 被拒绝输入、退出提示、切换状态及浏览器打开失败直接显示在当前 Dev 界面，不藏在退出后才显示的普通会话中；输入仍不交给模型，只有再次 `/dev` 结清后恢复原会话及输入焦点

## ADDED Requirements

### Requirement: 完整复制 WebGUI 后改造 Dev 三栏与紧凑导航

新 Dev 实现的第一步 MUST 将现有 WebGUI 前端代码完整复制到 Dev 自有前端并替换旧 Dev 前端，再仅修改复制后的 Dev 代码实现本组需求。MUST NOT 仅参考布局、挑选组件、直接挂载原 WebGUI 或在原 WebGUI 中增加 Dev 分支；原 WebGUI 前后端、入口、协议、构建配置及正式资源 MUST 保持不变。Dev 副本使用自己的前端状态、构建和资源入口，复用 OMP 原生能力而不另建执行器。新 Dev 使用左侧需求导航、中间 AI 会话、右侧只读材料；左侧沿用 WebGUI 同类控件及列表节奏，顶部项目与其 Release 在同一区域相邻展示，先选项目再选该项目的 Release，其下单一新建菜单承载两种需求来源与导入；中部为当前开发 SR 快捷入口、当前 Release 平铺 IR 及可折叠草稿，底部固定 OMP／设置入口。协作入口属于当前会话顶部。

#### Scenario: 先完整替换再实现
- **WHEN** 开始重构 Dev 前端
- **THEN** 先完整复制 `vendor/zcode-frontend/preview/` 的 WebGUI 前端代码替换现有 Dev 前端，后续需求改动仅落在 Dev 副本及其 Dev 集成，不保留旧 Dev 前端或双轨入口。

#### Scenario: 第一阶段仅评审前端原型
- **WHEN** 用户尚未确认本轮 Dev 前端的 UI/UX
- **THEN** 仅调整复制后的同一套 Dev 界面，独立运行并使用仓库内按模块维护的假数据，不接 OMP、真实模型、Git、业务 HTTP/WS 或真实协作；预览不要求安装 Rust、OMP 原生模块或配置模型凭据
- **AND** 每个展示中的 Dev 模块均有连贯的示例内容，覆盖项目、Release、正式 IR/SR、草稿、聊天、四阶段、材料、文件与审查、协作、设置及操作记录；必要交互只更新前端演示状态，源码、假数据、资源、锁文件和启动说明一并纳入仓库，另一台机器可按说明预览
- **AND** 不将模拟对话、材料、阶段状态、审批或日志冒充真实执行，不写入正式后端状态；此阶段只是临时评审，不满足本规格的真实业务交付要求

#### Scenario: 前端确认后恢复真实对接
- **WHEN** 用户明确确认当前 Dev 前端可进入后端对接阶段
- **THEN** 在同一套界面逐项将假数据替换为真实 OMP 原生能力，完成本组完整最终需求，不保留假数据兜底；不得将第一阶段独立预览理解为最终永久不接 OMP
- **AND** 默认 fastcheck/fulltest 和 `F:\testgithub\test` 中 OpenCode Go `beam-free` 的完整真实流程验收仅暂缓，须在用户允许恢复后完成；原型观察不抵充真实功能、日志或模型输出的验收证据

#### Scenario: 第一阶段保持 WebGUI 同类控件风格
- **WHEN** 在 Dev 副本调整已有组件或增加同类型组件、控件
- **THEN** 沿用原 WebGUI 的组件、CSS、间距、字体、颜色、圆角和交互状态，不建立另一套视觉体系；中间聊天输入框保持原组件及原有文字，不添加额外说明
- **AND** 只读材料作为原右侧面板中文件、审查、辅助对话的同级标签页，默认打开并选中，关闭、切换、收起和重新打开沿用原面板，不增加永久固定的额外材料栏


#### Scenario: 原 WebGUI 不受改造影响
- **WHEN** Dev 副本增加需求导航、多项目设置、材料查看及四阶段控制
- **THEN** `/webgui`／`omp webgui` 仍使用原来的前端与宿主，不新增 Dev 工作流，不修改原 WebGUI 源码、构建配置或正式资源；Dev 新状态不污染原 WebGUI 的项目、会话或浏览器状态。

#### Scenario: 紧凑需求列表
- **WHEN** 用户查看项目需求
- **THEN** 不展开 Release/IR/SR 三级树，不使用占据大量空间的需求卡片；IR 使用统一标题行及次级 SR 数量／状态，标题由 AI 生成。列表头部提供搜索和状态筛选，只有列表滚动，项目／Release 选择区、设置及新建入口保持稳定；搜索、筛选和展开不改变执行状态。

#### Scenario: 单一新建入口与草稿恢复
- **WHEN** 用户点击“新建需求”或查看草稿
- **THEN** 菜单分别提供项目内新建、整理并交接需求、导入需求包，选择后执行原有语义，不增加名称或背景前置表单；草稿与正式 IR 分开，可折叠并显示数量，当前选中或新建草稿保持展开。
- **AND** 项目与 Release 相邻并按父子关系选择，Release 选项只属于当前项目；手机端切换项目后保留导航，以便继续选择 Release，不强制跳回聊天。新建或导入不得引用其他项目的 Release。

#### Scenario: 跨 Release 定位当前开发
- **WHEN** 当前项目有开发中的 SR，而人员正在查看其他需求或 Release
- **THEN** 独立“正在开发”入口显示该 SR、所属 IR 及实际阶段；跨 Release 时注明来源，点击只返回既有会话及其 Release，不启动第二任务或推进阶段。选中背景表示查看位置，工作标记表示实际开发，两者不混为一体。

#### Scenario: 项目与需求的空状态
- **WHEN** 当前配置无项目、所选项目无 Release 或当前 Release 无正式需求
- **THEN** 分别引导添加已有 Git 项目、添加 Release 或从新建菜单创建草稿，不默认创建对象、回落到别的项目或启动 Agent；项目登记清单归 OMP 个人配置，每个项目的 Release 清单归其自身 Git 仓库，页面选择只影响当前浏览器。切换项目必须替换为该项目的 Release 首项，无 Release 时清空旧值，不沿用其他项目选择。

#### Scenario: 查看 IR 和 SR
- **WHEN** 用户选择 IR 或其 SR 标题
- **THEN** IR 恢复原需求讨论并展示 IR 和 SR 清单；选择 SR 只展示完整需求，不启动 Agent、不开始开发。

#### Scenario: 草稿与正式导航分离
- **WHEN** 新建后仅产生工作目录或未通过审核的材料
- **THEN** 不以此在正式 IR 列表添加占位需求；草稿恢复仍由真实记录和 OMP 会话引用支持。

### Requirement: 实际阶段与历史材料分离

SR 开始开发后，中央会话顶部 MUST 显示 SR 标题、实际阶段和四阶段导航。点击阶段只选择右侧材料，实际阶段及当前会话不因历史浏览改变。

#### Scenario: 当前阶段条
- **WHEN** SR 正在开发计划
- **THEN** 展示技术方案、开发计划、开发与验证、交付 PR；区分已完成、当前、未开始，不再展示旧八阶段。

#### Scenario: 查看过去阶段
- **WHEN** 用户在开发与验证时点击技术方案
- **THEN** 右侧显示历史方案并同时标明查看阶段与实际阶段；中间继续当前阶段会话，不停止 Agent、不回退或推进。

#### Scenario: IR 不显示开发阶段
- **WHEN** 用户处于浏览器需求讨论或 IR 总览
- **THEN** 只显示整理、待确认、检查中、可下载或待需求合入等适用状态；不把 IR 放入 SR 开发流水。

### Requirement: 正式材料只读与统一材料菜单

IR、SR、方案、计划、完成报告、验证及交付材料 MUST 全部只读。右侧默认展示当前阶段材料，支持切换、收起、重新打开、复制、下载和带入讨论，不另建阶段管理页面。

#### Scenario: 材料未生成或失效
- **WHEN** 所选资料缺失、尚未生成或依赖已变化
- **THEN** 分别显示尚未生成、真实错误或已失效需重新生成；不展示假产物，不把已失效测试报告作为当前结论。

#### Scenario: 统一材料入口
- **WHEN** 用户展开材料菜单
- **THEN** 能查看 IR、当前 SR、方案、计划、完成报告、UT/ST 记录及交付说明等已有材料；方案只维护一个当前版本，正文说明推荐理由和取舍，不提供候选 ID 选择流程。

#### Scenario: 修改正式内容
- **WHEN** 用户希望改标题或资料正文
- **THEN** 通过 AI 对话，在获准阶段内更新；不提供正文编辑器、重命名表单或拖拽拆分。设置中的项目名称和目录不属于 IR/SR 标题。

### Requirement: 单项目单 SR 与独立开发 worktree

同一项目跨全部 Release 和 IR MUST 同时最多一个 SR 处于开发流程。各 SR MUST 在实际开始时从默认分支创建固定开发分支和 worktree，并持续复用至本轮流程结束。

#### Scenario: 开始前检查
- **WHEN** 人员在 SR 材料顶部点击开始开发
- **THEN** 仅在需求已合入、整组已冻结且本项目无其他开发 SR 时允许；有远端先获取默认分支最新提交，失败暂停启动，无远端使用本地默认分支但不能绕过需求合入门槛。

#### Scenario: 实际开始
- **WHEN** 全部准入检查成功
- **THEN** 切换到该 SR 的技术方案会话，右侧显示方案或尚未生成；查看 SR 本身不会创建开发 worktree。

#### Scenario: 等待交付仍占用
- **WHEN** 当前 SR 等待评审或代码 PR 合入
- **THEN** 继续占用名额；暂停 Agent、关闭页面、重启 OMP、切换项目或删除本地显示记录不释放占用。

#### Scenario: 代码合入后结束
- **WHEN** 人员确认代码 PR 已合入默认分支且自有工作已结清
- **THEN** 结束本 SR 的 Dev 流程并释放名额，提醒清理 worktree；不自动删除工作目录或分支，未保存改动须如实披露。

### Requirement: 四阶段明确批准与真实验证

SR MUST 从技术方案开始，经开发计划、开发与验证、交付 PR 四阶段推进；进入下一阶段需要人员明确动作。开发与 UT、ST MUST 合并为开发与验证，分别记录真实 UT/ST 结果。

#### Scenario: 方案计划推进
- **WHEN** 人员查看当前方案或计划
- **THEN** 使用确认方案进入计划、确认计划进入开发与验证等明确动作；聊天、文件存在或 Agent 回复不形成批准。

#### Scenario: 开发验证报告
- **WHEN** Agent 完成获授权的实现和验证
- **THEN** 交付完成报告、验证记录、限制和未完成项，等待人员确认；未执行、失败和环境限制如实保留，不冒充全部通过。

#### Scenario: 不重复需求阶段
- **WHEN** SR 准备技术方案
- **THEN** 使用已确认冻结的 IR、SR 全文和记录，不再重复一遍业务整理或 SR 撰写。

### Requirement: 人工 PR 与代码合入终点

需求 PR 和代码 PR MUST 由开发人员在公司平台手动创建、评审和合并。Dev 可按明确操作执行 Git commit/push 并准备说明，但 MUST 不依赖 PR API。代码 PR 合入后本版 Dev 流程结束。

#### Scenario: 同仓库目标
- **WHEN** 开发人员准备交付
- **THEN** 使用同一仓库的默认分支作为 PR 目标，通常为 main 或 master；不要求 fork，不直接向默认分支推送。

#### Scenario: 人工状态标记
- **WHEN** 人员标记已提交 PR 或已合入
- **THEN** 记录对应明确决定及 Git 可证明的事实；无 API 时不伪称已经查询到平台审核或关闭结果，不把提交、推送和 PR 创建合并成同一状态。

#### Scenario: 普通状态变化
- **WHEN** 人员切换、确认或登记 PR 状态
- **THEN** 不强制为每次状态变化 commit/push，不创建无限的状态 PR；原生 Git 操作仍需明确范围与授权。

#### Scenario: 后置测试交给既有流程
- **WHEN** 代码 PR 已合入
- **THEN** 不新增测试人员测试、复测、关联修复 IR 或同 SR 多轮合入后修复管理；公司后续测试流程独立处理。

### Requirement: 返工保留代码并使后续材料失效

返回技术方案或开发计划前 MUST 停止并结清当前 SR 的 Agent 及递归子任务。返回 MUST 保留已有代码，不执行自动代码回退；修改前序材料后，需要重新确认并重新生成或验证相关后续成果。

#### Scenario: 只查看历史不失效
- **WHEN** 用户仅查看过去的方案或计划
- **THEN** 保留当前阶段、批准和报告资格；不把查看历史变成 Back。

#### Scenario: 实际修改方案计划
- **WHEN** 人员明确返回且 Agent 更新方案或计划
- **THEN** 该步骤批准及后续依赖产物失效，历史可查看；Agent 依据现有代码调整实现，后续验证必须检查旧实现残留和新方案一致性。

#### Scenario: 停止失败
- **WHEN** 后代任务、工具或外部进程未确认结清
- **THEN** 保持原阶段并显示可重试失败，不在仍有写入时完成返回。

#### Scenario: 已交付后请求返回
- **WHEN** 代码 PR 已合入
- **THEN** 不通过普通 Back 撤销默认分支代码或重开已结束执行；后续问题交公司既有流程。

### Requirement: 正式资料 Git 与共享流程 JSON 分离

正式需求、方案、计划及交付时已有报告 MUST 使用可读 Markdown 和必要 JSON 纳入 Git。当前阶段、开发占用、PR 标记、任务结果及 OMP 会话引用 MUST 作为非 Git 的共享工作流 JSON 保存，不新增 Dev 专用 SQLite。

#### Scenario: 运行状态不随资料提交
- **WHEN** 资料被提交到需求或开发分支
- **THEN** 不夹带进程、端口、队列、锁、绝对路径或聊天副本；Git 拉取只保证材料可读，不保证重建完整运行进度。

#### Scenario: NFS 上工作流数据共享
- **WHEN** 同项目存在多个 worktree 或用户顺序换机器
- **THEN** 访问同一份必要工作流状态，不能各 checkout 独立形成相互矛盾的开发占用；结构带格式版本和稳定引用，按钮状态从真实事实计算。

#### Scenario: 未生成的后置资料
- **WHEN** 代码交付时尚没有公司后续测试结论
- **THEN** 不预造未来报告，不强制通过 Dev 为未来每次测试状态创建 PR。
