# Proposal

## Why

Dev 需要成为以 AI 对话为中心的需求整理和开发工作台：既支持开发人员本地工作，也允许业务人员只通过浏览器，在开发人员长期运行的多项目 Dev 中整理可交接的完整需求。实现第一步是完整复制 WebGUI 前端代码并替换现有 Dev 前端，再仅修改复制后的 Dev 代码实现本组需求；原 WebGUI 不修改。现有八阶段单需求模型、旧 Dev 前端、单实例业务写作、平台 PR API 及 Git 状态管理，与本轮确认的 Release／IR／SR、人工 PR 和 NFS 使用方式不一致。此前较复杂的并行 SR、自动撤销和后置测试闭环已被明确收缩，需要形成可执行、可验收且不影响普通 OMP 和 WebGUI 的新需求基线。

## What Changes

### 1.1 分阶段实施与当前临时状态

**当前仅处于第一阶段：Dev 前端 UI/UX 原型评审。以下临时开发安排不替代第二节及配套增量规定的最终产品目标。**

Dev 的界面设计、实现和验收仅以桌面浏览器为目标，不要求手机布局、触屏交互或手机实机验证。桌面窗口尺寸变化仍应保持内容和操作可用。WebGUI 继续按其自身要求考虑手机适配；本轮不修改原 WebGUI 的需求、代码、构建或资源。

- 第一阶段继续调整已经从 WebGUI 复制的同一套 Dev 前端，不另建简化原型页面。原 WebGUI 不修改；所有 CSS、组件、控件、间距及交互状态沿用 WebGUI 同类型实现，新增控件也不得自创另一套风格。聊天输入框沿用原组件和原有文字，不增加额外说明。
- 第一阶段不对接 OMP 或真实后端，不启动原生 Agent、模型、Git、流程执行器、业务 HTTP/WS 或真实协作。独立预览只需要 Bun、浏览器及前端依赖，不以 Rust、OMP 原生模块、模型凭据或本机临时配置为前提。
- 每个展示中的 Dev 模块均须有单独维护的假数据，包括项目、Release、正式 IR/SR、草稿、对话、三阶段开发、只读材料、文件与审查、协作、设置及操作记录。数据须组成连贯的演示项目，源码、假数据、必要资源、锁文件和启动说明一并纳入仓库，另一台机器拉取后可按同一说明预览。
- 切换、展开、弹窗、选择和必要的编辑演示仅改变前端本地状态；样例对话回复、阶段状态、材料及日志全部是展示数据，不代表真实 AI 输出、审核通过、Git 操作、模型运行或业务成功。不得把演示假数据写入正式 OMP 状态、需求材料或配置。
- 右侧只读材料是原侧边面板中与文件、审查、辅助对话平级的一个标签页，默认打开并选中；不再增加永久固定的额外材料栏。
- 第一阶段以用户确认当前界面的布局、风格、内容和交互为退出条件。确认之前不得恢复后端业务开发、OMP 对接或软件测试；允许启动纯前端页面并实际查看、操作原型，不将页面观察记为业务验收通过。
- 第二阶段在用户确认前端后，将同一套界面的假数据来源逐项替换为真实 OMP 原生能力，完成本提案全部最终业务要求，不保留假数据兜底或另建执行器。
- 第三阶段在用户允许恢复测试后，完成默认 `bun run fastcheck`、`bun run fulltest`，并在 `F:\testgithub\test` 使用 OpenCode Go 的 `beam-free` 模型实际走通完整流程，核对真实功能、日志和 AI 输出。当前只是暂缓这些最终验收，不是取消、降低要求或以原型结果替代。


### 2. 最终产品目标

Dev 以 AI 对话为主要工作方式。用户在聊天中描述问题、回答追问、提供资料、提出修改和继续开发。正式资料的生成与修改由 AI 完成，人员通过明确动作确认或推进。实现顺序必须是：先将 WebGUI 前端代码完整复制到 Dev 自有前端并替换旧 Dev 前端，再修改该 Dev 副本实现本组需求，保留阶段文档清晰可见的能力；不是只参考布局、挑选组件或直接挂载原 WebGUI。

原 WebGUI 是只读复制来源，不修改其前端、后端、入口、协议、构建配置或正式资源，也不向 `/webgui`／`omp webgui` 增加 Dev 功能。本提案中的需求整理、多项目设置和三阶段开发均由 Dev 自身实现。Dev 副本使用自己的前端状态、构建和资源入口，继续复用现有 OMP 原生会话与底层能力，不另建执行器，不将 Dev 业务状态或控制写入原 WebGUI。

所有 IR、SR、标题、拆分结果、技术方案、计划、完成报告、验证资料和交付说明均只读。用户可以选择、查看、复制、下载、将资料带入讨论，以及执行明确流程动作；不提供正文编辑器、标题改写表单或拖拽拆分。设置中的项目名称、工作目录和个人追加提示词是配置，不属于需求标题或正式需求正文。

### 3. Release、IR、SR

- Release 组织计划交付范围和整体进度，先选项目、再选其 Release，不绑定代码分支。项目与 Release 清单统一存入 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`，全 Web 共享，所有人可同时查看；Release 始终归属项目，不随 OMP profile 或 Git clone 另建清单。共享项目路径只读，查看项目不要求配置个人开发目录。
- IR 保存背景、目标、范围、边界、规则及讨论结果，包含一个或多个 SR。
- SR 保存完整、明确、可测试的系统要求，是开发单位。小需求允许仅一个 SR。
- 提案方案覆盖整份 IR 和全部 SR；IR 本身不进入 SR 的开发计划、开发和验证流水。需求 Agent 一次整理 IR 和全部 SR，不让每个 SR 再重复业务整理及需求撰写。
- IR、SR 的标题全部由 AI 生成和修改。内部有稳定 ID 用于关系和追溯，左侧不显示编号。
- 同一 IR 的 SR 可以相隔很久才启动；第一版不实现 SR 依赖关系调度，不考虑多人同时开发同一个 SR，也不处理多人跨 clone 同时修改 IR/SR。

### 4. 统一需求提案入口

所有用户先以工号进入同一 Dev Web，入口只检查工号格式，无密码，不验证员工本人身份。服务由 A 的账号长期运行，模型调用和提交 PR 使用 A 的凭据，操作仍记录实际工号。工号格式为小写 `j` 加 8 位数字，例如 `j00808874`。

顶部提供“新建会话”和“新建需求提案”；需求提案不再区分本地新建与浏览器交接两条主流程。登录入口固定深色；左侧先“正式需求”、后“需求提案”，两栏使用原 WebGUI“项目”的可折叠标题，支持整栏及本栏所有 IR 展开／收起，并共用同一 IR／SR 列表、展开动画、类型标记、讨论入口及搜索筛选控件。提案 IR 可展开下属 SR；同一提案下点击任意 SR 或 IR 的“需求讨论”均进入该提案当前讨论阶段的同一个提案级 Agent 会话（业务需求 Agent／方案 Agent），共用该阶段历史、未发送输入与上下文，不按 SR 创建独立会话；SR 选择只影响材料定位。不同提案保持会话隔离，正式 SR 的开发会话规则不变，不提前进入三阶段开发。提案文件目标目录为 `/tmpdata/DFT_LAB/omp/{project_name}/工号/提案id/`。`project_name` 是登记时固定的目录标识，不随项目显示名变化；工号取原提交人，不取当前查看人。提案 IR 的“更多”展示只读目录并支持复制。所有项目元数据共用 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`，按项目 ID 关联，不拆分项目数据库；本轮仅展示样例与复制，不创建文件或数据库。

左侧在正式需求上方恢复“自由会话”：直接复用 WebGUI 的单项目行，仅把项目显示名改为“自由会话”，展开即当前项目最近 5 条聊天，不套“项目”分区、不重复显示当前项目名。保留原行内更多、文件、新建会话及会话操作和动画。项目仍由现有左下角菜单切换。自由会话不绑定 Release、IR 或 SR，不触发需求流程；聊天复用原生能力，右侧默认“审查”，正式需求和提案仍默认“只读材料”，上下文分别管理。服务查询层按更新时间降序且稳定排序限制最近 5 条元数据，选中才加载消息；旧记录保留，不先拉取全部历史再前端截断。会话创建时的目录身份保持原生规则，查看与切换项目不转移执行或重绑他人目录。此轮只实现前端内存样例和文档，真实持久化、权限和执行能力待后续对接。

提案状态与讨论阶段分开：草稿可处于业务需求或方案阶段；完成方案后为方案完成；提交 PR 后为 PR 待合并；经评审合并且默认分支包含相关文件后，才成为正式需求。不保留“待评审”状态，也不恢复独立草稿导航入口。业务需求和方案两阶段各由一个提案级 Agent 处理，IR 与全部 SR 在当前阶段共用该会话。

提交评审时不要求方案，草稿从业务需求阶段交给开发并进入方案阶段。评审需求的开发人员使用方案 Agent 完成最后必要的方案步骤，才能提交包含 IR、全部 SR 和方案的 PR。生成方案遇业务卡点，开发人员填写原因打回业务补充；回到草稿业务需求阶段，旧方案失效，补充后需重新交给开发并生成本轮方案。

本轮仅修改原型、演示数据和相关需求文档；方案生成、PR 提交及合并核对均为静态／内存演示，不接真实模型、Git、PR、数据库或开发权限验证。原 WebGUI 不承载新增流程。

### 5. 多项目设置和项目切换

- Dev 设置中登记项目名称和服务器共享目录，登记后共享目录只读；每个项目另提供按工号关联的个人开发目录。只登记服务器已存在且有效的 Git 仓库；不自动 clone，不替用户创建目录，不修改原 WebGUI 的项目设置。
- 项目与 Release 清单统一存入 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`，全 Web 共享，所有人可同时查看；Release 始终归属项目，不随 OMP profile 或 Git clone 另建清单。共享项目路径只读，查看项目不要求配置个人开发目录。
- 每位同事进入开发前，必须在所选项目下添加自己的“开发项目”路径，按工号与共享项目 ID 关联保存到同一数据库；该路径指 OMP 服务端可访问的已有 Git 工作目录，必须校验 Git 有效性、与共享项目的仓库对应关系及可写性，不可直接使用共享只读目录。修改个人路径不覆盖共享项目、不改变其他工号的绑定，不重定向已有运行任务。
- 项目与依赖它的 Release 选择入口收进左下角 工作区菜单，同组相邻，项目在前、Release 在后；打开方式、子菜单样式与动效沿用界面主题。左下角菜单按钮持续显示当前项目及 Release 摘要，顶部不再放置选择器。切换项目只改变当前浏览器的查看、输入和材料目标，同时替换 Release 选项并选择新项目的首个有效 Release；没有 Release 时清空旧选择并引导添加，不沿用其他项目的 Release。其他浏览器以及原项目的 Agent、任务继续保持原归属。
- 注册、打开或查看项目不启动模型。选择无效目录、项目不可用或连接绑定失败需明确报错，不默默回落到另一项目。
- 需求整理使用 Dev 自身的多项目宿主与 OMP 原生会话能力；切换项目、整理需求或下载不重复执行全进程模式交接，不结清其他项目工作。首次 `/dev` 进入及再次 `/dev` 退出仍遵守原生独占与结清规则；接手人自己的 Dev 开发入口继续存在，不借用或改造普通 WebGUI 入口。

### 5.1 个人级 Agent 模型与追加系统提示词

- Dev 提供“模型设置”和参照 WebGUI 风格的“个性化”页面，分别配置业务需求、需求评审、方案、计划、执行 5 个核心 Agent 的模型／思考强度和追加系统提示词。需求评审独立审查业务需求 Agent 的 IR、全部 SR 及整体覆盖；测试与技术审核复用 OMP 原生子代理和既有模型配置，不再增加独立 Dev 配置角色；完成报告与 PR 材料由执行 Agent 整理。
- 上述模型和提示词属于当前 OMP 个人配置／profile，不属于任何项目。最终持久化必须直接复用现有 OMP 用户级配置目录及其路径解析，默认示例为 `~/.omp/agent`，自定义配置根、agent 目录、profile 和 XDG 沿用现有规则；不硬编码默认目录，不写入各项目的 `.omp`、仓库、Release、IR/SR 或 worktree，不另建按项目的覆盖配置。
- 同一有效个人配置下，切换项目共用同一份角色模型、默认模型和追加提示词；不同个人配置／profile 按 OMP 原有隔离规则处理。设置页展示个人级、跨项目作用范围，不提供项目级作用范围切换。原型路径只能标为示例，正式路径由宿主返回。
- 个性化页面选择 Agent 后直接编辑其追加系统提示词，沿用已有编辑器、保存／取消及 Ctrl/Cmd+S。留空表示不追加个人内容，不能删除或替换内置系统提示词；保存一个角色的内容不能覆盖其他角色的内容或模型配置。未保存草稿与已保存配置区分，大小超限时明确阻止保存。
- 追加提示词不能扩大原生工具权限、改变角色职责、绕过冻结／人员确认，或解除项目写入与 Git 边界。保存配置不启动模型、重放请求或重建正在运行的会话；后续创建对应 Dev Agent 时采用其个人配置，不改写已有会话历史。普通 OMP／WebGUI 的全局用户指令和原生子代理配置继续沿用原机制。
- 本轮仅修改同一套 Dev 前端原型和相关文档：提供 5 个角色的静态提示词样例与内存交互，不读取或写入真实 OMP 目录，不实现配置服务、真实持久化、提示词注入或后端业务。真实对接仍等待第一阶段前端确认，不以“保存”演示宣称配置文件已落盘。

### 5.2 独立 Skill 设计入口

- 设置中新增与原“技能”并列的“Skill 设计”，不修改原技能页布局、功能或入口，不把新建表单塞入原技能管理页面。该入口不是新的 Dev 阶段或固定 Agent 角色，不增加 IR/SR 流程节点。
- 采用结构化任务说明＋补充讨论＋生成预览：核心任务、何时使用、需要哪些输入、期望输出与成功标准为 4 项必填；边界／不适用场景、流程／规则／参考资料、真实例子或失败情况为选填。名称与 description 由设计过程辅助生成，保存前确认标识、格式、名称冲突、引用与路径；不强迫用户先手写完整 Skill 格式。
- 桌面采用左右工作区：左侧填写技能说明，右侧通过“补充讨论／文件预览”标签切换，分别滚动，生成和保存操作保持可达；切换标签保留同一设计会话及未发送草稿。必填项显示完成数量、具体缺项和定位入口。不设置技能分类或示例模板下拉选择，只保留次要的“填入示例”按钮；填入示例只补齐空白，不覆盖已有内容。
- 问题、缺口、冲突和建议直接通过补充聊天说明；不提供字段建议面板、建议确认／忽略或回填表单操作，表单由用户手动修改。表单、标识或补充消息变化后保留旧文件预览，列出变更字段并可对照修改前后；重新生成前禁止保存。保存区集中展示当前目标项目、完整路径及同名冲突，禁止覆盖已有技能及重复保存。
- 补充讨论复用主页面聊天组件及 OMP 原生会话、消息、附件、停止、错误和必要工具／审批交互能力，只精简外围展示，不另建输入系统、聊天服务或执行器。技能设计会话须绑定目标项目及其草稿，并独立于当前 IR/SR；表单变化进入同一设计上下文，聊天中的补充保留在同一设计上下文并参与下次文件预览，不修改表单或借用需求会话。
- 目标默认当前 Dev 项目。产物属于项目技能，使用 OMP 原生项目级默认发现目录，默认形式为 `<项目根>/.omp/skills/<name>/SKILL.md`；正式路径由现有 OMP 路径解析和宿主确定，限制在明确目标项目，不保存到个人模型／追加提示词配置，也不覆盖其他同名技能。保存不等于当前会话已加载或技能行为验证通过，加载／刷新沿用原生机制。
- 生成预览包含 Skill 入口和必要资源规划，保持职责单一、输入输出及正反触发边界清晰；提出 3～5 个正常、错误触发及输入不足等验证用例，实际评测与格式检查分别记录，不用静态检查或文件存在冒充执行验证。
- 当前仅修改前端原型和说明：独立演示会话、表单上下文、补充聊天、静态预览、待试用例及项目内存保存可交互；不调用模型、创建真实原生会话、写技能文件、执行脚本或提交 Git。原型保存不改变原技能页的作用域和加载方式，也不作为真实目录扫描或技能加载证据。

### 5.3 恢复自动化入口

- Dev 左栏在“新建需求”下恢复 WebGUI 同样的“自动化”按钮和选中态，打开已复制的原自动化页面，不另造管理界面；切回 IR/SR 会话时恢复聊天。查看自动化不启动或推进需求，当前 SR 的开发占用不因页面切换改变。
- 保留原定时任务列表、状态筛选、新建／编辑、调度设置、启停、删除和运行历史界面；创建项目来自 Dev 的共享项目清单，定义及历史各自保持所属项目，不能串到另一项目。运行历史会话独立只读查看，不替换当前 IR/SR。
- 原“工作流”标签在 Dev 中展示 OMP 原生 task / workpool 的运行、父子 Agent、消息与产物，只读复用现有页面和组件，不将 Dev 变成另一套任意图执行器。
- 第一阶段提供四种定时任务状态、历史及子任务结构的内存样例；创建、编辑、启停、删除仅改变内存，“立即运行”只登记注明未执行的演示记录，不启动计时器、模型、进程或真实调度，不写入正式配置和 Git。真实接入继续等待前端确认；原 WebGUI 不修改。

### 6. 需求讨论和审核

需求 Agent 必须讨论实质业务内容，澄清场景、目标、范围、非目标、规则、异常与验收，区分事实、假设和待决问题。不能只检查字段和章节是否非空，也不能编造尚未确认的业务决定。

提案状态为草稿、方案完成、PR 待合并及转正后的正式需求；讨论阶段为业务需求、方案。草稿可以没有方案；提交评审只交给开发并切换方案阶段，状态仍为草稿，不要求先有方案。记录交接人工号、UTC 时间与轮次，时间以北京时间显示。

由评审需求的开发人员完成方案 Agent 的最后一步，方案覆盖整份 IR／全部 SR，说明实现、取舍、边界与验收对应，记录开发人、生成时间、版本以及绑定的需求快照／轮次后，状态变为方案完成。需求评审 Agent 继续只审查业务需求产物；技术审核／测试沿用原生子代理，不替代开发人员的判断。

生成方案发现业务细节缺失时，开发人员填写具体原因打回；返回草稿的业务需求阶段，记录反馈、时间与工号、增加轮次，保留原目录和各阶段会话。旧方案明确失效，不得因旧文件仍存在绕过门禁。补充后重新交接、完成本轮方案才能提交 PR。提交 PR 后的退回／关闭细化流程另定；本轮打回只覆盖提交 PR 前。

同一提案的 IR 和全部 SR 在每个讨论阶段共用该阶段 Agent 会话，阶段间历史保留并可只读查看，不按 SR 建方案会话；浏览历史不改变阶段。正式实现必须由服务端事务化校验状态、操作者、需求／方案版本及轮次，拒绝重复和迟到结果；仅输入格式正确工号不证明本人或开发权限。本轮不实现真实角色鉴权与后端写入。

### 7. 共享材料直接查看

所有人员在同一 Dev Web 直接读取共享提案、IR／SR、材料和状态，不再经过“下载需求包 → 交给他人 → 导入”的交接。不提供整份需求或 ZIP 包的下载、导出、导入、包格式验证或导入副本；新建只保留统一提案入口。

右侧保留当前单份材料的复制与下载，下载不改变需求状态或构成开发批准。接手开发直接选择共享正式需求，并配置自己的开发项目路径，不复制来源人的代码目录，不重建提案副本。

### 8. 公司 Git 与人工 PR 规则

- 所有人直接向同一个公司仓库提交 PR，不使用 fork 到个人仓库的协作模型。
- 默认分支通常为 main 或 master，实际使用仓库默认分支；它是所有需求 PR 和代码 PR 的目标。不得直接推送默认分支。
- OMP/Agent 可以在明确操作授权下处理限定范围的 commit/push，生成可复制的 PR 标题与说明；由评审需求的开发人员操作，提案 PR 使用服务账号 A 的既有凭据提交；公司平台评审与合并仍遵守原流程。
- 公司没有可用 PR API。Dev 不调用创建、查询、关闭或合并 PR API，不要求平台 SDK、gh/glab API 成功才能登记流程。
- “已提交 PR”“已合入”由人员明确登记。Git 只校验它能证明的分支、提交和文件内容，不伪称已自动验证平台审核状态。
- IR、全部 SR 与本轮方案合入并核对默认分支文件前，任何 SR 均不得进入开发计划。需求确认不等于需求 PR 合入，资料存在不等于获得开发批准。

### 9. 冻结与 SR 启动

**最新规则为需求 PR 合入即冻结整个 IR 和全部 SR。** 这取代此前“首个 SR 开始时才冻结”的版本；不再保留合入后、开工前通过追加需求 PR 修改的首版能力。

冻结覆盖 IR/SR 正文、标题及成员关系，不允许新增、删除、合并或重拆 SR。后端必须对主 Agent、后代和可写工具维护冻结权威；仅界面只读、提示词或下一次才发现变化的检查不够。已合入方案作为开发基线，计划和代码可在阶段权限内变化；不在执行侧重建方案 Agent 阶段。第一版没有解冻、需求版本变更或关联 IR。

各 SR 实际开始时分别从当时最新默认分支创建自己的分支和 worktree，持续复用。配置远端时先获取最新默认分支，失败暂停启动，不悄悄使用陈旧结果；没有远端的有效 Git 项目可以准备需求，但不能跳过需求已合入条件。开发计划输入包括冻结 IR／SR 全文、已合入方案、确认记录、相关背景及项目现有代码、接口、测试和约束。

### 10. 单 SR 和三阶段开发

同一项目跨所有 Release、IR，同时最多一个 SR 进入开发流程，范围从开发计划开始到代码 PR 已合入且人员明确确认结束。等待计划／代码审查或合入仍占用；关闭页面、停止模型、切换项目或重启 OMP 都不释放。不同项目不因当前浏览器选择而共用错误状态。本限制不把普通 OMP/WebGUI 原生会话全部改成单会话运行。

正式阶段为：**开发计划 → 开发与验证 → 交付 PR**。

- 方案在提案阶段完成，执行侧直接引用已合入方案，不重复生成；不做多候选 ID 选择、Dev Team 配置或比较产品。
- 开发计划给出步骤、修改范围及验证安排。
- 开发与验证合并原开发与 UT、ST，分别记录真实 UT/ST 结果、限制和未完成项；合并阶段不等于省略验证。
- 交付包含实际完成材料、提交信息和可复制 PR 说明；开发人员人工提 PR。
- 每次推进使用明确动作，例如“确认计划，进入开发与验证”“确认开发与验证，进入交付”。聊天、文件、AI 回复、测试退出码或 PR 状态查询不自动代签。
- 代码 PR 合入即结束本版 Dev。合入后的测试人员测试、缺陷、复测及多轮修复由公司现有流程处理，不再在 Dev 构建完整后置闭环。

### 11. 返回与材料失效

最新规则取消自动撤销代码。真正返回开发计划或开发与验证前，必须停止并结清当前 SR 主 Agent、子代理、队列、工具和 Goal 等自有工作；失败保持原阶段并可重试。

返回保留已有代码及资料历史。AI 根据实际代码调整计划，不改写已合入方案；发现基线方案不适用必须披露并阻塞，其后续变更规则另定；发生实质修改后，使本步骤批准及后续依赖产物失效，重新确认、生成和验证。后续验证必须检查旧实现残留。仅查看历史不使任何成果失效。

合入前可在原 SR 内按明确授权修正实现；报告更新需保留真实结果，普通询问不等于允许继续写。合入后不开放普通 Back 撤销默认分支，不再承诺原 SR 的合入后修复轮次或自动撤销所有所属文件。

### 12. Dev 副本外壳与阶段材料展示

左侧借鉴 WebGUI 的操作节奏与紧凑列表：顶部保留“新建需求提案”按钮及“自动化”入口；中部保留当前开发 SR 的稳定快捷入口，IR 沿用 WebGUI 项目分组样式，点击展开／收起下属 SR；SR 沿用原聊天记录行。“正式需求”列表的 IR／SR 标题前分别显示紧凑灰色描边类型标记，保留 SR 缩进和 IR 展开箭头，不展示内部编号。搜索沿用 WebGUI 命令中心弹窗及键盘选择、打开／关闭动效，筛选沿用原下拉菜单及动效，正式需求在上、需求提案在下，两栏可独立折叠；底部固定 工作区菜单／设置入口，项目和 Release 同组收进 工作区菜单，沿用界面主题的子菜单样式及动效，先选项目再选其 Release；左下角菜单按钮常驻显示当前上下文摘要。新建统一进入共享提案讨论，不增加名称／背景前置表单，不保留需求包下载、导出或导入入口，不把查看或整理解释为 SR 开始开发。IR 行用统一标题及 SR 数量，标题由 AI 生成，不展示内部 ID；只展开 IR → SR 两层，项目与 Release 不放入树。

列表选中态只表示当前查看目标，与实际工作标记分开。当前项目存在开发中的 SR 时，固定入口显示 SR 标题、所属 IR 和实际阶段；切换到其他 Release 后仍可定位它并显示所属 Release，点击返回其原会话及对应 Release，不新建、恢复执行、批准或推进阶段。点击 IR 只展开／收起 SR，不切换当前会话；需求讨论及相关 AI 工作沿用按钮操作，不新增导航层级。点击 SR 进入其聊天布局，未开始显示待开始及明确开始按钮，已完成显示历史只读，查看不启动 Agent。草稿默认可折叠，当前选中或刚创建的草稿保持展开；搜索与筛选只作用于查看，不改变真实业务状态。项目／Release／正式需求为空时分别引导添加项目、添加 Release 或新建草稿。

中间为当前 IR 或 SR 的 AI 会话，输入固定底部；协作成员与共享入口位于该会话顶部，不固定占用左侧导航。右侧为只读材料，Markdown 使用现有正文渲染器展示，复制和下载保留原文；默认打开并可通过原面板按钮操作。材料可收起重开，统一材料菜单可查 IR、SR、当前方案、计划、完成报告、UT/ST 记录和交付资料，不为阶段创建独立管理页。

SR 开始后，中间顶部显示 SR 标题、实际阶段和三阶段开发条，区分已完成/当前/未开始。点击阶段仅选择右侧材料，中间保留实际当前阶段会话；同时显示“正在查看”与“当前进行”。实际返回或推进使用独立动作；Git 范围、分支和操作记录收入可关闭的“更多”弹层，不常驻挤占聊天。未生成显示“尚未生成”，失效显示“已失效，需重新生成”，不可读显示真实错误，不用示例充数。

提案 IR 页显示草稿／方案完成／PR 待合并状态与业务需求／方案阶段；正式 IR 只读，未启动 SR 的完整内容可查看，只有明确开始才进入开发计划。普通 WebGUI/OMP 的原生命令、Skill、会话和工具能力继续按原合同提供，不因复制界面重新建立执行引擎。

### 13. 数据、OMP 与 NFS

正式资料使用 Markdown 和必要 JSON 随需求或代码提交进入 Git。共享数据库 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db` 保存项目、Release、提案状态与阶段、占用、PR 标记、反馈、方案版本、会话引用、轮次和真实操作结果，通过项目 ID 关联，独立于所有代码 worktree；不再要求每个阶段状态都产生 commit/push 或无限状态 PR。

项目与 Release 清单统一存入 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`，全 Web 共享，所有人可同时查看；Release 始终归属项目，不随 OMP profile 或 Git clone 另建清单。共享项目路径只读，查看项目不要求配置个人开发目录。 每位同事进入开发前，必须在所选项目下添加自己的“开发项目”路径，按工号与共享项目 ID 关联保存到同一数据库；该路径指 OMP 服务端可访问的已有 Git 工作目录，必须校验 Git 有效性、与共享项目的仓库对应关系及可写性，不可直接使用共享只读目录。修改个人路径不覆盖共享项目、不改变其他工号的绑定，不重定向已有运行任务。 Agent 模型与追加提示词仍沿用服务账号 OMP 配置，本次不调整。当前浏览器的项目、Release、搜索及折叠仅是查看偏好。原型只演示内存变化，不连接真实数据库、不写目录或 Git。

聊天正文和原生历史由 OMP 管理，Dev 只关联聊天 ID 等必要信息，不复制消息数据库。Dev 共享业务元数据使用上述单一 SQLite 文件，不按项目拆库，也不另建共享 JSON 状态权威。数据库应有结构版本、稳定引用、事务与必要的防重／过期检查；按钮状态、运行中等展示不能成为持久真值的替代。

实际环境中 OMP 配置、仓库和 worktree 都在 NFS，基本没有本地磁盘依赖。换机器后文件和路径保持，但执行进程不会迁移。第一版只支持顺序换机：同一配置/profile 同时仅在一台机器使用，换机前停止并退出旧机器使用该 profile 的全部 OMP 进程。不能只退出 Dev、保留同 profile 普通 OMP 在旧机运行。

当前 Linux 文件锁实际是本机 abstract Unix socket，不能证明跨机器互斥；现有 OMP SQLite 使用 WAL，不能因共享路径就宣称 NFS 并发安全。本版不顺带改造 OMP 底层数据库，不实现跨机自动抢占、分布式调度或任意中间步骤的自动续跑。必须如实显示旧宿主未结清、操作部分成功和历史不可用。

### 14. 完成、清理与异常的基本要求

代码 PR 合入后结束并释放该项目 SR 名额，提醒用户清理 worktree，不自动删除工作目录、分支或聊天历史。保存失败不能显示阶段成功；提交成功推送失败要保留实际提交，重试不能重复推进；重复点击不能重复建立分支、任务或批准；迟到事件不能写到另一项目/IR/SR。浏览器断开只断连接，已接收工作依旧属于宿主。

### 15. 已被最终决定替换的方案

| 讨论中的旧方案 | 最终结论 |
| --- | --- |
| 多 SR 并行开发 | 单项目最多一个 SR 开发 |
| 首个 SR 开工才冻结 | 需求 PR 合入立即整组冻结 |
| 开工前已合入需求还能追加修改 | 合入即冻结，首版不支持需求变更 |
| 返回计划／开发自动撤销代码 | 保留代码，修改后重新确认及验证 |
| Dev 固定八阶段 | SR 三阶段开发，IR 不走开发流水 |
| 所有业务状态必须 Git 管理 | 正式材料 Git，业务元数据共享 SQLite |
| 自动创建/查询/关闭/合并 PR | 开发人员人工 PR，无平台 API 依赖 |
| Dev 内测试人员测试和合入后修复轮次 | 代码合入即结束，交公司现有流程 |
| 独立统一需求服务、统一替代本地入口 | 开发者长期运行新 Dev，本地新建继续保留 |
| 业务专属入口和私有草稿 | 同一 Dev 界面，全部项目及草稿会话共享可见 |
| 修改 WebGUI 来承载 Dev | WebGUI 不改，完整复制其前端替换 Dev 后只改 Dev 副本 |
| 单项目 Dev | Dev 设置多项目，左下角 工作区菜单内项目／Release 相邻并按当前浏览器联动切换 |
| 换机只退出 Dev | 同 profile 的旧机 OMP 全部停止退出 |

### 16. 尚未确定的细节与承诺边界

以下事项没有在对话中最终决定，提案不擅自把它们补成业务能力：

- 需求 worktree 在需求 PR 合入后的具体清理时机；已经确定 SR 开发完成后提醒，不自动删除。
- 项目移除、工作目录变更后的迁移、弃置未完成 SR 的完整终止流程；不从设置删除或关页面推定开发已结束。
- NFS 实际挂载条件和现有 OMP SQLite 的实机兼容结果；本轮只核查源码，不将其报告为已验证。

这些边界可在实现前进一步确认；不应借实现方便扩大为解冻、版本变更、迁移、账号权限或自动接管产品。

### 17. 验收要求

后续实现验收应覆盖共享提案新建、提交评审与直接接手、需求 PR 合入冻结、单 SR 三阶段开发、历史材料查看、代码保留返工、人工 PR 无 API、多人多项目不串会话、NFS 顺序换机以及普通 OMP 和原 WebGUI 非干扰。必须确认先完整复制 WebGUI 前端替换 Dev，再只在 Dev 副本实现需求，原 WebGUI 的源码、构建配置、资源和入口未因本组需求改变。

关键异常包括重复点击、过期确认、review 期间改文档、默认分支获取失败、文件保存/commit/push 部分失败、停止后代未结清、历史缺失、worktree 缺失以及 squash/rebase 合入。必须使用真实结果，不能把原型、演示记录或文件存在当作已通过。

本组最初的需求编写不执行软件测试；当前第一阶段及后续恢复条件以上述“分阶段实施与当前临时状态”为准。文档格式检查、前端启动、假数据交互和界面观察均不能称为最终产品或真实业务验收。

## Capabilities

### New Capabilities

- `dev-requirement-intake`: 覆盖 Release/IR/SR 需求组织、两种需求来源、实质审核、成品包交接、人工需求 PR 与合入冻结。

### Modified Capabilities

本 change 自身只新增上述能力；以下既有能力的完整增量由本组配套 change 承担，路径和范围见前面的组清单：

- `dev-browser-workbench`: 完整复制 WebGUI 前端替换旧 Dev 后，在 Dev 副本实现三栏与三阶段开发、单 SR、只读材料、人工 PR、保留代码返工及 Git/JSON 分工。
- `spec-driven-orchestration`: 原生 Agent 职责、版本交接、冻结保护、任务归属、停止恢复及 NFS 顺序换机。
- `personal-commands`: 保留正式 Dev 入口及普通 OMP／WebGUI 边界，在 Dev 自身增加持久多项目设置、按浏览器选择和长期需求整理路径，不修改 WebGUI 功能。

## Impact

- 第一步完整复制 `vendor/zcode-frontend/preview/` 的 WebGUI 前端代码到 Dev 自有前端，替换 `packages/collab-web/src/dev-workbench/` 旧 Dev 前端；后续三栏、需求导航、多项目、需求整理和三阶段开发只修改 Dev 副本。原 WebGUI 前端及其构建配置、资源不变；旧 Dev 八阶段产品整体退役，不做双轨。
- 后端改动限于 Dev 所需的 `packages/coding-agent/src/dev-workbench/`、`src/spec-driven/` 及必要 Dev 集成；不修改 `src/webgui/` 或其服务合同。复用 OMP 原生 SDK 会话、工具、review 子代理和公共归档能力，不另建执行器或聊天数据库。
- 需要移除当前 Dev 对 PR 平台 API 的硬门禁，并区分当前材料、确认快照、Git 中正式资料和 共享业务数据库。共享材料存在不等于 Git 已交付。
- 需要在 Dev 内统一项目/IR/SR/worktree/session 绑定，避免现有单业务 runtime、checkout 级锁和全进程 Dev 交接被直接当作多项目共享服务；不将新需求转嫁给原 WebGUI。
- 保持 Firefox 128 原生运行基线、Dev 正式静态资源一致性、内网 offline 与非 offline 既有网络边界、原生 TUI/命令/Skill/MCP、资源打包及独立 OpenSpec 能力；原 WebGUI 的现有实现与行为不变，不更改其他未受影响的批准规则。
- 本提案不引入新 SQLite、身份系统、专用业务服务、PR API、分布式集群或自动 Git 回滚。
