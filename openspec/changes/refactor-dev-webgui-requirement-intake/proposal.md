# Proposal

## Why

Dev 需要成为以 AI 对话为中心的需求整理和开发工作台：既支持开发人员本地工作，也允许业务人员只通过浏览器，在开发人员长期运行的多项目 Dev 中整理可交接的完整需求。实现第一步是完整复制 WebGUI 前端代码并替换现有 Dev 前端，再仅修改复制后的 Dev 代码实现本组需求；原 WebGUI 不修改。现有八阶段单需求模型、旧 Dev 前端、单实例业务写作、平台 PR API 及 Git 状态管理，与本轮确认的 Release／IR／SR、人工 PR 和 NFS 使用方式不一致。此前较复杂的并行 SR、自动撤销和后置测试闭环已被明确收缩，需要形成可执行、可验收且不影响普通 OMP 和 WebGUI 的新需求基线。

## What Changes

### 1. 提案性质与阅读顺序

- 本文是本次完整对话的最终需求总提案；配套增量规格共同构成同一次 Dev 重构范围。
- 仅提出需求，不表示已经实现、通过软件验收、获准归档或可以覆盖已批准规格。
- 需求文档使用 `omp-spec`，保留 `proposal.md`、`.openspec.yaml` 和 `specs/**/spec.md`，不在需求编写过程中生成设计文件或实施任务表；产品实现按下述分阶段约束另行推进。

### 1.1 分阶段实施与当前临时状态

**当前仅处于第一阶段：Dev 前端 UI/UX 原型评审。以下临时开发安排不替代第二节及配套增量规定的最终产品目标。**

- 第一阶段继续调整已经从 WebGUI 复制的同一套 Dev 前端，不另建简化原型页面。原 WebGUI 不修改；所有 CSS、组件、控件、间距及交互状态沿用 WebGUI 同类型实现，新增控件也不得自创另一套风格。聊天输入框沿用原组件和原有文字，不增加额外说明。
- 第一阶段不对接 OMP 或真实后端，不启动原生 Agent、模型、Git、流程执行器、业务 HTTP/WS 或真实协作。独立预览只需要 Bun、浏览器及前端依赖，不以 Rust、OMP 原生模块、模型凭据或本机临时配置为前提。
- 每个展示中的 Dev 模块均须有单独维护的假数据，包括项目、Release、正式 IR/SR、草稿、对话、四阶段、只读材料、文件与审查、协作、设置及操作记录。数据须组成连贯的演示项目，源码、假数据、必要资源、锁文件和启动说明一并纳入仓库，另一台机器拉取后可按同一说明预览。
- 切换、展开、弹窗、选择和必要的编辑演示仅改变前端本地状态；样例对话回复、阶段状态、材料及日志全部是展示数据，不代表真实 AI 输出、审核通过、Git 操作、模型运行或业务成功。不得把演示假数据写入正式 OMP 状态、需求材料或配置。
- 右侧只读材料是原侧边面板中与文件、审查、辅助对话平级的一个标签页，默认打开并选中；不再增加永久固定的额外材料栏。
- 第一阶段以用户确认当前界面的布局、风格、内容和交互为退出条件。确认之前不得恢复后端业务开发、OMP 对接或软件测试；允许启动纯前端页面并实际查看、操作原型，不将页面观察记为业务验收通过。
- 第二阶段在用户确认前端后，将同一套界面的假数据来源逐项替换为真实 OMP 原生能力，完成本提案全部最终业务要求，不保留假数据兜底或另建执行器。
- 第三阶段在用户允许恢复测试后，完成默认 `bun run fastcheck`、`bun run fulltest`，并在 `F:\testgithub\test` 使用 OpenCode Go 的 `beam-free` 模型实际走通完整流程，核对真实功能、日志和 AI 输出。当前只是暂缓这些最终验收，不是取消、降低要求或以原型结果替代。


### 2. 最终产品目标

Dev 以 AI 对话为主要工作方式。用户在聊天中描述问题、回答追问、提供资料、提出修改和继续开发。正式资料的生成与修改由 AI 完成，人员通过明确动作确认或推进。实现顺序必须是：先将 WebGUI 前端代码完整复制到 Dev 自有前端并替换旧 Dev 前端，再修改该 Dev 副本实现本组需求，保留阶段文档清晰可见的能力；不是只参考布局、挑选组件或直接挂载原 WebGUI。

原 WebGUI 是只读复制来源，不修改其前端、后端、入口、协议、构建配置或正式资源，也不向 `/webgui`／`omp webgui` 增加 Dev 功能。本提案中的需求整理、多项目设置和四阶段均由 Dev 自身实现。Dev 副本使用自己的前端状态、构建和资源入口，继续复用现有 OMP 原生会话与底层能力，不另建执行器，不将 Dev 业务状态或控制写入原 WebGUI。

所有 IR、SR、标题、拆分结果、技术方案、计划、完成报告、验证资料和交付说明均只读。用户可以选择、查看、复制、下载、将资料带入讨论，以及执行明确流程动作；不提供正文编辑器、标题改写表单或拖拽拆分。设置中的项目名称和工作目录是配置，不属于需求标题。

### 3. Release、IR、SR

- Release 组织计划交付范围和整体进度；设置可添加 Release，界面可选择当前 Release。Release 不关联代码分支。
- IR 保存背景、目标、范围、边界、规则及讨论结果，包含一个或多个 SR。
- SR 保存完整、明确、可测试的系统要求，是开发单位。小需求允许仅一个 SR。
- IR 不进入技术方案、计划、开发和验证流水。需求 Agent 一次整理 IR 和全部 SR，不让每个 SR 再重复业务整理及需求撰写。
- IR、SR 的标题全部由 AI 生成和修改。内部有稳定 ID 用于关系和追溯，左侧不显示编号。
- 同一 IR 的 SR 可以相隔很久才启动；第一版不实现 SR 依赖关系调度，不考虑多人同时开发同一个 SR，也不处理多人跨 clone 同时修改 IR/SR。

### 4. 两种需求来源

**开发人员本地新建：**在已有 Git 项目的 Dev 点击新建，立即基于默认分支创建需求工作分支和 worktree，再开始对话。无名称、分类、背景等前置表单。创建工作目录本身不代表需求确认，不让草稿提前出现在正式 IR 导航。

**业务人员浏览器整理：**由一位开发人员在自己的 clone 目录长期运行新 Dev，业务人员仅使用浏览器。服务端已有 OMP 和代码目录，客户端不要求 OMP、Git、clone 或自己的代码。业务新建只创建服务端草稿及 OMP 会话，不操作 Git、不创建需求 worktree。完整检查通过后下载需求包；接手开发人员在自己的 clone 中导入，再提交需求 PR。

两条路径复用需求 Agent、检查规则和资料格式。并非另部署一套统一需求产品，不强制开发人员只能走远程入口，不创建业务专属 API 或角色视图。所有人使用同一 Dev 功能，全部登记项目、正式需求、草稿及会话共享可见；资料和任务依旧按项目、IR 关联，修改串行，不因共享可见而串会话。原 WebGUI 不承载新增需求整理流程。

### 5. 多项目设置和项目切换

- Dev 设置中维护项目名称和服务器工作目录，只登记服务器已存在且有效的 Git 仓库；不自动 clone，不替用户创建目录，不修改原 WebGUI 的项目设置。
- 项目列表由 Dev 持久保存，服务重启后仍可使用；目录指运行 Dev 的机器可访问的 NFS 目录，非业务人员浏览器电脑路径。
- 左下角切换项目，只改变当前浏览器的查看、输入和材料目标。其他浏览器以及原项目的 Agent、任务继续保持原归属。
- 注册、打开或查看项目不启动模型。选择无效目录、项目不可用或连接绑定失败需明确报错，不默默回落到另一项目。
- 需求整理使用 Dev 自身的多项目宿主与 OMP 原生会话能力；切换项目、整理需求或下载不重复执行全进程模式交接，不结清其他项目工作。首次 `/dev` 进入及再次 `/dev` 退出仍遵守原生独占与结清规则；接手人自己的 Dev 开发入口继续存在，不借用或改造普通 WebGUI 入口。

### 6. 需求讨论和审核

需求 Agent 必须讨论实质业务内容，澄清场景、目标、范围、非目标、规则、异常与验收，区分事实、假设和待决问题。不能只检查字段和章节是否非空，也不能编造尚未确认的业务决定。

人员点击“确认需求与拆分”后，程序先检查整组格式和关系；格式通过，再由主需求 Agent 派独立 review 代理审查当前 IR、全部 SR 和整体覆盖。审核包括缺口、重复、冲突、边界、假设及可测试性；纯措辞建议不自动阻塞。review 的输入和结果必须绑定同一份内容快照。

只有 IR、至少一个完整 SR、明确人员确认、格式检查和 review 全部通过后，才完成内部确认并在正式左侧列表出现 AI 标题。草稿仍可保存与恢复。review 失败由需求 Agent 修改，人员重新点击确认后重新检查；修改不能沿用旧批准。停止访谈不等于确认。

### 7. 下载和导入

一个 ZIP 包对应一个 IR，包含完整 IR、全部 SR、必要业务附件及确认/review 记录。正文 Markdown、结构 JSON；包内包含格式版本、稳定 ID、来源项目、文件清单和内容摘要。只为当前通过全部检查的版本开放下载，修改后收回当前版本可下载资格。

不携带 OMP 凭据、运行锁、服务器绝对路径或聊天正文副本。导入不要求恢复原业务会话或原人员加入协作。

开发人员导入时选择自己的目标项目和 Release。程序确定性校验包版本、结构、完整性、引用及路径，再从该项目默认分支建立需求分支/worktree；来源服务器目录不能作为本地导入目标。导入不启动 SR、不自动提交 PR，不强制重复整套业务 Agent review；开发人员负责检查项目适用性并通过公司需求 PR 评审。无法处理或重复请求不能覆盖已有冻结需求、重复建立工作目录或伪报成功。

### 8. 公司 Git 与人工 PR 规则

- 所有人直接向同一个公司仓库提交 PR，不使用 fork 到个人仓库的协作模型。
- 默认分支通常为 main 或 master，实际使用仓库默认分支；它是所有需求 PR 和代码 PR 的目标。不得直接推送默认分支。
- OMP/Agent 可以在明确操作授权下处理限定范围的 commit/push，生成可复制的 PR 标题与说明；实际创建、评审和合并 PR 均由开发人员在公司平台完成。
- 公司没有可用 PR API。Dev 不调用创建、查询、关闭或合并 PR API，不要求平台 SDK、gh/glab API 成功才能登记流程。
- “已提交 PR”“已合入”由人员明确登记。Git 只校验它能证明的分支、提交和文件内容，不伪称已自动验证平台审核状态。
- 需求资料全部合入前，任何 SR 均不得开始技术方案。需求确认不等于需求 PR 合入，资料存在不等于获得开发批准。

### 9. 冻结与 SR 启动

**最新规则为需求 PR 合入即冻结整个 IR 和全部 SR。** 这取代此前“首个 SR 开始时才冻结”的版本；不再保留合入后、开工前通过追加需求 PR 修改的首版能力。

冻结覆盖 IR/SR 正文、标题及成员关系，不允许新增、删除、合并或重拆 SR。后端必须对主 Agent、后代和可写工具维护冻结权威；仅界面只读、提示词或下一次才发现变化的检查不够。开发方案、计划和代码仍可在阶段权限内变化。第一版没有解冻、需求版本变更或关联 IR。

各 SR 实际开始时分别从当时最新默认分支创建自己的分支和 worktree，持续复用。配置远端时先获取最新默认分支，失败暂停启动，不悄悄使用陈旧结果；没有远端的有效 Git 项目可以准备需求，但不能跳过需求已合入条件。技术方案输入包括冻结 IR/SR 全文、确认记录、相关背景及项目现有代码、接口、测试和约束。

### 10. 单 SR 和四阶段开发

同一项目跨所有 Release、IR，同时最多一个 SR 进入开发流程，范围从技术方案开始到代码 PR 已合入且人员明确确认结束。等待评审/合入仍占用；关闭页面、停止模型、切换项目或重启 OMP 都不释放。不同项目不因当前浏览器选择而共用错误状态。本限制不把普通 OMP/WebGUI 原生会话全部改成单会话运行。

正式阶段为：**技术方案 → 开发计划 → 开发与验证 → 交付 PR**。

- 技术方案只有一个当前方案，包含实现思路、理由和取舍；不做多候选 ID 选择、Dev Team 配置或比较产品。
- 开发计划给出步骤、修改范围及验证安排。
- 开发与验证合并原开发与 UT、ST，分别记录真实 UT/ST 结果、限制和未完成项；合并阶段不等于省略验证。
- 交付包含实际完成材料、提交信息和可复制 PR 说明；开发人员人工提 PR。
- 每次推进使用明确动作，例如“确认方案，进入计划”“确认计划，进入开发与验证”“确认开发与验证，进入交付”。聊天、文件、AI 回复、测试退出码或 PR 状态查询不自动代签。
- 代码 PR 合入即结束本版 Dev。合入后的测试人员测试、缺陷、复测及多轮修复由公司现有流程处理，不再在 Dev 构建完整后置闭环。

### 11. 返回与材料失效

最新规则取消自动撤销代码。真正返回方案或计划前，必须停止并结清当前 SR 主 Agent、子代理、队列、工具和 Goal 等自有工作；失败保持原阶段并可重试。

返回保留已有代码及资料历史。AI 根据实际代码调整技术方案/计划；发生实质修改后，使本步骤批准及后续依赖产物失效，重新确认、生成和验证。后续验证必须检查旧实现残留。仅查看历史不使任何成果失效。

合入前可在原 SR 内按明确授权修正实现；报告更新需保留真实结果，普通询问不等于允许继续写。合入后不开放普通 Back 撤销默认分支，不再承诺原 SR 的合入后修复轮次或自动撤销所有所属文件。

### 12. Dev 副本外壳与阶段材料展示

左侧为紧凑需求导航，中间为当前 IR 或 SR 的 AI 会话，输入固定底部，右侧为只读材料。右侧可收起重开，统一材料菜单可查 IR、SR、当前方案、计划、完成报告、UT/ST 记录和交付资料，不为阶段创建独立管理页。

SR 开始后，中间顶部显示 SR 标题、实际阶段和四阶段条，区分已完成/当前/未开始。点击阶段仅选择右侧材料，中间保留实际当前阶段会话；同时显示“正在查看”与“当前进行”。实际返回或推进使用独立动作。未生成显示“尚未生成”，失效显示“已失效，需重新生成”，不可读显示真实错误，不用示例充数。

IR 页只显示整理、确认、检查、可下载或待需求合入等适用状态；未启动 SR 的完整内容可查看，只有明确开始才进入技术方案。普通 WebGUI/OMP 的原生命令、Skill、会话和工具能力继续按原合同提供，不因复制界面重新建立执行引擎。

### 13. 数据、OMP 与 NFS

正式资料使用 Markdown 和必要 JSON 随需求或代码提交进入 Git。工作流 JSON 保存当前阶段、占用、PR 标记、会话引用、轮次和真实操作结果，位于所有该项目 worktree 共用的非 Git 数据目录；不再要求每个阶段状态都产生 commit/push 或无限状态 PR。

聊天正文和原生历史由 OMP 管理，Dev 只关联聊天 ID 等必要信息，不复制消息数据库。第一版不新增 Dev 专用 SQLite。工作流 JSON 应有结构版本、稳定引用、原子保存和必要的防重/过期检查；按钮状态、运行中等展示不能成为持久真值的替代。

实际环境中 OMP 配置、仓库和 worktree 都在 NFS，基本没有本地磁盘依赖。换机器后文件和路径保持，但执行进程不会迁移。第一版只支持顺序换机：同一配置/profile 同时仅在一台机器使用，换机前停止并退出旧机器使用该 profile 的全部 OMP 进程。不能只退出 Dev、保留同 profile 普通 OMP 在旧机运行。

当前 Linux 文件锁实际是本机 abstract Unix socket，不能证明跨机器互斥；现有 OMP SQLite 使用 WAL，不能因共享路径就宣称 NFS 并发安全。本版不顺带改造 OMP 底层数据库，不实现跨机自动抢占、分布式调度或任意中间步骤的自动续跑。必须如实显示旧宿主未结清、操作部分成功和历史不可用。

### 14. 完成、清理与异常的基本要求

代码 PR 合入后结束并释放该项目 SR 名额，提醒用户清理 worktree，不自动删除工作目录、分支或聊天历史。保存失败不能显示阶段成功；提交成功推送失败要保留实际提交，重试不能重复推进；重复点击不能重复建立分支、任务或批准；迟到事件不能写到另一项目/IR/SR。浏览器断开只断连接，已接收工作依旧属于宿主。

### 15. 已被最终决定替换的方案

| 讨论中的旧方案 | 最终结论 |
| --- | --- |
| 多 SR 并行开发 | 单项目最多一个 SR 开发 |
| 首个 SR 开工才冻结 | 需求 PR 合入立即整组冻结 |
| 开工前已合入需求还能追加修改 | 合入即冻结，首版不支持需求变更 |
| 返回方案/计划自动撤销代码 | 保留代码，修改后重新确认及验证 |
| Dev 固定八阶段 | SR 四阶段，IR 不走开发流水 |
| 所有业务状态必须 Git 管理 | 正式材料 Git，工作流共享 JSON |
| 自动创建/查询/关闭/合并 PR | 开发人员人工 PR，无平台 API 依赖 |
| Dev 内测试人员测试和合入后修复轮次 | 代码合入即结束，交公司现有流程 |
| 独立统一需求服务、统一替代本地入口 | 开发者长期运行新 Dev，本地新建继续保留 |
| 业务专属入口和私有草稿 | 同一 Dev 界面，全部项目及草稿会话共享可见 |
| 修改 WebGUI 来承载 Dev | WebGUI 不改，完整复制其前端替换 Dev 后只改 Dev 副本 |
| 单项目 Dev | Dev 设置多项目，左下角按当前浏览器切换 |
| 换机只退出 Dev | 同 profile 的旧机 OMP 全部停止退出 |

### 16. 尚未确定的细节与承诺边界

以下事项没有在对话中最终决定，提案不擅自把它们补成业务能力：

- 导出后源业务草稿是否立即只读，以及开发侧合入/冻结怎样回传源 Dev；确定的是冻结开发副本不能被源包覆盖，不承诺跨 clone 自动同步。
- 同一包 ID、不同内容的重复导入如何更新未合入草稿，以及开发人员发现业务问题怎样退回修改；不能默认覆盖冻结需求或绕过重新确认。
- 需求 worktree 在需求 PR 合入后的具体清理时机；已经确定 SR 开发完成后提醒，不自动删除。
- 项目移除、工作目录变更后的迁移、弃置未完成 SR 的完整终止流程；不从设置删除或关页面推定开发已结束。
- NFS 实际挂载条件和现有 OMP SQLite 的实机兼容结果；本轮只核查源码，不将其报告为已验证。

这些边界可在实现前进一步确认；不应借实现方便扩大为解冻、版本变更、迁移、账号权限或自动接管产品。

### 17. 验收要求

后续实现验收应覆盖完整浏览器需求包交接、本地新建、需求 PR 合入冻结、单 SR 四阶段、历史材料查看、代码保留返工、人工 PR 无 API、多人多项目不串会话、NFS 顺序换机以及普通 OMP 和原 WebGUI 非干扰。必须确认先完整复制 WebGUI 前端替换 Dev，再只在 Dev 副本实现需求，原 WebGUI 的源码、构建配置、资源和入口未因本组需求改变。

关键异常包括重复点击、过期确认、review 期间改文档、默认分支获取失败、文件保存/commit/push 部分失败、停止后代未结清、历史缺失、worktree 缺失以及 squash/rebase 合入。必须使用真实结果，不能把原型、包内声明或文件存在当作已通过。

本组最初的需求编写不执行软件测试；当前第一阶段及后续恢复条件以上述“分阶段实施与当前临时状态”为准。文档格式检查、前端启动、假数据交互和界面观察均不能称为最终产品或真实业务验收。

### Modified Capabilities
