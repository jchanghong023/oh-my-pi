# Spec Delta

## Purpose

对齐当前 `openspec/specs/dev-browser-workbench/spec.md`：Dev 只管理需求、评审、方案、人员排期、提案分支与代码证据进度，不参与实际编码。本轮仅文档和独立演示原型，不代表真实模型、Git 或数据库服务实现。

## ADDED Requirements

### Requirement: Release、IR、SR 的职责与稳定关系

系统 MUST 按项目／仓库、Release、IR、SR 组织需求。一个项目对应一个仓库，一个 IR 对应一个 OpenSpec Change，每个 SR 对应一个能力 spec.md，共用 proposal.md 和 design.md。稳定 ID、change-id 和能力路径不随标题或查看人改变。

#### Scenario: 标准文件映射
- **WHEN** 创建和拆分提案
- **THEN** 使用 openspec/changes/<change-id>/proposal.md、specs/<capability>/spec.md 和 design.md；一份能力规格可含多条 Requirement，不逐条再造 SR，不另造 IR.md、SR.md 或方案 JSON；同名冲突交人处理
- **AND** Release 只组织范围，不代替分支；同仓库不同 clone／worktree 关联相同项目，不引入开发占用或名额

### Requirement: 共享 Web 的统一提案入口

Dev MUST 共享项目、Release、提案资料、正式需求及进度；只有所有者为 `j00808874` 的 Web 提供提案讨论，其他 Web 只读材料。访问者使用该 Web 所有者的模型 Token，工号只作操作标识，不是完整认证。

#### Scenario: 工号、聊天与共享业务分离
- **WHEN** 访问者输入一个小写 a–z 字母加八位数字工号
- **THEN** 保留前导零，不切换后端所有者、Token 或 profile；不要求个人 OMP、Git 目录或凭据
- **AND** 材料先在 /tmpdata/DFT_LAB/omp/{project_name}/{原提交人工号}/{提案id}/ 生成；项目代码只读参考，原生聊天归 A 的 OMP，不入业务库或在其他 Web 接管重放
- **AND** 各 Web 通过固定 18321 的 `omp dev_db` 服务访问 /tmpdata/DFT_LAB/omp/omp_dev_sqlite.db，不各自打开 NFS SQLite；真实服务本轮不实现

### Requirement: 需求讨论必须审查实质内容

业务需求 Agent MUST 澄清目标、范围、规则、异常及可验证验收行为。需求评审 MUST 为三个不同模型 A／B／C 独立并行只读评审同轮同版 IR／全部 SR，第四个综合评审汇总来源、依据和分歧，最终由人决定，不按投票、评分或模型标签自动放行／阻断。

#### Scenario: 报告、追问与重评
- **WHEN** 查看需求评审
- **THEN** 默认综合意见，可切换原始会话定向追问；只读禁止文件修改，不禁用当前报告对话；四份报告完整可读后才可人工通过或直接返回业务补充，不增裁决表单或逐项勾选
- **AND** 需求更新使旧报告、决定及方案失效；原始报告按同轮快照重试后重新综合，不沿用旧决定；历史保留，固定原型报告不代表真实并行评审

### Requirement: 提案状态与讨论阶段分离

Dev MUST 区分提案状态与业务需求、评审、技术方案和入库时间线，不新增“待评审”业务状态。提出人与方案参与人分别记录；评审不要求已有方案。

#### Scenario: IR 会话与方案补充循环
- **WHEN** 人工通过当前完整评审后进入方案
- **THEN** 在 A 的方案 Agent 生成 design.md，逐 SR 明确实现思路、稳定 SR 依赖、原因、可并行关系及不确定项，不编制编码执行计划，不要求个人目录
- **AND** 无法回答业务问题时人工粘贴意见并确认，直接返回业务 Agent，保留原文及历史；需求更新后重评和重新确认方案，旧方案不得入库
- **AND** 仅 IR 参与讨论；提案 SR 只显示自身规格及返回 IR 入口，不挂载聊天或阶段动作

### Requirement: 共享材料直接查看

系统 MUST 只读展示 proposal.md、全部 SR spec.md、design.md 及来源、版本和历史；IR 浏览全套需求，SR 仅显示自身规格，不混入开发阶段产物。

#### Scenario: 缺失与阅读边界
- **WHEN** 选择材料
- **THEN** 如实区分未生成、读取错误和旧版失效，保留目标，不以摘要或样例代替正文；不提供复制、下载、带入讨论或正文编辑按钮，阅读不产生批准或推进

### Requirement: 方案完成后创建提案分支，合入且文档完整自动转正

平台 MUST 在当前 IR、全部 SR 和方案完整且人工逐文件确认后，才从最新默认分支创建独立提案分支、提交推送文档并提供 PR 内容。人工在 Git 网页创建、评审和合并 PR；平台不自动创建或合并 PR，不依赖 PR API，不要求个人目录。

#### Scenario: 后台两条件转正
- **WHEN** 后台确认提案分支已合入默认分支，且 IR、全部 SR、方案完整有效
- **THEN** 自动转正并从包含提案的最新默认分支创建推送各 SR 分支，记录基点；支持 merge／squash／rebase，不要求 PR 地址、人工通知或再次批准，不重复转正或建分支
- **AND** 未合入、文档不完整或读取失败保留提案与原因并继续检查；分支创建失败保留已核验正式需求并重试；转正不表示代码完成，不归档 Change 或提前同步未实现规格

### Requirement: 人员排期与需求依赖分离

Dev MUST 将正文、验收标准、方案和稳定 SR 依赖写入 Git，将 IR 负责人、SR 开发者、AI 建议与人工排期及调整记录写入共享业务数据库。不单列工时，安排不构成执行锁或入库审批。

#### Scenario: 调整与转正保留
- **WHEN** 当前方案有效完成，管理员或 IR 负责人调整 SR 人员及起止时间
- **THEN** 管理员分配唯一 IR 负责人，负责人或管理员调整 SR，其他人只读；起止同时填写或清空，结束晚于开始，提示依赖和人员冲突，不自动移动其他 SR，不改文档版本或创建 PR
- **AND** 保留 AI 原建议与假设，不覆盖人工安排；IR 汇总 SR 最早开始／最晚结束，部分未排期明确提示；转正沿用同一 ID、人员及排期，缺人或冲突不增加门槛

### Requirement: 正式需求仅查看进度与材料

Dev MUST 不编码，不提供开始开发、计划／执行、测试、修复或 IR 验收归档流水线。正式需求在大表格与同页报告查看，开发者在平台外使用自己的工具，不要求个人 Web 或 Git 目录，不建立冻结锁、单 IR 或 SR 并发名额。

#### Scenario: 版本证据与完成
- **WHEN** 后台分析或管理员／IR 负责人调整 SR 进度
- **THEN** 基于需求、验收条件及代码证据报告百分比、问题、不确定项、版本、分支和合入依据；未合入最高 99%，已合入且全部条件满足才可自动 100%，AI 不确定时允许人工凭据判断并留记录；保留原问题，不把人工意见冒充新分析
- **AND** IR 进度为全部 SR 算术平均，全部完成才完成 IR，不需最终验收或归档 PR；平台外仓库修改以实际版本为准，旧报告不证明新内容
