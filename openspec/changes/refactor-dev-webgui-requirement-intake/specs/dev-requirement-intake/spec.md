# Spec Delta

## Purpose

规定所有人员通过长期共享 Dev 整理需求提案的共同业务边界，明确完整 IR/SR 的提交评审、共享记录，以及在同仓库人工需求 PR 合入默认分支后冻结业务需求的可观察行为。Dev 前端先完整复制 WebGUI 并替换旧 Dev，再仅修改 Dev 副本；原 WebGUI 不修改、不承载本次新增需求。

## ADDED Requirements

### Requirement: Release、IR、SR 的职责与稳定关系

系统 MUST 按 Release → IR → 一个或多个 SR 组织正式需求。IR 承载业务背景、目标、范围、边界及讨论结论；SR 承载完整、可测试的系统要求并作为开发单位。标题 MUST 由 AI 生成和修改，稳定内部 ID 不随标题变化。

#### Scenario: 小需求只拆一个 SR
- **WHEN** 需求范围较小
- **THEN** 允许一个 IR 只包含一个 SR；不强制拆出多条；提案方案覆盖整个 IR／全部 SR，IR 本身不进入代码开发流水。

#### Scenario: 版本与开发分支分离
- **WHEN** 用户在设置添加 Release 或选择版本
- **THEN** Release 只组织交付范围及进度，不绑定代码分支；清单与所属项目登记统一保存在共享数据库 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`，所有人可见；共享项目路径只读，进入开发前必须配置当前工号在该项目下的个人开发目录。新建提案使用当前选择项目的 Release，后续参与者直接查看共享记录，不导入副本。

#### Scenario: 标题和拆分只能对话修改
- **WHEN** 需求尚未冻结且用户提出修改
- **THEN** Agent 更新标题、正文或拆分；界面不提供重命名、拖拽拆分或正文编辑；导航不显示 IR、SR 编号。

### Requirement: 共享 Web 的统一提案入口

所有人员 MUST 通过同一长期运行的 Dev Web 创建与整理需求提案；业务人员不依赖自己的 OMP、代码仓库或 clone。仅提供统一“新建需求提案”，不区分本地新建／浏览器交接，不提供需求包导出、下载或导入流程。新增业务在 Dev 内实现，不修改原 WebGUI。

#### Scenario: 共享查看和接手
- **WHEN** 不同人员通过工号进入同一 Dev
- **THEN** 选择项目及其 Release，直接读取该项目共享的提案、IR／SR、材料、状态和讨论，不要求另存需求包、传递 ZIP、恢复来源人的会话文件或重新导入记录；资料与会话按项目和提案归属隔离。

#### Scenario: 新建提案不操作 Git
- **WHEN** 用户点击“新建需求提案”
- **THEN** 建立共享提案记录及业务需求会话，提案文件按约定项目／工号／提案 ID 目录归档；不自动创建代码目录、需求分支或 worktree，不提交推送，不启动 SR 开发。

### Requirement: 需求讨论必须审查实质内容

需求 Agent MUST 澄清问题、业务目标、使用场景、范围、非目标、规则、异常边界及验收行为，区分事实、假设和待确认问题；共同整理 IR 和完整 SR，并检查拆分覆盖、遗漏、重复和冲突。AI MUST NOT 编造未经确认的业务决定。

#### Scenario: 提案 IR 与 SR 共用阶段 Agent
- **WHEN** 用户点击同一需求提案内任意 SR，或 IR 的“需求讨论”按钮
- **THEN** 进入当前讨论阶段的提案级会话；业务需求阶段使用业务需求 Agent，方案阶段使用方案 Agent。每阶段 IR 与全部 SR 共用消息、上下文和未发送输入，不按 SR 创建新会话；两个阶段各保留会话和历史，不同提案隔离。切换查看历史不推进当前阶段，历史会话只读。

#### Scenario: SR 不能只有标题
- **WHEN** Agent 完成拆分
- **THEN** 每个 SR 包含行为、范围、业务规则、约束、异常及验收要求；全部 SR 合起来覆盖 IR，已知缺口和依赖背景如实记录，但第一版不实现 SR 依赖调度。

#### Scenario: 使用已有资料
- **WHEN** 用户提供文字、业务资料或附件
- **THEN** Agent 在可用权限内读取并引用资料，不能从字段齐全、章节非空或多个 Agent 意见相同推定业务正确；关键未决问题明确披露。

#### Scenario: 停止访谈
- **WHEN** 人员要求停止继续提问
- **THEN** 停止访谈并保留未决事项，按当前授权处理；停止访谈本身不构成确认、审核通过或开发批准。

### Requirement: 提案状态与讨论阶段分离

提案状态 MUST 为草稿、方案完成、PR 待合并及合并后的正式需求，不保留“待评审”。讨论分业务需求、方案两阶段，与状态独立。草稿表示尚无本轮完整可提交方案，可以处于任一讨论阶段；“草稿”是提案状态，不是额外导航分区。

#### Scenario: 无方案也可提交评审
- **WHEN** 人员在草稿的业务需求阶段点击“提交评审”
- **THEN** 记录项目／提案 ID、操作者工号、UTC 时间和交接轮次，讨论阶段切换为方案，状态仍为草稿；不要求已有方案、不生成审核通过结论、不创建 PR 或转正。在方案阶段重复执行此动作必须拒绝。

#### Scenario: 开发人员完成方案
- **WHEN** 评审该需求的开发人员在方案阶段操作方案 Agent
- **THEN** 以当前 IR、全部 SR、业务讨论及代码约束完成方案，说明可行性、取舍、接口、异常与验收映射；生成并确认完整方案是开发人员提交 PR 前的最后一个必要步骤。记录开发人工号、时间、方案版本及其绑定的需求快照和轮次，状态变为方案完成。生成失败、取消、材料不完整时保持草稿的方案阶段；未完成或失效方案不能提交 PR。

#### Scenario: 业务卡点打回补充
- **WHEN** 开发人员在提交 PR 前生成方案时发现需业务补充的细节
- **THEN** 必须填写原因，记录操作人和时间，提案回到草稿的业务需求阶段，保留 IR／SR、目录和讨论；旧方案失效并增加轮次。业务补充后重新提交评审，由开发人员完成新一轮方案，不得沿用旧方案或旧确认。PR 提交后的变更／关闭处理另行确定，不由本场景推导。

#### Scenario: 原型与实现边界
- **WHEN** 本轮评审上述流程
- **THEN** 仅修改 Dev 自有原型、样例和需求文档；生成方案使用静态样例，PR 提交／合并／默认分支核对仅为明确标注的演示。正式实现必须事务化状态校验、防重及版本校验，将业务元数据保存到 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`；由服务端生成 UTC 时间、页面显示北京时间。A 的模型／PR 凭据与实际操作人工号分开，输入工号不代表已验证本人或开发权限。本轮不新增真实角色鉴权、模型调用、Git／PR 或数据库接口。

### Requirement: 共享材料直接查看

系统 MUST 直接展示共享提案的 IR、全部 SR、必要附件、评审记录和业务需求会话，不提供整份需求包的下载、导出或导入。后续开发使用该共享提案及正式需求记录，不建立导入副本。

#### Scenario: 保留单份材料复制与下载
- **WHEN** 用户在右侧材料面板查看当前文档
- **THEN** 可复制或下载这一份材料，保留原文；不拼装整个提案、IR／SR 集合或 ZIP 需求包。单份材料下载不构成提案批准、PR 合入或开发授权。

### Requirement: 方案完成后提交 PR，合并核对后转正

需求 PR MUST 包含完整 IR、全部 SR 和本轮有效方案，目标为所属仓库默认分支，提交使用服务账号 A 的既有凭据、由评审需求的开发人员操作。只有方案完成状态且文件版本仍匹配当前需求时才允许提交；提交后仍为需求提案，状态为 PR 待合并。不得直接向默认分支推送。

#### Scenario: 无方案或旧方案不能提交 PR
- **WHEN** 尚未生成方案、方案生成未完成、被打回或需求版本变化
- **THEN** 拒绝 PR 提交，不因历史文件存在或状态残留绕过；补充后必须重新完成当前轮次方案。UI 禁用入口并说明原因，正式服务端同样检查，不只依赖 UI。

#### Scenario: PR 提交不转正
- **WHEN** 需求 PR 已提交但尚未合并
- **THEN** 保留在需求提案列表，不开放 SR 开发；公司平台的评审过程不新增“待评审”业务状态。

#### Scenario: 默认分支已有相关文件才能转正
- **WHEN** 需求 PR 经评审合并
- **THEN** 正式实现获取并核对真实默认分支中的 IR、全部 SR 和当前方案内容／版本，保存可追溯提交和文件证据后，才移入正式需求并冻结。仅登记 PR 地址、平台显示合并、页面勾选或文件同名存在都不足以转正；获取失败或文件缺失／不符时保留提案并明确阻塞。原型只演示此门禁，不提供真实核对。

### Requirement: 需求合入即冻结整组 IR、SR 与已交付方案

需求 PR 的已确认内容合入默认分支后，系统 MUST 立即冻结 IR、全部 SR 的正文、标题、拆分关系及合入的方案基线；冻结不能延后到首个 SR 启动。第一版 MUST 不提供解冻、需求版本变更或关联 IR 流程。

#### Scenario: 禁止修改冻结内容
- **WHEN** 人员或开发 Agent 尝试修改、增加、删除、合并、重新拆分需求
- **THEN** 后端拒绝改变冻结的权威需求及集合；页面显示业务需求及拆分结果已锁定；不以网页只读或提示词替代真实写入保护。

#### Scenario: 需求合入事实核对
- **WHEN** 人员标记需求 PR 已合入
- **THEN** 通过 Git 获取默认分支并核对完整 IR／SR 集合及本轮方案的确认版本；记录可定位的目标提交和内容依据，支持正常 merge、squash、rebase，不仅用源分支 SHA 判断。

#### Scenario: 后续代码已经变化
- **WHEN** 同 IR 的其他 SR 很久以后才启动
- **THEN** 仍采用原冻结需求，代码使用启动时最新默认分支；不能擅自改需求来适应代码。发现不兼容必须披露和阻塞。

### Requirement: 共享记录和个人开发目录的边界

提案与正式需求使用同一 Dev 服务中的共享记录，业务元数据保存在 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`；个人开发项目路径只关联工号与项目，不能通过接手开发建立第二份需求副本或覆盖已冻结的需求。

#### Scenario: 接手开发不复制提案
- **WHEN** 另一位同事准备开发已合入的正式需求
- **THEN** 直接读取共享 IR／SR，按既有规则配置自己的开发项目路径；不执行需求包导入，不复制来源人的绝对代码目录或更改提案创建人及资料归属。选择记录不等于获得开发批准。
