# Spec Delta

## Purpose

规定开发人员本地需求整理与业务人员通过长期 WebGUI 整理需求的共同业务边界，明确完整 IR/SR 的确认审核、可验证需求包交接，以及在同仓库人工需求 PR 合入默认分支后冻结业务需求的可观察行为。

## ADDED Requirements

### Requirement: Release、IR、SR 的职责与稳定关系

系统 MUST 按 Release → IR → 一个或多个 SR 组织正式需求。IR 承载业务背景、目标、范围、边界及讨论结论；SR 承载完整、可测试的系统要求并作为开发单位。标题 MUST 由 AI 生成和修改，稳定内部 ID 不随标题变化。

#### Scenario: 小需求只拆一个 SR
- **WHEN** 需求范围较小
- **THEN** 允许一个 IR 只包含一个 SR；不强制拆出多条，也不让 IR 自身进入技术方案或执行阶段。

#### Scenario: 版本与开发分支分离
- **WHEN** 用户在设置添加 Release 或选择版本
- **THEN** Release 只组织交付范围及进度，不绑定代码分支；本地新建使用当前 Release，导入时选择目标 Release。

#### Scenario: 标题和拆分只能对话修改
- **WHEN** 需求尚未冻结且用户提出修改
- **THEN** Agent 更新标题、正文或拆分；界面不提供重命名、拖拽拆分或正文编辑；导航不显示 IR、SR 编号。

### Requirement: 两种需求来源与共享多项目 WebGUI

系统 MUST 同时支持开发人员本地新建需求，以及业务人员远程使用开发人员长期运行的 WebGUI 整理需求。业务人员 MUST 不依赖自己的 OMP、代码仓库或 clone。两种来源复用需求 Agent 和材料格式。

#### Scenario: 浏览器访问长期宿主
- **WHEN** 一位开发人员在其 clone 目录长期运行 WebGUI
- **THEN** 业务人员通过浏览器访问同一实例，在左下角选择已登记项目；不另建统一需求产品、额外中转服务或业务专属接口。

#### Scenario: 相同界面和共享可见性
- **WHEN** 不同人员打开同一 WebGUI
- **THEN** 各项目、正式材料、草稿及需求会话共享可见，不区分业务、开发专属视图或另建角色授权；项目和 IR 的会话、材料及任务归属仍严格区分。

#### Scenario: 业务草稿不操作 Git
- **WHEN** 业务人员点击新建需求
- **THEN** 只建立该项目的服务端草稿及 OMP 会话，不创建需求分支或 worktree，不提交推送；下载后由接手开发人员独立导入。

#### Scenario: 开发人员保留本地新建
- **WHEN** 开发人员在自己的 Dev 点击新建需求
- **THEN** 从默认分支创建需求分支和 worktree，不要求名称、分类或背景表单；直接讨论，不要求先经过长期 WebGUI。

### Requirement: 需求讨论必须审查实质内容

需求 Agent MUST 澄清问题、业务目标、使用场景、范围、非目标、规则、异常边界及验收行为，区分事实、假设和待确认问题；共同整理 IR 和完整 SR，并检查拆分覆盖、遗漏、重复和冲突。AI MUST NOT 编造未经确认的业务决定。

#### Scenario: SR 不能只有标题
- **WHEN** Agent 完成拆分
- **THEN** 每个 SR 包含行为、范围、业务规则、约束、异常及验收要求；全部 SR 合起来覆盖 IR，已知缺口和依赖背景如实记录，但第一版不实现 SR 依赖调度。

#### Scenario: 使用已有资料
- **WHEN** 用户提供文字、业务资料或附件
- **THEN** Agent 在可用权限内读取并引用资料，不能从字段齐全、章节非空或多个 Agent 意见相同推定业务正确；关键未决问题明确披露。

#### Scenario: 停止访谈
- **WHEN** 人员要求停止继续提问
- **THEN** 停止访谈并保留未决事项，按当前授权处理；停止访谈本身不构成确认、审核通过或开发批准。

### Requirement: 人员确认、格式检查和独立 review

人员 MUST 明确点击确认需求与拆分，程序先检查格式，通过后由需求 Agent 派发 review 代理审查同一版本的 IR、全部 SR 及覆盖关系。只有整组检查通过才完成内部确认。

#### Scenario: 格式未通过
- **WHEN** 确认时发现结构或关系不合法
- **THEN** 指出文件及问题，不启动语义 review，不完成确认，不使导出或开发可用。

#### Scenario: review 检查实质问题
- **WHEN** 格式通过且需求 Agent 派发 reviewer
- **THEN** review 检查业务目标、边界、未确认假设、可测试性、遗漏、重复、冲突及整体覆盖，保存只读结论；措辞建议不自动成为阻断项。

#### Scenario: review 后修改需要重新确认
- **WHEN** review 不通过或 Agent 实质修改材料
- **THEN** 需求 Agent 修订，原确认失效；用户重新点击确认，再执行格式检查和 review；旧审核结果不能批准新字节。

#### Scenario: 检查版本发生变化
- **WHEN** review 在运行或准备应用结果时材料改变
- **THEN** 只认审核输入快照；拒绝将迟到结果套用到当前材料，明确待重新确认。

#### Scenario: 左侧正式 IR 出现时机
- **WHEN** 已经生成 IR 和至少一个 SR，但尚未完成内部确认
- **THEN** 草稿及会话可以保存恢复，但不加入正式 IR 导航；内部确认通过后才以 AI 标题显示。

### Requirement: 全部通过后导出完整需求包

系统 MUST 仅为当前内部确认和检查均通过的完整 IR 提供需求包下载。每包包含一个 IR、全部 SR、必要业务附件、确认和 review 记录，以 ZIP 承载 Markdown 正文和 JSON 结构。

#### Scenario: 包必须完整且可验证
- **WHEN** 用户下载需求包
- **THEN** 清单包含格式版本、稳定 ID、来源项目、完整文件清单和内容摘要；不能只下载标题列表、局部 SR 或示例材料冒充正式成果。

#### Scenario: 修改后收回可下载资格
- **WHEN** 可下载版本随后被 AI 修改
- **THEN** 旧版本不代表新材料已通过；当前材料重新确认并检查前不提供当前成品包下载。

#### Scenario: 包不复制运行环境
- **WHEN** 生成导出包
- **THEN** 不导出 OMP 配置凭据、进程锁、服务器绝对路径或聊天正文副本；不要求接手人恢复原业务会话。

### Requirement: 开发人员导入与需求分支

开发端 MUST 对需求包执行确定性的格式、完整性、引用关系及路径检查，再关联目标项目和 Release。导入不启动 SR、不形成业务批准、不自动提交 PR，也不强制重复整套业务 Agent review。

#### Scenario: 从另一 clone 导入
- **WHEN** 开发人员取得同项目需求包
- **THEN** 来源服务器的绝对目录不作为导入目录；使用当前明确选择的项目和 Release，从其默认分支创建需求分支和 worktree，保存独立材料副本。

#### Scenario: 导入失败或重复操作
- **WHEN** 包缺失文件、版本不支持、摘要不符、路径越界，或操作被重复请求
- **THEN** 失败保留原包和已有材料，不覆盖冻结记录、不重复创建 IR、SR 或 worktree；明确显示真实问题，重复导入的细化交互另行确定。

#### Scenario: 项目适用性由开发人员检查
- **WHEN** 包格式检查通过
- **THEN** 开发人员检查其适用性并通过公司需求 PR 评审；不把包内审核记录理解为已验证当前代码兼容性或允许立即开发。

### Requirement: 需求 PR 合入前的共同需求交付

开发人员 MUST 将完整 IR、全部 SR、拆分与确认依据提交到同一仓库的需求工作分支，人工创建以默认分支为目标的需求 PR。全部需求合入默认分支之前，任何 SR MUST NOT 进入开发。

#### Scenario: 内部确认不启动开发
- **WHEN** 人员完成内部确认或资料 Git 提交
- **THEN** 显示待需求 PR 合入，允许人员准备 PR 说明；不进入技术方案、不代为创建或合并 PR。

#### Scenario: 项目没有远端
- **WHEN** 本地 Git 仓库有效但尚不能提交公司 PR
- **THEN** 允许需求讨论和准备，明确披露远端缺失；不能宣称需求已合入或开放 SR 开发。

#### Scenario: 需求评审要求修改
- **WHEN** 需求 PR 尚未合入且评审提出业务内容修改
- **THEN** 经 AI 修改后重新确认、格式检查和 review，并更新需求 PR；不沿用旧内容批准。

### Requirement: 需求合入即冻结整组 IR 与 SR

需求 PR 的已确认内容合入默认分支后，系统 MUST 立即冻结 IR、全部 SR 的正文、标题及拆分关系；冻结不能延后到首个 SR 启动。第一版 MUST 不提供解冻、需求版本变更或关联 IR 流程。

#### Scenario: 禁止修改冻结内容
- **WHEN** 人员或开发 Agent 尝试修改、增加、删除、合并、重新拆分需求
- **THEN** 后端拒绝改变冻结的权威需求及集合；页面显示业务需求及拆分结果已锁定；不以网页只读或提示词替代真实写入保护。

#### Scenario: 需求合入事实核对
- **WHEN** 人员标记需求 PR 已合入
- **THEN** 通过 Git 获取默认分支并核对完整 IR/SR 集合与确认版本；记录可定位的目标提交和内容依据，支持正常 merge、squash、rebase，不仅用源分支 SHA 判断。

#### Scenario: 后续代码已经变化
- **WHEN** 同 IR 的其他 SR 很久以后才启动
- **THEN** 仍采用原冻结需求，代码使用启动时最新默认分支；不能擅自改需求来适应代码。发现不兼容必须披露和阻塞。

### Requirement: 需求来源和导入副本的边界

系统 MUST 将业务源草稿、已导出快照及开发人员导入副本区分管理；包的存在和导入均不表示 Git 已合入。服务端源资料不得通过重复导出或导入自动覆盖已冻结的开发需求。

#### Scenario: 无需原会话交接
- **WHEN** 开发人员只有成品需求包
- **THEN** 可以独立检查、导入、提交需求 PR；不要求业务人员安装 OMP、加入 Collab 或恢复原会话。

#### Scenario: 导出后业务侧继续处理
- **WHEN** 源草稿和开发导入副本分处不同 clone
- **THEN** 不假定存在自动同步、远程合入通知或跨 clone 编辑；源草稿导出后能否继续修改以及如何获知开发侧冻结，必须按总提案待决边界处理。
