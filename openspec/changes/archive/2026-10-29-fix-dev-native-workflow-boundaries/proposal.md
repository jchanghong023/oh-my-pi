# Proposal

## Why

Dev 的四阶段原生会话与完整文件交接已有明确契约，但全面审查及实际复现发现，一些原生能力、用户授权、批准材料和异常恢复的消费边界没有一致落实：执行会话能力被裁剪；报告可经原生 shell 写入却未进入待验收；阶段模型选择、存活子代理技能授权、损坏历史、未结清取消、递归规格、收尾失败和宿主会话操作存在可观察缺口。这些问题可能使未授权写入、未批准需求同步、阶段重叠、历史丢失或失败伪报成功。现需修复既有契约，并补充足够精确的可观察场景，避免再由单一调用路径或表面状态代替真实事实。

## What Changes

- 保留需求、方案、计划、执行四个专有原生 Agent、六个 `/dev` 入口及五类简单正式文件；进入阶段交接完整正式原文、全部方案候选、选中 ID 与原始用户决定，不增加阶段、交接文档、逐任务账本或平行消息系统。
- 执行阶段及其实施后代使用完整适用的原生工具能力与全部包内 Superpowers，仍受批准范围、报告后验收、收尾及生命周期约束；前三阶段权限不变。保留原生 `wait` 及已有等待场景。
- 无论通过何种实际原生写入路径交付正式报告，均落实待验收；区分普通讨论和用户明确的范围内修复授权。原生取消须真实结清后才可转换；阶段恢复保留自身模型选择，损坏或不可用的原生历史不丢弃有效流程；存活执行后代的技能授权随会话生命周期有效。
- 统一原生可归档的递归增量规格集合、批准版本检查和完整交接，阻止批准后新增未获批准材料进入同步。保留收尾实际副作用及未完成恢复工作，失败不伪报完成，路径包含空格或括号时仍可修复并重试。
- 在原生 TUI 与开放宿主落实现有操作归属：附件提交与拒收不重复或丢失；持久化工作目录变更及副屏分叉先成功退出 Dev；阶段会话级设置作用于可见阶段，不影响隐藏普通会话。桌面协议与投影以 `zcode-app-server` 既有契约为权威，不复制第二套桌面需求。

上述是拟修复的既有行为及拟增加的精确验收场景，不表示实现或验证已完成。仅用户明确 `/dev next` 批准阶段及最终验收；不以普通反馈、报告存在或代理回复替代决定。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `spec-driven-orchestration`: 补充原生执行能力、授权、递归材料、会话生命周期、宿主归属及异常恢复的可观察边界；与已有四阶段和桌面契约共同适用。

## Impact

影响 Dev 原生运行时、阶段会话与子代理生命周期、正式材料版本及交接、验收收尾、TUI 输入和 ZCode 现有原生接入，以及相应回归测试与用户文档。具体设计和实施不在本需求提案中；不改变独立 OpenSpec、普通会话、前三阶段写入权限或桌面协议权威。不新增工作树、强制提交或未经用户明确授权的发布操作。无待用户决定的范围问题。
