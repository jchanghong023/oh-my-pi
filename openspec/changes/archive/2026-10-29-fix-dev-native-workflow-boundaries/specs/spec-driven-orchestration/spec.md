# Spec Delta

## ADDED Requirements

### Requirement: 执行会话保留原生能力和技能存续授权

Dev 执行 Agent 及其实施后代 MUST 保有适用的完整原生会话能力和包内 Superpowers，受原有获批范围、用户验收及生命周期守卫约束；需求、方案、计划阶段既有权限不变。

#### Scenario: 执行代理和递归实施后代使用原生工具

- **WHEN** 执行 Agent 或默认实施子代理及其递归实施后代在获批范围内工作
- **THEN** MUST 按普通原生会话的配置、可用性及适用权限提供原生工具和已配置能力，包括可用的 `wiki`、`repo`、`web_search`、`eval`、LSP、MCP、扩展及自定义工具，不以固定精简名单裁掉能力；`wait` 仍遵循「执行阶段等待异步子代理」
- **AND** 能力可用不等于绕过用户批准、项目规则、报告后只读、收尾或停止边界；原生明确受限的其他代理仍遵守其自身限制，普通会话和前三阶段不受扩大

#### Scenario: 存活子代理续聊读取技能

- **WHEN** 执行子代理首次任务结束后原生会话仍保活、空闲或经原生恢复，用户或获准工作继续该会话并按引用读取包内 Superpowers
- **THEN** 该会话及其递归执行后代仍可自动发现和按需读取全部包内 Superpowers；授权持续到相应原生会话释放，不因首次任务返回而提前撤销
- **AND** 不修改上游技能正文，不扩大非执行阶段技能自动发现或工具权限

### Requirement: 完成报告和明确修复授权的真实边界

Dev MUST 按实际完成报告交付及用户明确决定执行待验收和修复限制，不以写入工具名称或单纯文字前缀替代真实边界。

#### Scenario: 原生工具交付完成报告

- **WHEN** 执行 Agent 或其获准后代通过原生 `write`、`edit`、`bash` 或其他可用写入路径完成当前正式完成报告的交付
- **THEN** MUST 进入等待用户验收的约束，停止 Goal 及其他可写工作的自主推进；后续普通询问或解释仅可只读，不能通过可写工具或可写后代修改业务文件
- **AND** 不因报告存在自动批准或切换阶段，最终 `next` 仍由用户提交并检查正式报告结构及既有版本

#### Scenario: 讨论修复不等于授权修复

- **WHEN** 待验收或待收尾时用户询问修复的影响、请求解释或明确要求不要修改，而非明确要求实施修复
- **THEN** MUST 保持原待验收或待收尾限制与报告资格，只允许解释和只读调查；不得因提问以“修复”开头而开放写入或撤销验收资格

#### Scenario: 用户明确要求范围内修复

- **WHEN** 用户以自然语言明确要求在已批准范围内修正问题或继续实施，包括不使用固定关键词的明确请求
- **THEN** MUST 允许当前执行会话依既有授权规则开展范围内修复，旧报告失去本轮验收资格，更新报告并重新等待用户最终 `next`
- **AND** 收尾失败后只允许用户明确要求的、不改变已验收内容的直接收尾故障修复；改变范围仍须遵循既有回退及实际副作用限制

### Requirement: 递归需求材料批准和交接一致

Dev MUST 以与原生 OpenSpec 可发现及同步的增量规格一致的完整递归能力路径集合，执行需求材料读取、批准版本检查和阶段交接。

#### Scenario: 嵌套能力规格完整交接

- **WHEN** 本次 change 含 `specs/<area>/<capability>/spec.md` 等原生合法递归能力路径
- **THEN** MUST 将每份规格的实际路径及完整原文连同 proposal 纳入需求材料及其字节版本，并在阶段进入时按既有规则完整交接；方案全部候选、选中 ID 和原始决定不被摘要替代

#### Scenario: 批准后新增嵌套规格

- **WHEN** 需求批准后新增一个原生可发现的嵌套增量规格，即使已批准文件未变化
- **THEN** MUST 判为新增未获批准需求产物，指出真实路径并阻止依赖旧批准的工作、推进及同步；须由用户重新确认，不得在最终归档时同步未批准内容
- **AND** 无法枚举时按「已批准需求集合新增产物即视为变化」报告原因并阻断

### Requirement: 取消结清和原生历史恢复边界

Dev MUST 依据实际原生工作结清情况准入控制操作，并在必要业务状态有效时恢复可用的阶段原生会话及其自身配置。

#### Scenario: 已取消任务仍在清理

- **WHEN** 阶段自有后台任务已显示 cancelled 或已返回取消回执，但其实际调用及清理尚未结清
- **THEN** MUST 拒绝 `next`、`back` 及其他冲突转换或新工作，不以显示终态代替结清；退出和 `drop` 按既有停止规则等待或报告可重试失败
- **AND** 待真实结清后才依据其他现有门禁重新判断，不影响无关会话

#### Scenario: 恢复阶段自身选模

- **WHEN** 阶段原生历史可恢复，且该阶段此前通过原生模型控制选择了模型
- **THEN** MUST 按该阶段原生历史恢复其模型选择，不用隐藏普通会话当前模型覆盖；其他阶段及普通会话保持各自选择

#### Scenario: 阶段历史存在但无法解析

- **WHEN** 必要 Dev 状态和批准有效，但当前或其他已保存阶段的原生历史文件缺失、损坏或无法由原生历史加载器恢复
- **THEN** MUST 按「原生聊天历史缺失不丢弃有效流程」处理不可用历史，保留同一流程、Team 和批准，明确提示历史不可用，不伪造历史或自动发送输入
- **AND** 用户主动续聊时依据正式材料、保存的原始批准及当前输入继续；不得因单份损坏历史永久阻断有效流程或清除其状态

### Requirement: 部分收尾的副作用与未完成恢复

Dev MUST 如实保留原生同步归档失败时已发生的副作用和未完成的必要恢复工作，直至实际解决，不把部分结果视作完整成功。

#### Scenario: 同步后回滚失败

- **WHEN** 原生同步已修改主规格，后续收尾失败且回滚未能恢复全部实际修改，即使 change 尚未归档
- **THEN** MUST 保留并呈现未恢复的实际副作用及真实失败，禁止常规 `back` 和普通业务修改；只能按既有实际收尾副作用规则进行限定修复、用户 `next` 重试、退出或 `drop`
- **AND** 不因缺少归档目录而将实际同步副作用视为零，不伪报回滚成功

#### Scenario: 归档目标已生成但源清理失败

- **WHEN** 原生归档复制回退已生成归档目标，但原生要求清除的暂存源目录仍因错误未清除
- **THEN** MUST 保留真实归档位置、清理失败及未完成工作，不在重试时仅因目标存在而宣布验收完成；用户排除故障后由用户 `next` 继续必要收尾
- **AND** 不重复同步或重建 change，不删除无关文件，不把未完成的原生清理伪报为成功

#### Scenario: 备份路径含空格及括号

- **WHEN** 原生 retirement 清理失败且实际备份路径包含空格、括号等合法路径字符
- **THEN** MUST 保留可准确定位完整备份的真实诊断和恢复事实；在该备份确已清除且其他收尾门禁满足后，用户 `next` 可继续剩余收尾，不因截断路径永久阻断
- **AND** 原生错误及仍未完成清理时不得显示完成

### Requirement: 原生输入和宿主操作归属

Dev MUST 将附件、会话级操作及工作目录变更绑定正确的原生会话，并遵循既有退出、停止和桌面接入契约。

#### Scenario: 附件提交成功或拒收

- **WHEN** TUI 以 Enter 或其他原生提交方式提交含附件的 Dev 输入，操作被接收或拒绝
- **THEN** 成功时只消费本次已提交附件；拒收或失败时原文、附件及对应标记各保留一次，不重复、不丢失、不改变其归属，也不调用模型处理被拒输入

#### Scenario: 持久化工作目录变更

- **WHEN** 用户在 Dev 内通过 `!cd` 或其他原生入口发起持久化工作目录变更
- **THEN** MUST 在移动会话日志或改变工作目录之前成功退出 Dev 并恢复普通会话；退出失败则阻止变更，保留原阶段及其历史引用
- **AND** 成功后普通会话与实际工作目录一致，之后进入原工作区时仍可恢复原阶段历史，不转移或复制 Dev 流程

#### Scenario: 桌面副屏分叉和阶段设置

- **WHEN** 开放桌面宿主在 Dev 活动期间请求副屏分叉，或请求修改当前可见会话的推理档
- **THEN** 副屏分叉须先成功退出并结清 Dev，退出失败不得创建子会话或发送首条输入；推理档设置只作用于当前可见原生阶段，不修改隐藏普通会话
- **AND** 协议、身份、投影和兼容性遵循 `zcode-app-server` 的「原生 dev 接入合同」，不建立第二套桌面状态机或批准入口
