# Proposal

## Why

Dev 需求必须统一表达已有工作区的唯一流程、唯一控制者、直接阶段聊天、Team 配置及可恢复生命周期，避免普通会话、进程内存或独立决策面板形成第二套流程归属。

本变更仅在无代理、需求、方案、计划、执行五种阶段状态间切换当前原生 OMP 会话，保留必要的文件批准、Team 配置及最小业务状态。聊天、工具、输入和 Goal 均复用原生能力；唯一新增的常驻显示是三行 Dev 固定区，不建立另一套界面、消息系统或开发执行引擎。已批准需求的唯一权威为 `openspec/specs/`；本提案及增量规格与其现行规则对齐，原生同步及归档不得回退后续已批准的行为和授权边界，需求记录不表示软件已实现或验收。

## What Changes

- **BREAKING**：Dev 配置和流程归属当前已有工作区；Git 项目按已有工作树统一子目录和路径别名，不按分支、普通会话或 OMP 实例另建流程。每个工作区仅一个未结束流程及一个控制者。Dev 不创建 Git 工作树，不要求用户先建工作树，不把创建工作树作为阶段、计划或子代理任务。
- **BREAKING**：仅保留 `/dev`、`/dev config`、`/dev new <需求内容>`、`/dev next [方案ID]`、`/dev back`、`/dev drop` 六个 Dev 入口。彻底删除其他旧 Dev 命令的注册、分发、补全、帮助、界面动作及提示词引用，不保留别名、兼容处理或旧命令专属迁移提示；旧命令与其他未知子命令一样报错，不交给模型。普通 OMP 原生命令不属于删除范围。
- 进入时检查普通会话工作结清、外层模式互斥、控制权及恢复条件；成功后切换主聊天显示但保留普通历史。退出与 `drop` 共用原生停止结清流程，涵盖当前 Agent、Team、Goal 及其他自有任务；退出再保存必要状态、释放控制权并恢复普通界面，失败不伪报安全退出，未结清时拒绝阶段切换且不延迟排队。
- 五种阶段状态只决定当前聊天对象及该阶段允许的工作，忙碌和错误直接来自原生运行。主聊天、消息、流式回复、工具事件、输入、附件、队列、草稿、历史、压缩及停止沿用 OMP，不复制父会话回复、不另建消息系统。唯一新增常驻界面为输入框上方三行 Dev 固定区；手动配置和详情也复用原生交互，不增加 Dev 专用决策、阶段或材料面板，不自动弹窗、不刷聊天摘要。
- `/dev config` 只管理当前工作区的方案 Team 开关，Git 项目保存在当前工作树的 Dev 状态中，默认关闭、保存后生效、取消不改变值。无代理及需求阶段可改，方案及后续阶段不可改，返回需求后可改；可修改性和按钮可用性根据阶段及实际运行推导，不另存冻结字段。正常完成保留值，`drop` 或无效旧状态清除后恢复关闭。
- `new` 继承配置，自动分配合法唯一变更 ID 并固定正式产物路径；失败保留此前配置和已创建文件，旧工作未结清不得新建。`next` 统一四次明确决定；`back` 仅退相邻阶段，保留文件和代码，撤销受影响批准且不自动启动工作；`drop` 结清自有工作并清除流程及配置，不回滚业务文件或增加确认。
- 保留需求、方案、计划、执行四阶段和原 OpenSpec／Superpowers 正式产物格式。Team 仅在进入方案时按配置启动，普通追问不重跑；失败后先结清自有工作，再 `back` 返回需求、`next` 重新进入方案，不新增同阶段 Team 重跑或专用重试入口。执行默认正常执行，用户可手动开启当前执行会话的原生 Goal，仍受获批计划及验收收尾约束。
- 删除 Dev 的 Goal 开关、冻结规则、持久化字段及状态区 Goal 开关显示。Goal 完全沿用原生生命周期，Dev 不按聊天轮次创建、删除、重建或改写其状态，不另存 Goal 状态，恢复 Dev 不自动启动 Goal。
- 阶段进入时完整交接原文件、全部方案候选、选中 ID、原始批准及 Team 配置；同阶段澄清、补充和范围内修复直接续聊，不反复注入未变化文件。产物结构检查集中在 `next`，正常澄清不因文件未生成报错、不自动切阶段。版本检查只复用本流程正式需求材料、方案、计划及完成报告已有的版本，返回结果而不直接改阶段；不扫描、快照或自动检测业务代码及整个工作区的变化，也不承诺据此发现业务代码的外部修改。
- 相关阶段子代理的角色提示词和阶段请求提示词必须同步上述规则：只约束阶段职责、真实产物及获批范围，不指导调用旧 Dev 命令、不创建工作树、不按轮次管理 Goal；普通追问沿原生会话续聊，不强制每轮重读全部材料或重写产物，也不重跑 Team。执行代理不得自行触发 `next`、代替用户验收或执行同步归档，提示词不得重新引入被移除的配置、协议或流程。
- 执行阶段 `next` 仅由用户触发，为唯一最终验收；程序直接调用原生 OpenSpec 同步、校验及归档，不调用模型、不委派执行代理、不新增收尾代理。部分失败时用户再次 `next` 只继续剩余收尾，不重新验收、重跑业务任务或重启 Goal。原生归档正常搬移后按实际归档结果定位同一材料，不重建原目录或重复归档；方案、计划、报告仍在原位置，收尾只自动核对正式材料版本，不追踪业务代码变化。
- 收尾失败保留当前执行阶段的原生会话、历史及实际进度，用户仍可直接对话；本次失败诊断可供执行代理按需读取，不要求用户手工复制。一般询问只读调查；用户明确要求修复时，只处理不改变已验收材料、范围和交付内容的直接收尾故障，不恢复业务任务或 Goal，不自行重试同步归档。修复后仍由用户 `next` 继续程序收尾；涉及已验收内容变化时沿既有回退或新变更规则处理。
- 只保存恢复业务所需的阶段、Team 配置、变更身份、方案选择、原生会话关联、批准原文与版本及必要验收收尾信息；保留既定正式产物路径约束，可由既有变更或会话引用取得的信息不重复保存。不另存忙碌标记、临时错误、消息队列、Goal 状态或完整正文，聊天和文件按原生会话及正式产物读取。显式进入恢复并核对，但不重放输入、工具或自动启动 Team／Goal；有效状态不因聊天缺失丢弃，确实不可恢复时才自动清除旧 Dev 状态和 Team 配置，旧工作未结清前不得新建。
- 对仍开放的 ZCode Dev 入口同步上述归属、控制、命令、配置、批准及恢复语义。冷历史查询仍只读；不通过查询恢复控制者、获得写权限或启动模型，不借动态工作流 journal 接管 Dev。

## Capabilities

### New Capabilities

无；本次均为既有能力的需求变更，不新增平行的 Dev 产品或工作流能力域。

### Modified Capabilities

- `spec-driven-orchestration`：替换 Dev 的命令、工作区归属、原生聊天及三行状态区、仅 Team 配置、阶段交接与同阶段续聊、`next` 产物检查、只返回结果的批准版本检查、统一停止、验收收尾及最小业务持久化恢复契约。
- `zcode-app-server`：仅调整原生 Dev 接入合同，使其投影相同工作区 owner、五种角色、原生消息及运行事实、Team 配置可修改性、手动原生 Goal 和恢复边界，不建立额外消息或持久状态；保留无关普通多会话、子代理、动态工作流及协议兼容合同。

## Impact

- 受影响的既有能力边界包括 `packages/coding-agent/src/spec-driven/`、原生 `/dev` 注册及补全、TUI 原生阶段会话切换与固定区、ZCode 的 Dev 路由和投影，以及 `src/prompts/agents/spec-driven.md`、`src/prompts/spec-driven-task.md`、`src/prompts/spec-driven-communication.md` 的相关阶段提示词（路径均相对 `packages/coding-agent/`）。本轮仅收口需求材料，不修改这些实现或提示词文件，也不重新声明软件实施或验收结果。
- 界面验收对象为 OMP TUI，覆盖 100×28、120×36 及尺寸调整；不新增桌面工作流、桌面页面、外层阶段、独立聊天存储、逐任务证据引擎或另一套 Team／Goal 通用配置。
- 普通聊天、独立 OpenSpec、Superpowers、Team、Goal 及原生工具保持正常用途；Dev 限制不扩散到非 Dev 会话。既有 Markdown 需求权威继续原位维护，不制造竞争性主规格。
- 收口范围为本变更的 proposal 及上述两份增量规格的对齐、原生校验、同步和归档；不新增功能，不修改业务实现、项目配置、模型配置、历史设计、实施计划或执行状态。
- 验收覆盖仅六个 Dev 入口、旧入口彻底删除、阶段提示词一致、不创建工作树、五种角色切换、原生 OMP 显示及唯一三行固定区；既有工作区隔离、批准、停止、恢复和必要收尾约束继续适用。原生需求校验不代表软件验收。
- MUST 避免过度设计：仅增加完成上述行为所需的最小 Dev 控制，不建立平行的会话管理、聊天渲染、消息队列、状态机、任务证据、工作树隔离或交互体系，不为假设的未来需求增加抽象和配置。
