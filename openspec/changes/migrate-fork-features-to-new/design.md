# Design

## Context

迁移动机和功能边界见 [proposal.md](proposal.md)，可观察合同见 [规格](specs/)。规划时，本地 `upstream` 与 `upstream/main` 同指 `49dc75e819`；`new` 相对此基线的已提交差异只有 `AGENTS.md` 和 `USER_FEATURES.md`，`main` 从同一基线发展出 2,066 个改动文件。因此以 `new` 的文件和接口为落点，`main` 只用于核对已在用的行为和筛选可独立迁移的实现。`new` 没有登记过的主规格；不复制 `main` 的规格树。

## Goals / Non-Goals

**Goals:** 逐域保持清单中的用户合同，把差异留在上游已有的设置或扩展点上；每批可用现有入口独立验证，失败不影响仍在使用的 `main`。

**Non-Goals:** 不为了隔离 fork 而另建配置框架、第二套会话运行时或兼容层；不要求目录结构与 `main` 一致，也不迁移测试、历史数据或未列出的构建和发布流程。

## Decisions

1. **按用户合同筛选，不按提交筛选。** 对照 `new`、`main` 和共同上游基线：行为等价则复用；独立且依赖中没有清单外行为的实现直接移植；共享文件只引入必要变更；旧接入方式不适合 `new` 时沿上游接口重写。拒绝合并、整段拣选复杂提交或覆盖共享文件：`main` 的 `builtin-modes.ts` 把清单命令与 `/todoloop` 混在一起，还有独立的 `/crawl`，这些不应进入 `new`。每批复核相对实施时上游基线的生产文件差异，不以行数代替维护面判断。
2. **先落运行设置和策略，再接模型。** 在 `packages/utils/src/dirs.ts` 的现有目录解析和现有 CLI、会话启动链路落实模式与目录；用已有设置定义表达默认值，硬边界和启动覆盖不写回用户配置。复用 `packages/ai/src/utils/proxy.ts` 一类共同 HTTP 入口和托管 Git 环境，Windows 系统代理属于非显式默认。宽松 TLS 仅限规格中的运行请求，安装器和 `omp update` 读取发行元数据走严格校验路径；内网凭据刷新禁令在实际刷新入口生效，不靠提示词阻止，显式配置的其他向量地址不得收到公司凭据。模型目录和策略沿用 `packages/catalog` 的描述符和 KDL；旧认证和向量实现仅移植必要的读取、注册、生命周期及错误处理，不另造模型路由表。逐入口打补丁或用进程全局开关替代明确优先级，都会扩大影响面。
3. **TUI 采用现有状态的显示投影。** `new` 已有状态栏、`ToolArgsRevealController` / `decodeStreamedToolArgs`、`ui-helpers.ts` 的历史重建和转录渲染。紧凑活动、输出、Diff 作为显示层，不因更改显示模式而重建会话或修改转录；实时和历史路径共用参数解码。`/tree` 在现有选择器上扩展实际工具记录。单独评估 `main` 的 `compact-dock` 等局部实现，不覆盖包含多个功能的 `interactive-mode.ts`，也不为预览维护第二份完整工具状态。
4. **终端命令沿用上游会话和协作接口。** `/wt` 由 `new` 的 `builtin-lifecycle.ts` 和 `workspace-tree.ts` 提供基础；仅补工作树放置、复用或保全方面实际缺失的行为。独立的 `/workspace`、`/minimal`、`/jchime`、`/sketch` 接现有命令表、提示和草稿入口。`/loopn` 复用当前轮、后台任务结束和取消信号，不另写全局计时器轮询会话。`/goal-autopilot` 沿 `goals/runtime.ts`、现有 Goal 持久化、队列与压缩继续机制增加无人值守行为；以请求、会话和有效目标绑定本次授权，暂停、替换或切会话不得沿用旧授权，普通 `/goal` 和普通表单不变。`/collab2` 仅添加编号房登记及其生命周期，复用 `new` 的 `builtin-collaboration.ts` 和 `collab/` 的会话传输与来宾接入，不复制协议或改变 `/collab`。
5. **内置能力只保留产品入口及必要资源。** 沿 `new` 的 CLI、技能、插件和工具发现入口接入 JCH、OpenSpec、Superpowers、Developer Test Agent 和 OpenWiki。`main` 的 `vendor/` 资源、`openwiki-cli.ts`、`openwiki-resources.ts` 与已有运行入口是筛选来源，不照搬整棵依赖、测试或发布树；构建接线仅保留源码运行和独立产物交付确需的部分。OpenWiki 的写入／模型生成入口与查询、预览、浏览、导出分开，后者不经过模型凭据初始化；沿用检查点及既有 Wiki 格式，不引入数据迁移。只移动独立模块，避免为单一适配场景引入通用插件框架。
6. **安装和更新保持有限的独立入口。** 用 `main` 的 `scripts/install.sh`、`scripts/install.ps1`、`cnb-release-contract.ts` 对照实际安装、日志和元数据合同，和 `new` 的现有更新命令衔接；集中渠道、平台和产物规则，不将 CNB 改造传播到上游通用 CI。先校验再替换；Windows 占用处理只作用于已核对映像路径的目标进程；PATH 和 Browser Relay 的部分失败不得伪报全成功或回滚已生效的更新。这比复刻整个发行流水线改动小，也比只改下载 URL 能覆盖真实安装合同。

## Risks / Trade-offs

- 51 条行为散落在共享入口，按文件拣选会漏项或带入额外功能 → 用任务清单的行号映射逐批验收；共享入口检查清单外调用者的原有合同。
- 紧凑视图的实时、历史和窄终端可能行为分叉 → 复用同一数据来源，在实际 TUI 检查受影响路径，不用快照替代交互。
- 内网凭据、公网刷新、无人值守审批及宽松 TLS 都可能因共享入口而超范围 → 分别核对模式和授权的正反条件，使用隔离配置与本地替代源，不用真实用户凭据做探测。安装和更新的发行元数据严格校验分别验收。
- Linux / CentOS 7、Windows 注册表和占用替换、独立产物或公司服务并非都能在一种环境验证 → 分开记载平台、源码或产物、隔离或实机证据。不可用的环境记为未验证，不用另一环境代验，不提前切换。

## Migration Plan

1. 在现有 `new` 上依次落地运行基础、模型、终端交互和命令、内置能力、发行入口；可独立的功能分批验收。先复用 `new` 的局部检查和真实入口；不引入旧测试，无明确回归缺口不新增测试。
2. 按 [tasks.md](tasks.md) 逐项核对清单和生产改动边界；验证时隔离用户配置及工作区，不改 `main`、真实凭据或日常使用环境。单批有缺陷，隔离并只撤销该批迁移改动，日常仍使用当前 `main` 产物。
3. 全部验收后才以 `new` 的交付物接替日常使用和维护；迁移不删除 `main`、不更改远端默认分支，也不覆盖用户现有数据。
