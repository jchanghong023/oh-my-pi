# team-configuration

## Purpose

规定 Team 的 profile 全局成员配置、候选模型、草稿预览、保存回执和 offline 双端持久化。GUI 配置不依赖或绑定聊天会话，所有入口使用同一个配置服务。

## Requirements

### Requirement: Team 配置属于 profile 全局用户设置

OMP MUST 让同一运行 profile 的所有会话共用 Team 成员、模型与顺序。GUI 可在未选择或创建聊天会话时查询、预览和保存该设置；workspace 仅用于可信路由和模型目录解析。保存不改变正在执行的讨论。

#### Scenario: 无聊天会话时编辑 Team

- **WHEN** 用户从 ZCode 的全局 Team 设置页打开配置，且没有聊天会话
- **THEN** 页面仍能读取候选、预览草稿并保存到运行 profile，操作不创建隐藏会话。

### Requirement: Team 保存接口的范围

OMP MUST 让 TUI、GUI 与经用户授权的 Agent 代配共用 Team 成员校验和保存服务。Team 保存接口不得被描述为 provider 定义保存接口；Agent 若获授权新增 provider，仍须遵守 offline 双端最小安全写要求，任意文本编辑不具有程序保存服务的锁、版本与事务保证。

#### Scenario: Agent 配置 provider

- **WHEN** 用户授权 Agent 新增 provider 定义
- **THEN** Agent 不将 Team 成员保存接口当作 provider 保存 API，并按 offline 双端写入要求处理配置。

### Requirement: Team 模型配置界面

OMP MUST 候选、顺序、重复、失效槽位和只读预览完整保留，取消不写盘。

#### Scenario: Team 模型配置界面的详细边界

- **WHEN** 本节所述功能在适用条件下运行
- **THEN** 以下具体约束适用：


**2.9.1 入口与可选范围**

* TUI 通过 `/team configure` 打开专用配置界面；原 `/team <问题或需求>` 的讨论语义不变。精确配置子命令由现有 slash 注册表识别，不把打开界面转发给模型，不把缺省 `/team` 改成必须先配置。
* Team 是 OMP 的内置聊天命令，不是独立应用页面。ZCode 必须有可发现、可直接打开的专用 Team 设置界面，只配置成员、模型及顺序，不承载任务输入和运行；聊天输入框通过 `/team …` 启动当前会话的讨论。设置复用本节有序成员、完整候选、只读预览、保存回执与冲突处理，不要求用户手写 YAML，不另建 Team 配置所有者。
* Team 模型／成员／顺序是运行 profile 的全局用户配置，所有会话共用，不按会话单独配置。GUI 无需先选择或创建聊天会话即可编辑和保存；执行端工作区仅用于路由和解析原生模型目录，不产生工作区私有的 Team 配置副本。运行中的讨论保留启动时配置，后续讨论读取保存后的全局值。
* 用户无需手工编辑配置文件。候选来自当前环境、profile 和项目上下文的实际模型注册表，覆盖所有已接入的 provider，不维护固定的几个模型或 company 专属名单。
* 可选择范围须与第 2.2 节的实际运行校验一致：聊天模型、已有必要认证、符合有效启用／禁用规则，且支持 Team 所需前端只读工具与结构化输出。embedding、reranker 不作为候选；已知但不可用或不支持 Team 的聊天模型可展示原因，但不能选入新名单。不为选择模型自动启用 provider、修改认证或探测真实模型。
* offline 沿用相同名单规则与已允许的内网来源，不因打开、搜索或刷新界面访问公网。普通模式也不以配置查询为由发送模型推理请求。
* 全局 Team 配置的冷目录必须复用正常 SDK 启动的本地凭据作用域模型缓存恢复；已认证且仅由 Copilot／Cursor 等本地缓存提供的聊天模型不能因未创建会话而缺失。恢复不刷新 provider、不发网络或推理请求、不创建隐藏会话，既有认证、enabledModels 和 Team 能力过滤保持不变。

**2.9.2 面板与交互**

采用“有序成员草稿列表＋添加／替换模型选择器”，不采用无法表达顺序和重复槽位的普通多选框：

ZCode 专页直接呈现该配置编辑器，不先打开空壳页面再弹出另一层全屏技术对话框。默认模型选择优先展示实际已配置可用的候选，未就绪候选可另行查看准确原因；无可用模型时提示先配置模型服务。主界面只保留模型成员、顺序及保存操作；下表中的上下文／原始存储事实和只读运行预览放入折叠高级详情，不读取或展示当前聊天会话主模型，不以会话运行条件阻挡全局配置。

| 区域 | 展示及操作 |
| --- | --- |
| 配置上下文 | 当前 profile、shm 活动端与原始 NFS 持久端各自的用户层原值／读取状态、实际生效来源及覆盖提示；非双端模式明确持久端不适用，不把两端不同简化为一个布尔标志 |
| 成员草稿 | 按槽位顺序保留原始 selector、可解析时的名称／完整 `provider/model-id` 与状态，失效项也有稳定的位置；支持添加、替换、上移、下移、复制槽位、删除 |
| 模型选择器 | 搜索名称、ID、provider 及已核实的中文别称／简称；同名跨 provider 的候选明确显示来源，由用户确认具体项 |
| 运行预览 | 通过共享服务的只读草稿预览同时展示当前生效配置、拟保存用户名单及考虑高层覆盖后的预计有效槽位，保留显式名单展开后的顺序、重复及默认回退选择；默认回退的实际主模型在启动讨论时确定；不写盘、不把预览当成已保存 |
| 操作区 | 保存、恢复默认、取消；恢复默认把草稿设为 `[]`，仍需保存确认，不立即写盘 |

* 同一模型可反复添加或复制，新增时明确提示这是另一个独立代理槽位，不自动去重；排序只影响草稿，不逐次写配置。
* 已保存但失效、被禁用或目录中消失的成员保留其原始 selector 并标错，允许替换／删除，不因候选过滤而静默丢失。全局配置不检查当前聊天会话的主模型或运行条件。
* 搜索只筛选真实候选；自然语言辅助匹配沿用第 4.6 节，不按相似度自动选第一项。可唯一核实的映射可供普通 Agent 代配直接采用，TUI 搜索仍由用户确认；多解或缺失不能拼造 ID。保存及落盘使用具体模型身份，不使用自然语言字符串。
* 打开面板后仅编辑本地草稿，保存时一次提交完整有序列表；取消不写盘。有未保存修改时退出须明确保留在面板或放弃，不隐式保存。支持键盘完成全部操作、滚动和窄终端显示，长 ID 不得导致来源、状态或关键操作不可辨认。
* 保存版本冲突时保留草稿，允许重新读取并比较后再次提交，不自动覆盖外部更新。收到外部设置变化通知且草稿已修改时只提示变化，不直接替换草稿；切换 workspace／profile 后丢弃迟到响应，不把旧草稿写入新上下文。
* GUI 草稿变化调用只读草稿预览（字段契约即 `omp-config-extension` 的 `get_team_config` preview data 结构，见 [ZCode 接入需求](../zcode-model-configuration/spec.md)），由共享服务计算结果；TUI 调用同一只读方法，不在两端复制运行模型选择／槽位算法。请求携带并回传草稿 `clientRevision`，只展示仍匹配当前 workspace／profile 和草稿版本的结果；无法解析的保留槽位可参与只读诊断，但修复／移除之前不能作为具体模型写入。
* 完整保存、保存但被高层覆盖、部分保存、结果未知须有可区分提示；Linux offline 展示活动与持久两处结果。保存只影响随后启动的 Team，不改变正在执行的讨论及当前主模型。

**2.9.3 与 GUI 的职责边界**

TUI、GUI 与普通 Agent 代配共用模型目录资格、成员校验及保存服务。GUI 管理布局和草稿，OMP 返回候选、有效来源、版本、槽位与保存结果；GUI 不读写 YAML、不推导 shm 路径、不访问数据库或复制凭据。ZCode 的全局 Team 配置通过 `omp/team/configure {workspace, request}` 调用同一原生服务，不依赖 sessionId；role 与临时会话模型仍使用各自原生接口。字段契约见 [Team 模型配置接口](../zcode-model-configuration/spec.md)。

#### Scenario: Team 模型配置界面的可观察行为

- **WHEN** 用户在 TUI 或 GUI 编辑成员草稿
- **THEN** 候选、顺序、重复、失效槽位和只读预览完整保留，取消不写盘

### Requirement: Team 配置保存服务

OMP MUST 共享服务按版本冲突和 offline 双端结果返回准确回执，不覆盖无关字段。

#### Scenario: Team 配置保存服务的详细边界

- **WHEN** 本节所述功能在适用条件下运行
- **THEN** 以下具体约束适用：


* **存储选择：** 继续复用统一 Settings 及 YAML 主设置 `config.yml`（兼容已有 `config.yaml`），持久键保持 `team.members`；不迁入 `agent.db`，不新增 Team 专用数据库、平行配置文件或独立 provider 定义。界面免除用户手写 YAML，不等于更换底层存储。
* **共享服务：** 将读取用户值／有效值、模型候选与资格、运行槽位预览、版本校验、保存及读回放在同一业务服务；TUI 和代配只适配输入／输出，不各自拼接 YAML 或实现一套模型筛选。复用既有模型注册表与 participant 解析规则，不重写五阶段编排。
* **界面复用：** 添加与替换复用现有模型浏览／选择器的 `selectOnly` 能力，只返回选择、不切会话模型；必须注入共享服务的 Team 候选池，不能把当前会话的 `scopedModels`／最近使用列表当成完整 Team 候选。验收覆盖会话候选受限而另一个模型仍符合 Team 资格的情形，不直接复用会话切换、上下文压缩或 role 保存副作用。新增列表编辑器只负责有序草稿和交互。
* **配置层：** 写入仅限当前 profile 的用户层，保留项目、overlay 和运行时优先级。`[]` 显式采用默认回退，移除字段则删除用户层值；两者均不得清除高层覆盖。默认／命名 profile、实际 `.yml`／`.yaml` 与原始根解析沿用现有目录机制，不能写死 home 或使用另一个进程的默认路径。
* **重复与校验：** 对本次读取、更新涉及的主配置原文先做严格 YAML 结构及重复映射键检查，包括重复 `team:`／`members:`；错误须带文件位置或逻辑位置。不能先用“后值覆盖前值”的解析结果保存、自动去掉重复键或隔离后用新文件掩盖歧义。合法的成员数组重复项与跨层覆盖不是重复键错误。复用已有 YAML 解析能力，不增加第二套格式。
* **单文件保存：** 非双端模式复用设置层的本机文件锁，采用锁内重读、目标字段版本比较、最小字段合并及原子替换；保留其他设置及可保留的 YAML 注释。NFS 持久端必须采用[双写权威要求](../offline-shm/spec.md)中的跨主机锁，不能直接复用 Linux 本机 socket 锁。锁内重复键或版本冲突不写文件；同值保存为幂等无变更，不能静默跳过旧写入却返回成功。
* **offline 两处保存：** 同一保存请求必须遵循[双写权威要求](../offline-shm/spec.md)，在相同 profile 的 shm 活动配置及原始 NFS 配置分别最小合并 `team.members`，两端都确认后才报告完整成功。共享服务负责实际路径、每端文件名与私有权限，GUI 不传路径；本接口不改 provider、凭据、数据库或备份。其他模式不虚构第二目标。
* **两处一致性：** 联合 revision 纳入活动／持久两端目标字段、缺失状态和实际文件身份。按权威要求先持有 NFS 跨主机锁、再持有活动端本机锁，在两锁内复核双方版本，再先写活动端后写持久端并读回；遵从锁协议的同旧版本竞争须在首次写前拒绝后提交者。写入中第二端失败按实际提交报告部分／未知，不回滚覆盖新改动，重试先重读双方现值并带新 revision。回执描述本请求锁内提交事实，返回 `config` 是随后查询的现值，两者不能混同。
* **持久边界：** 原始根 I/O 只发生在用户明确打开配置查询／保存时，不进入启动、普通讨论或输入就绪关键路径。沿用[离线 shm 契约](../offline-shm/spec.md)的原始环境、备份域和启动不恢复规则；后台备份不是用户配置双写，修改原始配置也不意味着 shm 清空后会自动回填。
* **生效与刷新：** 保存后重载当前服务的相关 Settings，复用 `settings_changed` 通知；下一次 Team 启动重新读取有效配置。其他进程不依赖本进程广播，须借既有文件变化读取及保存时版本检查处理新值。打开或保存配置不启动讨论、不测试真实模型、不修改主模型。

#### Scenario: Team 配置保存服务的可观察行为

- **WHEN** 用户保存 Team 成员配置
- **THEN** 共享服务按版本冲突和 offline 双端结果返回准确回执，不覆盖无关字段

#### Scenario: 全局配置不消费聊天会话模型

- **WHEN** 用户未创建会话，或当前聊天会话模型及可选模型范围发生变化
- **THEN** 全局 Team 配置仍可查询、编辑与保存，不展示聊天会话主模型、不据此缩减候选；默认回退只显示配置选择，实际主模型在启动讨论时确定。
