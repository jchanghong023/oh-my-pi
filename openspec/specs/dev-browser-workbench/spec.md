# dev-browser-workbench Specification

## Purpose
规定 OMP 新建需求的浏览器工作台：在复用现有 Dev 专有 Agent、原生会话和 offline Collab 的基础上，以八阶段材料、人员确认和 Git 记录支撑 Lander／Sailor 研发协作。浏览器不另建执行或协作引擎；开发按同目录同分支串行进行，ST、PR 和测试人员测试由人决定完成，未合入需求可撤销，合入后的问题通过关联新需求处理。

> 呈现状态：用户已纠正工作台UI要求，原先技术控制台式UI的完成结论失效；下述参考布局和默认深色的新呈现及视觉验收仍待完成，不宣称已获接受。已有未受影响的后端、普通OMP隔离、Git和Collab证据保留复用；新的广泛授权仅用于必要命令，不要求重跑无关全套验证。本次文档同步不执行软件检查。

## Requirements

### Requirement: 八阶段工作台与只读材料导航

工作台 MUST 参考已批准的 `runs/dev-workbench-demo/index.html` 及用户参考图的信息层级与四区布局，而非逐像素复制：左侧需求列表、中央材料上方的八阶段及状态、中央只读材料、右侧共享 AI 会话且输入框位于底部。Dev 工作台 MUST 默认深色，不改变普通 OMP 的主题默认值；固定采用业务需求、开发需求、技术方案、开发计划、开发与 UT、ST测试、提交与 PR、测试人员测试八阶段。查看位置与真实进行阶段 MUST 分离，不因浏览或聊天自动批准、推进或回退。

#### Scenario: 查看其他阶段
- **WHEN** 用户点击顶部某一阶段或从列表查看另一需求
- **THEN** 仅显示对应的真实材料与状态，不启动 Agent、不改变当前进行阶段、不发送草稿、不形成确认
- **AND** 材料未生成、缺失、不可读时显示真实原因，不显示原型示例作为实际结果

#### Scenario: 当前阶段的简洁操作
- **WHEN** 用户查看需求或切换查看阶段
- **THEN** 页面只呈现当前进行阶段适用的必要流程控制、人工标记、材料上传／下载及明确操作的确认／结果，不把所有阶段动作同时铺开；查看其他阶段不产生该阶段的操作授权
- **AND** 不提供原生命令下拉框、JSON 参数输入、JSON 状态／调试面板或内部 hash 控制台；正式方案仍保持既有文件格式，以可读候选和正文展示，不把内部数据结构变成工作台主界面

#### Scenario: 阶段操作不挤占聊天
- **WHEN** 用户查看当前阶段材料或展开更多需求操作
- **THEN** 当前阶段主操作及“更多”入口 MUST 位于中央材料工具栏的只读、复制、下载控件右侧；Back、提交、归档及测试状态等次级操作按适用阶段收入可关闭的弹层，不铺在右侧聊天正文与输入框之间
- **AND** 阶段说明、阻塞原因及可折叠操作回执 MUST 位于中央材料滚动区；顶部八阶段导航保持原位，右侧保留原生聊天、输入、模型选择及必要审批／提问，确认、权限及宿主门禁不变
- **AND** 查看非当前阶段时 MUST 以“回到当前阶段”替代阶段操作；窄屏控件在中央工具栏换行，弹层按可用空间展开并可滚动，不越出视口或挤压聊天

#### Scenario: 首次打开的空状态
- **WHEN** 工作台尚未选择需求，且用户未明确选择本地业务写作或加入真实共享会话
- **THEN** 显示引导新建需求的空状态，不默认进入本地业务写作，不自动创建需求或启动 Agent；无目标的会话输入不可发送

#### Scenario: 通过会话修改材料
- **WHEN** 用户需要修改当前获授权阶段的文档
- **THEN** 通过当前 Agent 会话处理，中央材料区域只读；不新增网页文档编辑器
- **AND** 可下载本需求实际 Markdown 材料；方案等原格式材料按既有可读方式展示，不为 UI 另造一套正式文档

#### Scenario: 前五阶段的推进和回退
- **WHEN** 用户操作第一至第五阶段
- **THEN** 使用 Next 完成适用材料检查及明确确认，Back 返回相邻上一阶段；第一阶段没有 Back，第五阶段 Next 进入 ST 而不是结束需求
- **AND** 除流程控制、人工标记和上传／下载等必要界面操作外，澄清、修改、实施和提交等具体工作通过会话完成；程序门禁遵循 `spec-driven-orchestration`，不在页面建立第二套批准真值

### Requirement: Dev 网页原生浏览器边界

Dev 工作台 MUST 以 Firefox 68 默认启用的原生能力作为最低运行环境及浏览器技术上限；现代浏览器使用同一实现及同一生产资源集。MUST NOT 引入 polyfill、API shim、浏览器专属回退、双构建或现代浏览器专属增强分支。允许开发期编译，但交付的全部脚本、样式、依赖及 Worker MUST 遵守此边界，并保持现有布局、八阶段流程与交互，不改变宿主权限、人员确认及网络安全边界。

#### Scenario: 同一原生实现完成需求流程
- **WHEN** 用户在 Firefox 68 或现代浏览器中打开同一 Dev 工作台地址
- **THEN** 均能查看需求列表、八阶段及真实只读材料，切换查看阶段而不推进流程，使用共享会话的消息、命令、工具过程和适用问答，并完成 Markdown 上传／下载、当前阶段 Next／Back、候选选择及人工标记／确认
- **AND** 缺失材料、不可用操作与实际执行错误须如实呈现；不得以静态演示、只读替代页或要求升级浏览器代替完整功能

#### Scenario: 连接恢复与安全边界不因浏览器改变
- **WHEN** 任一目标浏览器参与 offline 同会话协作、刷新或断线重连，或在非 offline 环境访问 Dev
- **THEN** 按现有 offline 普通 HTTP／WS 或非 offline 安全策略处理；重连只读取实际状态，不重放消息、工具调用或确认
- **AND** 不以兼容旧浏览器为由降低非 offline 的传输或权限要求，不新增绕过身份、确认或宿主限制的通道；浏览器缺少安全能力且现有策略无法满足时须明确拒绝，不伪称功能成功

#### Scenario: 兼容性检查与证据边界
- **WHEN** 评估 Dev 网页的 Firefox 68 原生能力边界
- **THEN** 检查实际交付的完整脚本、CSS、依赖、资源 URL 及适用 Worker，并通过生产 HTTP(S) 入口使用本机已安装的真实 Firefox 68、隔离临时配置及默认能力／安全设置，观察布局并操作加载、材料、会话、文件、阶段控制与人工确认；现代浏览器、构建成功或静态检查不能代替本机 Firefox 68 验证
- **AND** 记录实际可执行路径、精确版本、发布通道、操作系统、生产入口及流程结果；无法观察的中文输入法、真实桌面输入或其他交互须标记未验证，不自动安装浏览器、不改写个人浏览器配置、不把未观察到的结果报告为通过

#### Scenario: 工作台图标随生产资源交付
- **WHEN** 浏览器加载 Dev 工作台
- **THEN** 页面显式引用同一能力路径下的内嵌图标资源，真实图标请求成功；不依赖不存在的根目录 favicon，也不为图标放宽原有能力路径或访问限制


### Requirement: 已有 Markdown 直接进入格式检查

新建开发需求 MUST 经过第一阶段业务文档检查。输入 MUST 支持对话生成、上传 Markdown 及输入 OMP 所在机器的本地文件路径；只支持 Markdown，不支持 Word、PDF 或 HTTP／HTTPS 文档地址。已有文档 MUST 可直接点击 Next，不以业务 Agent 对话、AI 审核或原业务会话为前置。

#### Scenario: 合格文档无对话推进
- **WHEN** 开发人员上传或指定一个符合现有模板的 Markdown，未与业务 Agent 对话即点击 Next
- **THEN** 程序读取真实文件，检查需求名称及所有必要章节存在且内容非空；通过后记录本次材料确认并进入开发需求阶段
- **AND** 不调用业务 Agent、不要求至少一轮访谈、不增加语义评分或 AI 内容审核；后继需求 Agent 仍可在其阶段调查真实内容和开发边界

#### Scenario: 必要章节缺失或为空
- **WHEN** Next 检查发现没有需求名称，或缺少非空的“基本信息”“业务背景与目标”“实际使用场景与现状”“期望结果”“业务规则与边界”“典型例子”“业务验收预期”“待确认事项”“资料来源”“业务确认与交接”任一章节
- **THEN** 停留第一阶段并指出具体文件及缺项，保留输入和材料，不产生下一阶段批准
- **AND** 沿用既有模板，不新增强制字段；结构通过不代表业务事实正确、交接发生或软件验证通过

#### Scenario: 浏览器上传与宿主路径不同源
- **WHEN** 用户上传本机 Markdown，或在页面输入本地路径
- **THEN** 上传读取用户所选文件，路径读取 OMP 宿主文件；不得把远端浏览器电脑路径冒充宿主文件或自动挂载其他机器
- **AND** 无法读取、格式不支持或提供网络 URL 时明确拒绝并保留阶段，不自动下载、转换、覆盖或猜测来源

#### Scenario: 导入文档归属需求
- **WHEN** 当前需求导入外部 Markdown 后修改材料或删除需求
- **THEN** 操作只针对本需求持有的材料内容；导入不授权改写、删除外部源文档，不把其他人的原文件纳入本需求撤销范围

#### Scenario: 明确确认后替换已有业务材料
- **WHEN** 业务阶段的人员重新上传 Markdown 或指定宿主路径，且本需求已经持有业务材料
- **THEN** 页面显示本需求材料路径，未明确确认替换前禁用两种导入；确认只授权替换当时读取的确切材料版本，关闭或重新打开窗口、切换需求或材料版本变化均清除确认
- **AND** 宿主仅替换已登记的本需求副本，版本过期、材料消失或归属不符时拒绝；保留外部源文件及无关内容，不推进阶段、不形成材料批准、不启动 Agent 或提交推送 Git


### Requirement: 业务人员只生成本地文档

业务人员不继续开发时，工作台 MUST 允许其仅借助现有业务 Agent 生成、查看和下载本地 Markdown，不要求提交 Git、创建 PR、建立团队交付或接收状态。开发人员接手 MUST 在自己的目录新建需求并经过第一阶段检查，不依赖原业务会话。

#### Scenario: 显式选择本地业务写作
- **WHEN** 用户明确选择仅本地业务写作
- **THEN** 才进入对应的写作和会话入口；该能力不是首次打开工作台或未选择需求时的默认页面

#### Scenario: 仅本地辅助写作
- **WHEN** 业务人员生成文档后自行离开或通过其他方式把文档传给开发
- **THEN** 文档保持业务人员自己的本地资料，不自动提交、推送或对团队发布，不标记为已开发、已测试或开发变更已归档
- **AND** 不要求使用“仅业务交付完成”流程终态、接收审批或共享会话来完成线下传递

#### Scenario: 开发人员独立导入
- **WHEN** 开发人员取得上述文档后在自己的目录新建需求
- **THEN** 按同一 Markdown 模板检查入口处理，不要求恢复业务人员的流程、校验原会话身份或邀请原业务人员加入

### Requirement: 网页聊天复用现有 offline Collab

网页聊天 MUST 接入现有 offline Collab 的共享、join、原生会话和访客交互链路，让多人参与同一个 Agent 会话，主要满足第一阶段的共同澄清。MUST NOT 另建角色聊天、协作服务、会话迁移或跨阶段自动跟随机制；打开工作台与加入 Collab 是独立操作。

#### Scenario: 右侧输入复用内置命令与技能
- **WHEN** 用户在有实际目标且允许输入的右侧共享会话底部输入框中输入消息、现有内置斜杠命令或技能调用
- **THEN** 复用既有 Composer、命令／技能发现与调用及原生目标会话处理，不要求另用命令下拉框或 JSON 参数表单
- **AND** 保持既有权限、阶段范围和人员确认边界；命令或技能调用不成为业务批准，不新增聊天引擎、配置或权限系统

#### Scenario: 网页输入沿用 TUI 的两套预测
- **WHEN** 用户在 Dev 网页的可编辑正文输入框中输入文字，或当前原生会话正常完成一轮
- **THEN** 正文输入复用 TUI 的文本预测服务及 `spelling.autocomplete` 设置，以淡色后缀提示；Tab 接受并添加空格，右方向键只接受后缀，代码、路径、命令及中文输入法组合期间不误补全
- **AND** 会话输入复用原生 `composer.predictions`、`composer.predictionAlternatives`、当前模型和上下文，在空草稿中展示下一条消息建议及有效多候选；接受只填入草稿，不自动发送、不形成流程批准，额外模型用量仍计入原生账本
- **AND** 显式关闭对应设置时不请求或展示对应预测；只读、断线、目标或代次变化、已有草稿及迟到结果不得覆盖当前输入或将建议串入另一会话，秘密输入不接入预测，不因浏览器重连重复发起收费预测

#### Scenario: 多人加入同一会话
- **WHEN** 房主按现有 offline 机制共享当前 Agent 会话，其他人员通过既有 join 方式在网页参与
- **THEN** 参与者看到该会话的历史、实时回复、工具过程及适用交互，发送内容进入同一会话，模型和工具仍由原宿主执行
- **AND** 不按业务、开发、测试人员各开聊天，不把 Relay 变成执行端，不要求每个参与者自行运行 OMP 才能使用网页聊天

#### Scenario: offline 权限和网络沿用
- **WHEN** 参与者在已启用 `OMP_OFFLINE` 的工作台会话操作
- **THEN** 所有人可使用全部工作台操作，不增加业务角色审批或单独角色权限系统；仍由人员实际确认推进、删除和标记，不赋予 AI 代签能力或额外操作系统权限
- **AND** 复用既有内网 Relay 配置和用户名 join、普通 WS／HTTP 能力，不新增证书、SSO、凭据或公网服务前置；不能因现有独立 collab-web 的 secure-context／远端 WSS 限制而把本次浏览器接入报为不支持

#### Scenario: 非 offline 与换会话
- **WHEN** 非 offline 参与者使用协作，或原生 Collab 房间停止、会话切换、访客离开
- **THEN** 保持现有权限、安全、换代隔离及退出语义，不将 offline 的全部工作台权限扩展到非 offline
- **AND** 不自动把访客转入下一阶段 Agent 或另一个需求，不把换 Agent 的无缝跟随纳入交付要求；打开页面不隐含 join

### Requirement: 浏览器连接不拥有后台任务生命周期

工作台 MUST 将页面连接与原生 OMP 任务生命周期分开。关闭、刷新页面或临时断线 MUST NOT 停止已确认工作；重连 MUST 展示真实持久事实及仍存活的运行事实，不重放操作。OMP 宿主进程必须存活，本要求不承诺脱离宿主继续执行。

#### Scenario: 关闭页面后继续工作
- **WHEN** 原生 Agent 或获授权任务仍在运行，用户关闭或刷新浏览器
- **THEN** 宿主继续已有工作；再次打开同一工作台后显示所属需求的实际进度、结果和错误，不创建第二任务或自动再次提交输入

#### Scenario: 刷新恢复查看位置而非执行授权
- **WHEN** 同一工作台页签选择一个真实需求及某个查看阶段后刷新
- **THEN** 在读取宿主真实需求列表后恢复该需求和查看阶段；查看阶段可不同于实际进行阶段，恢复只读取和订阅现有状态，不启动会话、不加入共享房间、不重发消息、操作或人员确认
- **AND** 保存位置按工作台入口隔离；不存在的需求、无效阶段或不可用的浏览器存储不得导致误选其他需求或崩溃，未保存选择的新入口仍显示空状态


#### Scenario: 宿主退出或执行事实不可用
- **WHEN** 宿主退出、原生任务失败，或重连时无法确认原运行状态
- **THEN** 如实显示中断、失败或不可用，不因旧画面、旧 running 标记或文件存在推断任务仍在运行或成功
- **AND** 需要停止时复用原生显式停止及结清能力，关闭页面本身不是停止命令

#### Scenario: 当前 TUI 与网页互斥及退出
- **WHEN** 用户从普通 OMP 的 `/dev` 进入工作台，或再次 `/dev` 请求退出
- **THEN** 普通任务未结清时拒绝进入，提示先停止或等待，不暗中取消普通工作；成功进入后当前 TUI 只接受再次 `/dev`，拒绝所有普通命令及输入，不同时操作网页 Dev 与普通 TUI
- **AND** 再次 `/dev` 通过既有 native stop／settlement 结清 Dev 后恢复普通原会话；失败不提前解锁。退出不取消需求、不撤销 Git、不删除材料，关闭网页不退出 Dev 或停止任务
- **AND** 不为普通 `/new`／move／dispose 与 Dev 并存保留会话快照、克隆或额外生命周期；不要求私有 Provider／MCP 克隆，实际借用资源必须避免污染 root，原生生命周期及安全 Git 边界保持

#### Scenario: Dev 终端地址与当前反馈
- **WHEN** Dev 独占当前 TUI，用户查看工作台地址、提交普通输入或按 Esc／Ctrl+C
- **THEN** 地址独立完整显示，窄终端换行不丢失字符，保留终端原生鼠标选择复制及 Ctrl 点击链接能力，不启用该界面的鼠标捕获
- **AND** 被拒绝输入、退出提示、切换状态及浏览器打开失败直接显示在当前 Dev 界面，不藏在退出后才显示的普通会话中；输入仍不交给模型，只有再次 `/dev` 结清后恢复原会话及输入焦点

### Requirement: 同目录同分支只有一个开发需求

工作台 MUST 在同一目录、同一既有分支串行处理开发需求，不自动创建 worktree 或每需求分支。一个需求从开始处理到 PR 合入，或取消并完成改动撤销之前，MUST 持有唯一开发名额；“已开发”不等于释放。合入后的测试及待复测只更新自身记录时，不占用开发名额。

#### Scenario: 等待 PR 评审不能开始下一需求
- **WHEN** 当前需求已经分批提交或创建 PR，但 PR 尚未合入且该需求尚未取消并撤销完成
- **THEN** 不能启动另一个需求的开发流程，不能因切换页面、普通会话、同目录别名或重复启动 OMP 绕过限制
- **AND** 查看需求记录不受阻，不新增多分支并行、分布式调度或跨机器开发名额协调系统

#### Scenario: 合入后测试与新开发共存
- **WHEN** 前一个 PR 已合入，原需求处于测试人员测试、测试未通过或待复测
- **THEN** 可开始下一需求开发，原需求可测试并更新自身状态，但不得修改仓库其他文件或在原需求内修复代码
- **AND** 更新记录或提交时不夹带当前开发需求的暂存／未暂存内容，不以测试并行之名启动第二个开发任务

#### Scenario: 取消尚未结清
- **WHEN** 当前需求取消、停止或撤销尚未完成
- **THEN** 保留开发占用及明确失败／待结清原因，不把取消请求、停止回执或本地状态删除视为已释放

### Requirement: 需求文档和业务状态纳入 Git

每个开发需求 MUST 有稳定唯一编号和独立文档记录。文档、阶段、人员标记及实际操作者、提交和 PR 关联、原需求与修复需求关系 MUST 一起纳入 Git 管理。每次提交信息 MUST 关联需求编号，并记录可追溯的实际提交 SHA；MUST NOT 只依靠提交信息文本推测归属。

#### Scenario: 文档提前提交且代码分批提交
- **WHEN** 同一需求先提交业务或开发文档，之后多次提交代码、报告或状态
- **THEN** 各次提交均能追溯到同一需求，需求记录覆盖实际关联提交，不将第一次 commit 视为禁止删除或需求完成
- **AND** 不混入其他需求变更，不将状态与正式材料复制为相互竞争的权威文档

#### Scenario: git pull 后本机打开
- **WHEN** 开发或测试人员在自己的目录拉取本次新流程的已提交记录，再通过 `omp dev` 打开工作台
- **THEN** 可以查看需求材料、阶段、人工标记和关联关系，不要求原创建者进程在线才能读取仓库记录
- **AND** 不把 Git 拉取视为加入 Collab、迁移原生会话或接管其他机器的任务；聊天历史、连接和运行态不作为 Git 需求记录同步，不自动执行模型或工具

### Requirement: 最后三阶段由人标记而非自动裁决

ST测试、提交与 PR、测试人员测试 MUST 由人通过明确界面操作标记，AI 只辅助工作和报告。程序 MUST NOT 因 AI 回复、文件存在、测试退出码或 PR 查询自动标记完成，也 MUST NOT 增加“所有必需 ST 通过”或 AI 内容审核的完成门禁。人员决定和实际执行事实 MUST 分别保留。

#### Scenario: 开发人员标记 ST 完成
- **WHEN** 开发人员查看实际测试及披露限制后点击并确认“标记 ST 完成”
- **THEN** 按人工决定完成第 6 阶段并进入提交与 PR，保留原始失败、未执行和限制，不把完成标记改写成“ST 全部通过”
- **AND** ST 由开发人员负责，AI 可按请求辅助选择、执行和记录，不能代替人员点击或决定

#### Scenario: PR 提交与合入分开标记
- **WHEN** 人员在会话中完成获授权的提交／PR 操作，随后确认“PR 已提交”或“PR 已合入”
- **THEN** 前者把需求显示为“已开发”并继续等待评审／合入；后者记录合入事实并进入测试人员测试，不能把提交、PR 创建和合入混为同一状态
- **AND** 仅查看 PR 状态、CI 通过或 AI 声称已完成，不自动形成任一人工标记；已有真实操作错误不得伪报成功

#### Scenario: 测试人员标记已测试
- **WHEN** PR 合入后，测试人员按自己的方法完成测试并确认“标记已测试”
- **THEN** 记录实际决定并结束需求，后续为只读，不将开发人员的 ST 标记代替测试人员测试
- **AND** 测试阶段不再同步归档、不修改其他仓库文件，最多更新本需求记录；查看已完成需求不恢复执行

### Requirement: 人工状态标记同时确认提交和推送

第 6—8 阶段的人工状态标记 MUST 在同次确认中明确包含对应记录的 Git 提交和推送，展示需求编号、状态变化、文件范围及目标；不要求标记后另行发起提交。系统 MUST 只处理本次确认的需求变更，区分本地记录、提交和推送的真实结果，不把部分成功宣称为全部完成。

#### Scenario: 标记和 Git 操作成功
- **WHEN** 人员确认一项状态标记及其列出的提交推送范围
- **THEN** 保存决定并执行对应 commit／push，提交信息关联需求编号，记录实际结果；最后“已测试”的状态记录也包含在此次确认范围内
- **AND** 不因需求进入只读而遗漏最后状态提交，不顺带提交其他需求或未经确认的代码，也不执行发布或额外合并

#### Scenario: 用户取消确认
- **WHEN** 人员取消标记及提交推送确认
- **THEN** 不提交人工完成标记，不执行对应 commit／push，不因曾打开确认界面产生批准

#### Scenario: 提交成功而推送失败
- **WHEN** 本地标记已保存且 commit 成功，但 push 失败
- **THEN** 保留实际标记及已生成提交，明确显示尚未推送及原因，不报告已同步、不抹掉成功提交
- **AND** 人员重试时只继续未完成推送，不重复提交标记、不重复推进阶段；无法保存或 commit 失败同样报告实际边界，不伪造 SHA

#### Scenario: 重复或过期点击
- **WHEN** 多个参与者重复提交同一操作，或确认对应的需求、阶段、记录版本或范围已经变化
- **THEN** 不把重复点击变成下一阶段批准、重复 commit 或对另一需求的操作；过期确认明确拒绝并显示当前事实

### Requirement: 未合入需求可撤销全部所属改动

需求删除 MUST 以 PR 是否合入为边界，未合入时经人员确认可删除，无论已有多少文档／代码提交或是否已创建 PR。删除 MUST 取消未合入 PR（如有）并撤销该需求所有文档和代码改动，覆盖已提交、暂存及未暂存内容；保留 Git／PR 历史，不抹除审计事实或波及无关改动。

#### Scenario: 删除已分批提交且 PR 未合入的需求
- **WHEN** 人员从左侧删除入口确认该需求及完整撤销范围
- **THEN** 先停止并结清该需求自有工作，取消相关未合入 PR，撤销该需求各次实际改动，包括已提交文档和分批代码；更新可追溯的取消／撤销事实
- **AND** 不以已有 commit、已同步归档或已创建 PR 拒绝删除，不把旧 drop 的“只清状态保留文件”当作删除成功

#### Scenario: 文件在需求开始前已存在
- **WHEN** 删除的需求曾修改既有文件，或导入过另一位置的业务文档
- **THEN** 撤销本需求造成的修改，保留原文件原有及其他需求内容；只删除本需求独有新增内容，不删除整个共享文件或外部导入源

#### Scenario: 归属不明或与后续修改冲突
- **WHEN** 无法可靠判定某项未提交修改属于本需求，或撤销会覆盖无关／后续需求内容
- **THEN** 显示具体冲突并等待人员明确处理，不强制覆盖、不整体 reset、不 force push 抹除历史，不宣称已完整撤销或释放开发名额
- **AND** 已发生的取消、提交或部分撤销如实保留并可继续处理，不伪报全量回滚

#### Scenario: PR 已经合入
- **WHEN** 人员请求删除已合入的需求，或确认期间发现其已合入
- **THEN** 拒绝删除和撤销；需要修改时新建关联需求，不执行合入后 Git 回滚

### Requirement: 合入前修正与合入后关联修复

PR 合入前的范围内问题 MUST 在当前需求修正，需要改变上游材料时回退相应阶段重新确认。合入后发现 Bug 或调整需求 MUST 新建关联需求，不在原需求改代码。原需求测试未通过时 MUST 保留测试未通过／待复测，修复合入后由人员回原需求复测，不能自动标记已测试。

#### Scenario: ST 或 PR 评审发现本需求问题
- **WHEN** PR 尚未合入，ST 或评审发现获批范围内实现问题
- **THEN** 人员可授权当前需求继续修正并更新报告／PR；不强制另建一个被当前开发名额阻塞的修复需求
- **AND** 需要改变需求、方案或计划时先 Back 并重新确认；Back 保留代码和文件，不是 Git 回滚

#### Scenario: 合入后测试失败
- **WHEN** 测试人员发现已合入需求存在问题
- **THEN** 原需求记录测试未通过／待复测，关联新建修复需求，修复需求按同样八阶段和单点开发规则处理
- **AND** 修复 PR 合入只使原需求可复测，不自动改变原需求测试结论；人员复测并标记后才结束原需求

#### Scenario: 完成后新增调整
- **WHEN** 已标记已测试的需求又需要修改
- **THEN** 原需求保持只读，通过新需求关联原需求处理，不复活旧执行状态或直接改写已完成材料
