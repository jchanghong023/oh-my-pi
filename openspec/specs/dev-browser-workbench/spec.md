# dev-browser-workbench

## Purpose

维护最新 Dev 业务流程、职责和边界。

> 状态：用户已确认的最新 Dev 需求基线。共享 UI 与原型／OMP 数据源分离已接入；完整业务仍未按本规则完成实现或验收。

## Requirements


### Requirement: Dev 网页原生浏览器边界

Dev 工作台 MUST 仅以桌面浏览器为界面设计、实现和验收目标，不要求手机布局、触屏交互或手机实机验证；WebGUI 的手机适配要求不转移到 Dev，原 WebGUI 本轮不修改。桌面浏览器 MUST 以 Firefox 128 默认启用的原生能力作为最低运行环境及浏览器技术上限；现代浏览器使用同一实现及同一生产资源集，不再以 Firefox 68 为兼容或验收目标。MUST NOT 引入 polyfill、API shim、浏览器专属回退、双构建或现代浏览器专属增强分支。允许开发期编译，但交付的全部脚本、样式、依赖及 Worker MUST 遵守此边界，并保持现有布局、三阶段开发 SR 流程与交互，不扩大 Agent 工具权限或绕过人员确认；Dev 服务的多人访问按最新部署需求，保留适用的能力路径与网络请求校验。

#### Scenario: OpenSpec 材料映射与来源
- **WHEN** 在需求提案中选择 IR、SR 或方案阶段
- **THEN** 分别默认显示同一 change 的 proposal.md、对应 specs/<capability>/spec.md 或有效 design.md；未生成方案时继续显示已有需求材料，不伪称方案完成
- **AND** 展示固定临时工作区内的完整来源路径与仓库相对路径；提案 Agent 生成上下文使用临时工作区，PR 前不在项目目录生成；转正后展示仓库相对路径并保留临时来源

#### Scenario: 同一原生实现完成需求流程
- **WHEN** 用户在 Firefox 128 或现代浏览器中打开同一 Dev 工作台地址
- **THEN** 均能查看需求列表、三阶段开发及真实只读材料，切换查看阶段而不推进流程，使用共享会话的消息、命令、工具过程和适用问答，并完成 Markdown 上传／下载、当前阶段明确推进／返回、当前方案确认及人工标记／确认
- **AND** 缺失材料、不可用操作与实际执行错误须如实呈现；不得以静态演示、只读替代页或要求升级浏览器代替完整功能

#### Scenario: 连接恢复与安全边界不因浏览器改变
- **WHEN** 任一目标浏览器参与 offline 同会话协作、刷新或断线重连，或在非 offline 环境访问 Dev
- **THEN** 按现有 offline 普通 HTTP／WS 或非 offline 安全策略处理；重连只读取实际状态，不重放消息、工具调用或确认
- **AND** 不以兼容旧浏览器为由降低非 offline 的传输或权限要求，不新增绕过身份、确认或宿主限制的通道；浏览器缺少安全能力且现有策略无法满足时须明确拒绝，不伪称功能成功

#### Scenario: 兼容性检查与证据边界
- **WHEN** 评估 Dev 网页的 Firefox 128 原生能力边界
- **THEN** 检查实际交付的完整脚本、CSS、依赖、资源 URL 及适用 Worker，并通过生产 HTTP(S) 入口使用 Selenium＋geckodriver 驱动本机已安装的真实 Firefox 128（当前版本 128.14.0）、隔离临时配置及默认能力／安全设置，观察布局并操作加载、材料、会话、文件、阶段控制与人工确认；其他浏览器、构建成功或静态检查不能代替本机 Firefox 128 验证
- **AND** 记录实际可执行路径、精确版本、发布通道、操作系统、生产入口及流程结果；无法观察的中文输入法、真实桌面输入或其他交互须标记未验证，不自动安装浏览器、不改写个人浏览器配置、不把未观察到的结果报告为通过

#### Scenario: 工作台图标随生产资源交付
- **WHEN** 浏览器加载 Dev 工作台
- **THEN** 页面显式引用同一能力路径下的内嵌图标资源，真实图标请求成功；不依赖不存在的根目录 favicon，也不为图标放宽原有能力路径或访问限制

#### Scenario: 初始展开与用户折叠偏好
- **WHEN** 打开或刷新 Dev 工作台
- **THEN** 左侧自由会话、正式需求、需求提案栏目展开；自由会话展示最近 5 条聊天，需求栏目仅显示 IR 层，IR 下 SR 默认收起，不因恢复当前 IR／SR 会话而自动展开子项
- **AND** 右侧默认展开，自由会话显示审查，需求会话显示只读材料；只规定右侧面板默认可见，不把左侧 IR 子树全部展开
- **AND** 用户可手动展开 IR、收起栏目或面板；本页重渲染、会话组件重挂与阶段切换不覆盖用户的手动选择，刷新后恢复上述默认层级

#### Scenario: 本页记住展开选择
- **WHEN** 用户展开或收起分区／IR，随后在本页切回原范围
- **THEN** 恢复当前页面中的手动选择；偏好按工号、项目、Release 隔离，不写共享业务数据库或项目配置，不同步为其他同事的选择；刷新不恢复上次展开的 SR 子树
- **AND** 自由会话沿用原生项目行的交互，仅在刷新后的首次进入默认展开；偏好不包含执行授权或业务状态，原 WebGUI 不变

#### Scenario: 当前项目的自由会话入口
- **WHEN** 用户在 Dev 左侧使用自由会话
- **THEN** 复用 WebGUI 的单项目行、行内更多／文件／新建会话操作、会话操作及展开动画，行名显示“自由会话”，展开直接列出当前项目的会话，不增加外层“项目”分区或重复项目名
- **AND** 当前项目由既有工作区菜单决定；自由会话不依赖 Release、IR、SR，不自动创建提案、进入需求 Agent 或推进需求流程，复用原生会话与服务能力

#### Scenario: 自由会话沿用单项目功能与个人 Web 边界
- **WHEN** 显示 Dev 自由会话导航
- **THEN** 功能与 WebGUI 原“单项目”一致，只显示当前开发项目，历史只显示最近 5 条，保留原有更多、排序、文件、新建及会话操作；不增加其他项目或完整历史列表
- **AND** 访问他人启动的 OMP Web 时仍显示自由会话行和操作按钮，但不查询或显示历史；点击操作提醒“请进入自己启动的 OMP Web，以自己的工号登录并配置开发项目路径”，不创建会话、不执行原生操作
- **AND** 只有当前 Web 所有者在自己的 Web 中登录后才能使用自由会话；该限制不隐藏团队共享的项目、Release、正式需求或需求提案

#### Scenario: 新建自由会话沿用原生任务草稿
- **WHEN** 用户点击自由会话的“新建会话”，或从项目行新建任务
- **THEN** 与 WebGUI 原“新建任务”一致，先进入未发送草稿，不因点击分配可见会话记录；重复点击回到同一草稿，保留正文、附件及模型选择
- **AND** 切到已有会话后可以返回继续编辑；草稿按 Web、账号、项目及个人开发目录隔离，不依赖 Release、IR 或 SR，不进入需求 Agent
- **AND** 首次发送成功后才加入会话列表，复用原生首发接纳与草稿交接；失败保留输入及当前首发目标供重试，不自动重发、不生成可见空会话；原 WebGUI 不变

#### Scenario: 自由会话必须接入真实原生能力
- **WHEN** 从正式 `/dev` 或 `omp dev` 新建、打开或管理自由会话
- **THEN** 复用 OMP 原生会话的新建、历史读取、消息发送、流式回复、停止、重命名、置顶、归档及文件／审查能力；会话及消息按原生规则持久化，不以浏览器内存样例、预置回复或空列表代替真实结果
- **AND** 自由会话是 Dev 必需能力，不因需求流程数据源分离而取消或隐藏入口；读取或执行失败明确报错并保留原目标及草稿，不回退演示，也不自动重放操作
- **AND** 独立原型保留相同入口与交互，但样例演示不代表真实接入完成；原型与文档更新不修改正式适配层或宿主，也不构成正式功能验收

#### Scenario: 最近五条的查询与历史保留
- **WHEN** 加载或刷新当前项目的自由会话列表
- **THEN** 服务仅查询该项目按更新时间降序排列的最近 5 条可见会话元数据，等时使用稳定次序；选中后才读取消息，不先加载全部历史再在前端截取
- **AND** 新建、更新、归档后重新计算最近 5 条，较早记录仍保留，不因列表上限而删除；切换项目只加载目标项目，不混入其他项目或 IR／SR 会话

#### Scenario: 自由会话默认审查且目录身份不变
- **WHEN** 用户进入自由会话，或在自由会话与需求流程间切换
- **THEN** 自由会话右侧默认为原“审查”页面，正式需求与需求提案默认“只读材料”，查看上下文分别管理；自由会话不显示需求阶段和提案流程控件
- **AND** 按原生规则保留会话创建时的工作目录及身份，查看项目不等于进入开发或重新绑定执行目录，不绕过个人开发目录、宿主权限或确认边界

### Requirement: 中间聊天输入框全屏画图

Dev 中间聊天输入框 MUST 在模型选择器左侧提供画图按钮；点击后在当前网页全屏覆盖显示 Sketch 页面，覆盖三栏工作区，不另开标签页。MUST 复用现有 Sketch 绘图能力和聊天附件区，不替换聊天输入框或增加独立图片发送通道。

#### Scenario: 完成绘图后只回填附件
- **WHEN** 用户从中间聊天输入框打开 Sketch，完成绘图后点击画布中的“发送”
- **THEN** 将完整画布导出为 PNG，作为图片附件加入打开画布的原聊天输入框；成功加入后关闭全屏画布并返回该输入框，保留已有文字、附件及模型选择
- **AND** 画布中的“发送”仅回填附件，不提交聊天消息、不调用模型、不创建会话或提案、不推进阶段；用户仍须在聊天输入框明确发送

#### Scenario: 取消及附件回填失败
- **WHEN** 用户取消绘图，或图片未能加入原输入框
- **THEN** 取消只关闭画布，不添加附件、不改变原草稿；回填失败保留画布与绘图并显示原因，不伪称成功或自动发送
- **AND** 没有可编辑输入框的只读页面不增加画图入口，不绕过现有聊天权限；本轮仅更新需求文档与独立原型，不接入正式 OMP 宿主、Sketch 服务或模型，原 WebGUI 与原生 `/sketch` 保持不变

### Requirement: 聊天输入框语音转文字入口

Dev 聊天输入框 MUST 在发送按钮紧邻左侧提供麦克风图标入口；语音转文字结果须先回填原输入框，保留已有文字、附件和模型选择，由用户编辑并明确发送，不自动提交消息或推进需求流程。后续真实接入 MUST 复用 OMP 已有语音转文字能力，不另建语音识别实现。

#### Scenario: 独立原型演示
- **WHEN** 用户点击麦克风并停止演示录音
- **THEN** 显示明确标注为示例、可编辑的识别文字；确认后追加到打开入口的原输入框并返回输入框，不发送消息
- **AND** 本轮仅修改文档与独立原型，不申请麦克风权限、不采集音频、不调用识别服务或模型，不修改正式 OMP 宿主、适配层或 WebGUI；示例不代表真实识别成功

#### Scenario: 取消或无法回填
- **WHEN** 用户取消演示，或原输入框暂不可编辑
- **THEN** 取消不改变原草稿；回填失败保留示例文字并显示原因，不关闭弹窗或伪称成功；只读页面不提供可操作入口



### Requirement: 浏览器连接不拥有后台任务生命周期

工作台 MUST 将页面连接与原生 OMP 任务生命周期分开。关闭、刷新页面或临时断线 MUST NOT 停止已确认工作；重连 MUST 展示真实持久事实及仍存活的运行事实，不重放操作。OMP 宿主进程必须存活，本要求不承诺脱离宿主继续执行。

#### Scenario: 关闭页面后继续工作
- **WHEN** 原生 Agent 或获授权任务仍在运行，用户关闭或刷新浏览器
- **THEN** 宿主继续已有工作；再次打开同一工作台后显示所属需求的实际进度、结果和错误，不创建第二任务或自动再次提交输入

#### Scenario: 刷新恢复查看位置而非执行授权
- **WHEN** 同一工作台页签选择一个真实需求及某个查看阶段后刷新
- **THEN** 在读取宿主真实需求列表后恢复该需求和查看阶段；查看阶段可不同于实际进行阶段，恢复只读取和订阅现有状态，不启动会话、不加入共享房间、不重发消息、操作或人员确认
- **AND** 保存位置按工作台入口隔离；不存在的需求、无效阶段或不可用的浏览器存储不得导致误选其他需求或崩溃，未保存选择的新入口仍显示空状态


#### Scenario: 宿主退出或执行事实不可用
- **WHEN** 宿主退出、原生任务失败，或重连时无法确认原运行状态
- **THEN** 如实显示中断、失败或不可用，不因旧画面、旧 running 标记或文件存在推断任务仍在运行或成功
- **AND** 需要停止时复用原生显式停止及结清能力，关闭页面本身不是停止命令

#### Scenario: 当前 TUI 与网页互斥及退出
- **WHEN** 用户从普通 OMP 的 `/dev` 进入工作台，或再次 `/dev` 请求退出
- **THEN** 普通任务未结清时拒绝进入，提示先停止或等待，不暗中取消普通工作；成功进入后当前 TUI 只接受再次 `/dev`，拒绝所有普通命令及输入，不同时操作网页 Dev 与普通 TUI
- **AND** 再次 `/dev` 通过既有 native stop／settlement 结清 Dev 后恢复普通原会话；失败不提前解锁。退出不取消需求、不撤销 Git、不删除材料，关闭网页不退出 Dev 或停止任务
- **AND** 不为普通 `/new`／move／dispose 与 Dev 并存保留会话快照、克隆或额外生命周期；不要求私有 Provider／MCP 克隆，实际借用资源必须避免污染 root，原生生命周期及安全 Git 边界保持

#### Scenario: Dev 终端地址与当前反馈
- **WHEN** Dev 独占当前 TUI，用户查看工作台地址、提交普通输入或按 Esc／Ctrl+C
- **THEN** 地址独立完整显示，窄终端换行不丢失字符，保留终端原生鼠标选择复制及 Ctrl 点击链接能力，不启用该界面的鼠标捕获
- **AND** 被拒绝输入、退出提示、切换状态及浏览器打开失败直接显示在当前 Dev 界面，不藏在退出后才显示的普通会话中；输入仍不交给模型，只有再次 `/dev` 结清后恢复原会话及输入焦点


### Requirement: 正式需求访客只看材料，提案允许业务讨论

C、D 访问 A 的 Web 时，MUST 根据正式需求与需求提案分别处理聊天，不得把共享 Token、共享业务记录或只读权限解释为可以读取 A 的正式需求开发会话。聊天正文及历史归所属 OMP 保存，不写共享数据库。

#### Scenario: 访客查看正式 IR 或其 SR
- **WHEN** C、D 在他人启动的 Web 中打开正式 IR、其任意 SR 或 IR 验收入口
- **THEN** 中间不展示聊天记录，改为只读说明空态：解释当前访问他人的 Web，正式需求的开发聊天不向访客展示，并引导到右侧阅读完整材料；不加载、订阅、展示或恢复所有者的历史，也不挂载输入框、阶段讨论、开始开发或验收控件；右侧默认显示完整 IR 的只读材料
- **AND** 从提案切换到正式需求、刷新或切换工号均不得残留聊天正文；仅把 SessionPane 设为只读不足以满足本规则
- **AND** 空态明确说明修改方式：需求调整通过新建需求提案讨论，可讨论提案的 Web 提供原有新建入口，其他 Web 引导进入 j00808874 的 Web；代码修改由开发人员启动自己的 OMP Web、以自己的工号登录并配置开发项目路径后处理。不得以完全空白代替说明，需求提案仍保留正常聊天

#### Scenario: 业务人员参与提案讨论
- **WHEN** C、D 在所有者为 j00808874 的 Web 中打开需求提案
- **THEN** 保留当前提案的需求或方案讨论，使用 A 的后端和 Token，记录保存在 A 的 OMP；不因访问者不是 Web 所有者而把提案讨论清空或禁用
- **AND** 讨论不授予个人开发路径、代码、Git 或个人配置修改权限；其他所有者的 Web 仍只查看提案材料，不读取或接管 A 的提案会话

#### Scenario: 需求材料按 IR／SR 隔离且独立于会话
- **WHEN** 任何用户选择 IR
- **THEN** 右侧提供同一 IR 的完整 OpenSpec 文件目录，包含 proposal.md、IR 的技术 design.md、每个 SR 对应的 specs/<capability>/spec.md，不混入开发计划、完成报告、UT/ST、交付等 SR 开发阶段文件；中间没有聊天或 SR 尚未开始不影响读取这些需求文件
- **AND** 选中 IR 默认读取 proposal.md；选中 SR 后右侧仅显示该 SR 自己的 spec.md 及其所选开发阶段／轮次的文件，不混入 IR 文件、其他 SR 文件或其他阶段文件；提案中的 SR 仅显示自身规格，返回 IR 才浏览整份需求文件；正式材料来自项目仓库，提案材料来自其临时工作区，材料区不提供复制、下载或带入讨论按钮，也不提供向聊天输入框插入材料的隐式入口

- **WHEN** 用户选择已访问阶段或旧轮次
- **THEN** 读取原阶段／轮次的会话与材料并标明历史只读，不能发送消息、生成材料、批准、返回、停止或登记交付；可返回实际阶段，不重启任务、不重绑 worktree
- **AND** 已完成 SR 仍可只读查看原阶段／轮次会话，不显示可写当前阶段返回入口。尚未进入的阶段禁用；动作层独立检查查看范围，不能只依赖按钮禁用。工作区仍为当前固定目录，历史材料不等同历史代码快照

#### Scenario: 开发验证报告
- **WHEN** Agent 完成获授权的实现和验证
- **THEN** 交付完成报告、验证记录、限制和未完成项，等待人员确认；未执行、失败和环境限制如实保留，不冒充全部通过。

#### Scenario: 不重复需求阶段
- **WHEN** SR 准备开发计划
- **THEN** 使用默认分支已合入的 IR、SR、提案方案和确认记录，不重复业务整理、SR 撰写或方案 Agent 阶段；发现正式需求或方案需要调整，可在自己的 Web 和 Git 项目中自由修改、提交；保留旧版本记录，不用旧报告证明新版本已验证。

### Requirement: 人工 PR、IR 验收与最终归档

提案、SR 和最终验收归档 PR MUST 均由 AI 提交／推送分支并提供标题及正文，由人工创建、评审、合并和告知结果。平台 MUST 核对默认分支中的真实文件版本及合并事实，不依赖 PR API，不以通知、链接或勾选代替核验；支持 squash／rebase 后提交身份变化。

#### Scenario: 提案合入
- **WHEN** 人工告知提案 PR 已合并
- **THEN** 核验 proposal.md、全部 SR 增量规格和确认 design.md 已进入默认分支，成为正式提案，显示在正式需求导航；不提前把未实现的增量规格同步到 openspec/specs

#### Scenario: SR 交付范围与合并前验证
- **WHEN** SR 准备交付 PR
- **THEN** 同一 PR 包含代码、测试及该 SR 对 openspec/specs/<capability>/spec.md 的同步，记录源 Change／SR／版本；合并前对齐最新默认分支并重跑受影响验证，需求冲突和 Git 合并冲突暂停交人工，普通实现问题由 Agent 修复
- **AND** 不向默认分支直接推送，不把提交、推送、人工 PR 创建与合并当成同一状态，不为普通状态变更制造额外状态 PR

#### Scenario: IR 验收与最终 PR
- **WHEN** 全部 SR 的代码、测试与规格已合入
- **THEN** 当前简化设计中，IR 验收 Agent 基于已合并 SR 走固定流程，生成通过报告，不发现问题、返工或复验；最终 PR 仅做 Change 归档，仍保留人工评审合并及版本核验
- **AND** 最终 PR 只做归档；归档前核对各 SR 的实现、测试、规格合并记录，归档只移动 Change 目录，不再次同步规格

#### Scenario: IR 完成
- **WHEN** 人工合并最终 PR 并告知平台
- **THEN** 核验默认分支中的最终候选成果、验收版本和归档结果后才标记 IR 完成、释放仓库 IR 占用；SR PR 合并只完成该 SR，不代表整个 IR 已完成

### Requirement: 返工保留代码并使后续材料失效

返回开发计划或开发与验证前 MUST 停止并结清当前 SR 的 Agent 及递归子任务。返回 MUST 保留已有代码，不执行自动代码回退；修改前序材料后，需要重新确认并重新生成或验证相关后续成果。

#### Scenario: 只查看历史不失效
- **WHEN** 用户仅查看过去的方案或计划
- **THEN** 保留当前阶段、批准和报告资格；不把查看历史变成 Back。

#### Scenario: 实际修改计划或实现
- **WHEN** 人员明确返回开发计划或开发与验证，Agent 更新计划或实现
- **THEN** 增加执行轮次，该步骤批准及后续依赖产物失效，原材料、会话、确认与旧 PR 记录保留历史但不可作为本轮交付；新轮次重新生成并确认材料；Agent 依据现有代码调整实现，后续验证必须检查旧实现残留，以及实现与已合入方案的兼容性；正式方案可在自己的 Git 项目中修改提交，旧验证对新版本不自动有效。

#### Scenario: 停止失败
- **WHEN** 后代任务、工具或外部进程未确认结清
- **THEN** 保持原阶段并显示可重试失败，不在仍有写入时完成返回。

#### Scenario: 已交付后请求返回
- **WHEN** 代码 PR 已合入
- **THEN** 不通过普通 Back 撤销默认分支代码或重开已结束执行；当前简化流程不设置 IR 验收返工；后续需求变化可在自己的 Git 项目另行修改提交；不使用普通 Back 撤销已合并结果。

### Requirement: 正式资料 Git 与共享业务数据库分离

正式需求、方案、计划及交付时已有报告 MUST 使用可读 Markdown 和必要 JSON 纳入 Git。项目、Release、提案状态与阶段、开发占用、PR 标记、反馈、方案版本、操作记录及 OMP 会话引用 MUST 统一保存于非 Git 的共享数据库 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`，通过项目 ID 隔离，由团队 Web 和各开发者 OMP 后端共同访问，不另建每项目／每后端数据库或共享 JSON 状态权威；不保存开发者个人模型配置、Token、个性化、技能或 Skill 设计草稿。原生聊天正文及历史仍由所属 OMP 后端管理，Dev 关联含后端归属的必要会话引用。

#### Scenario: 运行状态不随资料提交
- **WHEN** 资料被提交到需求或开发分支
- **THEN** 不夹带进程、端口、队列、锁、绝对路径或聊天副本；Git 拉取只保证材料可读，不保证重建完整运行进度。

#### Scenario: NFS 上工作流数据共享
- **WHEN** 同项目存在多个 worktree 或用户顺序换机器
- **THEN** 访问同一份必要工作流状态，不能各 checkout 独立形成相互矛盾的开发占用；结构带格式版本和稳定引用，按钮状态从真实事实计算。

#### Scenario: 未生成的后置资料
- **WHEN** 代码交付时尚没有公司后续测试结论
- **THEN** 不预造未来报告，不强制通过 Dev 为未来每次测试状态创建 PR。

业务需求 Agent 的写入范围仅限需求文件，不创建或修改 SR 开发计划、完成报告、验证、交付文件或代码。IR 技术 design.md 由方案职责维护；SR 开发材料归各自开发阶段，不因它们属于同一 IR 就纳入业务需求会话或 IR 材料菜单。

IR 右侧仅保留文档选择和只读正文，不显示 SR 导航列表、SR 点击跳转、重复的 proposal.md 快捷入口或额外评审卡片。切换文档不改变当前 IR／SR 选择；进入 SR 统一使用左侧导航。

IR 与 SR 的右侧统一显示文件路径和只读正文，有阶段操作权限时在正文外的固定底栏提供阶段操作。路径本身沿用文档选择控件切换文件，不重复显示路径，不显示材料数量、类型、来源标签、阶段、轮次说明或额外导航卡片。真正的读取错误与未生成状态仍明确反馈，不冒充正文。

### Requirement: 桌面聊天顶部统一阶段与人工操作

提案 IR 与正式 IR／SR 聊天顶部 MUST 使用 Dev 自有 WebGUI 副本组件，固定为标题、居中阶段条、单行状态三行；当前处理责任并入状态行，长内容截断并可悬停查看，不重复标题、人员或目录行。人工操作另设于右侧文档固定底栏，正文独立滚动。正式 IR／SR 的“…”紧邻问号左侧，复用提案的简洁下拉菜单，仅提供只读信息与操作记录，不再打开混合流程的大弹窗或嵌套“目录与历史”；不显示协作按钮。提案更多保留提案信息、操作记录及允许删除时的删除提案。

#### Scenario: 阶段与 Agent 分别表达
- **WHEN** 查看提案 IR
- **THEN** 显示“业务需求 → 需求评审 → 技术方案 → 需求入库”；依次对应业务需求 Agent、业务需求评审 Agent、方案 Agent、人工确认及 PR 评审合并。评审使用独立只读 Agent 的原生聊天，报告问题并允许询问；只有人工入库节点展示流程说明
- **AND** 正式 SR 显示“开发计划 → 开发与验证 → 交付合并”，分别使用计划 Agent、执行 Agent及执行交付职责；交付没有独立 Agent，人工 PR 合并和核验不可跳过
- **AND** 正式 IR 显示“SR 开发 → 整体验收 → 完成归档”，开发由各 SR 分别处理，全部 SR 合并后才允许 IR 验收 Agent 开始，最终 PR 由人工评审合并；Skill 设计 Agent 不加入需求流程

#### Scenario: 人工推进与回退固定在文档底部
- **WHEN** Agent 已完成当前文档，用户在右侧检查内容
- **THEN** 只有显式点击“下一步：目标阶段”才确认推进并进入对应 Agent；Agent 工作中、文档缺失／失效、依赖或权限不满足时禁用，并给出实际原因；不因 Agent 回复结束、点击阶段或查看文件自动推进
- **AND** SR 执行或交付阶段提供“回退”，在确认弹窗中选择已进入的前置阶段；回退保留代码、文件和历史，原有轮次／批准失效规则保持不变；方案退回业务需求须填写业务补充原因
- **AND** 入库、交付和归档操作沿用已有逐文件确认、候选绑定、人工 PR 登记与合并核验；“下一步”不替代这些门槛，不把登记链接视为已合并

#### Scenario: 查看历史不改变当前阶段
- **WHEN** 点击已进入的阶段或历史轮次
- **THEN** 只切换所查看的 Agent 会话、评审结果或人工流程说明，不启动新 Agent，不更改执行阶段；顶部显示历史只读，文档底部操作栏只保留“返回当前阶段”；提案辅助菜单在标题旁，正式 IR／SR 辅助菜单在问号左侧
- **AND** 未进入且无历史的阶段禁用。已完成显示勾选，当前阶段突出显示，未来阶段弱化；仅真实运行投影存在时显示运行动画，支持减少动态效果，不用持续动画冒充工作中
- **AND** 业务访客查看正式需求只显示进度与只读说明，不读取开发聊天或提供推进操作；提案讨论权限仍按 Web 所有者规则处理。右侧正文仍仅显示文件路径和文件内容，阶段操作独立置于固定底栏，并按 IR／SR、阶段和轮次限定文件范围

阶段控件复用 WebGUI 的 Button、Progress 与主题变量，采用编号圆点、完成勾选、阶段连接线和进度轨道；当前阶段的实心圆点及选中背景突出，未进入阶段仍可读但不可跳转，不新增独立配色。技术方案文档完成后停在方案阶段，只有人工点击下一步并完成原有逐文件确认后才进入需求入库，不能因文档生成自动推进。

正式 IR 的“SR 开发”节点只展示整体进度和进入左侧 SR 的说明，不把入库前的业务讨论历史当成当前开发 Agent；计划、执行聊天分别归属所选 SR，整体验收开始后才展示 IR 验收会话。

IR 与 SR 统一：标题、居中阶段条、单行状态构成三行头部。右侧文档底栏保留回退和下一步／当前人工动作，正文独立滚动。查看历史时只保留返回当前阶段；无操作权限或当前已完成且不在查看历史时不显示操作栏。正式 IR／SR 的“…”紧邻问号左侧，仅提供信息、操作记录，不显示协作按钮，不恢复复制、下载、带入讨论等材料按钮。

### Requirement: 需求提案以 IR 为讨论和修改单位

需求提案 MUST 以 IR 为整体进行讨论、修改、评审、方案及入库推进；其 SR 仅为规格阅读入口，不具备独立聊天或阶段操作。正式需求的 SR 开发流程不受此限制。

#### Scenario: 阅读提案内 SR 后返回 IR
- **WHEN** 用户从导航、搜索或恢复的页面状态选择提案中的 SR，无论提案处于哪个阶段
- **THEN** 中间区域正中央仅显示居中对齐的“请进入所属 IR 讨论或修改需求”和“返回 IR”入口，不加载聊天记录或输入框，不显示阶段条、Agent 状态、更多流程操作或文档底部阶段按钮
- **AND** 右侧仅显示该 SR 自身 spec.md 的路径和正文，不混入其他 SR、IR 文档或开发文件
- **AND** 点击“返回 IR”后进入同一 IR 当前阶段，沿用已有会话和未发送草稿，不新建 Agent、不改变阶段；讨论和修改仍遵守当前 Web 及阶段的权限和只读门槛

### Requirement: 提案流程入口统一且可解释

需求提案 IR MUST 将当前阶段的评审、交接、接手、生成、人工确认、退回与入库流程操作统一置于右侧文档固定底栏；MUST NOT 在更多菜单、信息弹窗或其他入口重复提供同一操作。阅读后由人工判断是否操作，不增加滚动已读门禁。沿用现有阶段、角色、版本及逐文件确认门槛，不以界面简化绕过 PR 和合并核验。

#### Scenario: 打开提案更多菜单
- **WHEN** 用户点击提案 IR 标题旁的更多
- **THEN** 打开简洁下拉菜单，仅有提案信息、操作记录，以及权限允许时的删除提案；删除独立分隔并使用危险样式，沿用原有确认和禁止删除规则
- **AND** 提案信息及操作记录均只读；信息仅展示人员、模型、临时目录及已登记 PR，记录展示操作及历史评审／历轮补充意见，不包含评审、生成、交接、打回、交付或停止按钮

#### Scenario: 明确当前操作人与缺失条件
- **WHEN** 用户处于提案当前阶段
- **THEN** 主页面直接显示接手人及当前操作所需条件，不只在悬停或更多中说明；文档底栏使用简短原因说明文件缺失、本轮版本失效、等待接手或人工确认；禁用原因与实际门槛一致
- **AND** design.md 的存在不表示本轮方案已生成有效版本；有效生成后仍须人工逐文件确认，不能自动入库

#### Scenario: 有目标和影响的退回
- **WHEN** 接手人从技术方案退回业务
- **THEN** 底栏显示“退回业务需求补充”，确认前要求填写业务问题，明确保留文件和历史、旧方案失效、由业务 Agent 补充文件后重评，再继续方案；取消不改变状态
- **AND** 评审阶段返回业务补充只是进入编辑阶段，只有实际修改需求时才按已有规则使旧版本失效；返回只切换业务 Agent 对话，不弹确认框，不要求填人工争议处理表单

#### Scenario: 根据评审问题定位文档
- **WHEN** 阅读当前或历史评审结果
- **THEN** 显示当前结论与已有结构化问题，按记录提供对应文件路径；点击仅在右侧定位当前 IR 范围内文件，保留评审阶段，不启动聊天或修改需求；不虚构行号或缺失的问题数据
- **AND** 文件选择器完整路径可换行，实际文件名保持可读；文档内部的表格和代码块操作也隐藏，不只删除外层工具栏；读取失败时仍可重新读取

### Requirement: 方案问题由开发粘贴，业务通过 AI 补充

提案 MUST 以 AI 为中心：人员对话、提供意见、检查只读文件、确认阶段；IR、SR、方案与复制入库文件均由对应 AI 生成或修改，不提供人工编辑文件作为常规操作路径。业务需求、评审、技术方案均在 A 的 OMP 和 NFS 临时目录运行；方案阶段不得以个人 Web 或项目路径作为准入条件。

#### Scenario: 大输入框退出方案
- **WHEN** 本轮方案开发人无法回答方案 Agent 的问题并点击右侧底栏“退出方案，退回业务补充”
- **THEN** 打开与站点一致的大弹窗和多行输入框，开发自行粘贴问题原文并可补充说明；空白不可确认，关闭／取消不改变阶段
- **AND** 确认后直接回业务需求 Agent，显示最新待处理意见，不进入评审页；不增加问题拆分、自动分派、逐项状态或人工勾选解决流程
- **AND** 最新意见在业务聊天上方醒目显示，支持长文本阅读；业务与 Agent 对话，由 AI 更新 IR／SR，再人工发起当前文件的评审；通过后开发点击下一步继续 A 的方案 Agent，允许多轮循环且保留原文和会话历史

#### Scenario: 固定提出人及当前操作责任
- **WHEN** 查看提案 IR
- **THEN** 左侧紧凑双行显示名称、提出人工号及状态，SR 仍保持一行；中间头部说明当前由谁补充或继续方案，提出人不得被最后发言人、方案或入库人覆盖
- **AND** 最新退回意见在重新进入方案后移入只读操作历史；新一轮退出替换当前最新意见，旧意见仍保留

#### Scenario: 技术方案与最终个人入库分离
- **WHEN** 当前需求通过评审
- **THEN** 开发点击“下一步：技术方案”直接在 A 的 OMP 开始方案讨论，不再要求先交给开发后再次接手，不要求个人开发项目
- **AND** 方案有效完成后，入库按钮仅在本人启动的 Web 且个人项目有效时可用，由 AI 复制 A 临时草稿、提交推送；入库人可以不同于方案开发人。只读 Web 不展示 A 的聊天，即使该 Web 可以执行最终入库
- **AND** 当前版本逐文件确认、候选归属及人工 PR／合并核验门槛保留；不存在因为出现 design.md 或一次退回就自动放行的路径

最新待处理意见须兼容长文本：页面内正文限制高度、独立滚动并支持键盘聚焦，不撑开页面或挤掉聊天；提供只读全屏阅读，标题和返回操作固定，全文独立滚动。保留段落、列表及换行，长链接和连续字符可换行，不产生横向页面溢出。打开／关闭不发送消息、不改变阶段或意见状态，返回原讨论及原滚动位置。大输入框支持长意见粘贴及内部滚动，不截断原文。

### 需求评审 Agent：工具只读，对话可用

需求评审是独立 Agent 会话，中间必须显示聊天记录和可发送输入框；“只读”指不能修改 IR／SR 或其他项目文件，不是禁用聊天。Agent 只读取当前需求、报告问题、解释对应文件和判断依据，不替用户修改需求、自动返回上一步或执行方案／入库。用户遇到问题或有疑问可直接询问，不提供“处理业务争议”、裁决表单、处理方式选择或额外人工确认记录。业务人员自行点击右侧底栏“上一步：业务需求”，直接切回业务 Agent，无确认弹窗；由业务 Agent 根据对话修改文件，再显式重评。评审未通过时下一步进入技术方案禁用，通过后由开发确认继续。历史评审会话只读查看，不覆盖当前结论，不把用户发言当作文件修改或通过凭证。原型聊天回复为固定演示，不代表真实 AI 内容评审。

需求提案 IR 与正式 IR／SR 的聊天顶部固定为三行：第一行原生标题与工具图标，第二行居中阶段条，第三行单行显示当前 Agent、状态及必要处理人，长内容截断并可悬停查看。提案辅助菜单保留标题旁位置；正式 IR／SR 的“…”移到问号紧邻左侧。删除重复标题、独立人员／路径行和协作按钮；没有聊天会话的总览、入库或只读节点仍保留原生标题。所有流程操作仍在右侧文档底栏。

正式 IR 的下拉菜单仅保留“需求信息”“操作记录”：信息只读展示需求文件、验收人、工作目录／分支、模型和已登记需求／归档 PR。正式 SR 仅保留“SR 信息”“操作记录”：信息展示自身规格路径、开发人、开发项目、固定工作目录／分支、当前轮次、模型和代码 PR；记录仅展示该 SR 的操作、阶段确认和历史代码 PR，不混入其他 SR。菜单不放开始、生成、下一步、回退、停止、交付或删除入口；必要流程操作只保留在原聊天或文档底栏，原型阶段材料生成移到文档底栏。删除旧混合详情弹窗、嵌套目录／历史及复制入口。本轮仅改文档和原型，不修改正式宿主，不运行测试。

### 正式需求筛选简化及五份 IR 样例

当前简化约定：IR 验收 Agent 只走正常流程并生成通过报告，不发现问题、不返工、不复验。筛选只保留“全部需求、待开发、开发中、验收与归档、已完成”五项，按当前 Release 的 IR 整体进度聚合，不能按某一个 SR 是否正在运行判定。“全部需求”不是业务阶段。

- 待开发：没有任何 SR 开始。
- 开发中：已有 SR 开始或完成，尚未全部合并核验；即使当前没有运行中的 Agent，也不回到待开发。
- 验收与归档：全部 SR 合并核验后，覆盖等待验收、正在验收、通过后准备归档及最终 PR 等待合并核验的整个阶段。
- 已完成：最终归档 PR 已合并，成果与归档均已核验；不能仅凭全部 SR 完成就判断 IR 完成。

原因：在验收不会失败的假设下，待验收、验收中、待归档只是同一条固定后续流程的内部进度，不需要再占据多个筛选项；行内仍可说明待验收、验收中等具体进度，不新增问题／返工分类。SR 的开发计划、开发与验证、交付合并继续作为 SR 阶段，不混入 IR 筛选。

默认 Aurora 项目当前 Release 共五份正式 IR：团队数据总览（待开发）；账号与权限体验（开发中）；报表导出（全部 SR 已合并，待验收）；通知中心（验收中）；操作审计（最终 PR 与归档均已核验，已完成）。因此各筛选数量为全部 5、待开发 1、开发中 1、验收与归档 2、已完成 1。五个 IR 的具体进度不同，但不为匹配五个选项而虚构一个“全部”阶段。提案和其他项目样例保持独立。

这些都是静态内存数据，未执行真实模型、测试、Git 或归档。待验收和验收中的共享摘要使用不同 OMP 标识，不占当前 A 的开发名额；并发准入仍只检查当前 OMP Web。

### 需求提案列表只展示 IR

需求提案左侧列表仅展示 IR，不显示展开箭头、下属 SR 或展开／收起全部按钮。点击整行直接进入该 IR，并显示当前选中状态；保留提出人、阶段／待处理提示，以及搜索、筛选和排序。

原因：提案的讨论、评审、方案和入库均以 IR 为单位，SR 没有独立阶段操作，树形列表容易让用户误以为可以单独推进 SR。SR 数据及文档不删除：在 IR 右侧文件选择器中查看 `proposal.md`、各 SR 的 `spec.md` 和 IR 的 `design.md`。正式需求仍保留 IR 展开 SR，因为开发后各 SR 有独立流程。

### 新提案首发权限

“新建需求提案”的未发送草稿尚无 IR 编号，仍属于提案讨论。A（j00808874）的 Web 上，业务人员首次发送需求文字或附件不要求拥有该 Web，也不要求配置个人 Git 开发路径；其他 Web 仍不能发起提案讨论。首次发送成功后才加入提案列表，重复点击新建不会生成空提案，发送失败保留草稿供重试。

修正原因：旧权限检查未区分草稿，且首条消息发送时从普通列表读取，遗漏了尚未公开的提案，误用了正式需求开发限制，导致业务人员首次发送失败。此修正仅涉及原型的讨论权限判定，不放宽正式需求开发、个人配置或最终需求入库权限。

### 只读材料：类型、路径与正文分层

所有 IR、SR、提案及开发阶段共用的只读材料面板，依次展示材料类型下拉框、所选文件完整路径、文档正文、底部阶段操作按钮。下拉框使用“IR 原始需求、SR 系统需求、IR 方案设计、开发计划、完成报告、UT 报告、ST 报告、交付说明”等业务名称，不显示文件名或路径。IR 内存在多份 SR 规格时，使用“SR 系统需求 · 需求标题”区分，不能把文件路径放回选项。

路径独立显示，使用已记录的工作区与材料路径，长路径完整换行、不截断；已归档材料显示实际归档路径。路径与正文在同一阅读滚动区，阶段操作固定在面板底部，保持原有权限和流程。原因：先按材料用途选择，再查看来源和正文，避免长路径挤占下拉框并妨碍识别。
