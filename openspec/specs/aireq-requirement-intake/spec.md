# aireq-requirement-intake

## Purpose

维护最新 AIReq 业务流程、职责和边界。

> 状态：用户已确认的最新 AIReq 需求基线。原型与正式入口已共用同一前端 bootstrap 和网络客户端，旧 `runtime/omp-data-source.ts` 宿主适配已移除；原型业务状态与模拟任务由服务端纯内存持有。真实 OMP 业务后端尚未实现，接入只需实现既有冻结请求、响应、错误及事件合同并配置后端地址，不再修改前端、替换客户端或转换接口格式；真实服务未改造，发行内嵌资源未重新生成。原型 API 检查、浏览器演示及 packages/aireq-frontend/README.md 的既有启动命令、截图与交互记录保留原有证据范围，不代表真实 OMP 已接通，也不是真实模型、Git、数据库、正式宿主业务或发行产物的实现／验收证据。

## Requirements

### Requirement: 自然语言拆分、实现依赖与工期预估

用户 MUST 能通过自然语言描述原始需求，经需求 Agent 澄清生成 IR、拆分 SR 并明确验收条件。方案 Agent MUST 输出方案、逐 SR 前置依赖、工期预估及假设；可并行关系由依赖图推导。提案只有提交人，不设负责人、开发人员或计划起止时间。预估不是实际用时或承诺日期，不直接相加为 IR 总工期；IR 进度仍为各 SR 百分比的算术平均值。

#### Scenario: 提案工期预估与依赖共同存储
- **WHEN** 当前方案有效完成
- **THEN** 方案 Agent 同轮维护 design.md 及同目录 sr-dependencies.json，JSON 结构为 `{ "srs": [ { "srId": "...", "estimate": { "workingDays": 3, "assumptions": "估算依据与不确定项" }, "prerequisites": [ { "srId": "...", "reason": "..." } ] } ] }`；覆盖全部稳定 SR ID，每个恰好一次，无依赖使用空数组
- **AND** estimate.workingDays 为正数工作日，支持小数；estimate.assumptions 为非空估算依据、范围及不确定项；不允许未知 ID、自依赖或循环；可并行关系从图推导，不重复存储
- **AND** “技术方案／SR 依赖／工期预估”可直接切换。预估逐 SR 只读展示，不提供人员、日期或预估编辑表单；人通过方案对话要求 AI 修改文件
- **AND** 预估和依赖是同一 JSON 的仓库权威，不存数据库可编辑副本。design.md 引用 JSON，不重复清单；SR spec.md 不维护这些字段
- **AND** 两个方案产物同轮生成、更新、失效与逐文件确认，任一变化使旧确认失效；JSON 缺失、无效或过期时禁止沿用旧确认、提交或自动转正，不回退旧文件

#### Scenario: 转正后才安排人员和日期
- **WHEN** 提案分支已合入默认分支且全部材料完整有效
- **THEN** 自动转正保留相同项目、IR、SR ID 及仓库中的工期预估和依赖；不从预估自动生成负责人、开发者或计划起止时间，新 SR 进度仍为 0%
- **AND** 正式需求由管理员分配 IR 负责人，管理员或负责人安排 SR 开发人员及起止时间；这些安排仍是数据库元数据，独立于 Git 内的工期预估，不新增入库审批条件

#### Scenario: 人工调整与 IR 汇总
- **WHEN** 管理员或 IR 负责人调整 SR 开发人员及计划开始、结束时间
- **THEN** 保存数据库元数据，保留原 AI 建议并标记人工调整，后续后台分析不得直接覆盖人工安排；允许未分配人员或未排期，清空排期须同时清空起止时间，结束必须晚于开始
- **AND** 依赖与人员时间冲突须提示并持续可见，但不擅自修改其他 SR 的排期或仓库依赖；IR 起止时间取全部 SR 最早开始与最晚结束，部分 SR 未排期须明确显示，不把部分范围当作完整计划
- **AND** 正式需求中的依赖只读展示；变更依赖通过仓库文档及人工 PR 评审流程，不通过排期弹窗改变需求和验收条件；分析须绑定实际仓库版本，旧证据不能用于新内容

原型已由网络后端提供夹具并在服务端纯内存编辑，模拟身份通过后端数据表达，共享前端经同一网络客户端请求和展示业务数据；不实现真实 AI 排期、人员日历、数据库写入或 Git 操作。方案旁的排期卡片仍是文档外元数据，不混入提交到仓库的正文。共享入口与客户端已统一不表示真实 OMP 业务后端已实现这些能力或已接通；真实接入只实现后端既有合同并配置地址。

### Requirement: Release、IR、SR 的职责与稳定关系

系统 MUST 按项目／仓库、Release、IR、SR 组织需求。一个项目 MUST 对应一个仓库，一个 IR MUST 对应一个 OpenSpec Change；IR 包含一个或多个 SR，每个 SR 对应该 Change 的一个能力 spec.md，共用同目录的 design.md 与 sr-dependencies.json 两个方案产物。稳定 ID、change-id 和能力路径 MUST 不随显示标题或查看人改变。

#### Scenario: 标准 OpenSpec 文件映射
- **WHEN** 创建和拆分提案
- **THEN** 使用 openspec/changes/<change-id>/proposal.md 表达 IR，specs/<capability>/spec.md 表达每个 SR，design.md 表达整份技术方案、架构、模块、文件及函数职责，并引用同目录 sr-dependencies.json 作为唯一依赖来源
- **AND** 一个能力规格可以包含多条 Requirement／Scenario；不为每条 Requirement 再造 SR，不另发明 IR.md、SR.md 或替代 design.md 的方案 JSON 格式；sr-dependencies.json 承载 SR 依赖、工期预估及假设；同名 Change 冲突交人处理，不覆盖

#### Scenario: Release 和仓库身份
- **WHEN** 添加项目、Release 或个人开发 clone
- **THEN** Release 只组织交付范围，不代替分支；同仓库的不同 clone／worktree 关联同一项目身份；共享项目身份不引入跨 OMP Web 的开发互斥

### Requirement: 唯一共享 Web 直接访问 SQLite

正式部署 MUST 只启动一个共享 `omp aireq_web`，所有访问者使用同一地址，不再启动各自的正式 Web。唯一共享 `omp aireq_web` MUST 由自身后端进程直接打开和读写 `/tmpdata/DFT_LAB/omp/omp_aireq_sqlite.db`，不需要独立数据库服务或数据库监听端口。浏览器仍通过现有 Web HTTP／WS 接口访问业务数据，不直接连接 SQLite。`omp aireq_web --port <端口>` 指定端口，省略时自动选择并显示实际地址。此唯一性不禁止独立启动原型后端；原型后端不连接正式业务库。这里规定目标行为，本轮只更新需求文档与原型说明，不实现真实 SQLite 连接、持久化、命令或单实例门禁。

#### Scenario: 访问者与 Web 所有者分开
- **WHEN** A 启动唯一共享 `omp aireq_web`，其他人通过浏览器访问该地址
- **THEN** 所有访问者使用 A 的模型 Token／profile，不提供个人 Token 或另启个人 Web
- **AND** 浏览器账号格式为一个小写 a–z 字母后接 8 位数字，保留前导零；仅格式检查，不增加密码或完整员工认证。切换账号不切换 Web 所有者、OMP profile 或 Token，也不因此获得项目写入入口

#### Scenario: 唯一提案讨论后端
- **WHEN** 用户查看或讨论需求提案
- **THEN** 所有访问者在唯一共享 Web 查看、创建和讨论提案，聊天记录归启动者的 OMP 管理
- **AND** 讨论权限不授予其他设置修改权，不要求访问者提供个人 Git 目录

#### Scenario: 临时工作区与共享数据
- **WHEN** 业务需求、评审或方案讨论生成材料
- **THEN** 在 `/tmpdata/DFT_LAB/omp/{project_name}/{原提交人工号}/{提案id}/` 生成材料；共享项目代码及已实现规格只读。生成这些临时材料不等于修改项目或执行 Git
- **AND** 共享 `omp aireq_web` 后端直接读写 `/tmpdata/DFT_LAB/omp/omp_aireq_sqlite.db`；所有访问者查看同一业务数据，聊天归共享 Web 宿主，不进入业务库；宿主不可用时不另启个人 Web 自动接管或重放

### Requirement: 共享前端与双后端契约

AIReq MUST 遵循 [aireq-browser-workbench 的界面与数据源边界](../aireq-browser-workbench/spec.md)：原型和正式版使用同一份前端、同一接口客户端及完全相同的浏览器代码，仅以配置的后端地址选择原型后端或 OMP 后端，不按 prototype／runtime 模式分支业务界面或注入两套前端业务数据源。两类后端 MUST 可独立启动并实现同一请求、响应、错误及实时事件契约；共享前端持续连接原型后端开发和演示后，接 OMP MUST 无需复制、重写或替换前端及客户端。既有业务流程、权限和人工／版本门禁不变。

#### Scenario: 双后端使用同一需求客户端
- **WHEN** 使用同一浏览器代码分别连接独立运行的原型后端和 OMP 后端，创建提案、读取材料、调整排期并接收状态事件
- **THEN** 只改变后端地址配置，使用同一请求、响应、错误和事件处理路径，不替换业务数据源；两类后端失败均显示错误，不自动回退样例或重放动作
- **AND** 原型后端在服务端纯内存持有数据、状态、模拟回复、任务及事件，不依赖 OMP、模型、Git 或数据库，模拟标识由其数据表达；OMP 后端负责真实业务、持久化和外部能力，复用原生宿主，不新增第二执行器

#### Scenario: 提案原型状态随服务而非页面存活
- **WHEN** 原型后端已接纳提案更新或模拟入库检查，用户刷新、关页或断线后重新连接同一服务
- **THEN** 继续读取服务端当前业务及任务状态，不因页面离线停止服务任务或恢复样例；重启原型后端才恢复初始样例
- **AND** 服务端纯内存不等于真实文件、Git、模型或数据库能力；浏览器主题与未发送输入草稿沿用既有作用域，不作为业务状态权威

### Requirement: 开发者配置与共享业务数据分离

模型、提供者、Token、Agent、提示词和技能配置 MUST 使用唯一共享 Web 启动者的 OMP 后端及 profile，不按访问工号另建或切换配置。所有人可查看全部设置；外观和独立 Skill 设计所有人可用，其他设置仅启动者可修改。共享业务数据与 OMP 配置／会话分开，不隐藏页面代替权限判断。

#### Scenario: 单个后端承载多人访问
- **WHEN** 多名用户访问共享 OMP Web
- **THEN** 唯一共享 Web 后端直接访问同一份 SQLite，读取项目、Release、需求、提案阶段、人员排期及进度；不另启数据库服务，不按用户启动个人 Web 或复制数据库
- **AND** AIReq 不执行编码，不维护 SR 开发占用、并发名额、仓库单 IR 锁或依赖执行调度；依赖与人员冲突只作安排提醒
- **AND** 所有访问者共用启动者的模型配置和 Token；配置、凭据、聊天正文及 Skill 设计临时产物不进入共享业务数据库，项目技能是否进入 Git 由显式提交决定

#### Scenario: 个人设置与会话归属
- **WHEN** 开发者打开个性化、模型、技能或 Skill 设计
- **THEN** 明示共享 Web 启动者及实际配置归属；profile 技能沿用该 OMP 实际目录，常规为 `~/.omp/agent/skills/`。切换工号或业务项目不切换配置所有者
- **AND** 共享工作流记录保存必要会话引用及所属后端标识；原生会话历史由创建它的 OMP 后端管理。个人 Skill 设计会话、草稿、临时目录和文件不得作为团队共享需求记录，也不能只凭同名 session ID 连接另一后端或重放消息
- **AND** 模型和追加提示词变更只用于该后端之后新建的角色会话；已有会话保留创建时快照，不切换或重写另一后端的会话

#### Scenario: 全部设置可看，外观和 Skill 设计全员可用
- **WHEN** 启动者或其他账号访问共享 Web 的任意设置页面
- **THEN** 所有人可以查看全部页面与配置；外观和独立 Skill 设计所有人可操作，其余设置（含项目、Release、模型、提供者、Agent、提示词和技能管理）仅启动者可修改
- **AND** 受限设置覆盖草稿编辑、保存、快捷键及全部写入口；其他访问者仍可切换查看、搜索、筛选及复制，不隐藏页面或清空详情，不提示启动个人 Web

#### Scenario: 正式 SR 进入统一分析调度
- **WHEN** 提案自动转正并生成正式 SR
- **THEN** 每个正式 SR 按项目和稳定 ID 自动取得唯一分析任务记录，不生成独立定时器或要求手动新建任务；保留 SR 级状态、历史和失败原因，由统一调度器按项目开关和全局间隔执行
- **AND** 新项目默认关闭；完成停止自动分析、重新打开复用原记录恢复资格，开关关闭不删除记录或取消在途分析。入口在平台配置“需求分析”，全员可查看和筛选，仅 Web 启动者可配置或触发


#### Scenario: 所有访问者可确认保存设计技能
- **WHEN** 任意访问者完成 Skill 设计并预览临时文件
- **THEN** 可明确选择保存整份技能目录到有效项目 `.omp/skills/<skill-name>/` 或共享 OMP 实际 profile 的 `skills/<skill-name>/`；技能标识由模型推荐，不引入个人开发目录登记，目标明示实际归属，不冒充访问者个人后端
- **AND** 无有效可写项目目标时只阻止项目保存，不阻止有效 profile 目标；未确认前不写正式目标，不写目标外或共享只读目录，不覆盖同名技能；该能力不开放原技能管理或模型、提示词配置的写权限

### Requirement: 需求讨论必须审查实质内容

业务需求 Agent MUST 澄清目标、范围、规则、异常和验收行为，整理 IR 与完整 SR。需求评审 MUST 由 A／B／C 三个不同模型独立并行只读检查同轮同版 IR／全部 SR，第四个综合评审 Agent 汇总来源、依据及分歧。最终通过与否由人判断，不按投票、评分或模型问题标签自动放行／阻断。

#### Scenario: 需求评审反馈与重评
- **WHEN** 评审发现遗漏、冲突、重复或不可验证要求
- **THEN** 给出引用到 proposal／能力 spec 的问题和依据；默认查看综合意见，可切换 A／B／C 原始会话定向追问，只读限制文件写入而非对话
- **AND** 同轮同版三个原始报告和综合意见完整可读后，人工可通过进入方案或自行返回业务 Agent 补充；缺失、失败、未完成或过期报告不能用于批准，不增加裁决表单、逐项勾选或已读门禁
- **AND** 需求更新使旧报告、方案和人工决定失效并保留历史；单个原始评审按同轮快照重试后重新生成综合意见，不能沿用旧决定

#### Scenario: 会话和职责
- **WHEN** 在同一提案中选择 IR 或 SR
- **THEN** 仅 IR 进入业务需求或方案讨论；提案 SR 只查看自身 spec.md，中间显示返回 IR 的说明和入口，不挂载聊天、阶段条或操作。需求评审 Agent 只读取业务产物，不修改 IR／SR 文件，不替代方案／代码审查；原生聊天由 A 的 OMP 管理

### Requirement: 提案状态与讨论阶段分离

需求讨论和技术方案 MUST 是提案的两个阶段，与草稿、方案完成、PR 待合并、正式需求等状态分开。提交需求评审 MUST 不要求已有方案；同轮同版四份报告完整后由人工判断是否进入方案，不新增“待评审”业务状态。提交人和方案参与人 MUST 分开记录。

#### Scenario: 开发人员接手方案
- **WHEN** 当前需求版本评审材料完整且人工决定通过，开发人员点击下一步进入技术方案
- **THEN** 记录方案参与人工号、时间和轮次，固定提出人另行保留；直接进入 A 的方案 Agent，不要求先交接或配置自己的开发项目，也不自动生成方案或提交 PR

#### Scenario: 技术方案与实施依赖
- **WHEN** 需求版本已满足进入方案的条件
- **THEN** 方案 Agent 同轮生成同一 Change 的 design.md 和 sr-dependencies.json；design.md 解决纯技术问题，保留实现思路、技术取舍和验证安排并引用 JSON，JSON 独立记录前置依赖及原因，界面从依赖图推导顺序与可并行范围
- **AND** 需要业务细节时交回业务需求 Agent，保留反馈并使旧方案失效；补充和重评后重新确认方案。AIReq 不设置编码执行阶段或执行 Agent

### Requirement: 共享材料直接查看

系统 MUST 展示同一共享提案的 proposal.md、全部能力 spec.md、design.md、sr-dependencies.json、资料及评审记录，原生聊天正文仍由 OMP 管理。材料区仅提供选择和只读阅读；右侧选中 sr-dependencies.json 时复用现有图画布及控件显示 SR 依赖图，节点包含稳定 ID 与标题，箭头从前置 SR 指向依赖方，可缩放、平移并点击连线查看依赖原因，不展示 JSON 正文。独立 SR 保留节点，缺失、无效或过期材料明确报错，不绘制旧图。不提供复制、下载或带入讨论按钮；查看材料 MUST 不产生批准、执行或状态推进。

#### Scenario: 原格式与查看范围
- **WHEN** 选择 IR、SR 或方案
- **THEN** 分别默认查看 proposal.md、对应能力 spec.md 或 design.md，方案材料同时可选择查看 sr-dependencies.json，区分临时来源、仓库相对路径、版本和历史；没有材料如实显示，不用样例或其他需求替代

### Requirement: 方案完成后创建提案分支，合入且文档完整自动转正

方案设计完成并经人工逐文件确认当前 IR、全部 SR、design.md 和有效 sr-dependencies.json 后，平台 MUST 才从项目最新默认分支创建独立提案分支，一同提交并推送同一 Change 的完整材料，通过公司内网 Git API 自动创建包含 JSON 的 MR，记录编号、地址、分支与状态。此前 MUST NOT 创建提案或 SR 分支。人工 MUST 在企业 Git 平台评审和合并 MR；平台 MUST NOT 自动合并。项目只配置 Git 仓库和默认分支，平台按需维护工作副本，不要求个人开发目录。

#### Scenario: 准备需求 PR
- **WHEN** 当前需求、方案及人工确认齐备
