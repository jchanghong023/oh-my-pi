# dev-requirement-intake

## Purpose

维护最新 Dev 业务流程、职责和边界。

> 状态：用户已确认的最新 Dev 需求基线。本次仅更新文档；现有代码和原型尚未按本规则完成实现或验收。

## Requirements

### Requirement: Release、IR、SR 的职责与稳定关系

系统 MUST 按项目／仓库、Release、IR、SR 组织需求。一个项目 MUST 对应一个仓库，一个 IR MUST 对应一个 OpenSpec Change；IR 包含一个或多个 SR，每个 SR 对应该 Change 的一个能力 spec.md，共用一个 design.md。稳定 ID、change-id 和能力路径 MUST 不随显示标题或查看人改变。

#### Scenario: 标准 OpenSpec 文件映射
- **WHEN** 创建和拆分提案
- **THEN** 使用 openspec/changes/<change-id>/proposal.md 表达 IR，specs/<capability>/spec.md 表达每个 SR，design.md 表达整份技术方案、架构、模块、文件、函数职责及 SR 顺序／依赖
- **AND** 一个能力规格可以包含多条 Requirement／Scenario；不为每条 Requirement 再造 SR，不另发明 IR.md、SR.md 或方案 JSON 正式格式；同名 Change 冲突交人处理，不覆盖

#### Scenario: Release 和仓库身份
- **WHEN** 添加项目、Release 或个人开发 clone
- **THEN** Release 只组织交付范围，不代替分支；同仓库的不同 clone／worktree 关联同一项目身份；共享项目身份不引入跨 OMP Web 的开发互斥

### Requirement: 数据库服务与各自 Web 的简化部署

A、B 可在同一台或不同机器上启动各自的 Web，内网互通，`/tmpdata` 为 NFS 共享目录。`omp dev_db` MUST 启动唯一共享数据库服务，固定监听 18321；各 `omp dev_web` MUST 经该服务访问同一份业务 SQLite，而不是各自直接并发打开 NFS 数据库文件。`omp dev_web --port <端口>` 显式指定 Web 端口；未指定时 MUST 自动选择一个可用端口，并显示实际访问地址。多人同机启动时不要求共用 Web 端口。这里规定目标行为，本会话不实现这些命令。

#### Scenario: 访问者与 Web 所有者分开
- **WHEN** A 启动自己的 `omp dev_web`，C、D 通过浏览器访问 A 的实际地址和端口
- **THEN** A、C、D 均使用 A 的模型 Token；B 启动自己的 Web，使用 B 的 Token。C、D 不提供自己的 Token，也不启动开发后端
- **AND** 浏览器账号格式为一个小写 a–z 字母后接 8 位数字，保留前导零；仅格式检查，不增加密码或完整员工认证。切换账号不切换 Web 所有者、OMP profile 或 Token，也不因此获得项目写入入口

#### Scenario: 唯一提案讨论后端
- **WHEN** 用户查看或讨论需求提案
- **THEN** 全部 Web 可查看共享提案资料；当前简化规则仅允许所有者为 `j00808874` 的 OMP Web 创建、讨论和修改提案，其聊天记录由该 OMP 管理。此限制检查后端所有者，不检查访问者是否输入 `j00808874`
- **AND** B 的 Web 只能查看提案材料，不能发送提案 AI 消息、修改提案或创建本地讨论副本；需要讨论时进入 A 的 Web。C、D 可在 A 的 Web 提需求和讨论，但不能修改项目或执行 Git

#### Scenario: 临时工作区与共享数据
- **WHEN** 业务需求、评审或方案讨论生成材料
- **THEN** 在 `/tmpdata/DFT_LAB/omp/{project_name}/{原提交人工号}/{提案id}/` 生成材料；共享项目代码及已实现规格只读。生成这些临时材料不等于修改项目或执行 Git
- **AND** `omp dev_db` 统一管理 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`；所有 Web 看见相同的项目、Release、正式需求和提案。需求聊天不存此业务库，进入 A 的 Web 才能讨论；A 的 Web 不可用时不在 B 的 Web 自动接管或重放

### Requirement: 开发者配置与共享业务数据分离

个性化、模型及提供者配置、Token、Agent 配置、个人技能、Skill 设计会话与临时产物 MUST 属于每个开发者自己的 OMP 后端和 profile。当前开发后端只能展示和修改该开发者自己的配置；不得因连接相同 SQLite 或使用相同浏览器工号而展示、继承、覆盖其他开发者或团队服务的个人配置。A 的 Web 可长期供业务人员访问，来访者共用 A 的 Token，但不因此获得 A 的个人配置修改或项目写入权限；所有人看到相同页面，在受限操作入口提醒不支持，不隐藏整页。

#### Scenario: 多个后端共享业务，个人配置独立
- **WHEN** 开发者甲、乙分别启动自己的 OMP Dev，团队长期 Web 也在运行
- **THEN** 各 Web 经固定 18321 端口连接同一 `omp dev_db` 服务，由该服务管理 `/tmpdata/DFT_LAB/omp/omp_dev_sqlite.db`，共同读取项目、Release、需求、阶段、开发占用及操作记录；不得在各机器同名路径创建独立副本冒充共享
- **AND** 共享业务数据的一致性由 `omp dev_db` 负责；SR 并发、名额和依赖只检查同一个 OMP Web 内的执行状态，不做跨 Web 的 SR 互斥、仓库单 IR 锁、名额协调或依赖调度
- **AND** 甲的个性化、模型、Agent、Token、个人技能及 Skill 设计属于甲的后端/profile，乙同理；C、D 访问 A 时调用 A 的模型 Token，不切换为 C、D 的个人配置。配置和凭据不写入共享业务数据库，也不从团队 Web 或另一开发者复制；项目技能只按各自当前开发项目实际加载，文件是否经 Git 共享由显式提交决定

#### Scenario: 个人设置与会话归属
- **WHEN** 开发者打开个性化、模型、技能或 Skill 设计
- **THEN** 明示当前后端及配置所有者，以该开发者自己的 OMP 配置为准；个人技能目录沿用其实际 profile，常规位置为 `~/.omp/agent/skills/`。切换业务项目不切换个人配置所有者
- **AND** 共享工作流记录保存必要会话引用及所属后端标识；原生会话历史由创建它的 OMP 后端管理。个人 Skill 设计会话、草稿、临时目录和文件不得作为团队共享需求记录，也不能只凭同名 session ID 连接另一后端或重放消息
- **AND** 模型和追加提示词变更只用于该后端之后新建的角色会话；已有会话保留创建时快照，不切换或重写另一后端的会话

#### Scenario: 个人设置修改权限归当前 Web 所有者
- **WHEN** X 或其他账号访问 X 启动的 Web 中的模型、个性化和技能
- **THEN** 所有人可以查看相同页面与当前 OMP 返回的配置；只有 X 本人可修改 X 的模型、个性化和技能，其他访问账号只读；要修改自己的配置，必须启动自己的 OMP Web。查看权限不变更配置归属，不把配置写入共享业务数据库
- **AND** 该限制覆盖编辑草稿、保存、快捷键及技能创建／导入／启停／删除和设计保存；非所有者可切换查看、搜索、筛选及复制，不通过隐藏页面或清空详情限制读取

#### Scenario: 技能保存目标由开发者选择
- **WHEN** 开发者在自己的 OMP Dev 中完成 Skill 设计并预览临时文件
- **THEN** 技能标识由模型推荐，无须用户预先填写；可明确选择保存整份技能目录到项目路径或开发者个人路径：项目技能使用为该开发者登记的当前开发项目 `.omp/skills/<skill-name>/`；个人技能使用该开发者实际 OMP profile 的 `skills/<skill-name>/`，供其不同项目加载
- **AND** 未绑定有效开发项目时只阻止项目目标，不阻止有效个人目标；未确认前不写正式目标，不写共享只读项目或他人的目录，不覆盖目标中的同名技能。个人保存不依赖用户在共享 SQLite 登记一个项目

### Requirement: 需求讨论必须审查实质内容

业务需求 Agent MUST 澄清目标、范围、规则、异常和验收行为，整理 IR 与完整 SR；业务需求评审 Agent MUST 检查这些产物，指出具体问题和依据。不通过 MUST 返回补充，不能用格式齐全或 Agent 自称通过代替内容评审和人工决定。

#### Scenario: 需求评审反馈与重评
- **WHEN** 评审发现遗漏、冲突、重复或不可验证要求
- **THEN** 给出引用到 proposal／能力 spec 的问题和依据，业务需求 Agent 补充后对当前版本重新评审；旧版本意见不能作为新版本已通过证据
- **AND** 反复不通过、意见冲突或范围争议交人裁决，不无限循环；人工裁决及依据单独记录，不伪造 Agent 通过结果

#### Scenario: 会话和职责
- **WHEN** 在同一提案中选择 IR 或任意 SR
- **THEN** 共用当前提案阶段的业务需求或方案会话；需求评审专门审业务产物，不替代方案／代码审查；原生聊天由 OMP 管理，不按 SR 复制需求讨论正文

### Requirement: 提案状态与讨论阶段分离

需求讨论和技术方案 MUST 是提案的两个阶段，与草稿、方案完成、PR 待合并、正式提案等状态分开。提交需求评审 MUST 不要求已有方案；通过需求评审及必要人工裁决后，才形成可进入方案阶段的需求版本，不新增“待评审”业务状态。提交人和接手开发人 MUST 分开记录。

#### Scenario: 开发人员接手方案
- **WHEN** 开发人员明确接手已提交的提案
- **THEN** 记录接手工号、时间和轮次，与提交人记录分开；接手不等于需求评审通过，不自动生成方案或提交 PR

#### Scenario: 技术方案与实施依赖
- **WHEN** 需求版本已满足进入方案的条件
- **THEN** 方案 Agent 生成同一 Change 的 design.md，解决纯技术问题，明确 SR 顺序、前置依赖、可并行范围、技术取舍和验证安排
- **AND** 需要业务细节时交回业务需求 Agent，保留反馈并使旧方案失效；补充和重评后重新确认方案。执行阶段不再设置方案 Agent

### Requirement: 共享材料直接查看

系统 MUST 展示同一共享提案的 proposal.md、全部能力 spec.md、design.md、资料及评审记录，原生聊天正文仍由 OMP 管理。材料区仅提供选择和只读阅读，不提供复制、下载或带入讨论按钮；查看材料 MUST 不产生批准、执行或状态推进。

#### Scenario: 原格式与查看范围
- **WHEN** 选择 IR、SR 或方案
- **THEN** 分别默认查看 proposal.md、对应能力 spec.md 或 design.md，区分临时来源、仓库相对路径、版本和历史；没有材料如实显示，不用样例或其他需求替代

### Requirement: 方案完成后提交 PR，合并核对后转正

人工 MUST 确认需求和方案的当前版本；AI 随后将临时工作区的确认文件带入项目可写的提案分支，执行提交和推送并提供 PR 标题、正文。人工 MUST 创建、评审和合并 PR，再告知平台；平台核对默认分支实际文件及版本后才成为正式提案，不自动创建或合并 PR。

#### Scenario: 准备需求 PR
- **WHEN** 当前需求、方案及人工确认齐备
- **THEN** 提交同一 Change 的 proposal.md、全部能力 spec.md、design.md 及必要资料，不直接推默认分支，不把共享只读项目当个人开发目录；缺失、过期、仓库不符或同名冲突时阻塞

#### Scenario: 提交、合并通知与核对
- **WHEN** AI 已推送分支或人工告知 PR 已合并
- **THEN** 推送与 PR 创建／合并分别记录；人工通知后获取实际默认分支并核对目标提交和完整文件版本，兼容 merge／squash／rebase；只登记地址或勾选不能转正
- **AND** 需求 PR 合并只完成提案入库，不表示实现完成、不占用 SR 并行名额、不归档 Change，不把尚未实现的增量提升为已实现规格

### Requirement: 正式需求在各自项目中自由修改和提交

正式需求已合入项目仓库。开发者 MUST 在自己启动的 `omp dev_web` 中配置自己可访问、同仓库且可写的 Git 项目路径后，才可修改项目、开发 SR 或执行 Git；业务访问者不能借用 Web 所有者的路径。正式需求可以在自己的 Git 项目中自由修改、提交，不要求返回 A 的提案讨论、重新走提案 PR 或以首个 SR 开始为由禁止修改。

#### Scenario: 自由修改与版本事实
- **WHEN** A 或 B 要修改已入库的正式需求、方案或代码
- **THEN** 在自己的 Web 和 Git 项目中修改、提交，并以仓库内容和提交版本为准；共享目录仍只读，查看资料不自动改写文件。已有执行记录、报告和会话保留历史，不能把旧报告冒充对新提交的验证
- **AND** C、D 即使在 A 的 Web 中输入合法账号或给聊天发送改代码指令，也不获得开发路径、项目写入或 Git 操作能力；必须自行启动自己的 Web 并配置自己的 Git 路径，才属于开发入口

### Requirement: 共享记录和个人开发目录的边界

共享项目目录内容 MUST 只读，供需求和方案讨论参考；路径配置可由管理员 `j00808874` 修改，其他账号只能查看。修改路径须保持同一项目仓库身份和已有业务关联，不移动已生成材料或替换个人开发路径。开发人员按工号和项目登记服务端可访问的 Git 开发仓库，校验仓库对应关系和可写性。SR 的分支、worktree、基点和会话 MUST 在开始时固定，后续查看或修改个人目录不重绑已有工作。

#### Scenario: 不同同事接手和并行
- **WHEN** 同事开发已入库提案中的依赖就绪 SR
- **THEN** 读取同一共享需求版本，在自己的开发仓库创建该 SR 独立分支、worktree 和会话，只按当前 OMP Web 内的状态检查 SR 并发、依赖及既有默认名额；不考虑另一个 Web 对同一 SR 的重复开发，不建立跨 Web 占用约束
- **AND** 不复制来源人的绝对代码目录或聊天文件；元数据统一保存共享数据库，真实目录和 Git 操作失败如实保留

### Requirement: 业务访问区分正式需求与提案会话

C、D 在 A（j00808874）的 Web 中可以讨论需求提案，包含当前需求或方案讨论；聊天由 A 的 OMP 保存，不写共享业务库。相同访问者打开正式 IR、其 SR 或验收入口时，中间 MUST 不展示开发聊天，显示说明原因和修改途径的只读空态，不读取或展示 A 的开发历史，也不提供开发输入和执行控件。共同使用 A 的 Token 不代表共享其正式需求会话。其他 Web 仍只读提案材料。

右侧材料 MUST 独立于上述会话权限，展示完整 IR 的 OpenSpec 需求文件、技术 design.md 及全部 SR 的 spec.md。正式需求读取仓库材料，提案读取临时工作区；不能用聊天为空、尚未开始 SR 或当前阶段无产物解释为没有需求材料。选择 SR 后只显示该 SR 自身的规格和对应开发阶段文件；返回 IR 才浏览整份需求文件。

正式需求的访客空态需说明：当前访问他人的 OMP Web，开发聊天不向访客展示；完整需求、技术设计和各 SR 规格在右侧阅读。需要调整需求时通过新建需求提案讨论；需要改代码时，由开发人员启动自己的 OMP Web、登录自己的工号并配置开发项目路径后处理。该说明不替代或禁用需求提案的聊天，也不恢复材料区已删除的操作按钮。

材料目录严格随对象切换：IR 只显示 OpenSpec proposal.md、全部 SR 的 specs/<capability>/spec.md 和 IR 技术 design.md，不显示开发阶段产物；每个 SR 只显示自己的 spec.md 和自己所选开发阶段／轮次的文件，提案 SR 仅显示自己的规格，不混入 IR 或其他 SR 的文件。业务需求 Agent 仅修改需求相关文件，design.md 由方案职责维护，不修改开发计划、完成报告、UT/ST、交付文件或代码。
