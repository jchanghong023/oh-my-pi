# spec-driven-orchestration

## Purpose

规定面向单个开发者的 `/dev` 协同开发模式：固定需求、方案、计划、执行四个 Agent，由程序检查真实文件、格式及最低字段，在用户明确决定后交接原文并切换阶段。Agent 负责工程工作，程序不以文件存在证明软件正确。正式需求唯一权威为 `openspec/specs/`，博客仅作说明；接入其他已有 Markdown 需求权威的项目时保留其原文，不建立竞争性主规格。

## Requirements

### Requirement: 独立能力与开发模式的边界

OMP MUST 保留独立 OpenSpec、Superpowers、JCH 及普通会话能力；用户须先显式进入 Dev，再以 `/dev new <需求内容>` 建立固定的需求、方案、计划、执行四阶段流程。进入模式、配置及需求接受均不代表业务实施或软件验收。

#### Scenario: 独立能力与开发模式的详细边界

- **WHEN** 用户使用独立能力或进入 Dev
- **THEN** 以下职责、来源及授权边界适用：
  - 独立内置 OpenSpec 的 CLI、默认 `spec-driven` schema、模板工厂及解析、校验、合并、归档等底层能力 MUST 与固定上游 1.15.0 一致；OMP 通过 `omp openspec` 封装，不要求另装 OpenSpec，不只复制说明文字，不依赖开发机绝对路径。Dev 单独使用 `omp-spec` 需求 schema，阶段职责及权限仍由 Dev 控制。
  - 固定来源为 OpenSpec 1.15.0、Superpowers 7.0.1（`2ce8aa15d05bd57213e6f746f953aafb7ded7a8b`）；JCH `jch-grill-me` 的真实 `SKILL.md` 和 `agents/openai.yaml` 一并交付并绑定来源修订；固定版本不代表平台验收通过。
  - Dev 执行阶段必须由实施子代理按测试先行实施，并由独立审查子代理审查，不因此增加阶段、强制提交或固定修复轮次。
  - 独立 OpenSpec 不依赖 Dev 状态、Team 或批准；独立同步归档不代表软件交付。`openspec-verify-change` 不要求 Dev 记录，也不改变 Dev 验收状态。
  - 普通 bug 修复若预期行为未变，不强制修改需求或新建 change。普通代码实施、原生 task／reviewer、独立 Team／Goal、SDK、TUI 与其他宿主保持原语义，不附加 Dev 阶段状态、系统规则、后台工作或证据采集。
  - Dev 不提供轻量跳阶段变体，不强制 Team，不建立第五阶段、逐任务状态机或强制 Git 提交。启用能力、进入模式或批准计划不扩大项目规则及工程授权，不隐含 commit、push、PR、合并、发布或不可逆操作授权。

#### Scenario: 独立需求维护

- **WHEN** 用户未进入 Dev 而请求维护需求
- **THEN** 独立 OpenSpec 不创建 Dev 流程、不要求四阶段批准；实际写入范围及授权由用户和项目规则确定，需求接受不代表软件已实现

#### Scenario: 显式启动

- **WHEN** 用户进入 Dev、读取恢复状态或查看保存配置
- **THEN** 不自动调用模型、启动 Team 或 Goal；只有进入成功后有效的 `/dev new <需求内容>` 才创建新流程并启动需求 Agent

### Requirement: 包内技能发现与资源兼容

OMP MUST 复用既有发现、补全、按需读取与资源授权，不因四阶段简化改变独立技能行为。

#### Scenario: 技能发现与资源兼容的详细边界

- **WHEN** 会话发现、手动调用或读取包内技能与命令资源
- **THEN** 以下发现范围、资源授权及兼容约束适用：

| 范围 | 技能 | 规则 |
| --- | --- | --- |
| 普通模型可发现 | 固定上游全部 Superpowers 技能 | 默认索引提供名称与描述，正文按需读取 |
| 按当前目录发现 | 固定上游 OpenSpec 的十二项 `openspec-*` 技能 | 当前会话工作目录直接有 `openspec/` 目录时提供名称和上游描述，正文按需读取；其他目录仅手动调用 `/skill:<name>` |
| 普通会话仅手动调用 | `jch-grill-me` | 保留原资源和显式调用，不默认发现；Dev 需求代理必须自动注入，正文置于系统提示最后 |

OpenSpec 目录条件不向父目录查找，普通同名文件不满足条件，每次发现／重载重新计算，不依赖进程全局 cwd。普通会话可按技能引用读取包内 Superpowers 资源，不要求逐项显式调用；Dev 阶段仍遵循其准确资源授权与工具权限，进入 `/dev` 输入模式本身不授予资源权限。其他隐藏技能仍按既有规则授权。

独立 `omp openspec init`、`update`、选项及工具安装能力遵循固定上游，默认 schema 为原生 `spec-driven`；`omp-spec` 是供 Dev 使用的独立需求 schema，不替换或裁剪原生默认 schema。Dev 需求阶段仍只生成获授权的 proposal／增量规格，其他阶段及原有写入、用户批准和验收边界不因原生能力恢复而扩大。

Superpowers 的技能、上游插件及扩展保留固定版本原始文件，不为 OMP 改写工具名称、子代理名称或脚本调用；依赖宿主提供的能力及实际可用性不改变上游基线。

#### Scenario: 普通会话发现

- **WHEN** 用户启动普通会话或重载技能
- **THEN** 普通会话提供全部包内 Superpowers 技能索引；跨技能引用可读取对应资源，原生宿主与 Dev 阶段授权边界仍适用

### Requirement: 四个固定 Agent 与真实文件门禁

OMP MUST 仅设置需求、方案、计划、执行四个固定阶段 Agent，各有独立、可持续对话及可恢复原生历史的 SDK 会话，承接原生模型、上下文与工具能力。角色状态仅为无代理、需求、方案、计划、执行；同一时刻仅一个活动阶段 Agent。忙碌、错误及停止进度依据实际原生运行情况显示，待验收及待收尾保留必要约束，不增加代理角色或重复持久化运行状态。

#### Scenario: 四个固定 Agent 与文件门禁的详细边界

- **WHEN** Dev 建立阶段、读取正式材料或用户请求推进
- **THEN** 阶段职责及原格式产物如下，单能力变更共五个正式文件，一个变更可含多个能力增量规格：

|阶段|职责|正式产物|
|---|---|---|
|需求|调查事实，澄清目标、范围、非目标、约束及可观察验收行为|`openspec/changes/<change-id>/proposal.md` 与 `openspec/changes/<change-id>/specs/<capability>/spec.md`|
|方案|基于确认需求调查可行方向，说明范围、实现思路、取舍、风险和验证方向|`docs/superpowers/plans/YYYY-MM-DD-<change-id>-solutions.json`|
|计划|将确认需求及选定方案转成执行范围、任务、依赖、修改位置及验证安排|`docs/superpowers/plans/YYYY-MM-DD-<change-id>.md`|
|执行|在批准范围内实施、验证、调试及完成必要审查并如实报告|`docs/superpowers/plans/YYYY-MM-DD-<change-id>-completion.md`|

- **AND** 需求 Agent 加载原 OpenSpec instructions，需求文件真实、可读、非空且通过原生结构校验；已有明确 Markdown 需求权威继续原位维护，proposal／增量描述变更并引用原权威，不复制第二套主规格，也不以原权威替代这两个正式产物
- **AND** 需求阶段不提前写实现方案、计划或业务代码，方案及计划阶段不提前实施；澄清回答不等于最终需求批准，材料原文不升级为系统授权
- **AND** 需求 Agent 必须自动注入包内原版 `brainstorming` 与 `jch-grill-me` 全文，顺序为 Brainstorming 在前、Grill-me 在系统提示最后，无需用户另行调用技能；新建及恢复需求会话均适用，资源授权仅限该会话。两项技能用于当前阶段需求澄清，不越权生成方案、计划、额外设计文件或自动推进阶段；冲突的澄清提问方式以最后注入的 Grill-me 为准。普通会话的 Superpowers 发现与引导不改变技能原文或 Dev 阶段权限
- **AND** 新需求的需求 Agent 必须至少提出一个与请求相关的问题，等待用户回答后再撰写需求；不得询问可从工作区取得的事实。方案、计划、执行 Agent 不向用户提问或要求额外确认，以已批准输入与可用证据工作；确有缺口时直接报告阻塞，不编造答案。原生 `/dev next` 的用户阶段批准不变。方案 Agent 不自动注入 Brainstorming／Grill-me，直接依据已确认需求调查并写出完整候选与推荐；需求、计划及执行所需技能由宿主自动注入，非需求阶段的固定职责约束置于技能正文之后，覆盖冲突技能步骤
- **AND** 计划 Agent 自动注入原 `writing-plans` 中执行交接章节之前的正文，跳过要求用户选择执行方式的 `Execution Handoff`；执行 Agent 自动注入原 `subagent-driven-development` 全文，不以 `executing-plans` 替代。新建及恢复阶段会话均适用，准确资源授权限定当前会话，不递归自动启用其他阶段技能。子代理驱动仍受 Dev 获批范围、既有工作区、正式产物及用户验收边界约束，不创建工作树、逐任务状态文件、强制提交或自动验收
- **AND** 不生成额外交接、确认、逐任务状态或计划 JSON 文件；必要流程持久状态不属于新的正式交付材料，不建立逐任务证据执行引擎

#### Scenario: 阶段子代理提示词与简化规则一致

- **WHEN** Dev 使用需求、方案、计划或执行子代理的角色、阶段请求及协作提示词
- **THEN** 相关提示词 MUST 一致采用当前阶段职责和六个新 Dev 入口，不指导调用旧命令、创建工作树、另建流程或消息协议，不要求用户管理另一套聊天
- **AND** 只在阶段进入时要求完整必要材料；同阶段普通追问直接续聊，不强制每句重读全部未变化文件、写出或重写正式产物，产物缺失不妨碍正常澄清，实际产物检查仍集中在 `next`
- **AND** Team 仅按方案阶段进入规则启动，Goal 仅由用户在当前执行会话手动使用；提示词不再依赖已删除的 Dev Goal 配置或 `useGoal` 开关，不按聊天轮次创建、重建或删除 Goal，不恢复旧的转述、重复回复或自动批准行为
- **AND** 四阶段 Agent 及其内部协作者的提示词禁止调用当前未开放的工具、禁止提交与推送；计划阶段使用可用只读工具及只读 `scout` 调查，不调用未开放的 `bash`，不得将提交或推送列为计划步骤。计划正文保持有效 Markdown，不附加与需求无关的助手／工具控制标记或未完成调用；这些提示约束不扩大阶段工具权限或替代已有程序守卫

#### Scenario: Wiki 检索不扩大写入权限

- **WHEN** 需求或方案 Agent 调查企业术语、规范或技术约束
- **THEN** 两者均可直接使用原生只读 `wiki` search／grep，复用当前 profile 既有索引，不仅向 Team 子代理开放；没有索引时如实说明，不自动建库
- **AND** 检索不开放索引管理、shell 或可写子代理，不扩大写入白名单；需求只写本次需求材料及原有明确需求权威，方案只写指定方案 JSON，计划及执行工具范围不因此变化，非授权业务写入被拒绝

#### Scenario: 前三阶段使用只读 Scout

- **WHEN** 需求、方案或计划 Agent 需要并行调查
- **THEN** 可使用原生 `task` 派发只读 `scout`，获取真实调查结果；不能派发其他代理或授予写入、命令执行、可写工具与子代理派生权限，也不得创建工作树
- **AND** Agent 定义覆盖、工具注入和其他调用参数不得绕过只读边界；失败如实返回，不降级为可写代理
- **AND** 子代理工作属于当前 Dev 流程，忙碌、停止及结清遵循原生生命周期；方案 Team 开关及仅进入方案时讨论的规则不变，执行阶段工具范围不变

#### Scenario: 前三阶段只能修改对应文档本体

- **WHEN** 需求、方案或计划 Agent 调用 write／edit 修改当前阶段白名单中的文档
- **THEN** 宿主在工具执行前核对精确授权路径，并拒绝目标文件或工作区根以下任一父目录上的符号链接、Windows junction（包括指向工作区内部及悬空目标的链接）；已有目标必须是硬链接数为一的普通文件，不因路径字符串匹配而允许修改别名指向的业务文件
- **AND** 未经授权的业务文件保持不变；普通目录下尚不存在的授权文档仍可创建，已有普通授权文档仍可编辑；需求阶段合法能力目录的 spec.md 通配授权及已有 Markdown 需求权威规则不扩大
- **AND** 此限制只用于前三阶段的文档写入，不改变执行阶段实施业务代码的权限，也不禁止只读检查已有链接

#### Scenario: 方案候选完整且可选择

- **WHEN** 用户通过 `next` 检查正式方案产物
- **THEN** 文件为真实 JSON，根字段 `candidates` 为非空数组，每项含非空字符串 `id`、`title`、`content`；ID 唯一且不含空白，`content` 为完整方案 Markdown
- **AND** 根字段 `recommendedCandidateId` 为非空字符串且精确匹配一个候选 ID，单候选亦需明确推荐；方案 Agent 向用户说明推荐及理由。至少提供一个合理候选，不强制凑多个；界面按可读方案展示完整内容、ID 和推荐，详情可查看原始 JSON；用户仍决定选择，程序不按关键词或候选数量裁定方案优劣

#### Scenario: 计划与当前工作区一致

- **WHEN** 计划 Agent 制定或在回退后调整计划
- **THEN** 正式计划真实、可读、非空并沿用 Superpowers `writing-plans` 原格式，不增加另一计划 JSON、逐任务流程文件或自制栏目门禁
- **AND** 区分当前已完成、需调整及未完成工作；回退导致范围变化时说明本流程已有改动哪些保留、调整或撤销；计划写出不自动启动实施

#### Scenario: 完成报告如实呈现交付

- **WHEN** 执行 Agent 交付完成报告
- **THEN** 正式 Markdown 标题为 `# 完成报告`，含非空的 `## 完成情况`、`## 验证结果`、`## 未完成项`；没有未完成项时明确写“无”
- **AND** 报告说明实际完成内容、真实验证命令与结果、失败或未运行的检查、限制及未完成事项，不把未运行写成通过，不以报告存在证明软件正确

#### Scenario: Team 仅在方案阶段内部协作

- **WHEN** 用户通过 `next` 成功进入方案阶段，按当前 Team 配置开始方案工作
- **THEN** 关闭 Team 时由方案 Agent 正常工作；开启时复用原生只读 Team 编排、既有 `team.members` 及并发约束，以完整确认需求、原始用户决定及本轮反馈开展讨论，方案 Agent 根据完整结果形成正式候选
- **AND** 主聊天始终属于方案 Agent，不切到成员、不把普通用户输入广播给全部成员；协作通过原生工具或协作显示呈现，不启动其他外层阶段、不实施业务代码、不替用户选择方案
- **AND** Team 不可用、配置不全、失败、取消、无可采用候选或正式候选冒用不可采用方向时显示真实原因并受阻，不静默改成单 Agent 并声称 Team 成功；原生调查审查保留，不额外增加 Dev 审查门禁
- **AND** Team 只在进入方案阶段时启动讨论；同阶段普通追问直接继续当前方案会话，不重新派发讨论，查看、配置、恢复、返回界面或 `back` 也不自动重跑；选择方案仅授权制定计划，不授权实施
- **AND** Team 失败或取消后若需重新讨论，先结清自有工作，再通过已有 `back` 返回需求、`next` 重新进入方案；不增加同阶段 Team 重跑、自动重试或专用重试入口，普通追问及当前方案会话的原生重试不重新派发 Team

#### Scenario: Goal 属于当前执行 Agent

- **WHEN** 用户进入执行阶段，或在该阶段手动开启原生 Goal
- **THEN** 进入执行默认正常执行，不因批准计划或保存 Dev 配置自动创建 Goal；用户手动启用的 Goal 只作用于当前可见执行会话，仍受完整获批计划、上游批准及项目规则约束
- **AND** Dev 不提供 Goal 配置、冻结规则或独立 Goal 状态，不按聊天轮次创建、删除、重建或改写 Goal；目标设置、状态、预算及暂停继续均沿用原生 Goal 生命周期，不另开外层会话、不增加 Dev 入口或阶段
- **AND** 恢复 Dev 不自动启动 Goal；用户显式手动操作才可继续其原生工作，不能借 Goal 绕过批准版本、待验收及待收尾限制
- **AND** 退出、丢弃及必要停止统一通过原生能力结清 Goal 和自有任务；用户停止当前执行后不得立即自动续轮，待验收或待收尾不得继续自主写入，Goal 完成不等于验收、不自动同步归档
- **AND** 范围内修复直接在当前执行会话续聊，是否使用 Goal 由用户按原生能力手动控制；变更范围先回退重新确认

#### Scenario: 缺失产物不得推进

- **WHEN** 当前 Agent 仍在澄清、尚未生成文件，或声称文件已完成
- **THEN** 不从自然语言、贴在聊天中的材料或文件存在推断批准；正常澄清不自动作为流程错误，用户执行 `next` 时才针对本次推进报告缺口
- **AND** 推进检查实际文件存在、可读、非空、对应格式和最低字段、所依赖上游批准版本及消息调用结清；失败保留阶段、对话、输入、附件及文件，状态区给出具体文件和原因，诊断可供当前 Agent 使用而无需用户手工复制
- **AND** 读取材料保留真实路径、完整内容和基于实际字节的版本

#### Scenario: 合法文件仍等待用户

- **WHEN** 当前阶段已生成符合最低结构的正式文件
- **THEN** 不因 Agent 回复、文件存在、勾选或本地 commit 自动检查并推进；阶段产物检查集中在用户的 `next`，该明确命令检查通过后才记录决定并转换

#### Scenario: 同次批准启用阶段内部能力

- **WHEN** 用户以 `next` 确认需求，且已保存的 Team 开关为开启
- **THEN** 成功进入方案后使用原生 Team，仍只有四阶段及原正式文件，不额外批准、不自动验收归档；批准计划只进入正常执行，不代替用户手动开启原生 Goal

#### Scenario: 未提交开关不产生工作

- **WHEN** 用户仅编辑 Team 开关后取消或关闭面板，或在普通文字中提及 Team 配置参数
- **THEN** 不改变已保存 Team 值，不因配置编辑启动模型、Team 或 Goal；重新打开显示保存值，未保存勾选或普通说明不代替配置保存及阶段批准

### Requirement: 完整文件与用户原始确认交接

OMP MUST 在阶段进入时直接交接完整正式原文件、选定候选 ID、原始用户决定及相关 Team 配置，不以摘要代替原文，不额外调用模型总结，不生成交接或确认文档，不调用 `AgentSession.handoff()`；同阶段追问复用原生会话，不反复注入全部未变化材料。批准只对当时确认的材料版本有效。

#### Scenario: 方案选择完整交给计划

- **WHEN** 用户通过 `next` 明确推进阶段
- **THEN** 后继获得所需完整确认需求、完整方案文件（含全部候选）、选定 ID、完整计划及其他必要正式材料、用户原始确认命令与相关批准说明、实际采用配置
- **AND** 原始决定逐字传递，不裁剪改写，不借模型或聊天摘要交接；尤其方案到计划不能只传选中候选，下一阶段不依赖上一 Agent 未保存记忆

#### Scenario: 同阶段追问不重复交接

- **WHEN** 用户在当前阶段继续澄清、补充、追问或明确要求批准范围内修复
- **THEN** 直接向当前原生阶段会话提交本次输入及受支持附件，不再次包装为阶段进入，不重复注入全部未变化文件或重新启动 Team
- **AND** 实际变化且当前工作需要的材料按需读取；仍在继续依赖批准的工作前核对上游版本，聊天续接不代替新范围批准

#### Scenario: 已批准文件发生变化

- **WHEN** 继续依赖上游批准的工作、阶段推进或恢复前核对本流程正式需求材料、方案、计划及完成报告中所需的已有文件版本
- **THEN** 检查只返回匹配结果、变化文件及具体原因，不直接修改阶段、执行回退、重写批准原文或清除流程；失配材料不能继续依赖旧批准。此自动版本检查仅覆盖正式材料，不扫描、快照或自动检测业务代码及整个工作区的变化，不承诺发现业务代码的外部修改
- **AND** 原生准入据失配结果阻止新的依赖工作，包括内部协作及 Goal 续轮，已有工作按停止规则收尾；状态区说明须返回哪个阶段重新确认，允许查看、解释、退出或丢弃，不自动跳阶段、不回滚文件、不把普通聊天视为重新授权

#### Scenario: 保留的下游文件必须重新核对

- **WHEN** 上游变化后存在旧方案、计划或报告，或回退后重新进入执行
- **THEN** 根据当前需求及真实工作区重新核对适用性，可复用仍适用内容并更新需调整部分，不只因格式合格恢复本轮有效性，不默认全部重做，也不沿用旧进度跳过新增要求
- **AND** 处理本流程旧改动不得波及无关用户改动

#### Scenario: 修复使旧报告失去本轮资格

- **WHEN** 用户在最终验收前明确要求在批准范围内进行业务修复或继续实施
- **THEN** 撤销旧完成报告的本轮验收资格；更新后的报告及验证结论对应当前交付，不适用的旧验证明确标为过期，验证范围按实际变化确定，完成后重新等待最终 `next`

### Requirement: 工程责任、完成报告与验收后收尾

OMP MUST 由执行 Agent 负责获批范围内工程实施、验证、调试及必要审查；用户决定是否接受交付及披露限制。执行阶段 `/dev next` 仅由用户触发，作为唯一最终验收；程序直接调用原生 OpenSpec 同步、校验和归档，不调用模型、委派执行代理或增加收尾代理。执行 Agent 不得自行触发 `next`、代替用户验收或执行同步归档。

#### Scenario: 工程责任与验收收尾的详细边界

- **WHEN** 执行 Agent 实施获批计划
- **THEN** 必须通过原生 `task` 委派实施子代理，先写并运行针对本次行为的失败测试，再实施并运行通过；完成后必须派独立 `reviewer` 子代理审查并处理获批范围内问题。实施、验证或审查未完成时如实披露，不伪造结果；受项目权限或测试授权限制时报告阻塞。不得硬编码审查模型、修复轮次、本地提交、隔离分支或发布账本
- **AND** 不擅自改写已批准需求、方案或计划以适应实现；需要变更范围先回退相应阶段，内部任务受执行授权及停止规则约束，普通 Team／reviewer／独立 Goal 不因此删除

#### Scenario: 报告后等待验收

- **WHEN** 执行 Agent 完成当前交付并等待用户验收
- **THEN** 角色仍为执行，保留待验收的必要写入限制，Goal 及其他可写工作停止自主推进；普通询问反馈仅允许解释或只读调查，不开放写工具及可写后代，完成报告结构在最终 `next` 时核验，不因每轮回复自动核验文件或切换阶段
- **AND** 只有用户明确要求在已批准范围内修复或继续实施才恢复执行，不要求已废弃的 `repair` 命令；变更需求、方案或计划范围必须先回退
- **AND** 状态及详情如实显示未完成、验证失败和未验证项，不概括成全部完成或全部通过；用户可通过最终 `next` 接受已披露的实际结果及限制，程序不替用户裁定业务全部正确，不增加第二次验收确认

#### Scenario: 验收后正常同步归档

- **WHEN** 用户在执行阶段明确提交最终 `next`，且运行条件及正式材料版本符合要求
- **THEN** 程序不调用模型、不经执行 Agent，直接运行原生 OpenSpec 收尾；原生项目将相应增量同步到主规格，已有 Markdown 权威继续原位维护，不生成竞争性主规格，使用原生 `--skip-specs` 避免向影子权威写入
- **AND** Markdown 修改采用保留原文件、标题和定位的最小补丁，不用原生整块覆盖非原生章节；定位歧义、来源变化或无法无损维护时受阻
- **AND** 使用真实原生同步、校验、归档引擎；同步已完成、获准跳过或采用 Markdown 权威时用 `--skip-specs` 防止重复同步，不以 `--no-validate` 或直接移动目录伪造归档
- **AND** 只归档需求变更，方案、计划、完成报告保留在原计划目录；必要收尾全部成功后结束流程、回到无代理，保留原生聊天、正式产物及工作区配置，解除冻结供后续配置或 `new` 继承
- **AND** 原生归档已将需求文件搬移到实际归档位置时，使用已发生的原生归档结果定位同一材料；这不属于外部材料失配或丢失，恢复、查询及剩余收尾不重建原 change 目录、不另选日期重新生成路径、不重复执行已完成归档，方案、计划和报告位置不变
- **AND** 验收不隐含提交、推送、PR、合并或发布授权
- **AND** 所有必要收尾成功后，固定状态区明确提示本次验收完成及实际需求归档路径；不得仅回到无代理而无完成回执，不暗示已执行未适用的同步或业务验证

#### Scenario: 收尾失败

- **WHEN** 同步或归档失败或部分成功
- **THEN** 保留执行角色及当前执行 Agent 的原生会话和历史，不因收尾失败结束会话；保留必要待收尾业务事实及实际成功进度，状态区显示真实失败，完整诊断可通过原生详情查看并供当前执行代理按需读取，不要求用户手工复制，不得标为完成
- **AND** 不自动调用模型或启动修复；用户再次 `next` 时仍由程序只继续原验收未完成的收尾，不重新验收、重跑业务任务、重启 Goal 或重复已完成步骤；冲突操作不排队，不增加确认、代理或阶段，Team 仍按执行阶段不可修改，不另存冻结、临时错误或忙碌字段

#### Scenario: 收尾失败后的对话与限定修复

- **WHEN** 收尾失败后用户主动在当前执行会话提问、反馈或明确请求修复
- **THEN** 沿用原生执行会话直接对话，必要时读取本次失败诊断及实际进度，不重复交接全部材料或把状态摘要复制成聊天；一般询问和反馈只允许解释及只读调查
- **AND** 只有用户明确要求修复，才允许处理不改变已验收正式材料、范围及交付内容的直接收尾故障，不恢复普通业务任务、Team 或 Goal 自动推进；单纯收尾故障修复不按业务修复撤销原验收
- **AND** 执行 Agent 不自行提交 `next`、运行同步归档或决定重试；修复后仍停留执行及待收尾状态，用户再次 `next` 才由程序继续剩余收尾
- **AND** 若需改变已验收材料或交付内容，按既有回退、重新确认或 `drop` 后新变更规则处理，不借故障修复绕过版本和部分收尾限制

#### Scenario: 收尾副作用限制回退与修改

- **WHEN** 流程处于待收尾
- **THEN** 未产生实际同步或归档结果时，可按相邻回退规则返回相应阶段修改并重新确认
- **AND** 一旦产生实际结果，停止普通业务修改，拒绝常规 `back`；只允许不改变已验收范围和内容的直接收尾故障修复、`next` 重试、`/dev` 退出或 `drop` 放弃跟踪
- **AND** `drop` 明确显示既有同步、归档及文件变化不会撤销，不补做归档、不伪报交付完成

#### Scenario: 已验收内容外部变化

- **WHEN** 收尾期间本流程已验收的正式需求材料、方案、计划或完成报告的内容版本与原验收不一致
- **THEN** 拒绝沿用旧验收继续收尾，明确说明材料不一致；用户可恢复原已验收材料后重试，或 `drop` 后通过新变更处理，不静默采用变化内容
- **AND** 自动保护只复用上述正式材料已有的版本依据，不新增业务文件清单、代码版本快照或全工作区变化检测；业务代码被外部修改不在本项自动检测承诺内，不将材料版本一致表述为业务代码未变化或软件正确

### Requirement: 共用控制器、输入与用户决策

OMP MUST 由共用原生控制逻辑管理工作区流程、阶段、Team 配置、原生阶段会话关联及动作；TUI 和仍开放的其他入口只呈现和调用同一事实，不建立第二状态机或消息系统。输入、附件、队列、草稿、历史、压缩及停止复用 OMP 原生能力。所有 Dev 控制命令针对提交时的流程和阶段，阶段批准只能来自有效明确命令，不能来自普通文字或 Agent 回复。

#### Scenario: 共用控制器与用户决策的详细边界

- **WHEN** 用户提交 Dev 命令
- **THEN** 仅保留以下入口；普通模式下任何 `/dev …` 子命令均拒绝并提示先 `/dev`，不得隐式进入、创建流程或执行部分操作：

|---|---|
|`/dev`|进入或退出 Dev|
|`/dev config`|手动查看及保存工作区的方案 Team 开关|
|`/dev new <需求内容>`|创建新流程并进入需求|
|`/dev next [方案ID]`|检查材料、记录当前阶段明确决定并推进；执行阶段最终验收|
|`/dev back`|返回相邻上一阶段|
|`/dev drop`|结清自有工作，丢弃流程并清除 Dev 配置，保留文件及代码|

- **AND** 缺参、不适用参数及未知子命令直接报错，不交给模型、不执行部分操作；旧 `help`、`start`、`status`、`answer`、`confirm-spec`、`choose`、`confirm-plan`、`revise-plan`、`accept`、`repair`、`amend`、`change-solution`、`cancel-message`、`pause`、`resume`、`cancel` 等 Dev 命令从注册、分发、补全、帮助、界面动作及代理提示词中彻底删除，不保留别名、兼容处理或旧命令专属迁移提示，调用时与其他未知子命令一样拒绝；普通 OMP 原生命令不在删除范围
- **AND** 四角色及其流程内协作的用户回复、问题、理由和交付说明使用中文；代码、命令、路径、标识符、协议字段和原始输出不翻译，不改变普通会话语言

#### Scenario: 无代理的普通输入失败且保留内容

- **WHEN** Dev 中无活动阶段 Agent，用户发送普通文字或附件
- **THEN** 不调用模型、不加入任何 Agent 对话，保留输入及附件，提示先 `/dev new <需求内容>`；配置、清除状态、详情及 `/dev` 退出仍可用，`next`、`back` 不可用

#### Scenario: 原始输入与明确决定分离

- **WHEN** 有活动阶段 Agent，用户发送普通内容，包括“可以”“继续”“同意”
- **THEN** 输入交给当前 Agent，在当前阶段权限内澄清、讨论和完善材料，不自动确认需求、选择方案、批准计划或最终验收；待验收及待收尾另遵守只读和修复限制

#### Scenario: 草稿与消息绑定提交归属

- **WHEN** 用户编辑草稿、切换支持保留草稿的原生界面或忙碌时提交普通消息
- **THEN** 不自动发送未提交内容，不把草稿带到错误阶段；草稿恢复沿用原生能力，不新增独立 Dev 草稿持久化要求
- **AND** 忙碌消息及回执完全沿用原生会话和队列，绑定提交时流程、阶段及实际 Agent；Dev 不维护独立消息队列、草稿副本、消息处理状态机或持久化收据状态，旧阶段输入不交给后继，退出或 `drop` 通过原生能力取消未处理输入
- **AND** 迟到结果不改变当前状态、不混入新阶段对话、不复活旧代次或把当前 provider 错误伪报成功；无结果与明确错误分别呈现，不用旧回复代替本轮失败

#### Scenario: next 统一四次明确决定

- **WHEN** 用户在当前阶段提交有效的 `/dev next [方案ID]`
- **THEN** 需求阶段确认当前需求并按 Team 配置进入方案；方案阶段确认选中候选并进入计划；计划阶段批准当前计划及范围并进入默认正常执行；执行阶段接受当前交付及报告披露结果限制后收尾
- **AND** 本命令集中检查当前阶段真实产物及仍依赖上游批准，进入方案前在状态区明确本次 Team 配置；多候选必须提供有效 ID，单候选可省略，无效 ID 报错并给出查看入口，其他阶段不允许方案 ID 参数；计划批准不自动创建或启动 Goal
- **AND** 新阶段建立成功且必要状态保存后才报告成功并正常开始工作；再次进入已经工作过的阶段依据当前输入核对可复用材料及剩余工作，不从旧文件格式推断本轮完成

#### Scenario: back 仅返回相邻阶段

- **WHEN** 空闲且未受实际收尾副作用限制时提交 `/dev back`
- **THEN** 执行返回计划、计划返回方案、方案返回需求；需求及无代理拒绝回退
- **AND** 展示目标阶段可恢复原生历史，不自动调用模型、重跑 Team 或启动 Goal；撤销返回阶段及下游确认、候选选择、执行批准或验收资格，保留有效更上游批准
- **AND** 保留全部正式文件、已有代码和配置值，不回滚；按目标阶段重定可修改开关，用户完善后以 `next` 重新确认

#### Scenario: 忙碌及冲突控制不延迟执行

- **WHEN** 模型、工具、Team 成员、Goal 推进或普通消息尚未结清
- **THEN** 拒绝 `next`、`back`，允许 `/dev` 退出或 `drop` 发起停止并等待收尾；主 Agent 回复结束不足以证明所有自有工作结清
- **AND** 校验、切换、恢复、退出、清理、同步归档等控制操作进行时拒绝冲突操作，不排队；重复 `next` 不得在首次切换后变成下一阶段批准，重复收尾不得执行两次
- **AND** 配置可查看，但保存仍受冻结及冲突约束，不将当前不允许的修改延迟到其他阶段生效

#### Scenario: 阶段建立或保存失败不伪报成功

- **WHEN** 目标阶段尚未成功建立或所需状态保存失败
- **THEN** 保留原阶段、原生对话和输入，不提前改变阶段所决定的 Team 可修改性，不报告创建或切换成功，不启动依赖未保存变更的模型或 Team，也不自动启动 Goal
- **AND** 真实已经发生的文件修改保留，不声称回滚；成功进入目标后才发生的模型、网络、Team 或 Goal 错误保留目标阶段并显示实际错误

#### Scenario: 取消尚未结清

- **WHEN** 原生停止、退出或 `drop` 已请求取消，但旧消息、调用、内部协作、Goal 推进或 runtime 尚未真实结清
- **THEN** 不把取消回执或界面终态当完成清理，不准许冲突转换或新流程接管；保留原 owner 的收尾及可重试失败事实，不影响其他会话

#### Scenario: drop 停止清除但不回滚

- **WHEN** 当前控制者执行 `/dev drop`
- **THEN** 与 `/dev` 退出共用原生停止结清流程：停止新派发及 Goal 续轮、取消未处理原生排队输入、停止并结清当前 Agent、Team 成员、Goal、执行子任务及其他 Dev 自有工作，再清除流程与 Team 配置，回到无代理及默认关闭，可重新配置或新建；不增加额外确认，不删除或复制原生 Goal 状态
- **AND** 保留正式产物、原生聊天、代码、配置文件、其他工作区修改及既有同步归档结果；不回滚、提交、推送、验收或补做归档
- **AND** 仅有保存配置时仍可清除；确实无任何 Dev 状态时提示无需清除；停止或清理失败显示真实错误并可重试，旧工作未结清不得新建，状态已清但旧任务尚存时再次 `drop` 可重试收尾

#### Scenario: 原生操作只影响可见阶段

- **WHEN** Dev 中使用原生取消、重试、压缩上下文或会话管理操作
- **THEN** 支持的会话级操作只影响当前可见阶段 Agent，全局设置仍按原作用域；执行阶段可手动使用该会话的原生 Goal，不视作新增 Dev 子命令，也不作用于隐藏普通会话；不支持或超出阶段权限的操作明确说明原因
- **AND** 新建、切换、分叉、删除原生会话以及切换工作目录须先成功退出 Dev；退出失败阻止操作，不静默清除、复制或转移工作区流程

### Requirement: TUI 主聊天与固定状态区

OMP MUST 只在无代理、需求、方案、计划、执行五种阶段状态间切换当前原生会话及工作权限，聊天显示和交互沿用 OMP。唯一新增常驻显示是输入框上方的三行 Dev 固定区；不得另建 Dev 聊天组件、渲染体系、决策或阶段面板。配置及详情复用原生交互，不自动弹窗、不追加状态聊天或抢焦点，在 100×28、120×36 及尺寸调整下仍可用。

#### Scenario: 主聊天使用原生阶段会话

- **WHEN** Dev 显示当前阶段或用户切换阶段
- **THEN** 仅展示当前 Agent 的原生用户消息、流式回复、工具调用及结果，沿用原生折叠、滚动、复制和受支持附件显示；不复制到父会话后重新输出，不经另一主代理转述、汇总或重复输出，不混入其他阶段和迟到结果
- **AND** 切换后展示目标阶段会话，返回已有阶段展示其可恢复原生历史；Team 主聊天仍属方案 Agent，Goal 主聊天仍属执行 Agent

#### Scenario: TUI 三行固定区与提醒的详细边界

- **WHEN** Dev 状态刷新
- **THEN** 覆盖固定区域，不不断增加聊天行；各行内容如下：

|行|内容|
|---|---|
|1|Dev 模式、五种角色之一及当前阶段、实际运行情况，以及 `Team：开/关`，不显示 Dev Goal 开关|
|2|当前主要操作及明确后果|
|3|当前错误、进度或简短提示|

- **AND** Team 开关显示已保存值，不冒充讨论正在运行；忙碌、错误及按钮可用性根据当前阶段和实际原生运行事实显示，不另存推导字段；主要操作在方案时明确“确认候选并进入计划”，计划时明确“批准计划并开始执行”，执行时明确“验收当前交付并同步归档”
- **AND** 命令结果及流程校验错误显示在状态区，不反复作为 Agent 对话追加；未解决错误不被无关进度或帮助提示覆盖，长内容截断并提供明确详情入口
- **AND** 当前原生会话或 Team 讨论可由原生中断键停止时，运行中主要操作提示该键可停止当前操作并保留流程，不将 `/dev drop` 显示为首要操作；其他不可中断的控制操作显示等待结清，不伪称可用中断键
- **AND** 方案阶段主要操作显示 `/dev next [方案ID]`；缺失正式需求规格或完成报告时，状态区优先说明缺失材料及补齐后重试，保留原始诊断；`/session` 的 Dev 详情位于普通会话信息之前，便于查看完整路径与错误
- **AND** 阶段会话空闲或已停止时不计入运行中子代理徽章，普通子代理的计数与生命周期不变

#### Scenario: 查看详情无工作或批准副作用

- **WHEN** 用户主动打开详情、查看材料或操作帮助
- **THEN** 通过 OMP 既有的原生查看及交互能力读取完整产物、全部候选及 ID、失败原因、配置说明和操作帮助，不另建 Dev 专用材料或决策界面，不调用模型、不发送草稿、不提交批准、不切阶段

#### Scenario: 自动提醒保留编辑内容

- **WHEN** 流程等待、报错或回复结束，引起自动状态提醒
- **THEN** 只更新独立状态区，不自动打开详情、决策或配置面板，不抢输入焦点，不清除或发送草稿及附件；原有自动等待弹窗规则不再适用

#### Scenario: 小终端与输入保持可达

- **WHEN** 在 100×28、120×36 使用 ANSI／native TUI 或调整终端尺寸
- **THEN** 固定状态区、输入框、手动配置、主要操作和详情仍可用，长内容可按原生方式查看，中文操作提示可达，状态区不遮挡输入

### Requirement: 原生 dev 的桌面后端合同

OMP MUST 让仍开放的 ZCode Dev 入口投影并调用同一工作区原生控制者，遵守本能力规定的唯一流程、控制权、六入口、仅 Team 配置、五种角色、原生聊天、批准、统一停止及最小状态恢复清理。协议兼容、查询订阅及身份按 `zcode-app-server`；不另建桌面工作流、页面、阶段、消息队列、批准 API 或执行引擎。

#### Scenario: 原生 dev 桌面后端的详细边界

- **WHEN** 协商扩展的客户端查询或操作 Dev
- **THEN** 每次成功 `new` 对应独立流程身份；角色仅无代理、需求、方案、计划、执行，忙碌、错误和停止情况来自实际原生运行，验收、收尾及完成结果如实呈现而不新增角色；仅进入、配置、查看和独立技能不创建流程行
- **AND** 投影真实接收 Agent、原生消息及工具事件、当前动作、完整材料与版本、选定 ID 及已保存 Team 值，Team 可修改性及按钮可用性由阶段和实际运行推导，不持久化其副本，不新增 Dev Goal 配置或状态；仍走既有 sendText／builtin 入口，由原生 owner 核对归属及准入，不重建允许表或消息系统，不伪造任务进度、审查配额、成功或空内容

#### Scenario: 冷历史读取与显式恢复分离

- **WHEN** 客户端仅打开列表、详情、历史或产物
- **THEN** 只投影真实观测，不创建阶段 AgentSession、不取得控制权或写权限、不恢复批准或执行、不启动模型；缺失 owner 的活动观测明确为历史或未知，不伪装仍在运行
- **AND** 只有用户显式进入 Dev 才按有效工作区状态、唯一控制权及版本核对恢复；有效状态可继续同一流程，不从历史材料猜测批准，也不借动态工作流 journal 接管

#### Scenario: 两种界面共用事实

- **WHEN** TUI 与已有其他入口观察同一工作区流程
- **THEN** 获取同一原生阶段、材料、配置、消息和动作事实；新增协议事实须显式 capability 协商，旧客户端不收到未知字段或枚举，动态工作流定义、引擎、actor、journal 及恢复合同保持不变
- **AND** 主聊天切换、配置及固定三行的界面验收对象为 TUI，不要求另建桌面 UI，后端结果不替代未进行的桌面验收

### Requirement: 工作区归属与唯一控制权

OMP MUST 将 Dev 配置和流程归属工作区，每个工作区最多一个未结束流程，并且只有成功进入 Dev 的一个 OMP 实例拥有控制权；即使无代理也受该控制者管理。保存配置可独立于活动流程存在。

#### Scenario: Git 工作树统一身份

- **WHEN** 从同一 Git 工作树的不同子目录、路径别名、分支或不同普通 OMP 会话使用 Dev
- **THEN** 使用同一配置及流程，不形成多个独立运行；换分支不新建流程，后续依据实际文件核对；普通会话切换不创建、复制或清除 Dev 状态
- **AND** 同仓库不同工作树的配置、流程、控制权及清理互相隔离；非 Git 项目以进入 Dev 时确定的工作目录为范围

#### Scenario: Dev 不创建工作树

- **WHEN** 进入、新建、推进、回退、恢复或执行 Dev 工作，包括阶段内部 Team 和执行子任务
- **THEN** 使用进入时已有工作目录或 Git 工作树，Dev 及相关子代理不得自动创建工作树，不要求用户先建工作树，不把创建工作树或调用工作树隔离工作流作为前置、计划步骤或阶段任务
- **AND** 已有不同工作树仍按各自工作区独立处理，不因 Dev 改造全局禁用用户在 Dev 外的原生 Git 或独立工程能力

#### Scenario: 其他实例不能操作被占用工作区

- **WHEN** 其他实例尝试进入已由控制者占用的同一工作区
- **THEN** 显示已占用，保留原普通聊天界面、输入及附件，不创建、推进、回退、丢弃、清除流程或修改配置，不把占用判成恢复失败
- **AND** 配置共享不绕过控制权或冻结；原控制者成功退出后释放控制权，后继实例使用同一状态；原进程消失不证明旧任务已停止，仍检查旧工作收尾

#### Scenario: 进入前拒绝未结清普通工作或冲突模式

- **WHEN** 普通模式执行 `/dev`
- **THEN** 先检查普通会话模型调用、工具任务、待执行输入结清及工作区控制权；未结清时拒绝进入、保留原界面，提示停止或等待，不自动停止其他窗口或无关会话
- **AND** 已有不能共存的 Plan、Loop、Goal、Vibe 等外层模式时明确要求先退出，不静默覆盖；内部执行 Goal 不改变此互斥边界

#### Scenario: 进入成功才切换主聊天

- **WHEN** 控制权、读取和必要恢复清理均成功
- **THEN** 恢复已有配置及流程，或进入无代理，才清除主聊天的普通会话显示并展示 Dev 当前阶段内容，不删除普通历史、不自动启动模型或内部协作
- **AND** 占用、读取或清理错误导致进入失败时保留原普通界面，不先清空后留下不可操作页面

#### Scenario: 退出须结清保存并释放

- **WHEN** Dev 中再次执行 `/dev` 或正常关闭所属实例
- **THEN** 与 `drop` 共用原生停止结清流程：停止新派发、取消未处理原生输入、停止并结清当前 Agent、工具、Team 成员、执行子任务、Goal 及其他 Dev 自有工作；必要业务状态保存成功，控制权成功释放后才报告安全退出，不借退出删除原生 Goal 状态
- **AND** `/dev` 退出恢复进入前普通聊天显示，保留配置、当前阶段、批准、原生聊天和正式文件，不验收、同步、归档、提交或回滚；停止、保存或释放失败显示真实错误并可重试
- **AND** “已请求停止”不等于“已经停止”，停止失败保留可重试事实，不回滚已发生写入，不影响无关进程；强退或崩溃不作为任务已结束的证据

### Requirement: 工作区配置及阶段冻结

OMP MUST 让 `/dev config` 复用原生交互，仅管理“方案阶段使用 Team”开关，不另建 Dev 专用配置界面。开关默认关闭，保存在当前已有工作区的 Dev 状态中，Git 项目按当前已有工作树保存；仅保存成功生效。可修改性按当前阶段和实际运行判断，不另存冻结字段，不设置 Dev Goal 配置，也不为保存配置创建工作树。

#### Scenario: 手动配置面板的保存与取消

- **WHEN** 无代理或已有流程时打开配置面板
- **THEN** 只显示已保存 Team 开关、不自动弹出；原生选择器标明当前已保存值并默认选中该值，取消或关闭不改变值，保存成功才生效，不因查看或保存创建流程、调用模型、Team 或 Goal
- **AND** Team 成员配置及原生 Goal 设置仍沿用原生能力和原有作用域，不在 Dev 面板另建配置或 Goal 状态
- **AND** 保存失败显示真实错误，不显示成功、不以未保存值启动讨论；控制操作进行中或旧工作尚未结清时拒绝冲突保存，不延迟生效

#### Scenario: 当前阶段决定配置可修改范围

- **WHEN** 用户查看或保存 Team 配置
- **THEN** 依据当前阶段和实际运行直接判断可修改性；关闭状态同样受阶段限制：

|当前阶段|方案 Team|
|---|---|
|无代理|可修改|
|需求|可修改|
|方案|不可修改|
|计划|不可修改|
|执行（包括必要验收及收尾约束期间）|不可修改|

- **AND** `next` 成功进入方案时采用已保存 Team 值；进入失败仍在原阶段时不改变原可修改性，界面说明不可修改原因及须返回需求阶段，不另存冻结标志、采用配置副本或按钮可用性

#### Scenario: 回退改变可修改性但不重置值

- **WHEN** 执行退回计划、计划退回方案、方案退回需求，或退出重启后恢复
- **THEN** 执行退计划和计划退方案仍不能改 Team，方案退需求后才可改；保持保存值，根据恢复后的同一阶段重新推导限制，不通过退出、重启或换普通会话绕过

#### Scenario: 配置独立保存且新流程继承

- **WHEN** 无代理保存 Team 配置、随后 `new`，或退出重启后再进入
- **THEN** 仅有配置是有效状态，不算已有流程、不阻止新建；`new` 继承保存值，不重新关闭，仅配置恢复时仍无代理
- **AND** `new` 初始化失败保留此前配置，正常完成保留值并因回到无代理而可修改；`drop` 或确实不可恢复的旧 Dev 状态清除成功后 Team 恢复关闭，不清除原生 Team 通用配置或原生 Goal 状态

### Requirement: 新流程标识与初始化

OMP MUST 仅在工作区无未结束流程且旧 Dev 工作已结清时接受 `/dev new <需求内容>`，继承保存配置、自动生成合法唯一 change ID、固定正式产物路径，先保存必要状态并建立可对话的需求阶段，再报告成功并启动 Agent。

#### Scenario: 新流程不覆盖保留材料

- **WHEN** 控制者在 Dev 无代理时以非空需求正文及可选原生支持附件执行 `new`
- **THEN** 自动分配合法唯一变更 ID，不覆盖现有、已丢弃流程保留或已归档文件；创建时固定正式路径，跨日期、回退及恢复均沿用；原生归档正常搬移需求材料是例外，按其实际归档结果定位，不重建原目录
- **AND** 仅保存配置不阻止新建；已有未结束流程则拒绝并提示继续或先 `drop`，旧任务尚未结清时拒绝新工作；需求为空或参数非法不执行部分创建

#### Scenario: 初始化失败只清除本次失败流程

- **WHEN** 需求阶段成功建立前初始化失败
- **THEN** 只清除本次失败流程状态，保留此前保存配置及本次已经创建的正式文件，清理成功才返回无代理；清理失败显示实际错误，不假装可重新创建

#### Scenario: 已建立阶段中的模型失败可继续

- **WHEN** 需求阶段已成功建立后模型、网络或服务失败
- **THEN** 保留需求阶段及配置，显示真实错误，允许用户主动继续或重试，不按初始化失败清除有效流程

### Requirement: 状态保存与正常恢复

OMP MUST 保存恢复工作区配置及流程所需事实，复用原生阶段聊天记录而不另建聊天系统；必要保存成功是相关配置或控制操作报告成功并启动依赖工作的前提。显式进入时恢复有效状态并核对材料，但不自动执行工作。

#### Scenario: 保存必要流程事实

- **WHEN** 保存配置或流程状态
- **THEN** 仅保存必要业务事实：当前阶段、Team 配置、流程与变更标识、方案选择、原生阶段会话关联、批准原文及正式材料已有字节版本、必要验收和同步归档收尾信息（包括已经发生的原生归档结果）；不另存业务代码版本或工作区快照，可由既有引用稳定取得的信息不重复保存
- **AND** 不另存 Team 冻结字段、按钮可用性、采用配置副本、忙碌标记、临时错误、消息队列、Goal 状态或完整正文；批准原文是必要授权记录，不因禁止复制正文而删除，普通消息和原始需求沿原生会话读取，完整材料沿正式文件读取，不建立第二聊天或消息系统
- **AND** 无流程仅保存 Team 配置是有效状态，不判损坏或误认为已有流程

#### Scenario: 必要状态保存失败

- **WHEN** 必要状态无法保存
- **THEN** 显示真实错误，不报告配置修改、创建或切换成功，不启动依赖未保存变更的工作，不以未保存 Team 值启动讨论，也不自动启动 Goal；已经发生的文件修改如实保留，不声称回滚
- **AND** 已保存状态后来确实无法恢复时，按无效状态自动清除规则处理，不承诺保存后永不损坏

#### Scenario: 显式进入恢复但不重放工作

- **WHEN** 再次进入 Dev、OMP 重启或机器重启后用户进入 Dev，存在有效可恢复状态
- **THEN** 恢复保存 Team 值及必要业务事实，有流程时恢复同一流程和阶段、仅配置时进入无代理；核对必要文件及批准版本，检查只返回结果，由准入阻止依赖失配批准的新工作，不由检查改变阶段或重写批准原文
- **AND** 原生运行事实不足时明确中断或未知，不读取持久忙碌及临时错误副本伪装仍在运行或成功；依据当前阶段和真实运行重新推导配置可修改性及动作可用性
- **AND** 展示可用原生历史，不自动发送草稿、重放工具、重跑 Team 或启动 Goal；用户主动续聊或手动原生操作才继续当前阶段，不构成下一阶段批准，必要待验收及待收尾限制继续有效

#### Scenario: 原生聊天历史缺失不丢弃有效流程

- **WHEN** Dev 必要状态有效但原生阶段聊天记录不可用
- **THEN** 保留 Team 配置、流程及批准事实，提示历史不可用，不伪造对话或声称记得缺失内容；用户主动继续后依据正式产物、已保存原始批准及用户当前输入开展本阶段工作，不依赖 Dev 聊天正文副本，不因此清除有效状态

### Requirement: 无效旧状态自动清除与任务收尾

OMP MUST 仅在旧 Dev 状态确实无法恢复时自动清除无效流程、其配置及失效控制关联，不要求额外确认、迁移、备份或手工修复；清除不表示任务已经停止、交付完成或文件回滚，未结清旧任务继续阻止冲突的新 Dev 工作。

#### Scenario: 确实无法恢复时自动清除

- **WHEN** 升级不兼容、损坏、必要状态缺失或其他原因使旧状态确实不可恢复
- **THEN** 直接清除旧 Dev 状态及其中 Team 配置，开关恢复默认关闭；不操作原生 Goal 状态，升级本身不是清除理由，可恢复状态继续使用
- **AND** 清除成功且无未结清旧任务时显示“旧 Dev 状态无法恢复，已清除；配置已恢复默认，可执行 `/dev config` 或 `/dev new <需求内容>`。”

#### Scenario: 自动清除仅涉及旧 Dev 状态

- **WHEN** 执行无效旧状态清除
- **THEN** 保留原生聊天、需求权威、proposal／增量、方案、计划、报告、代码、配置文件、其他工作区修改、既有同步归档结果、其他工作区 Dev 状态及原生 Team／Goal 自身作用域通用配置
- **AND** 不从残留文件猜测或恢复旧批准；后续新流程从需求阶段开始，不将清除算作验收或交付完成

#### Scenario: 可恢复错误不得误清状态

- **WHEN** 工作区被其他实例控制，或存在模型／服务／网络／Team／Goal 错误、普通 `next` 校验失败、产物缺失需修改、批准材料变化、原生聊天缺失但必要状态有效、仅有保存配置、普通 `new` 初始化失败
- **THEN** 不按旧状态恢复失败清除有效配置及流程，按各自错误或初始化失败规则处理

#### Scenario: 清除失败或旧任务未结清

- **WHEN** 清除失败，或状态已清除但仍有可确定属于旧 Dev 的工具、Team 成员或其他任务运行
- **THEN** 清除失败显示真实错误，不声称可新建；已清但有旧任务时显示“旧状态已清除，旧任务收尾中，暂不能新建 Dev。”
- **AND** 旧任务停止并结清前阻止新 Dev 工作，保留可重试收尾方式，仅处理旧 Dev 自有任务、不影响无关进程；任务收尾是活动状态，不增加代理角色
