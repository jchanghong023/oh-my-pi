# spec-driven-orchestration

## Purpose

规定面向单个开发者的 `/dev` 协同开发模式：固定需求、方案、计划、执行四个 Agent，由程序检查真实文件、格式及最低字段，在用户明确决定后交接原文并切换阶段。Agent 负责工程工作，程序不以文件存在证明软件正确。正式需求唯一权威为 `openspec/specs/`，博客仅作说明；接入其他已有 Markdown 需求权威的项目时保留其原文，不建立竞争性主规格。

## Requirements

### Requirement: 独立能力与开发模式的边界

OMP MUST 保留独立 OpenSpec、Superpowers、JCH、普通会话和 Dev 专有 Agent 能力。新建开发需求只使用浏览器八阶段流程，业务文档检查必经；终端 `/dev` 进入 Dev 并打开网页，当前 TUI 此后只接受再次 `/dev` 退出，不提供旧 Dev 终端子操作。只处理新流程，不提供旧模式兼容、旧流程迁移或旧状态恢复。

#### Scenario: 独立能力与开发模式的详细边界
- **WHEN** 用户使用独立 OpenSpec、Superpowers、JCH 或普通 OMP 会话
- **THEN** 不附加工作台阶段、批准、后台工作或证据采集；普通 bug 修复若预期行为未变，不强制新建 OpenSpec change
- **AND** 内置 OpenSpec 固定上游 1.15.0，Superpowers 固定 7.0.1（`2ce8aa15d05bd57213e6f746f953aafb7ded7a8b`），JCH 保留真实 SKILL.md、agents/openai.yaml 及来源修订；这些来源及非本次变更的解析、校验、同步、合并和归档语义保持，不依赖开发机绝对路径
- **AND** 保留原生 spec-driven schema；Dev 仍使用包内 omp-spec。固定版本不代表平台验收通过

#### Scenario: Dev 模块隔离且不影响普通 OMP

- **WHEN** 用户正常使用 OMP，或显式开启并使用 Dev
- **THEN** Dev MUST 作为单独功能模块，普通 OMP 启动、会话和命令不得隐式启动 Dev 服务、任务或持久状态；只有显式 Dev 入口启动工作台，具体任务与业务状态变更仍须相应明确操作，打开或查看页面不启动模型、Team 或 Goal
- **AND** Dev 会话、临时模型／主题设置、工具限制、锁及生命周期 MUST 隔离于普通 OMP，不串用普通聊天、不覆盖其配置、不阻塞无关普通工作；停止、取消和关闭只处理 Dev 自有资源
- **AND** 为 Dev 扩展的公共接口 MUST 仅保留必要且默认关闭的接入，非 Dev 调用者保持原默认语义及配置作用域；Collab 网页适配优先复用普通接口，不使普通 TUI、命令、模型、Team、Goal 或 Collab 回归。不新增网页全局 Team／模型角色配置入口，继续既有配置方式；不另建角色权限或重复配置系统

#### Scenario: 网页 Dev 与当前普通 TUI 互斥

- **WHEN** 用户在正常 OMP 中输入 `/dev`
- **THEN** 普通模型、工具或自有任务尚未结清时 MUST 拒绝进入并提示先停止或等待，不悄悄取消普通任务；进入成功后当前 TUI MUST 拒绝所有普通命令和输入，只允许再次 `/dev` 退出，不同时操作网页 Dev 与普通 TUI
- **AND** 再次 `/dev` MUST 通过既有 native stop／settlement 结清 Dev 自有工作后恢复普通原会话；失败则保留 Dev 及真实原因，不提前恢复普通输入。退出不取消需求、不回滚 Git、不删除材料，关闭网页也不退出 Dev 或停止后台工作
- **AND** 不为跨模式并存建立普通会话快照、克隆或额外 `/new`／move／dispose 并发架构；借用根资源时仅保留防止 Dev Actor 重置 root provider 所需的最小显式 inherited 接入，原生 Provider／MCP 生命周期及安全 Git 边界不放松

#### Scenario: 独立需求维护
- **WHEN** 用户未启动工作台而维护需求
- **THEN** 独立 OpenSpec 默认 mini 仍只生成 proposal 和 specs，不生成 design／tasks，不实施或验证软件，不要求 Dev、Team 或阶段批准；已有 change 和显式选择 schema 不强制转换
- **AND** 用户自行实施验证后显式请求同步或归档，沿用原生校验；不使用 --no-validate 或手工移动伪造归档，不以需求归档代表软件交付

#### Scenario: 开发人员手动提供业务文档直接起步
- **WHEN** 用户在网页新建需求，包括直接提供已有业务 Markdown
- **THEN** 采用业务需求、开发需求、技术方案、开发计划、开发与 UT、ST测试、提交与 PR、测试人员测试八阶段；导入文档可直接 Next 进行程序格式检查，不必启动业务访谈
- **AND** 不提供跳过业务文档检查或四个开发阶段材料的轻量路径；末三阶段为人主导的流程阶段，不要求新增三个专有 Agent

#### Scenario: 显式启动
- **WHEN** 用户通过 /dev、omp dev 或重复打开网页查看需求及配置
- **THEN** 不自动创建需求、调用模型、启动 Team／Goal 或接受软件交付；新建及继续须来自明确人员操作

#### Scenario: 功能复用不等于旧模式兼容
- **WHEN** 新工作台替换 Dev 专属 TUI
- **THEN** 保留原生专有 Agent、模型、工具、材料格式及适用权限，只改变交互入口和本次明确修改的流程；不保留旧模式入口、迁移或恢复要求，也不借此删除已有用户文件和 Git 历史
- **AND** 进入网页或批准计划不隐含 commit、push、PR、合并、发布或不可逆操作授权；只有相应明确确认及 dev-browser-workbench 规定的标记确认授权对应操作

### Requirement: 包内技能发现与资源兼容

OMP MUST 复用既有发现、补全、按需读取与资源授权，不因浏览器八阶段流程改变独立技能行为。

#### Scenario: 技能发现与资源兼容的详细边界

- **WHEN** 会话发现、手动调用或读取包内技能与命令资源
- **THEN** 以下发现范围、资源授权及兼容约束适用：

| 范围                                               | 技能                                                                                                                                                    | 规则                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 普通会话及其子代理、Dev 业务及开发前三阶段及其后代仅手动调用 | 所有包内固定上游 Superpowers 技能，包括 `using-superpowers`                                                                                             | 不出现在模型自动发现索引，保留用户显式调用；Dev 执行代理及其所有递归子代理可自动发现并按需读取                                                                                                                                                                                                                                                                                                                                                     |
| 普通模型可发现                                     | 固定上游 OpenSpec `core` 中五项技能：`openspec-propose`、`openspec-explore`、`openspec-update-change`、`openspec-sync-specs`、`openspec-archive-change` | 以包内固定上游 `init --tools oh-my-pi --profile core` 在隔离默认配置下生成的 `SKILL.md` 为基准，生成时按 core 集合解析可选工作流分支；CLI 调用统一写为 `omp openspec ...`，同步工具声明及兼容性说明，并仅为独立需求流程适配正文和描述。同步保留原生行为，归档只检查需求完整性及原生格式，不要求实施或软件验证。任意目录提供名称与描述，正文按需读取，通过原生 `/skill:<name>` 调用；`openspec-apply-change` 及其他非所列技能不注册、不提供手动调用 |
| 普通会话仅手动调用                                 | `jch-grill-me`                                                                                                                                          | 保留原资源和显式调用，不默认发现；Dev 业务及需求代理均必须自动注入，分别使用业务与开发需求职责约束，固定职责及访谈停止规则置于技能正文之后                                                                                                                                                                                                                                                                                                                                                         |

包内 Superpowers 的隐藏和执行阶段可见性仅适用于包内资源；同名非包内自定义技能继续遵循既有发现、调用与优先级规则，不被此例外覆盖。用户显式调用包内技能仍沿用原生调用及授权规则；Dev 阶段技能注入、资源授权和工具权限不因发现范围变化而扩大，打开 `/dev` 网页本身不授予阶段资源权限。

配套五项 `/opsx-propose`、`/opsx-explore`、`/opsx-update`、`/opsx-sync`、`/opsx-archive` MUST 在任意工作目录通过既有文件 slash-command 发现、补全及执行链路提供。五份命令文件以同一次固定上游 `init --tools oh-my-pi --profile core` 在隔离默认配置下生成的 `.omp/commands/opsx-*.md` 为基准，CLI 调用统一写为 `omp openspec ...`，正文和描述仅按独立需求流程适配；同步保留原生行为，归档只检查需求完整性及原生格式。命令使用既有参数展开、扩展禁用及同名用户／项目命令覆盖机制；不另建分发表、不自动执行 init、不向用户项目复制文件，不注册 `/opsx-apply` 或其他可选工作流命令，也不改变 `/dev` 的阶段权限或批准边界。

独立 `omp openspec init` MUST 复用固定上游初始化实现，但由 OMP 封装层固定使用 `--tools=none`：技能和命令已内置，不再交互选择工具，也不在用户项目或全局目录生成技能和命令；显式传入 `--tools` 也不得重新启用生成。目录、配置、目标路径、语言及原生错误处理保持不变，不主动删除已有技能和命令。独立 OpenSpec 默认 schema 为 `mini`；现有 change 及显式选择的 schema 不强制转换，原生 `spec-driven` 资源仍保留。`update` 及其余 CLI 能力遵循固定上游；`omp-spec` 是供 Dev 使用的独立需求 schema，Dev 需求阶段仍只生成获授权的 proposal／增量规格，其他阶段及原有写入、用户批准和验收边界不变。

Superpowers 的技能、上游插件及扩展保留固定版本原始文件，所有包内 Superpowers `SKILL.md` 均增加 `disable-model-invocation: true`；未来同步或更新上游资源时同样保留该字段。不为 OMP 改写工具名称、子代理名称或脚本调用。依赖宿主提供的能力及实际可用性不改变上游基线。

#### Scenario: 普通会话发现

- **WHEN** 用户启动普通会话或重载技能
- **THEN** 所有包内 Superpowers 技能均不出现在普通会话及其子代理的模型自动发现索引，但保留用户显式调用；Dev 业务、需求、方案、计划代理及其后代同样不可自动发现，原生宿主与 Dev 阶段授权边界仍适用

#### Scenario: 执行阶段递归发现

- **WHEN** Dev 执行代理或其任意深度的子代理发现或按技能引用读取包内 Superpowers 资源
- **THEN** 可自动发现全部包内 Superpowers 技能并按需读取，恢复执行会话及递归子代理同样适用；不改变阶段自动注入内容、工具权限或获批范围
- **AND** 同名非包内自定义技能仍按既有优先级生效，不因执行阶段的包内可见性改变

#### Scenario: 初始化不重复安装内置资源

- **WHEN** 用户运行 `omp openspec init [path]`，包括已检测到工具、显式指定工具或重复初始化
- **THEN** 仅执行原生项目初始化，建立必要的 `openspec/` 目录及配置，不生成技能和命令；保留已有自定义命令及配置，仍支持 `--language` 和 `--` 后的目标路径

### Requirement: Dev 需求 schema 固定为包内 omp-spec

OMP MUST 把 `omp-spec` 的唯一来源固定为随包内置 schema；项目或用户同名覆盖 MUST 被拒绝，不得静默改用另一套 Dev 工作流。

#### Scenario: 解析来源必须是包内 schema

- **WHEN** Dev 初始化新流程、需求阶段读取 OpenSpec 指令，或需求校验与归档前确认 schema
- **THEN** schema 解析结果 MUST 声明来源为包内，且其实际路径按真实路径比较等于随包内置的 `omp-spec` 目录，两者同时满足才可继续
- **AND** 不得接受工作区或用户目录中的同名 schema，也不得为通过检查而复制、改写或移动内置 schema

#### Scenario: 外部覆盖阻断流程

- **WHEN** `omp-spec` 被项目级或用户级 schema 覆盖，或解析结果来源不是包内
- **THEN** MUST 拒绝并阻断初始化、需求校验与归档，报错说明外部 schema 遮蔽了内置 schema，且须在不修改已有 change 的前提下解决冲突
- **AND** 不创建 change、不迁移或转换已有 change、不回退为其他 schema，也不报告成功

### Requirement: 包内 Superpowers 脚本执行入口

OMP MUST 通过 `omp superpowers <relative-script> [args...]` 提供包内技能脚本入口，只运行随包交付的脚本，不执行工作区任意脚本。

#### Scenario: 只运行包内清单内脚本

- **WHEN** 用户运行 `omp superpowers <relative-script> [args...]`
- **THEN** 只接受随包脚本清单中存在且位于 `skills/` 下的相对路径；其他路径 MUST 报“不是包内技能脚本”并拒绝执行
- **AND** 脚本参数原样透传，不解释为 Dev 命令或阶段操作

#### Scenario: 运行环境与外部工具

- **WHEN** 运行包内 JavaScript 或 shell 脚本
- **THEN** JavaScript MUST 由 OMP 内嵌的 Bun 执行，不依赖外部 Node；shell 脚本 MUST 要求 Bash 与 POSIX 工具，Unix 使用可用的 `bash`，Windows 使用 Git for Windows 的 Bash，WSL 的 `bash` 不适用；缺少 Bash MUST 报固定错误并失败
- **AND** MUST 在 PATH 前置包内运行时目录（Windows 另加所用 Bash 及其 POSIX 工具目录），并设置 `BRAINSTORM_DIR` 指向工作区下的 `.superpowers/brainstorm`
- **AND** Graphviz 等外部工具由脚本自行解析，其真实退出状态随脚本透传，不预先替换或伪造

#### Scenario: 缺参与帮助的退出码

- **WHEN** 未提供脚本参数，或提供 `-h`／`--help`
- **THEN** 缺参 MUST 把用法写入 stderr 并以退出码 2 结束；`-h`／`--help` MUST 把用法写入 stdout 并以退出码 0 结束
- **AND** 脚本的 stdout、stderr 与退出码 MUST 原样透传；入口自身异常（例如 Bash 缺失或脚本不存在）MUST 写入 stderr 并以退出码 1 结束

#### Scenario: 中断转为脚本中止

- **WHEN** 脚本执行期间收到 SIGINT 或 SIGTERM
- **THEN** MUST 转为中止信号并等待脚本结束，再按实际结果退出；不得遗留子进程，也不得把中断报成成功

### Requirement: 四个固定 Agent 与真实文件门禁

OMP MUST 复用业务、需求、方案、计划、执行五个现有专有 Agent 及各自独立、可持续对话的原生 SDK 会话、模型、上下文和工具能力。八个业务阶段不等于八个 Agent；已有文档直接检查时不强制建立业务会话，末三阶段只由原生能力辅助人员。忙碌、错误及停止进度依据真实运行，不用业务完成标记伪造执行状态。

#### Scenario: 四个固定 Agent 与文件门禁的详细边界

- **WHEN** Dev 建立阶段、读取正式材料或用户请求推进
- **THEN** 前五阶段职责及原格式产物如下；每个开发需求须持有通过模板检查的业务文档，四个开发阶段沿用原正式材料，一个变更可含多个能力增量规格；Git 需求记录按 dev-browser-workbench 管理，不另建逐任务证据引擎：

| 阶段 | 职责                                                               | 正式产物                                                                                                |
| ---- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| 业务 | 面向懂业务、未必懂代码的人，结合业务知识检索和 Grill-me 澄清业务并编写详细文档 | 本需求的 `docs/business-requirements/<change-id>.md`；支持对话生成或导入现有 Markdown |
| 需求 | 调查事实，澄清目标、范围、非目标、约束及可观察验收行为             | `openspec/changes/<change-id>/proposal.md` 与 `openspec/changes/<change-id>/specs/<capability>/spec.md` |
| 方案 | 基于确认需求调查可行方向，说明范围、实现思路、取舍、风险和验证方向 | `docs/superpowers/plans/YYYY-MM-DD-<change-id>-solutions.json`                                          |
| 计划 | 将确认需求及选定方案转成执行范围、任务、依赖、修改位置及验证安排   | `docs/superpowers/plans/YYYY-MM-DD-<change-id>.md`                                                      |
| 执行 | 在批准范围内实施、验证、调试及完成必要审查并如实报告               | `docs/superpowers/plans/YYYY-MM-DD-<change-id>-completion.md`                                           |

- **AND** 需求 Agent 加载原 OpenSpec instructions，需求文件真实、可读、非空且通过原生结构校验；已有明确 Markdown 需求权威继续原位维护，proposal／增量描述变更并引用原权威，不复制第二套主规格，也不以原权威替代这两个正式产物
- **AND** 需求阶段不提前写实现方案、计划或业务代码，方案及计划阶段不提前实施；澄清回答不等于最终需求批准，材料原文不升级为系统授权
- **AND** 业务 Agent 的系统提示须面向业务人员，围绕场景、流程、业务规则、典型例子和业务验收预期访谈；需求 Agent 的系统提示须基于已确认业务材料（如有）及相关规格、代码、测试和配置探索问题，澄清开发目标、范围、约束及可观察验收；两者均区分已确认决定、建议和未决问题，不臆造用户意图或批准。宿主自动注入包内原版 `jch-grill-me` 全文，在其后注入 Dev 固定职责和访谈停止规则；默认按其调查、分轮提问和共同理解确认流程开展访谈，Dev 阶段权限及用户明确停止访谈优先于冲突的技能步骤。不注入 `brainstorming` 或 `openspec-explore`；新建及恢复业务与需求会话均适用，资源授权仅限该会话。用户可随时用自然语言停止访谈，停止后不再继续访谈提问，保留未决事项而不编造答案，并在阶段权限内遵循用户要求的后续动作；停止访谈不等于批准业务文档或开发需求、完成业务交付或推进阶段。访谈不得越权生成方案、计划、额外设计文件或自动推进阶段，不修改原技能正文
- **AND** 需求撰写须遵循宿主提供的 OpenSpec instructions 和模板，将 context／rules 作为约束而不复制正文；按变更范围调查相关既有需求、实现、测试、配置和文档，以证据确定范围及验收，区分现状、假设和拟议变更，明确指出与既有需求的冲突；每个受影响能力均写入指定增量 spec，关键证据缺失须说明，不编造未决答案。该原则直接写入 Dev 系统提示，不注入或修改原版 `openspec-propose` 技能

- **WHEN** Dev 为受限子代理开启 Goal 能力
- **THEN** 该子代理仍只拥有既有工具清单与读取范围，Goal 之外的调用继续被拒绝

### Requirement: Markdown 需求权威探测

OMP MUST 为沿用既有 Markdown 需求权威的项目确定唯一权威目录，并把该目录下的全部 Markdown 纳入需求物版本集合。

#### Scenario: 权威目录探测顺序与歧义

- **WHEN** Dev 建立新流程或读取需求物
- **THEN** MUST 依次检查 `docs-zh-CN/requirements`、`docs/requirements`、`requirements`，取第一个真实存在的目录作为唯一权威
- **AND** 同时存在多个候选 MUST 报歧义并阻断新建，不任选其一、不自动合并；检查候选时的非“不存在”错误 MUST 直接报错，不静默跳过

#### Scenario: 权威目录内容进入版本集合

- **WHEN** 权威目录内存在 Markdown 文件
- **THEN** 该目录下递归的任一新 `.md` MUST 纳入需求物版本集合，按相对权威目录的路径记录，与 proposal 及增量规格共同构成需求物版本
- **AND** 目录为空 MUST 报“无权威 Markdown 需求”并阻断；不复制原文、不改写原文件、不另建第二套主规格

### Requirement: 方案来源须可从原生阶段历史确证

OMP MUST 在读取正式方案时不仅校验格式，还须由宿主从真实原生单 Agent／Team 阶段历史及结果确证来源与候选可采用关系，并持久化绑定方案实际字节 hash 的最小事实；无法确证 MUST 阻断，不得降级为单 Agent 结果。历史仍可用时 MUST 继续核对，历史缺失时只可依赖已确证且版本匹配的事实与正式材料，不复制聊天或 Team 全文到 Git。

#### Scenario: 读取正式方案时核对来源

- **WHEN** Dev 读取正式方案 JSON，包括 `next` 检查及阶段交接
- **THEN** 宿主 MUST 从原生阶段历史中最近一次方案阶段进入记录确证角色为方案、该记录为阶段进入、且带有本轮 Team 开关状态，并核对真实原生结果；持久化方案字节 hash、全部候选 ID、可采用候选 ID、单 Agent／Team 来源及原生会话／entry 引用
- **AND** 这些事实只能由宿主确证后保存，不能信任模型自填、任意 JSON 或浏览器上传的来源声明；历史可用时仍核对，缺失时仅在已保存事实与实际方案 hash、候选集合匹配时继续，不重造历史或猜测批准
- **AND** 未有已确证事实、方案 hash 改变、候选集合不符或可用历史与已存事实冲突时 MUST 阻断并说明来源无法确证及需返回需求阶段重新进入；不能以历史缺失放宽来源检查，也不能把旧 hash 的事实用于修改后的方案

#### Scenario: Team 开启时每个候选必须可采用

- **WHEN** 原生历史或宿主已确证且与当前方案版本匹配的最小来源事实表明本轮方案由 Team 讨论产生
- **THEN** 每个正式候选 MUST 对应本轮一个可采用的 Team 候选，且其正文 MUST 包含该 Team 候选的原始 proposal 原文；宿主在保存可采用事实前从真实原生结果核对这两项，历史可用时仍复核
- **AND** 任一候选不满足 MUST 阻断并指出该候选 ID；不得改写候选 ID、裁剪原文或把失败、取消及不可采用方向写成正式候选，不因历史不可用静默降级；本轮未启用 Team 时不要求候选与 Team 结果对应

### Requirement: Dev 阶段会话的强制运行默认值

OMP MUST 在所有 Dev 阶段会话上强制一组运行默认值，且只作用于该会话，不写回用户或项目配置。

#### Scenario: 编辑模式强制整文件替换

- **WHEN** Dev 建立任一阶段 Agent 会话，包括新建与恢复
- **THEN** `edit.mode` MUST 被覆盖为 `replace`（整文件替换），显式压过用户设置及按模型变体回退
- **AND** 该覆盖不改写持久配置，普通会话仍按原设置解析

#### Scenario: 前三阶段关闭投机启动

- **WHEN** 业务、需求、方案或计划阶段会话执行其获授权的工具调用或派发任务
- **THEN** 工具与任务的投机启动 MUST 关闭，即使配置为开启
- **AND** 执行阶段沿用配置值；该关闭不改变阶段工具权限或阶段门禁

### Requirement: 完整文件与用户原始确认交接

OMP MUST 在阶段进入时直接交接完整正式原文件、选定候选 ID、原始用户决定及相关 Team 配置，不以摘要代替原文，不额外调用模型总结，不生成交接或确认文档，不调用 `AgentSession.handoff()`；同阶段追问复用原生会话，不反复注入全部未变化材料。批准只对当时确认的材料版本有效。

#### Scenario: 方案选择完整交给计划

- **WHEN** 用户通过 `next` 明确推进阶段
- **THEN** 后继获得所需完整确认需求、完整方案文件（含全部候选）、选定 ID、完整计划及其他必要正式材料、用户原始确认动作、输入与相关批准说明、实际采用配置
- **AND** 原始决定逐字传递，不裁剪改写，不借模型或聊天摘要交接；尤其方案到计划不能只传选中候选，下一阶段不依赖上一 Agent 未保存记忆

#### Scenario: 同阶段追问不重复交接

- **WHEN** 用户在当前阶段继续澄清、补充、追问或明确要求批准范围内修复
- **THEN** 直接向当前原生阶段会话提交本次输入及受支持附件，不再次包装为阶段进入，不重复注入全部未变化文件或重新启动 Team
- **AND** 实际变化且当前工作需要的材料按需读取；仍在继续依赖批准的工作前核对上游版本，聊天续接不代替新范围批准

#### Scenario: 已批准文件发生变化

- **WHEN** 继续依赖上游批准的工作、阶段推进或恢复前核对本需求已确认的业务文档、正式需求材料、方案、计划及完成报告中所需的已有文件版本
- **THEN** 检查只返回匹配结果、变化文件及具体原因，不直接修改阶段、执行回退、重写批准原文或清除流程；失配材料不能继续依赖旧批准。此自动版本检查仅覆盖正式材料，不扫描、快照或自动检测业务代码及整个工作区的变化，不承诺发现业务代码的外部修改
- **AND** 原生准入据失配结果阻止新的依赖工作，包括内部协作及 Goal 续轮，已有工作按停止规则收尾；状态区说明须返回哪个阶段重新确认，允许查看、解释、退出或丢弃，不自动跳阶段、不回滚文件、不把普通聊天视为重新授权

#### Scenario: 保留的下游文件必须重新核对

- **WHEN** 上游变化后存在旧方案、计划或报告，或回退后重新进入执行
- **THEN** 根据当前需求及真实工作区重新核对适用性，可复用仍适用内容并更新需调整部分，不只因格式合格恢复本轮有效性，不默认全部重做，也不沿用旧进度跳过新增要求
- **AND** 处理本流程旧改动不得波及无关用户改动

#### Scenario: 修复使旧报告失去本轮资格

- **WHEN** 用户在最终验收前明确要求在批准范围内进行业务修复或继续实施
- **THEN** 撤销旧完成报告的本轮验收资格；更新后的报告及验证结论对应当前交付，不适用的旧验证明确标为过期，验证范围按实际变化确定；第五阶段重新等待 Next，末三阶段仍由人员决定并点击标记，不恢复旧最终 `next` 终结语义

#### Scenario: 业务 next 完整交接而不替代开发需求

- **WHEN** 用户在业务阶段通过网页 Next 确认当前业务文档并继续开发
- **THEN** 需求 Agent MUST 获得完整业务文档、真实路径、基于实际字节的版本及用户原始确认，不以聊天摘要代替文档，也不把业务文档当作已批准的开发规格
- **AND** 需求阶段仍获得适用的原有 Markdown 需求权威和 OpenSpec instructions，不因已有业务输入而漏掉原有权威材料；原始请求沿本流程实际起步会话读取
- **AND** 继续依赖本流程业务确认前核对其文档版本；变更后要求返回业务阶段重新确认，不自动回退、改写批准或扫描业务代码变化

### Requirement: 已批准需求集合新增产物即视为变化

OMP MUST 把“已批准之后的任何新增需求产物”视为批准失效，即使已批准文件的字节未变。

#### Scenario: 新增未获批准的增量规格

- **WHEN** 需求已获批准后，出现新的 `openspec/changes/<change-id>/specs/<capability>/spec.md`
- **THEN** MUST 判为需求材料变化，并以“新增未获批准的需求产物”为原因阻断推进与续做，要求用户重新确认
- **AND** 不要求仍被批准的原文件被修改；不得把新增文件视为已批准范围

#### Scenario: 权威目录新增 Markdown

- **WHEN** 已批准后既有 Markdown 需求权威目录内新增任一 `.md` 文件
- **THEN** MUST 同样判为变化并阻断，原因指向该文件的实际路径

#### Scenario: 无法枚举已批准集合

- **WHEN** 已批准集合无法被枚举，例如权威目录不可读
- **THEN** MUST 判为不匹配并阻断，报出无法枚举的原因；不得当作匹配而继续依赖旧批准

### Requirement: 工程责任、完成报告与验收后收尾

OMP MUST 由执行 Agent 负责获批范围内实施、UT、调试和独立审查，人员决定接受结果。第五阶段 Next 只进入 ST，不最终验收或同步归档。需求同步、原生校验及归档 MUST 在第七阶段提交 PR 前经人确认执行；归档不是需求终态，不自动提交、推送、合并或标记已测试。

#### Scenario: 工程责任与验收收尾的详细边界
- **WHEN** 执行 Agent 实施获批计划
- **THEN** 通过原生 task 委派实施，先运行相关失败测试，再实施并验证；派独立 reviewer 审查并处理范围内问题，受权限或测试授权限制时如实报告阻塞
- **AND** 不硬编码审查模型、轮次、验证 ID、本地提交或隔离分支，不擅自改写已批准上游材料；报告如实保留未完成、未审查、未复审及未验证项，不以文件存在代替结果

#### Scenario: 报告后等待验收
- **WHEN** 执行 Agent 交付本轮完成报告
- **THEN** 停止 Goal 及其他可写工作的自主推进，普通询问只读；人员明确要求范围内修复才可继续，报告更新后重新等待第五阶段 Next
- **AND** Next 核对报告结构、上游批准和工作结清，进入第六阶段，不运行同步归档、不结束需求；程序不增加独立审查程序门禁或把 ST 预报为通过

#### Scenario: 验收后正常同步归档
- **WHEN** 人员在提交 PR 前明确确认需求同步和归档
- **THEN** 原生宿主在当前材料及批准有效时直接调用现有同步、校验和归档，不由模型自行发起、不增加收尾 Agent；实际需求权威继续唯一
- **AND** OpenSpec 项目同步相应增量；已有 Markdown 权威原位维护，避免向影子权威写入；按原生语义使用 --skip-specs 避免重复同步，不使用 --no-validate 或手工移动伪造成功
- **AND** 修改既有 Markdown 采用可无损定位的最小修改；定位歧义、来源变化或不可无损维护时明确阻塞
- **AND** 方案、计划及完成报告保留在原路径；需求按真实归档位置读取，文档与代码在人员确认范围内提交，不因归档本身隐含 commit、push、PR、合并或发布授权

#### Scenario: 收尾失败
- **WHEN** 第七阶段同步或归档失败或部分成功
- **THEN** 保留当前需求、原生会话、已完成副作用和真实诊断，不标记 PR 完成；人员可解释性对话或明确要求处理本次故障，再显式重试剩余收尾
- **AND** 不自动调用模型修复、不重复已完成同步或归档、不重建已归档的源目录，不把取消或文件存在视为成功

#### Scenario: 收尾副作用限制回退与修改
- **WHEN** 已同步归档但 PR 尚未合入，人员要求修正当前需求
- **THEN** 完整成功的归档不单独禁止继续修正或 Back；范围内问题在当前需求处理，上游材料变化回退并重新确认，在更新 PR 前处理必要的同步归档
- **AND** 保留实际材料位置和已发生的副作用，不以旧批准掩盖改变；尚未结清的部分收尾必须先安全处理，不能混同为可直接覆盖的完整成功

#### Scenario: 收尾失败后的对话与限定修复
- **WHEN** 第七阶段同步归档失败后，人员解释性提问或明确要求处理故障
- **THEN** 保留原生会话及真实诊断；普通提问只读，明确修复只处理当前收尾故障，不自动改变已确认材料或继续业务开发
- **AND** 修复不自行触发同步归档重试或人工完成标记；自有工作及副作用结清后，合入前业务修正仍按原需求确认和回退规则进行

#### Scenario: 已验收内容外部变化
- **WHEN** 同步归档所依赖的已确认材料发生外部变化
- **THEN** 拒绝用原批准继续处理，指出变化文件，不静默接受新内容；人员恢复原版本或在安全结清后回退重新确认，才可继续本需求
- **AND** 正式材料版本核对不宣称业务代码未变；不因旧模式的最终验收约束要求合入前一律另建需求

#### Scenario: 最终完成在测试人员阶段
- **WHEN** 第七阶段归档成功或人员确认 PR 已合入
- **THEN** 不宣称需求已测试；最终只读完成以第八阶段人员标记为准，合入前修正、合入后新建修复及标记提交推送遵循 dev-browser-workbench

### Requirement: 工作区配置及阶段冻结

OMP MUST 保留原 Dev 的“方案阶段使用 Team”配置，默认关闭，只在同一原生工作区保存成功后生效。配置及成员设置通过网页可用的既有交互能力完成，不再依赖 /dev config 终端界面，不另建通用配置体系或 Dev Goal 配置。

#### Scenario: 手动配置面板的保存与取消
- **WHEN** 用户查看、修改或取消 Team 开关
- **THEN** 读取已保存值，只有成功保存才改变有效配置；取消、失败和查看不创建需求、不调用模型、不启动 Team 或 Goal
- **AND** Team 成员、模型及顺序继续通过既有原生配置方式维护并保持原作用域，不新增网页全局 Team／模型角色配置入口；原生 Goal 设置不复制到 Dev

#### Scenario: 当前阶段决定配置可修改范围
- **WHEN** 无活动开发需求，或当前需求处于业务、开发需求阶段
- **THEN** 可修改 Team；技术方案及其后续开发阶段不可修改，界面显示原因，返回开发需求后才可修改
- **AND** 配置只在成功进入方案时使用，不持久化冻结字段或采用配置副本，不因退出页面、重新打开、失败切换或普通聊天绕过限制

#### Scenario: 回退改变可修改性但不重置值
- **WHEN** Back 返回开发需求，或前一需求释放开发名额后新建需求
- **THEN** 根据实际阶段重定可修改性并保留已保存值；仅配置存在是有效状态，不阻止新建
- **AND** 控制操作进行中或旧工作尚未结清时拒绝冲突保存，不把保存延迟到后续阶段执行；不为保存创建分支或工作树

#### Scenario: 配置独立保存且新流程继承
- **WHEN** 无活动开发需求时保存 Team 配置，随后新建需求或重新打开工作台
- **THEN** 仅配置存在不算已有开发需求，新流程继承成功保存的值，不重置为关闭或伪造阶段冻结；保存失败不改变当前有效值

### Requirement: 新流程标识与初始化

OMP MUST 在唯一开发名额可用且既有自有工作已结清时接受网页新建开发需求，分配稳定唯一需求／change 标识和独立正式材料路径，继承有效配置并保存必要状态。每个新需求从业务文档阶段开始，导入文档路径不强制建立业务 Agent 会话。

#### Scenario: 新流程不覆盖保留材料
- **WHEN** 人员新建需求并选择对话生成或导入已有 Markdown
- **THEN** 自动分配合法唯一标识，固定本需求材料路径，不覆盖已有、已取消或已归档需求文件；跨日期和回退继续使用同一身份，实际归档移动按真实结果定位
- **AND** 导入可以不提供访谈正文，不要求 /dev new 或 /dev business；材料归属、Git 记录和本地路径边界遵循 dev-browser-workbench

#### Scenario: 初始化失败只清除本次失败流程
- **WHEN** 新需求保存或目标阶段建立失败
- **THEN** 保留此前配置和已经发生的真实文件变更，清理仅本次失败的运行关联；不报告创建成功或启动依赖未保存状态的工作
- **AND** 清理失败显示实际原因，不假报可立即开始另一个开发需求

#### Scenario: 已建立阶段中的模型失败可继续
- **WHEN** 新需求及相应 Agent 已成功建立之后模型、网络或服务失败
- **THEN** 保留实际阶段、配置、文档和历史，允许人员主动继续或重试，不当作初始化失败删除有效需求

### Requirement: 执行会话保留原生能力和技能存续授权

Dev 执行 Agent 及其实施后代 MUST 保有适用的完整原生会话能力和包内 Superpowers，受原有获批范围、用户验收及生命周期守卫约束；需求、方案、计划阶段既有权限不变。

#### Scenario: 执行代理和递归实施后代使用原生工具

- **WHEN** 执行 Agent 或默认实施子代理及其递归实施后代在获批范围内工作
- **THEN** MUST 按普通原生会话的配置、可用性及适用权限提供原生工具和已配置能力，包括可用的 `knowledge_search`、`web_search`、`eval`、LSP、MCP、扩展及自定义工具，不以固定精简名单裁掉能力；`wait` 仍遵循「执行阶段等待异步子代理」
- **AND** 能力可用不等于绕过用户批准、项目规则、报告后只读、收尾或停止边界；原生明确受限的其他代理仍遵守其自身限制，普通会话和前三阶段不受扩大

#### Scenario: 存活子代理续聊读取技能

- **WHEN** 执行子代理首次任务结束后原生会话仍保活、空闲或经原生恢复，用户或获准工作继续该会话并按引用读取包内 Superpowers
- **THEN** 该会话及其递归执行后代仍可自动发现和按需读取全部包内 Superpowers；授权持续到相应原生会话释放，不因首次任务返回而提前撤销
- **AND** 不修改上游技能正文，不扩大非执行阶段技能自动发现或工具权限

### Requirement: 完成报告和明确修复授权的真实边界

Dev MUST 按本轮完成报告、当前阶段和人员明确决定执行写入限制，不以工具名称、报告存在或自然语言前缀替代真实授权。合入前的获批范围内修正可在当前需求继续；合入后修正必须新建关联需求。末三阶段完成由人员点击，不由报告交付触发。

#### Scenario: 原生工具交付完成报告
- **WHEN** 执行 Agent 或获准后代通过 write、edit、bash 或其他获授权工具交付当前报告
- **THEN** 停止获批执行的自主可写推进并等待人员确认；普通追问只读，不借可写后代继续修改，报告结构仍在第五阶段 Next 检查
- **AND** 不因报告存在进入 ST、同步归档或标记软件完成

#### Scenario: 讨论修复不等于授权修复
- **WHEN** 人员询问修复影响、要求解释或明确要求不要修改
- **THEN** 保持当前写入限制及报告资格，只允许解释和只读调查，不按“修复”等文字前缀推定实施授权

#### Scenario: 用户明确要求范围内修复
- **WHEN** PR 未合入，人员明确要求当前已批准范围内修复或继续实施
- **THEN** 沿原生能力继续当前需求，旧报告失去本轮适用资格，更新材料和结果再由人确认；范围改变先回退相应阶段
- **AND** 完整成功的同步归档不额外封死修复；未结清的部分收尾先处理真实副作用，不借修复绕过批准版本或自行 commit／push／合并

#### Scenario: 合入后修复只能新需求
- **WHEN** 已合入需求测试发现问题或已完成需求需要调整
- **THEN** 原需求不开放代码写入，按 dev-browser-workbench 记录待复测并关联新需求；实际测试、状态与结果不能伪造

### Requirement: 递归需求材料批准和交接一致

Dev MUST 以与原生 OpenSpec 可发现及同步的增量规格一致的完整递归能力路径集合，执行需求材料读取、批准版本检查和阶段交接。

#### Scenario: 嵌套能力规格完整交接

- **WHEN** 本次 change 含 `specs/<area>/<capability>/spec.md` 等原生合法递归能力路径
- **THEN** MUST 将每份规格的实际路径及完整原文连同 proposal 纳入需求材料及其字节版本，并在阶段进入时按既有规则完整交接；方案全部候选、选中 ID 和原始决定不被摘要替代

#### Scenario: 批准后新增嵌套规格

- **WHEN** 需求批准后新增一个原生可发现的嵌套增量规格，即使已批准文件未变化
- **THEN** MUST 判为新增未获批准需求产物，指出真实路径并阻止依赖旧批准的工作、推进及同步；须由用户重新确认，不得在最终归档时同步未批准内容
- **AND** 无法枚举时按「已批准需求集合新增产物即视为变化」报告原因并阻断

### Requirement: 取消结清和原生历史恢复边界

Dev MUST 依据实际原生工作结清情况准入新工作台控制操作，并在本次新流程必要业务状态有效时恢复可用的原生会话及其自身配置；不包括旧 Dev 状态迁移或恢复。

#### Scenario: 已取消任务仍在清理

- **WHEN** 阶段自有后台任务已显示 cancelled 或已返回取消回执，但其实际调用及清理尚未结清
- **THEN** MUST 拒绝 Next、Back 及其他冲突转换或新工作，不以显示终态代替结清；显式停止、宿主关闭和需求删除按原生停止规则等待或报告可重试失败，不恢复旧 `drop` 入口
- **AND** 待真实结清后才依据其他现有门禁重新判断，不影响无关会话

#### Scenario: 恢复阶段自身选模

- **WHEN** 阶段原生历史可恢复，且该阶段此前通过原生模型控制选择了模型
- **THEN** MUST 按该阶段原生历史恢复其模型选择，不用隐藏普通会话当前模型覆盖；其他阶段及普通会话保持各自选择

#### Scenario: 阶段历史存在但无法解析

- **WHEN** 必要 Dev 状态和批准有效，但当前或其他已保存阶段的原生历史文件缺失、损坏或无法由原生历史加载器恢复
- **THEN** MUST 按「原生聊天历史缺失不丢弃有效流程」处理不可用历史，保留同一流程、Team 和批准，明确提示历史不可用，不伪造历史或自动发送输入
- **AND** 用户主动续聊时依据正式材料、保存的原始批准及当前输入继续；不得因单份损坏历史永久阻断有效流程或清除其状态

### Requirement: 部分收尾的副作用与未完成恢复

Dev MUST 如实保留原生同步归档失败时已发生的副作用和未完成的必要恢复工作，直至实际解决，不把部分结果视作完整成功。

#### Scenario: 同步后回滚失败

- **WHEN** 原生同步已修改主规格，后续收尾失败且回滚未能恢复全部实际修改，即使 change 尚未归档
- **THEN** MUST 保留并呈现未恢复的实际副作用及真实失败，未结清时拒绝冲突 Back 和普通业务修改；人员可明确处理本次故障、重试剩余收尾、停止或按安全撤销规则删除需求。实际副作用结清后，PR 合入前仍可继续当前需求修正和回退
- **AND** 不因缺少归档目录而将实际同步副作用视为零，不伪报回滚成功

#### Scenario: 归档目标已生成但源清理失败

- **WHEN** 原生归档复制回退已生成归档目标，但原生要求清除的暂存源目录仍因错误未清除
- **THEN** MUST 保留真实归档位置、清理失败及未完成工作，不在重试时仅因目标存在而宣布验收完成；用户排除故障后由人员在第七阶段显式重试必要收尾
- **AND** 不重复同步或重建 change，不删除无关文件，不把未完成的原生清理伪报为成功

#### Scenario: 备份路径含空格及括号

- **WHEN** 原生 retirement 清理失败且实际备份路径包含空格、括号等合法路径字符
- **THEN** MUST 保留可准确定位完整备份的真实诊断和恢复事实；在该备份确已清除且其他收尾门禁满足后，人员在第七阶段显式重试可继续剩余收尾，不因截断路径永久阻断
- **AND** 原生错误及仍未完成清理时不得显示完成

### Requirement: 原生输入和宿主操作归属

Dev MUST 将网页附件、会话级操作及工作目录绑定正确的原生会话，保留既有停止、取消、草稿和身份隔离边界。当前 TUI 在 Dev 中仅接受再次 `/dev` 退出；不提供旧 Dev 终端子操作，也不因页面切换转移正在运行的需求。

#### Scenario: 附件提交成功或拒收
- **WHEN** 网页提交含附件的输入，操作被接收或拒绝
- **THEN** 成功只消费本次附件，拒收或失败保留原文、附件及标记各一次，不重复、不丢失、不改变其归属、不调用模型处理被拒输入

#### Scenario: 持久化工作目录变更
- **WHEN** 用户在 Dev 中尝试普通 TUI 的工作目录变更、新建、分叉或其他会话命令
- **THEN** MUST 拒绝，提示先通过 `/dev` 成功退出并结清 Dev；不为这些命令克隆普通会话、转移执行或维持跨模式并存
- **AND** 退出后原生普通命令保持原语义，不移动、复制或清除原需求的材料、历史引用及业务记录；单纯浏览另一需求或关闭网页不停止任务，也不成为代码回滚或需求删除

#### Scenario: 原生会话设置归属
- **WHEN** 用户调整当前原生会话的模型、推理档或使用其他已有会话级操作
- **THEN** 只作用于正确的目标会话，不修改隐藏的普通会话或其他需求

### Requirement: 内置执行代理具备必要原生能力

OMP MUST 为内置 `spec-executor` 提供完成已批准执行阶段委派、验证、独立审查及等待所需的适用原生能力，同时保留阶段权限与获批范围限制。

#### Scenario: 委派实施和独立审查
- **WHEN** `spec-executor` 被用于实施获批计划且未达到原生派生限制
- **THEN** 其可用工具 MUST 包含原生 `task`，使其能够派发实施子代理和独立 `reviewer`；适用异步工作 MUST 可使用原生 `wait` 等待真实结果。
- **AND** 验证能力 MUST 能执行获授权的计划内验证；缺少权限或其他必需能力时 MUST 报告阻塞，不能伪报实施、验证或审查完成。
- **AND** 需求、方案、计划阶段的只读权限与其他显式受限代理的边界保持不变。

### Requirement: 详细业务需求文档与业务确认

业务 Agent MUST 面向懂业务、未必懂代码的人，通过业务知识检索和 Grill-me 将口头需求整理为详细、可交接的业务需求 Markdown；不要求业务人员提供代码位置、技术方案或测试用例，不以聊天摘要代替需求文档，也不代替人员确认业务事实。

#### Scenario: 按业务模板形成可交接文档

- **WHEN** 业务人员提供实际问题、已有资料并完成必要业务澄清
- **THEN** 文档 MUST 包含需求名称、基本信息、业务背景与目标、实际使用场景与现状、期望结果、业务规则与边界、典型例子、业务验收预期、待确认事项、资料来源及业务确认与交接信息
- **AND** 项目版本或环境等暂未知信息可明确标为待确认；典型例子用业务输入或操作、当前现象与期望现象表达，不要求业务人员指定代码入口、UT 或 ST 用例
- **AND** 对话生成路径中，业务目标、实际场景、期望结果和业务验收预期由业务人员实际确认；确认人、确认时间、交接及版本信息只按实际发生情况填写，不预填接收或确认成功

#### Scenario: 业务文档保存与关键缺口

- **WHEN** 业务 Agent 生成草稿或用户请求业务交付
- **THEN** 宿主 MUST 自动为本流程分配工作区内唯一业务 Markdown 路径，当前约定为 `docs/business-requirements/<change-id>.md`；网页新建的对话生成入口不要求用户提供或确认路径；导入已有文档时宿主将内容纳入同一需求的材料范围，不修改外部源文件。该精确路径沿用既有写入守卫，跨阶段及恢复保持不变，不覆盖其他流程的文档，不自行写到另一团队、建立竞争性需求权威或创建额外交接、确认文件
- **AND** 无法实际保存时如实说明，可在聊天中继续澄清或提供草稿，但不得声称正式文件已保存；影响业务理解或验收的关键问题不能用空字段或猜测代替答案，不能把未确认草稿报为已确认交付
- **AND** 同阶段普通补充只更新相关内容，未变化材料不要求每轮重读或重写；停止访谈保留未决事项，不等于批准或交付完成

#### Scenario: 导入不要求原业务会话批准
- **WHEN** 开发人员上传已有 Markdown 或提供 OMP 本地路径后直接 Next
- **THEN** 程序只检查现有模板的标题、必要章节及非空内容，不要求原业务人员在线、实际交接审批或先完成业务 Agent 对话；不把格式通过说成业务事实已被验证
- **AND** 本地纯业务写作只生成和下载文档，不需要 Git 提交或仅业务交付终态；开发人员接手后另建需求检查

### Requirement: 业务阶段的知识检索与文档权限

业务 Agent MUST 以既有只读 `knowledge_search`、`openwiki_search` 和 `openwiki_read` 为主要调查工具，按需读取授权业务资料，只能写本次指定业务文档；不得借技能、工具别名、设备传输或派生会话扩大权限，不承担代码细节调查或工程实施。

#### Scenario: 从业务资料中查明事实

- **WHEN** 业务 Agent 需要核对术语、功能、业务规则、历史案例或版本条件
- **THEN** MUST 优先检索已有授权业务知识及 Wiki，并按需读取命中原文；已有资料能回答的事实不重复询问业务人员，需要业务判断或资料无法确定的事项才交由业务人员澄清
- **AND** 记录关键来源与适用版本，区分资料记载、用户陈述、已确认决定和拟议变更；资料冲突或版本不明须保留待确认，不将 Wiki 或历史资料当作当前代码行为已核实的证据
- **AND** 知识库、Wiki 或原文不可用时如实说明限制，使用仍可取得的业务资料继续可确定的工作，不自动建库、更新索引、编造检索结果或假定覆盖当前项目

#### Scenario: 业务访谈不取得开发权限

- **WHEN** 业务 Agent 或其工具请求代码调查、命令执行、协作派发、索引管理或非本阶段文档写入
- **THEN** 宿主 MUST 拒绝越权能力；业务阶段不开放 `lsp`、`bash`、`eval`、`task`、Team 或 Goal，也不写 proposal、开发规格、方案、计划、完成报告或代码
- **AND** 必要的资料读取和指定文档写入仍可用，且写入沿用精确路径及符号链接、Windows junction、硬链接和非普通文件守卫；无法从业务资料确定的实现事实留给需求阶段调查
- **AND** 原版 Grill-me 的事实调查或子代理步骤不能越过这些边界；可用检索工具能够完成的调查直接完成，不为遵从技能而扩大工具面

### Requirement: 网页共用控制器与人员决定

OMP MUST 由同一原生控制逻辑拥有新工作台的需求、阶段、Team 配置、会话、材料批准及动作；浏览器和其他保留的适配只呈现及调用同一事实，不建立第二状态机、执行器或消息系统。前五阶段以网页 Next／Back 控制，末三阶段以人员标记控制，不能从普通文字或 AI 回复推断决定。

#### Scenario: 输入和原始决定分离
- **WHEN** 用户在当前阶段发送文字、附件、问题或“可以”“同意”等普通内容
- **THEN** 原生会话按当前权限处理，不自动批准材料、选择候选、推进阶段、提交 Git、合并或标记完成；记录真实人员动作与对应材料版本，不裁剪或改写原始确认
- **AND** 浏览器采用原生流式消息、工具、问答和审批能力，不能要求返回终端完成正常流程交互；原生操作可用性和真实错误由原 owner 判断

#### Scenario: 前五阶段 Next
- **WHEN** 用户明确点击当前阶段 Next
- **THEN** 第一阶段检查业务文档进入需求；第二阶段批准需求进入方案；第三阶段批准明确选中候选进入计划；第四阶段批准计划进入开发与 UT；第五阶段确认报告进入 ST
- **AND** 多候选须明确选择有效 ID，单候选可省略额外选择；其他阶段不接受方案选择参数。方案选择不批准实施，计划批准不启动 Goal，导入业务文档不要求先对话
- **AND** 目标阶段及必要状态保存成功才报告成功并启动获准工作；失败保留原阶段、输入和已有文件，不伪称回滚实际写入

#### Scenario: Back 只退阶段
- **WHEN** 空闲且相关工作已结清，PR 未合入的用户点击 Back
- **THEN** 返回相邻上一阶段，第一阶段不可回退；撤销目标阶段及下游确认和选择，保留有效上游批准、材料、代码和配置，不执行 Git 回滚
- **AND** 只恢复可用原生历史，不自动调用模型、重跑 Team 或启动 Goal；用户完善后重新 Next，保留文件不代表已重新批准
- **AND** 已归档不单独禁止合入前回退；部分同步归档未安全结清时先显示真实阻塞。合入后不再 Back，问题另建关联需求

#### Scenario: 无阶段与错误输入
- **WHEN** 没有活动 Agent、控制动作参数不适用或不合法
- **THEN** 明确指出当前可用动作，保留草稿及附件，不调用错误会话、不执行部分操作或将无效控制交给模型

#### Scenario: 原生队列和草稿归属
- **WHEN** 页面切换、忙碌时提交、收到迟到结果或恢复原生历史
- **THEN** 草稿、输入、附件、队列及回执沿用原生能力，绑定提交时需求、阶段和 Agent；不另存独立 Dev 消息队列或正文副本，不把旧阶段输入送到后继
- **AND** 模型错误真实呈现，不用旧回复替代本轮失败，不自动发送未提交草稿；中文交互规则保留，命令、路径、协议字段和原始输出不翻译

#### Scenario: 冲突控制不排队为未来批准
- **WHEN** 模型、工具、Team、Goal 或自有异步调用尚未结清，或者已有控制操作在进行
- **THEN** 拒绝冲突 Next、Back、删除或配置保存，明确原因；显式停止使用原生取消并等待真实结清，不把主 Agent 回复结束或 cancelled 回执当作全部停止
- **AND** 重复或过期点击不变成下一阶段确认，保留可重试实际事实，不影响无关进程；末三阶段标记及 Git 同步按 dev-browser-workbench 的人员决定与幂等边界

#### Scenario: 旧终端交互不作为备用入口
- **WHEN** 用户调用 /dev 或尝试旧终端 Dev 子操作
- **THEN** /dev 仅按 personal-commands 打开网页；旧模式和子操作不再执行，不保留旧批准、drop 或 finish-business 兼容路径；其仍需要的业务能力通过网页调用同一原生控制者
- **AND** 不删除普通 OMP 原生命令、独立技能、专有 Agent 或底层功能

### Requirement: 工作台目录归属与开发名额

Dev MUST 将新工作台配置和需求归属当前既有目录，由唯一原生 owner 管理，同一目录同一分支最多一个占用开发名额的需求，不创建 worktree 或每需求分支。合入后的测试／待复测只更新自身记录时可以并存；“一个未结束流程”的旧限制不再阻止该例外。

#### Scenario: 目录身份和多人参与
- **WHEN** 从同一 Git 目录的不同子目录、别名、普通会话或多个浏览器连接打开工作台
- **THEN** 指向同一原生工作区和开发名额，不创建并行开发 run；Collab 参与者操作同一 owner，不是多个独立控制者
- **AND** 不同已有目录保持原生隔离，不因 Dev 在全局禁用独立 Git 或其他工程能力，也不提供分布式开发调度

#### Scenario: PR 边界决定开发名额
- **WHEN** 当前开发需求等待 ST、提交、评审或 PR 合入
- **THEN** 继续占用开发名额；只有 PR 已合入，或取消并完成所属改动撤销且自有工作结清后，才可处理下一开发需求
- **AND** PR 合入后的原需求测试和待复测不占用开发名额，只能改自身记录；具体行为遵循 dev-browser-workbench

#### Scenario: 工作区已被另一 owner 占用
- **WHEN** 另一个独立 OMP owner 尝试对同一目录启动冲突开发
- **THEN** 显示已占用，不抢占、清除配置或以恢复失败删除有效记录，不影响原运行及无关会话

#### Scenario: 关闭网页与关闭宿主分开
- **WHEN** 用户关闭网页，或明确停止／关闭所属 OMP 宿主
- **THEN** 关闭网页只结束其连接，不结清或终止后台工作；显式停止／宿主关闭才按原生生命周期取消未处理输入、停止并等待本需求 Agent、工具、Team、Goal 和自有子任务
- **AND** 必要状态保存及控制权释放成功才报告安全停止，失败保留可重试事实；不自动验收、同步归档、回滚、提交或删除普通历史

### Requirement: 新工作台状态保存与恢复

OMP MUST 保存本次新工作台需求的必要业务事实，并将文档、阶段、人员标记和 Git／PR／修复关联纳入 Git。原生聊天、运行 owner、连接、临时错误及队列继续由原生机制拥有，不复制到 Git 需求记录。只恢复本次新建需求，不兼容或迁移旧 Dev 状态。

#### Scenario: 业务事实与运行事实分离
- **WHEN** 保存新需求或配置
- **THEN** 保留稳定身份、材料引用及真实字节版本、原始批准、方案选择、必要同步归档进度、人员状态和提交关联；本地原生会话引用按既有能力保留
- **AND** 不重复保存完整文档、聊天正文、Team 冻结、按钮可用性、忙碌、队列或 Goal 副本；提交 SHA 及撤销归属为需求所需事实，不等于另建全工作区快照或逐任务证据系统

#### Scenario: 必要保存失败
- **WHEN** 配置或流程必要状态保存失败
- **THEN** 报告真实错误，不报告依赖该保存的阶段切换或配置修改成功，不启动相应新模型工作；已发生文件或 Git 副作用如实保留，不伪称回滚
- **AND** 人工标记后的 commit／push 部分失败按 dev-browser-workbench 区分实际结果，不重复已有提交或推进

#### Scenario: 新需求重新打开
- **WHEN** 同一新流程重开网页、OMP 重启后重新打开，或在另一目录拉取其 Git 记录
- **THEN** 依据真实记录呈现需求和材料，配置及动作从实际阶段与运行状态推导，不自动发送草稿、重放工具、重跑 Team、启动 Goal 或形成批准
- **AND** 读取记录不等于取得运行 owner；只有明确继续及准入成功才开展工作。拉取仓库不迁移聊天或接管其他机器的 Agent，不把持久 running 标记当作真实运行

#### Scenario: 原生聊天历史缺失不丢弃有效流程
- **WHEN** 新需求必要记录有效，但所属原生历史缺失或无法解析
- **THEN** 保留需求、配置和真实批准，明确历史不可用；人员主动继续时依据正式材料及当前输入工作，不伪造记忆、不自动清除有效需求

#### Scenario: 不接管旧 Dev 流程
- **WHEN** 工作目录留有本次变更之前的 Dev 运行状态或材料
- **THEN** 不把它们迁移或恢复为新工作台需求，不从旧材料猜测新八阶段批准；也不因不兼容而删除用户文档、代码或 Git 历史

### Requirement: 业务阶段继续开发与本地写作

业务文档阶段 MUST 提供网页 Next 进入开发需求；人员只希望本地借助 AI 写文档时，不要求进入开发链、提交 Git 或建立“仅业务交付完成”的团队终态。开发人员另建需求导入文档时仍须经过第一阶段格式检查，不从原业务会话继承批准。

#### Scenario: 网页 Next 进入开发
- **WHEN** 用户确认当前业务文档并点击 Next
- **THEN** 宿主检查该文档模板及必要状态、工作结清，保存真实决定并进入需求 Agent，完整交接文件、路径和版本；不要求后续开发材料提前存在
- **AND** 需求 Agent 沿用 Grill-me 和代码调查，已有内容不重复访谈；导入文档路径在 Next 前不要求模型对话，业务文档确认不替代开发规格、方案或计划批准

#### Scenario: 只生成本地业务文档
- **WHEN** 业务人员不开发，只使用 AI 整理文档并自行传递
- **THEN** 保留可查看和下载的本地 Markdown，不创建 PR、不提交或推送仓库、不同步归档、不生成完成报告、不宣称软件交付
- **AND** 不要求 finish-business、团队交接／接收状态或协作会话；开发人员在自己的目录另建需求，不恢复原业务流程

#### Scenario: 失败或离开不冒充完成
- **WHEN** 文档保存／检查失败、用户停止访谈或关闭网页
- **THEN** 呈现实际文件、错误及可继续事实，不记录业务或软件验收成功、不自动进入后续阶段；关闭网页按工作台生命周期保留后台工作
