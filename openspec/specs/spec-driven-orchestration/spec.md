# spec-driven-orchestration

## Purpose

规定面向单个开发者的 `/dev` 协同开发模式：固定需求、方案、计划、执行四个 Agent，由程序检查真实文件、格式及最低字段，在用户明确决定后交接原文并切换阶段。Agent 负责工程工作，程序不以文件存在证明软件正确。正式需求唯一权威为 `openspec/specs/`，博客仅作说明；接入其他已有 Markdown 需求权威的项目时保留其原文，不建立竞争性主规格。

## Requirements

### Requirement: 独立能力与开发模式的边界

OMP MUST 保留独立 OpenSpec、Superpowers、JCH 及普通会话能力；只有用户明确启动 `/dev` 才建立四阶段运行。

#### Scenario: 独立能力与开发模式的详细边界

- **WHEN** 用户使用独立能力或显式启动 `/dev`
- **THEN** 以下职责、来源及授权边界适用：

- OpenSpec 负责需求探索、提案、规格、同步、独立核对与归档，不承担代码实施。`opsx-propose` 只形成 proposal／specs，`opsx-update` 修订或补齐已确认范围内的需求，不新建 design／tasks 或实施代码。
- 包内保留真实 schema、解析、校验、合并、归档引擎及运行依赖。命令指向 `omp openspec`，不要求另装 OpenSpec；不能只复制说明文字，也不能依赖开发机绝对路径。
- 固定来源清单为 OpenSpec 1.14.3、Superpowers 7.0.1（`2ce8aa15d05bd57213e6f746f953aafb7ded7a8b`）；来源、版本、校验与适配由 `packages/coding-agent/src/spec-driven/vendor/inventory.json` 及现有生成链管理。JCH `jch-grill-me` 的真实 `SKILL.md` 和 `agents/openai.yaml` 一并交付并绑定来源修订。固定版本不代表已通过平台验收。
- Superpowers 全部原有技能、必要脚本和 `using-superpowers/references/` 保留。计划、TDD、调试、子代理、代码审查与收尾是可用工程方法，不是 `/dev` 的额外程序阶段或固定审查配额。
- 独立 OpenSpec 不依赖 `/dev` 状态、计划、Team 或批准。独立需求同步与归档可以早于代码实现，不代表软件交付；独立 `opsx-verify` 沿用固定上游核对行为，不要求 `/dev` 记录，也不改变其验收状态。
- 普通 bug 修复若预期行为未变，不强制修改需求或新建 change。普通代码实施、原生 task／reviewer、独立 Team／Goal、SDK、TUI 与其他宿主保持原语义，不附加本功能的阶段状态、系统规则、后台工作或证据采集。
- `/dev` 不提供轻量跳阶段变体、不强制 Team 流程、不建立额外 Goal 阶段、逐任务状态机、TDD／审查证据引擎或强制 Git 提交。方案内可选 Team、执行内可选 Goal 只改变本阶段工作方式。普通工程工具的使用服从用户授权及项目规则，计划批准不隐含 push、PR、发布或不可逆操作授权。

#### Scenario: 独立需求维护

- **WHEN** 用户未启动 `/dev` 而请求维护需求
- **THEN** 独立 OpenSpec 可完成需求维护闭环，不创建开发运行或要求四阶段批准；仅文档操作不改业务代码、不运行软件测试、不宣称软件已实现

#### Scenario: 显式启动

- **WHEN** 用户执行 `/dev start <change-id> <需求正文...>` 或等价面板操作
- **THEN** 才创建运行并启动需求 Agent；仅切换模式、查看帮助或编辑需求草稿不启动 Agent

### Requirement: 包内技能发现与资源兼容

OMP MUST 复用既有发现、补全、按需读取与资源授权，不因四阶段简化改变独立技能行为。

#### Scenario: 技能发现与资源兼容的详细边界

- **WHEN** 会话发现、手动调用或读取包内技能与命令资源
- **THEN** 以下发现范围、资源授权及兼容约束适用：

| 范围 | 技能 | 规则 |
| --- | --- | --- |
| 普通模型可发现 | `systematic-debugging`、`verification-before-completion`、`writing-skills` | 默认索引只提供名称与描述，正文按需读取 |
| 仅手动调用 | 其余十二项 Superpowers 技能（含 `brainstorming`） | 保留 `/skill:<name>` 补全和管理，不默认发现；显式调用后仅当前分支可读准确资源 |
| 按当前目录发现 | `opsx-explore`、`opsx-update`、`opsx-propose`、`opsx-sync`、`opsx-archive`、`opsx-verify` | 当前会话工作目录直接有 `openspec/` 目录时提供名称和中文描述，正文按需读取；其他目录仅手动调用 |
| 仅手动调用 | `jch-grill-me` | 保留原资源和显式调用，不在 `/dev` 中强制自动加载 |

手动 Superpowers 包括 `diagnosing-superpowers`、`dispatching-parallel-agents`、`executing-plans`、`finishing-a-development-branch`、`receiving-code-review`、`requesting-code-review`、`subagent-driven-development`、`test-driven-development`、`using-git-worktrees`、`using-superpowers`、`writing-plans` 与 `brainstorming`。限制按包内来源身份，不限制用户或项目同名技能。跨技能引用不自动授权另一项手动资源；不新增递归加载或整套预加载。

目录条件不向父目录查找，普通同名文件不满足条件，每次发现／重载重新计算，不依赖进程全局 cwd。条件满足时自然语言任务可以触发模型按需读取，无需先输入 slash 命令。条件不满足时保留技能管理和手动补全；`skill://` 读取需当前分支显式调用记录或宿主准确资源授权。授权限定所属会话及生命周期，不泄漏到其他阶段或运行；进入 `/dev` 输入模式本身不授予资源权限。

只保留 `/skill:opsx-*`，不提供 `/opsx-*` 命令、旧 `/skill:openspec-*`、`opsx-new`、`opsx-continue` 或实施类 `apply`／`ff`／`bulk-archive`／`onboard`／`feedback` 工作流入口。底层 `omp openspec new change`、`status`、`instructions` 等原生能力保留。删除范围不包括用户独立 OpenSpec 工作区、项目既有需求或历史实施产物。

`omp openspec init [路径] [--language <语言>]` 默认使用需求专用 `omp-spec` schema，只声明 proposal／specs 及依赖；不提供 `--tools`、外部工具选择安装、迁移、Copilot／profile 配置、原生 `update` 工具安装更新入口及 `experimental` 安装别名。重复初始化保留已有配置、需求、历史和外部工具文件，保留原生外部 store／语言配置边界，不在 pointer 项目内创建另一规格根。旧 schema 无法安全隔离需求部分时报告不兼容，不静默迁移或删除历史产物。

保留 `omp superpowers <relative-skill-script> [args...]`；JavaScript 使用 OMP 自带 Bun，Shell 仍依赖 Bash／POSIX，部分脚本需 Git／Graphviz。缺失条件报告真实错误，不在线补装或伪造成功。普通技能的原生任务名适配为 `task`／`reviewer`，不创建 `general-purpose` 别名，不强制 `/dev` 使用这些角色。

#### Scenario: 发现范围不扩大

- **WHEN** 用户启动普通会话、手动调用技能或重载目录技能
- **THEN** 按上述发现及准确资源授权读取正文，不因安装 `/dev` 自动启用完整工程流程；原有独立技能与普通多代理行为不变

### Requirement: 四个固定 Agent 与真实文件门禁

OMP MUST 仅设置需求、方案、计划、执行四个固定阶段 Agent，每个使用独立、可持续对话的原生 SDK 会话，承接当前父会话的模型、上下文与原生工具能力。验收、收尾、等待、暂停是生命周期状态，不是额外 Agent。

#### Scenario: 四个固定 Agent 与文件门禁的详细边界

- **WHEN** `/dev` 运行任一阶段 Agent 或读取其产物
- **THEN** 以下角色、五个正式文件及最低格式约束适用：

| Agent | 工作责任 | 程序读取的产物 | 用户决定 |
| --- | --- | --- | --- |
| 需求 | 调查项目并澄清目标、范围、约束、非目标及验收行为，维护正式需求 | 原生 change 的 proposal／delta specs；已有 Markdown 权威作为额外原始依据 | 确认需求 |
| 方案 | 基于已确认需求调查并比较实际可行方向，不硬凑三案 | `YYYY-MM-DD-<change>-solutions.json` | 选择候选并确认 |
| 计划 | 根据已确认需求、完整方案、选定候选和原始确认回复编写执行计划 | `docs/superpowers/plans/` 中本次唯一 Markdown 计划 | 批准计划并开始执行 |
| 执行 | 按获批计划实施、验证、组织必要协作并如实报告 | `YYYY-MM-DD-<change>-completion.md` 完成报告 | 最终验收，或明确返回修复 |

需求 Agent 调查工具能查明的事实并澄清目标、范围和验收行为，加载原 OpenSpec instructions，生成原格式 proposal／specs；计划 Agent 加载原 `writing-plans`。不强制自动加载完整 Brainstorming／Grill-me 或另一套工作流，原资源、手动调用及按授权使用方法的能力不变。需求阶段不提前写方案、计划或业务代码；方案及计划阶段不提前实施。用户的澄清回答不替代正式需求批准；各角色不把材料原文升级为系统授权。

单能力变更只需要五个正式文件：OpenSpec 原模板的 `proposal.md` 和能力 `spec.md`，以及方案、计划、完成报告。OpenSpec 原模板与 Superpowers `writing-plans` 原格式、技能和方法保持不变。后三个执行材料同放 `docs/superpowers/plans/`：`YYYY-MM-DD-<change>-solutions.json`、`YYYY-MM-DD-<change>.md`、`YYYY-MM-DD-<change>-completion.md`，不迁入需求目录。不生成交接文档、确认文件、任务状态文件或流程 `state.json`；仅在内存保留当前阶段、决定及界面所需文件内容与字节版本，现有 app-server 自身历史投影可以正常保存。

所有文档读取结果包含 `path`、完整 `content`、基于实际文件字节摘要的 `version`。每次 Agent 运行或阶段对话完成后，程序 MUST 重新读取本阶段文件并检查格式和最低字段；聊天文本只用于呈现与交流，不要求 JSON／yield，不从自然语言中的“完成”“通过”推断转换。

- 需求产物始终包含原格式 proposal／delta specs，必须真实存在、非空并通过原生结构校验。已有 Markdown 权威作为额外原始依据读取和原位维护，proposal／delta 描述变更并引用它，不生成第二套主规格，也不以原权威文件替代这两个正式产物。
- 方案必须是实际 JSON 文件，根字段 `candidates` 为非空数组，每项含非空字符串 `id`、`title`、`content`，ID 唯一且不含空白，可直接用于 `choose <candidate-id>`。允许只有一个合理候选。`content` 是完整方案 Markdown，提示要求说明范围、实现方法、取舍风险与验证思路；程序不按关键词匹配可用性，也不裁定语义或技术优劣。
- 计划必须是实际、可读、非空的 Markdown 文件，沿用 Superpowers 原格式，不附加自制计划 JSON 或额外栏目门禁。计划 Agent 负责需求覆盖、任务范围、依赖、修改位置与验证安排，程序不把这些工程内容解析为另一套逐任务执行状态。
- 报告必须是实际 Markdown，标题为 `# 完成报告`，包含非空的 `## 完成情况`、`## 验证结果`、`## 未完成项` 三个栏目。验证说明真实命令、状态、结果与限制，区分已运行、未运行和失败；没有未完成项时明确写“无”。程序检查结构不证明其陈述为真。

有效产物只使本阶段进入等待用户决定，绝不自动启动下一 Agent。缺失、不可读、格式错误或最低字段不全时保持当前活动阶段，显示具体文件和原因；用户可以继续对话让该 Agent 修正，不设自动重试、固定审查席位或修复额度。

两个独立开关 MUST 默认关闭、仅属于本次运行，并随现有明确决定一次提交：确认需求面板勾选 Team 或 `/dev confirm-spec --team`，批准计划面板勾选 Goal 或 `/dev confirm-plan --goal`。不增加阶段、固定 Agent、审批、正式文件、全局设置或热切换入口。未提交的勾选、关闭窗口、草稿和普通确认说明不得启用能力；选项只解析确认命令正文开头的参数，`--` 结束选项解析。阶段启动后冻结所选方式，范围内对话、修订及修复沿用；需求回退撤销 Team 选择，计划需重新批准时重新选择 Goal。

启用 Team 时 MUST 复用既有只读 Team 编排、`team.members` 解析及并发约束，完整需求、用户原始确认和本轮反馈直接交给讨论；方案 Agent 消费完整结果，将获审可采用候选完整写入原方案 JSON。讨论失败、取消、无可采用候选或产物冒用不可采用方向时显式受阻，不静默回退单代理，不把 Team 完成当作用户选择。Team 内部既有调查与审查不变，不另加 `/dev` 审查门禁。

启用 Goal 时 MUST 仅在执行 Agent 自己的原生 SDK 会话中使用 Goal；目标直接取完整获批计划、上游原文件、用户原始批准及范围内修复说明，不要求另输目标，不切换外层会话。普通执行仍保持原行为。Goal 的预算、停止与续接沿原生机制；请求结清、暂停、取消和待验收时不得继续自主写入，待验收对话保持只读，明确 repair 后才恢复获批范围。Goal 完成不等于验收，仍由原完成报告和显式验收收尾。

#### Scenario: 同次批准启用阶段内部能力

- **WHEN** 用户分别在现有需求确认及计划批准中启用 Team 与 Goal
- **THEN** 仍只有需求、方案、计划、执行四阶段和原五份正式文件；方案运行既有 Team，执行运行自己会话的 Goal，不新增审批，也不自动验收归档

#### Scenario: 未提交开关不产生工作

- **WHEN** 用户勾选能力后关闭面板，或只在普通确认说明中提及参数
- **THEN** 不派发讨论或执行；重新打开确认面板仍默认关闭，只有明确带选项提交才启用

#### Scenario: 缺失产物不得推进

- **WHEN** 计划 Agent 声称完成但计划文件不存在，或执行 Agent 只在聊天贴出报告
- **THEN** 程序保留当前阶段并报告缺失文件，不进入计划批准或最终验收

#### Scenario: 合法文件仍等待用户

- **WHEN** 任一阶段生成符合最低文件合同的产物
- **THEN** 程序展示材料并等待对应明确决定；不以文件存在、Agent 回复、checkbox 或本地 commit 自动批准

### Requirement: 完整文件与用户原始确认交接

OMP MUST 在需求→方案、方案→计划、计划→执行三次转换时，直接把完整原文件和用户原始确认回复作为下一 Agent 的输入，不生成交接文档或确认文件，不调用模型、`AgentSession.handoff()` 或摘要 Agent。

后继获取全部必要原文，不依赖会话记忆、聊天摘要或模型转述。尤其用户选择方案后，计划 Agent MUST 收到完整方案 JSON（所有候选原文，不仅选中候选）、已确认需求、所选候选 ID 和用户完整原始确认回复，不能再让模型额外总结后转交。

原始确认回复逐字传递，不裁剪、不改写，包含明确决策入口的原始用户回复及说明。转换前重新读取并比较上游文件字节版本；已批准材料变化时拒绝旧决定并要求重新确认，不静默采用新文件。不新增交接保存、确认文件或任务状态机制。

#### Scenario: 方案选择完整交给计划

- **WHEN** 用户选择候选并提交确认原文
- **THEN** 程序直接把完整方案、需求、候选 ID 和原始回复交给计划 Agent，不生成中间文档或额外模型总结

#### Scenario: 已批准文件发生变化

- **WHEN** 下一阶段启动前上游实际文件字节与批准版本不一致
- **THEN** 拒绝转换并要求重新确认当前材料，不沿用旧批准

### Requirement: 工程责任、完成报告与验收后收尾

OMP MUST 将工程实施交给执行 Agent，程序只管理文件、用户决定、阶段与运行生命周期，不保留另一套 Task／TDD／原生证据执行引擎。

#### Scenario: 工程责任与验收收尾的详细边界

- **WHEN** 执行 Agent 实施、报告交付或用户决定修复与验收
- **THEN** 以下工程责任、写入授权及原生收尾约束适用：

执行 Agent 可用普通原生工具亲自实施或按实际独立性委派协作，负责遵守计划、项目规则、测试授权、验证与必要代码审查。是否采用 TDD、如何拆分、并行及记录工程证据由已批准约定和目标项目规则决定；不由 `/dev` 硬编码固定审查模型、修复轮次、RED／GREEN 记录、验证 ID、本地提交、隔离分支或发布账本。普通 Team、reviewer 和独立 Goal 资源不因此删除。

完成报告文件通过最低格式检查后，进入 `awaiting-acceptance`，而不是 `completed`。报告不是软件正确证明，不能把未运行检查写成通过。待验收对话仅允许执行 Agent 解释与只读调查，原生写工具及可写后代必须受当前调用边界限制；普通反馈不恢复写入。明确 `/dev repair <说明...>` 后，撤销旧报告的验收资格，复用执行 Agent 按获批范围修复、更新报告，再等待用户验收。需求、方案或计划需要变化时，走对应回退与重新批准，不扩大 repair 权限。

只有用户最终接受当前材料，才进入 `closing`，调用包内原生 OpenSpec 同步与归档。原生布局将增量合入 `openspec/specs/`；已有 Markdown 权威在需求阶段原位维护，不额外制造待同步的影子主规格，收尾使用 `--skip-specs` 避免写入竞争性权威。Markdown 修改保留原文件、标题和原文定位，使用最小补丁，不把非原生章节交给原生 `specs-apply` 整块覆盖。定位歧义、来源变化或无法无损维护时明确受阻。

归档使用真实原生校验与归档引擎；同步已完成、获准跳过或采用既有 Markdown 权威时使用 `--skip-specs` 避免重复同步，不用 `--no-validate` 绕过检查，不直接移动目录冒充归档。归档只归档需求变更；方案、计划与报告继续保留在 Superpowers 计划目录。原生失败显示实际原因，不报告完成；只有必要收尾成功才进入 `completed`。验收不隐含 commit、push、发布、PR 或分支合并。

#### Scenario: 报告后等待验收

- **WHEN** 执行 Agent 写出符合格式的完成报告
- **THEN** 停在待用户验收，仍允许只读讨论；未得到明确接受前不自动同步归档

#### Scenario: 收尾失败

- **WHEN** 用户接受后原生同步或归档失败
- **THEN** 保留真实材料及失败原因，不把待收尾的运行标记为完成，也不以直接移动目录伪造成功

### Requirement: 共用控制器、输入与用户决策

OMP MUST 由同一原生控制器独占阶段、消息归属、输入模式、草稿与动作；TUI 与 ZCode 只呈现和调用，不建立第二状态机。

#### Scenario: 共用控制器与用户决策的详细边界

- **WHEN** 用户输入、决定、暂停、取消或释放 `/dev` 运行
- **THEN** 以下状态、命令、消息归属及生命周期约束适用：

活动阶段为 `requirements`、`solution`、`planning`、`executing`；决策状态为 `awaiting-specification`、`awaiting-choice`、`awaiting-plan`、`awaiting-acceptance`，另有 `idle`、`closing`、`completed`、`cancelled`。暂停是独立事实，受阻保留实际阶段及 `blockedReason`。中文用于四角色及其流程内协作的用户回复、问题、理由、摘要与交付说明；代码、命令、路径、标识符、协议字段和原始输出不翻译。不改变普通会话语言。

| 命令 | 语义 |
| --- | --- |
| `/dev` | TUI 切换普通聊天／协同开发输入模式，不启动流程或打开面板 |
| `/dev help` | 打开当前阶段决策面板，不切换模式或启动流程 |
| `/dev start <change-id> <需求正文...>` | 明确创建新运行 |
| `/dev status` | 当前真实状态、路径、完整材料和阻塞诊断 |
| `/dev answer <回答...>` | 交给当前 Agent 的显式对话；协同开发模式也可直接输入普通文字 |
| `/dev confirm-spec [--team] [确认说明...]` | 确认当前需求，将完整文件和原始回复直接交给方案 Agent；可选在方案内运行 Team |
| `/dev choose <candidate-id> [确认说明...]` | 确认候选，将完整方案及原始回复交给计划 |
| `/dev confirm-plan [--goal] [确认说明...]` | 批准当前计划，将完整材料和原始回复直接交给执行 Agent；可选在其会话内启用原生 Goal |
| `/dev revise-plan <修改说明...>` | 保留未变的已批准上游，回到计划，撤销旧计划批准及验收资格；不自动实施 |
| `/dev accept` | 最终接受当前交付，再执行同步归档 |
| `/dev repair <修复说明...>` | 从待验收明确返回执行并使旧验收失效 |
| `/dev amend <修改后的需求...>` | 回到需求，撤销受影响下游批准，保留实际文件 |
| `/dev change-solution <原因...>` | 需求未变但核心方案改变时回到方案 |
| `/dev cancel-message <message-id>` | 取消所属运行指定消息，不取消整个流程 |
| `/dev pause`、`/dev resume`、`/dev cancel` | 暂停／恢复存活运行／取消，保留文件，不重置工作区 |

不保留旧版本参数或 `extend-review` 兼容命令。命令不要求用户手抄文件摘要，但程序仍核对当前会话、run、阶段、消息结清及文件版本；过期或错误归属操作明确拒绝。普通文字“继续”“同意”交给当前 Agent，不自动授权转换。

- 等待决定时当前 Agent 仍可解释或修改本阶段未批准文件；改变已批准上游必须走明确回退操作。普通输入不能使需求、方案、计划越权实施。
- 未启动输入仅作为草稿；暂停期间不调用 Agent。恢复不自动提交草稿，用户须重新发送。关闭面板或切回普通聊天不取消后台运行。
- 忙碌输入绑定会话、运行、阶段及实际 Agent 排队；回执区分已排队、已接收、处理中、取消中与实际已取消，不把旧消息转给后继。待处理、处理中或取消中的消息阻塞阶段转换。
- 排队消息可取消；处理中消息须停止其调用及自有后代，确认停止并隔离迟到结果才完成取消。取消请求 ACK 不等于已停止，不能影响无关会话，也不自动撤销已经发生的文件写入。
- 暂停、取消、回退及释放必须结清自有调用与后代，旧代次不得发布结果、改写当前状态或将 provider 错误转为成功。保留当前实际 provider 错误，不复用旧回复；无结果与明确错误分别呈现。
- 取消显示终态不代表清理完成；面板和直接 start 均等待旧消息及 runtime 真实释放。释放失败显示原因并可重试取消，不提前把新运行交给仍存活的 owner。
- 状态与批准仅属于当前进程存活会话；归档、聊天和历史观测不恢复旧运行或旧批准，不新增流程状态文件。功能不是 OS 沙箱、IAM 或多人审批。
- 协同开发输入模式与外层 Plan、Goal、Vibe 互斥，不静默覆盖已有模式；执行 Agent 内部可选 Goal 不改变外层会话或独立能力。

#### Scenario: 原始输入与明确决定分离

- **WHEN** 用户在等待方案选择时发送普通文本或明确 choose 操作
- **THEN** 普通文本只交给当前方案 Agent，choose 则在原生门禁通过后记录原始回复并转换；界面不能自行批准

#### Scenario: 取消尚未结清

- **WHEN** 旧运行已显示 cancelled 但其消息或 runtime 尚未释放
- **THEN** 同会话的新 start 被拒绝并显示真实原因；不丢失清理状态，不影响其他会话

### Requirement: TUI 决策面板与自动打开

OMP MUST 保留当前阶段决策面板、可读完整材料、自动等待提醒和草稿安全，不把精简程序合同变成难用的命令菜单。

#### Scenario: TUI 决策面板与提醒的详细边界

- **WHEN** 用户打开决策面板或流程进入新的等待、暂停或受阻状态
- **THEN** 以下材料呈现、明确决定、自动提醒及草稿安全约束适用：

`/dev help` 首屏呈现当前阶段、结果或缺失文件、待决定事项与动作后果。动作分当前决策／查看材料／流程管理；批准时默认选安全的查看材料，不预选确认。无运行先填需求，再提供合法 ASCII、避免现有 change 冲突且可编辑的自动 change ID，明确提交才调用 start。澄清问题、推荐及理由与可编辑回答同屏，长正文可滚动；不从模型聊天要求额外 JSON 问卷。

已启动运行结束本轮工作、消息结清并等待澄清／确认／选择／批准／验收，或暂停／受阻时，自动打开同一个面板，即使当前在普通聊天模式。已有对话框时等待其结束，不覆盖、不清除草稿或附件。同轮关闭或刷新不重复弹出，新等待才再次提示；不自动切模式、批准、提交草稿或恢复历史运行。

自动聊天仅显示阶段摘要、关键问题、文件缺口与动作后果，去重、不重复铺开内部 JSON／长 ID／命令／统计。完整材料及命令保留于显式详情和 status；面板、聊天和 ZCode 消费同一动作事实。中文按键提示、滚动和按钮在 ANSI／native 的 120×36、100×28 下可达；查看或高亮不执行，取消流程说明停止工作并保留文件，再确认一次。不因摘要省略而让澄清无法回答。

#### Scenario: 自动提醒保留编辑内容

- **WHEN** 流程等待决定而用户有输入草稿、附件或其他对话框
- **THEN** 等现有对话框结束后打开同一面板，保留内容；关闭本轮窗口不重复弹出，也不提交任何决定

### Requirement: 原生 dev 的桌面后端合同

OMP MUST 在 `modes/zcode/` 投影同一原生控制器，不把 `/dev` 包装成可执行动态工作流，不新增桌面页面、消息队列、批准 API 或执行引擎。wire 兼容、查询订阅和身份要求见 [zcode-app-server](../zcode-app-server/spec.md)。

#### Scenario: 原生 dev 桌面后端的详细边界

- **WHEN** 桌面客户端协商扩展并查询或操作原生 `/dev` 运行
- **THEN** 以下运行投影、真实材料、能力兼容及历史只读约束适用：

每次明确 start 对应独立 run 行，包含 change、身份、时间、真实阶段、等待／暂停／受阻、错误与终态。仅切换模式、帮助、独立技能和普通聊天不创建运行。四个 Agent 与等待、验收和收尾如实区分，待验收不是完成；不投影已删除的程序任务完成数、审查配额或证据引擎状态。

扩展提供输入模式、实际接收 Agent、普通对话、消息生命周期、草稿、原生当前动作、完整需求、完整方案与选择、计划和完成报告，并以可选 `useTeam`／`useGoal` 投影本次真实选择，不新增交接或任务状态文件。内容来自真实文件并保留字节版本；缺失、不可读和未知明确呈现，不伪造空内容或成功。动作仍走既有 sendText／builtin 命令入口，需求确认和计划批准允许相应选项及原始确认说明，归属、阶段和当前材料门禁由 native owner 再检查。

capability 显式协商新增扩展，旧客户端不收到未知字段／枚举；既有动态工作流定义、引擎、actor、journal 和恢复行为保持不变。历史仅保存真实观测和材料，冷读取不得创建 AgentSession、获取写权限或恢复执行。失去 live owner 的活动记录明确显示历史不可继续，不伪装 running 或 resumable。桌面 UI 实施及验收不由后端结果替代。

#### Scenario: 两种界面共用事实

- **WHEN** TUI 与协商扩展的 ZCode 客户端观察或操作同一运行
- **THEN** 获取同一四阶段、文件、消息及动作事实，走同一原生准入；历史只读且不恢复批准
